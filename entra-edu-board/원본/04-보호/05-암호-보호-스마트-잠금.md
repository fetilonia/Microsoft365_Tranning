## L2 · 암호 보호 · 스마트 잠금 — 약한 암호 · 무차별 대입 방어

- 설정(Control Plane): 사용자 지정 금지 암호 목록 (최대 1000개) · 스마트 잠금 임계값 · 기간 | 온프레미스 암호 보호 사용 · 모드 (감사 / 적용)
- 강제(Enforcement): Entra 암호 변경·재설정 시 전역 + 사용자 지정 금지 목록 검증 | 로그인 시 스마트 잠금 · 온프레미스 DC 에이전트
- 증적(Evidence): 로그인 로그 오류 AADSTS50053 (잠금) | DC 에이전트 Admin 이벤트 로그 10014 · 10016 · 10024 등
- 메뉴(Admin Center): 보호 > 인증 방법 > 암호 보호
- 라이선스(License): 전역 금지 목록은 클라우드 사용자 Free · 사용자 지정 목록과 잠금 값 변경은 P1 이상 · 온프레미스 AD DS 동기화 사용자의 암호 보호는 P1·P2 [확인 필요: 고객의 SKU 보유·대상 사용자 할당 및 온프레미스 적용 자격]

### L3 · 0 · 기능 상태 전이 — 기본 보호만 → 사용자 지정 구성 → 온프레미스까지 확장

#### L4 · ⓪ 비활성 — 사용자 지정 · 온프레미스 보호가 없다

1. [시작] 사용자가 암호를 변경하거나 로그인을 시도
   - 주체: 사용자
   - 위치: 내 계정 › 암호 변경 (My Apps 프로필 › Change password) · SSPR 새 암호 화면 (aka.ms/sspr) · 로그인 화면 (login.microsoftonline.com)
   - 데이터: 새 암호 · 로그인 시도. 금지 암호 검사는 사용자 또는 관리자가 암호를 변경·재설정할 때만 돌고, 로그인 시도는 스마트 잠금의 대상입니다
   - 해설: 클라우드 계정에서 암호를 바꾸거나 로그인합니다. 두 방어는 서로 다른 시점에 작동합니다
2. [처리] 전역 금지 목록만 검사
   - 주체: Entra ID
   - 위치: Entra 암호 검증 (서비스 내부)
   - 데이터: Microsoft 보안 텔레메트리 분석으로 만든 전역 목록 (외부 데이터나 유출 암호 목록이 아니며 내용 비공개 · 편집·비활성화 불가) · 사용자 이름(이름·성)·테넌트 이름 부분 일치 검사 (4자 이상일 때만). 클라우드 전용 사용자는 Entra ID Free로 충분
   - 해설: 아무것도 켜지 않아도 기본 검사는 클라우드 사용자에게 항상 적용됩니다
3. [처리] 조직 맞춤 금지어가 없음
   - 주체: Entra ID
   - 위치: 보호 › 인증 방법 › 암호 보호 (Entra ID › Authentication methods › Password protection) › 사용자 지정 목록 적용 (Enforce custom list) = 아니오
   - 데이터: 회사명 · 제품명 · 본사 위치 같은 단어가 금지되지 않음. 사용자 지정 목록은 Entra ID P1 이상 라이선스가 필요합니다
   - 해설: 회사 이름을 넣은 암호도 점수 조건(5점)만 넘으면 통과합니다
4. [처리] 스마트 잠금은 기본값으로 이미 동작
   - 주체: Entra ID
   - 위치: 같은 화면의 사용자 지정 스마트 잠금 (Custom smart lockout) 영역
   - 데이터: 기본 임계값 10회 (Azure 공용 · 21Vianet, 미국 정부는 3회) · 기본 기간 60초 · 값 변경은 P1 이상이며 21Vianet 테넌트는 사용자 지정 불가
   - 해설: 스마트 잠금은 모든 고객에게 항상 켜져 있고, 라이선스가 있으면 값만 조직에 맞게 바꿀 수 있습니다
5. [처리] 온-프레미스 AD 암호 변경은 클라우드 목록 검사를 안 받음
   - 주체: 온프레미스
   - 위치: 도메인 컨트롤러 (DC 에이전트 없음)
   - 데이터: AD DS 복잡성·길이·기록 정책만 적용. 프록시 서비스와 DC 에이전트를 설치하고 등록하기 전에는 Entra 금지 목록이 DC에 내려오지 않습니다
   - 해설: 에이전트가 없으면 DC에서 바꾸는 암호는 금지 목록과 무관합니다
6. [끝] 맞춤 금지어 · 온프레미스 보호 부재 — 약한 암호가 남음
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 로그인 로그 · 감사 로그
   - 데이터: 목록에 없는 단어 기반 암호 · AD에 저장된 약한 암호. 다수 계정에 소수의 흔한 암호만 시도하는 암호 스프레이가 이런 암호를 노립니다
   - 해설: 암호 스프레이에 쓰이는 흔한 조합이 조직 안에 남습니다

#### L4 · ① 구성 — 금지어 · 잠금 값 · 온프레미스 사용 · 모드를 정한다

1. [시작] 관리자가 Entra Admin Center에 로그인
   - 주체: 관리자
   - 위치: entra.microsoft.com — 사용자 지정 목록·스마트 잠금은 Authentication Policy Administrator 이상, 온-프레미스 사용 설정 문서는 Authentication Administrator 이상으로 안내
   - 데이터: 역할 할당 (roleAssignments). 사용자 지정 목록과 잠금 값 변경은 Entra ID P1 이상 라이선스가 있는 테넌트에서 가능
   - 해설: 암호 보호 설정을 바꿀 수 있는 역할로 로그인합니다. 두 문서가 다른 역할 이름을 적으므로 운영에서는 필요한 설정에 맞는 역할을 확인합니다
2. [처리] 암호 보호 설정 페이지를 연다
   - 주체: 관리자
   - 위치: 보호 › 인증 방법 › 암호 보호 (Entra ID › Authentication methods › Password protection)
   - 데이터: 스마트 잠금 (Lockout threshold · Lockout duration in seconds) · 사용자 지정 목록 (Enforce custom list · Custom banned password list) · 온-프레미스 보호 (Enable password protection on Windows Server Active Directory · Mode)가 한 화면에 있음
   - 해설: 세 가지 설정이 같은 페이지에 모여 있어 한 번에 저장합니다
3. [처리] 스마트 잠금 임계값 설정
   - 주체: 관리자
   - 위치: 암호 보호 › 사용자 지정 스마트 잠금 › 잠금 임계값 (Lockout threshold) · 온프레미스 값 확인은 그룹 정책 관리 › Computer Configuration › Policies › Windows Settings › Security Settings › Account Policies › Account Lockout Policy
   - 데이터: 기본 10 (Azure 공용 · 21Vianet) · 미국 정부 3 · 통과 인증(PTA)이면 AD DS 임계값을 Entra 임계값의 2~3배 이상으로 (즉 Entra 값이 AD보다 낮게). 예: Entra 10이면 AD 20
   - 해설: 첫 잠금이 걸리기까지 허용할 실패 횟수입니다. 데이터센터 간 동기화 때문에 실제 허용 횟수는 설정값과 약간 다를 수 있습니다
4. [처리] 잠금 기간 설정
   - 주체: 관리자
   - 위치: 암호 보호 › 사용자 지정 스마트 잠금 › 잠금 기간(초) (Lockout duration in seconds)
   - 데이터: 기본 60초 · 통과 인증이면 Entra 기간을 AD DS 기간보다 길게 (Entra는 초, AD DS는 분 단위). 예: Entra 120초 · AD 60초
   - 해설: 반복해서 잠기면 기간이 자동으로 늘어나고(증가율 비공개), 잠금이 풀린 뒤 첫 로그인도 실패하면 곧바로 다시 잠깁니다
5. [처리] 사용자 지정 금지 암호 목록 적용
   - 주체: 관리자
   - 위치: 암호 보호 › 사용자 지정 금지 암호 목록 › 사용자 지정 목록 적용 (Enforce custom list) = 예
   - 데이터: 설정이 켜져야 아래 목록이 검사에 쓰임. 끄면(= 아니오) 목록은 남아도 검사에서 빠집니다
   - 해설: 목록을 먼저 채워도 이 스위치를 켜야 실제로 적용됩니다
6. [처리] 금지어 입력
   - 주체: 관리자
   - 위치: 사용자 지정 금지 암호 목록 입력란 (한 줄에 하나)
   - 데이터: 최대 1000개 · 4~16자 · 대소문자 무시 · 0↔o, @↔a 같은 흔한 문자 치환 고려. 변형까지 막을 수 있으니 Contoso · London · Widget처럼 핵심 단어만 넣습니다
   - 해설: 회사명·제품명·본사 위치·사내 용어·약어·현지어 월/요일 같은 조직 특화 단어를 넣습니다. 대량의 암호 차단용이 아닙니다
7. [처리] 온-프레미스 암호 보호 사용
   - 주체: 관리자
   - 위치: 암호 보호 › Windows Server Active Directory에서 암호 보호 사용 (Enable password protection on Windows Server Active Directory) = 예
   - 데이터: 아니오이면 설치된 DC 에이전트가 모든 암호를 그대로 수락 (검증·감사 이벤트 없음). 선행: 프록시 서비스·DC 에이전트 설치와 포리스트 등록 (L3 B)
   - 해설: DC 에이전트 설치는 별도이며 이 스위치가 켜져야 검증이 시작됩니다
8. [처리] 모드 선택 — 감사로 시작
   - 주체: 관리자
   - 위치: 암호 보호 › 모드 (Mode): 감사 (Audit) / 적용 (Enforced)
   - 데이터: 감사 = 위반 암호도 허용하고 이벤트만 기록 (다른 동작은 적용 모드와 동일) · 적용 = 위반 암호 거부. 적용 모드의 거부 메시지는 클라이언트가 정해 "새 암호가 길이, 복잡성 또는 기록 요구 사항을 충족하지 않습니다" 같은 일반 오류로 보일 수 있습니다
   - 해설: 영향을 본 뒤 적용 모드로 전환하라고 권장합니다
9. [끝] 저장 — 반영까지 몇 시간 걸릴 수 있음
   - 주체: 관리자
   - 위치: 저장 (Save)
   - 데이터: 사용자 지정 목록 변경은 반영까지 수 시간 · 온-프레미스는 DC 에이전트가 정책을 다시 내려받을 때까지 지연 (시작 시 + 정책이 1시간 넘으면 재요청). 실시간 정책 엔진이 아니며 큰 환경의 정책 갱신 주기는 보통 시간이 아니라 일 단위로 봅니다
   - 해설: 저장 직후 바로 강제되지 않으니 지연을 감안해 시험합니다

#### L4 · ② 활성 — 약한 암호는 거부되고 반복 실패는 잠긴다

1. [시작] 사용자가 암호 변경 또는 재설정 요청
   - 주체: 사용자
   - 위치: 내 계정 › 암호 변경 · SSPR 새 암호 화면 (aka.ms/sspr) · 관리자 암호 재설정
   - 데이터: 새 암호 후보. SSPR로 재설정하려면 테넌트에 SSPR이 구성되고 사용자가 등록돼 있어야 합니다
   - 해설: 사용자 또는 관리자가 새 암호를 제출하는 단계입니다. 로그인 시점에는 이 검사가 돌지 않습니다
2. [처리] 암호 보호 검증 호출
   - 주체: Entra ID
   - 위치: Entra 암호 변경·재설정 서비스
   - 데이터: 사용자 이름(이름·성) · 테넌트 이름 · 정책 (사용자 지정 목록 적용 여부). 전역 목록은 항상, 사용자 지정 목록은 적용이 켜진 경우에만 합쳐집니다
   - 해설: 변경·재설정 때마다 같은 검증기를 거칩니다
3. [처리] 전역 + 사용자 지정 목록과 대조
   - 주체: Entra ID
   - 위치: 암호 보호 검증기 (서비스 내부)
   - 데이터: 정규화(소문자화 + 0→o · 1→l · $→s · @→a) → 퍼지 매칭(편집 거리 1) → 부분 문자열(이름·성·테넌트명) → 점수 계산 (L3 A에서 단계별로 설명)
   - 해설: 두 목록과 이름·테넌트명을 합쳐 점수로 판정합니다
4. [판단] 점수가 기준(5점) 이상인가?
   - 주체: Entra ID
   - 위치: 암호 보호 검증기 (서비스 내부)
   - 데이터: 금지어당 1점 + 남은 글자당 1점. 예: C0ntos0Blank12 → contoso·blank·1·2 = 4점이라 거부
   - 해설: 5점 미만이면 변경이 거부되고 사용자에게는 "추측하기 쉬운 단어·구문·패턴" 또는 "관리자가 차단한 단어" 계열의 오류가 보입니다
   - 예 → 5
   - 아니오 → [차단] 변경 거부 — "쉽게 추측할 수 있는 단어" 오류
5. [처리] 새 암호 저장 + 변경 기록
   - 주체: Entra ID
   - 위치: 모니터링 및 상태 › 감사 로그 (Audit logs)
   - 데이터: 자격 증명 갱신 · 감사 로그 (암호 변경 활동) [확인 필요: 활동 이름]
   - 해설: 통과한 암호만 저장됩니다
6. [처리] 이후 로그인 시도 — 스마트 잠금이 실패를 계산
   - 주체: Entra ID
   - 위치: Entra 로그인 서비스
   - 데이터: 익숙한 위치 · 낯선 위치의 별도 카운터 · 직전 잘못된 암호 해시 3개 비교 (통과 인증은 인증이 온-프레미스에서 일어나 해시 추적 불가). 잠금 상태는 데이터센터 간 동기화됩니다
   - 해설: 같은 잘못된 암호를 반복해도 카운터가 올라가지 않습니다
7. [판단] 실패 횟수가 임계값에 도달했는가?
   - 주체: Entra ID
   - 위치: Entra 로그인 서비스
   - 데이터: 잠금 임계값 (기본 10 · 미국 정부 3). 낯선 위치와 익숙한 위치는 카운터가 따로라 낯선 위치 시도가 먼저 잠깁니다
   - 해설: 공격자로 보이는 낯선 위치의 시도를 먼저 막아 정상 사용자가 계속 쓰게 하려 하지만, 정상 사용자가 절대 잠기지 않는다고 보장하지는 않습니다
   - 예 → [차단] 계정 잠금 — AADSTS50053 · 잠금 기간 60초부터 증가
   - 아니오 → 8
8. [처리] 로그인 성공 또는 일반 실패로 처리
   - 주체: Entra ID
   - 위치: Entra 로그인 서비스
   - 데이터: 올바른 암호면 인증 진행 · 실패면 카운터 유지
   - 해설: 임계값에 못 미친 실패는 그대로 다시 시도하게 둡니다
9. [끝] 거부와 잠금이 로그에 남음
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 로그인 로그 · 감사 로그
   - 데이터: SigninLogs ResultType 50053 (AADSTS50053 IdsLocked) · 잠금 중 화면 메시지 "Your account is temporarily locked to prevent unauthorized use…" · 감사 로그 암호 변경 실패 [확인 필요: 활동 이름]
   - 해설: 거부된 변경과 잠긴 계정을 로그로 찾아 조사합니다
- 시나리오: 예 ▸ 예 :: 강한 암호 저장 뒤 반복 실패로 계정 잠금
- 시나리오: 예 ▸ 아니오 :: 강한 암호 저장, 임계값 미달로 로그만 남음
- 시나리오: 아니오 :: 점수가 기준에 못 미쳐 약한 암호 변경 거부

> 교육 포인트: 암호 보호는 "새 암호의 품질"을, 스마트 잠금은 "로그인 시도의 반복"을 막습니다. 두 방어는 서로 다른 단계(변경 vs 로그인)에서 작동하니 함께 설명합니다.
>
> 주의: 정책 변경은 즉시 적용되지 않을 수 있고, 통과 인증 환경에서는 직전 잘못된 암호 해시 비교가 되지 않습니다.

### L3 · A · 금지 암호 평가 — 정규화 · 매칭 · 점수

#### L4 · 암호 한 개가 점수로 판정되기까지

1. [시작] 사용자가 새 암호를 제출
   - 주체: 사용자
   - 위치: 내 계정 › 암호 변경 · SSPR 새 암호 화면
   - 데이터: 새 암호 문자열 (예: 정규화 결과 contosoblank12). 이 예에서는 contoso가 사용자 지정 목록에, blank가 전역 목록에 있다고 가정합니다
   - 해설: 금지 목록과 비교할 후보가 들어옵니다
2. [처리] 정규화 1 — 소문자로 통일
   - 주체: Entra ID
   - 위치: 암호 보호 검증기 (서비스 내부)
   - 데이터: 대소문자를 구분하지 않는 비교용 문자열
   - 해설: 작은 금지 목록이 훨씬 많은 변형을 막도록 형태를 단순화합니다
3. [처리] 정규화 2 — 흔한 문자 치환 되돌림
   - 주체: Entra ID
   - 위치: 암호 보호 검증기 (서비스 내부)
   - 데이터: 0→o · 1→l · $→s · @→a 치환 (예: Bl@nK → blank, "blank"가 금지어이면 거부)
   - 해설: 숫자·기호로 바꾼 글자를 원래 글자로 되돌려 봅니다
4. [처리] 퍼지 매칭 — 편집 거리 1
   - 주체: Entra ID
   - 위치: 암호 보호 검증기 (서비스 내부)
   - 데이터: 전역 목록 · 사용자 지정 목록에 있는 단어와 편집 거리 1 비교. 예: abcdef가 금지어이면 abcdeg(글자 변경) · abcdefg(추가) · abcde(삭제) 모두 일치로 봅니다
   - 해설: 글자 하나가 다른 변형도 같은 금지어로 봅니다
5. [처리] 부분 문자열 매칭 — 이름과 테넌트명
   - 주체: Entra ID
   - 위치: 암호 보호 검증기 (서비스 내부)
   - 데이터: 사용자 이름 · 성 · 테넌트 이름 (4자 이상만) · 온-프레미스 DC에서는 테넌트명 제외. 예: 이름이 Poll인 사용자의 p0LL23fb → poll23fb에서 이름이 발견되어 목록에 없어도 걸림
   - 해설: 목록에 없어도 사용자 이름이 들어 있으면 걸러냅니다
6. [처리] 점수 계산
   - 주체: Entra ID
   - 위치: 암호 보호 검증기 (서비스 내부)
   - 데이터: 찾은 금지어 1개 = 1점 · 금지어가 아닌 남은 글자 1개 = 1점 · 합계가 5점 이상이어야 수락
   - 해설: 금지어를 덮을 만큼 다른 글자가 늘어야 점수가 오릅니다
7. [판단] 점수가 5점 이상인가?
   - 주체: Entra ID
   - 위치: 암호 보호 검증기 (서비스 내부)
   - 데이터: 예: contoso + blank + 1 + 2 = 4점
   - 해설: 5점 미만은 거부, 이상은 허용입니다. 금지어가 들어 있어도 전체가 충분히 강하면 수락될 수 있습니다
   - 예 → 8
   - 아니오 → [차단] 거부 — 예: contoso + blank + 1 + 2 = 4점
8. [끝] 허용 — 예: contoso + blank + f + 9 + ! = 5점
   - 주체: Entra ID
   - 위치: 암호 보호 검증기 (서비스 내부)
   - 데이터: 점수 5점 이상 → 암호 저장 진행. 알고리즘과 전역 목록은 보안 분석에 따라 언제든 바뀔 수 있고, 온-프레미스 DC 에이전트는 소프트웨어를 업그레이드해야 새 알고리즘이 반영됩니다
   - 해설: 같은 금지어라도 다른 글자가 더해지면 통과할 수 있습니다
- 시나리오: 예 :: 점수 5점 이상이라 새 암호 허용
- 시나리오: 아니오 :: 점수 5점 미만이라 새 암호 거부

> 교육 포인트: 사용자 지정 목록은 "차단 목록"이 아니라 "점수 계산용 단어 목록"입니다. 단어 몇 개로 변형까지 막지만, 5점을 넘기면 통과하므로 대량 차단 용도는 아닙니다.
>
> 주의: 사용자 지정 목록은 최대 1000개이고 단어 길이는 4~16자입니다. 전역 목록은 편집할 수 없습니다.
>
> 출처: https://learn.microsoft.com/entra/identity/authentication/concept-password-ban-bad

### L3 · B · 온프레미스 암호 보호 — 프록시 서비스 + DC 에이전트

#### L4 · 클라우드 정책이 DC까지 내려가 AD 암호를 검사하는 길

1. [시작] 관리자가 프록시 서버에 프록시 서비스 설치
   - 주체: 관리자
   - 위치: 도메인 가입 멤버 서버 — AzureADPasswordProtectionProxySetup.exe (/quiet 무인 설치 가능 · 재시작 불필요)
   - 데이터: Windows Server 2012 R2 이상(Server Core 포함) · .NET 4.7.2 · Universal C Runtime · 아웃바운드 TLS 1.2 · login.microsoftonline.com / enterpriseregistration.windows.net / autoupdate.msappproxy.net 접근 · DC가 프록시에 로그온할 수 있도록 "Access this computer from the network" 권한 · DC에서 프록시로 RPC 135번 포트와 RPC 서버 포트(기본 49152~65535 동적, 고정 가능) · 설치 중 Windows Firewall 서비스 실행 필요 · 대부분 2대면 가용성 충분 · RODC에는 설치 불가 · 애플리케이션 프록시와 같은 서버에 설치 금지
   - 해설: DC가 인터넷에 직접 나가지 않도록 중간 서버를 둡니다. DC가 인터넷에 직접 나갈 수 있어도 프록시 서비스는 필수입니다
2. [처리] 프록시와 포리스트를 Entra ID에 등록
   - 주체: 관리자
   - 위치: 프록시 서버의 64비트 PowerShell (Import-Module AzureADPasswordProtection) — Register-AzureADPasswordProtectionProxy · Register-AzureADPasswordProtectionForest · 확인: Test-AzureADPasswordProtectionProxyHealth -TestAll
   - 데이터: 테넌트에서 프록시를 처음 등록할 때는 Global Administrator, 이후 프록시·포리스트 등록은 Security Administrator 이상 · 포리스트 등록에는 AD 엔터프라이즈 관리자와 로컬 관리자 권한도 필요 · 인증은 대화형 / -AuthenticateUsingDeviceCode / -AzureCredential(MFA 불가) 중 선택 · 포리스트 등록은 포리스트당 평생 한 번, 아무 프록시에서나 실행
   - 해설: 포리스트와 프록시를 같은 테넌트에 묶는 단계입니다. 포리스트와 모든 프록시는 반드시 같은 테넌트에 등록해야 하며 서로 다르면 정책 다운로드가 실패합니다. 등록 중 MFA 요구로 막히면 디바이스 설정의 "조인 시 MFA 요구"를 임시로 아니오로 바꾸는 우회가 있습니다
3. [처리] 모든 DC에 DC 에이전트 설치
   - 주체: 관리자
   - 위치: 각 DC — AzureADPasswordProtectionDCAgentSetup.msi (msiexec /i … /quiet /qn /norestart)
   - 데이터: Windows Server 2012 R2 이상(Server Core 포함) · .NET 4.7.2 · SYSVOL 복제는 반드시 DFSR(FRS면 정상 동작 안 함) · Key Distribution Service 활성화 · 일부 DC만 설치하면 일관된 강제 불가 (시험용으로만 권장) · 설치·제거·업그레이드 모두 재시작 필요 (암호 필터 DLL이 재시작으로만 로드됨) · RODC에는 설치 불필요 (변경이 쓰기 가능 DC로 전달됨)
   - 해설: 에이전트가 있는 DC에서 처리한 변경만 검증됩니다. 재시작이 끝나야 설치가 완료됩니다
4. [처리] DC 에이전트가 프록시를 찾음
   - 주체: 온프레미스
   - 위치: AD DS serviceConnectionPoint 개체
   - 데이터: 프록시와 DC 에이전트가 각각 SCP를 만들어 광고 (프록시 SCP는 DC 에이전트가 프록시를 찾는 데, DC 에이전트 SCP는 주로 보고·진단에 사용) · 스키마 변경 없음 · 별도 AD 계정 불필요
   - 해설: AD 안의 SCP로 서로를 찾아 통신 경로를 정합니다. Get-AzureADPasswordProtectionDCAgent로 SCP에 등록된 DC 에이전트 현황을 볼 수 있습니다
5. [처리] 프록시를 거쳐 정책 다운로드
   - 주체: 온프레미스
   - 위치: DC 에이전트 → 프록시 (RPC over TCP) → Entra ID
   - 데이터: 전역 + 테넌트 사용자 지정 금지 목록 (온프레미스와 클라우드가 같은 목록 사용) · 프록시는 상태 없음 · 정책을 캐시하지 않음 · DC 에이전트는 프록시를 라운드 로빈으로 고르고 응답 없는 프록시는 건너뜀 · 프록시가 DC 에이전트를 호출하는 일은 없음
   - 해설: DC 에이전트는 수신 포트를 열지 않고 정책을 가져옵니다. 프록시 등록 때 AADPasswordProtectionProxy 서비스 주체에 자격 증명이 추가되어 감사 로그에 관련 이벤트가 보일 수 있습니다
6. [처리] 정책을 SYSVOL에 저장
   - 주체: 온프레미스
   - 위치: 도메인 SYSVOL 공유 루트의 전용 폴더
   - 데이터: 서비스 시작 시 항상 새 정책 요청 + 이후 매시간 정책 나이를 확인해 1시간을 넘으면 재요청 · 다른 DC는 복제로 수신 (복제되어 들어온 새 정책도 감시)
   - 해설: 정책은 DC마다 캐시되어 프록시가 일시적으로 끊겨도 검증은 계속됩니다. 정책이 아예 없으면 모든 암호가 자동 수락되고 경고 이벤트(30001)가 남습니다
7. [처리] 암호 변경이 DC에 도착해 필터가 호출됨
   - 주체: 온프레미스
   - 위치: DC 에이전트 암호 필터 DLL → DC 에이전트 서비스 (로컬)
   - 데이터: 변경 또는 설정(set) 이벤트 · 평문 암호는 DC를 떠나지 않음 · AD DS는 모든 암호 검증 구성 요소(서드파티 필터 포함)가 동의해야 암호를 수락하므로 기존 AD 정책을 대체하지 않고 추가로 적용됨
   - 해설: 운영체제가 암호 필터 DLL에 검증을 요청합니다
8. [판단] 캐시된 정책에 위반되는가?
   - 주체: 온프레미스
   - 위치: DC 에이전트 Admin 이벤트 로그 (\Applications and Services Logs\Microsoft\AzureADPasswordProtection\DCAgent\Admin)
   - 데이터: 로컬 정책 점수 판정 (평가 알고리즘은 클라우드와 같고 테넌트명 부분 일치는 제외) · 정책이 없으면 자동 수락 + 경고 이벤트
   - 해설: 정책 위반 여부만 먼저 가립니다. 통과한 암호는 이벤트 10014(변경)·10015(설정)로 기록됩니다
   - 예 → 9
   - 아니오 → [끝] 통과 — 이벤트 10014 (변경) · 10015 (설정)
9. [판단] 모드가 적용(Enforced)인가?
   - 주체: 온프레미스
   - 위치: 보호 › 인증 방법 › 암호 보호 › 모드
   - 데이터: 감사 / 적용. 거부 시 이벤트 10016(변경)·10017(설정)과 원인별 상관 이벤트가 쌍으로 남음 — 사용자 지정 정책 30002/30003 · Microsoft 정책 30004/30005 · 결합 30026/30027 · 사용자 이름 30021/30022
   - 해설: 같은 위반이라도 모드에 따라 거부와 기록만으로 갈립니다. 쌍은 같은 CorrelationId로 묶입니다
   - 예 → [차단] 거부 — 이벤트 10016 (변경) · 10017 (설정)
   - 아니오 → 10
10. [끝] 감사 통과 — 허용하고 이벤트만 기록
   - 주체: 로그
   - 위치: DC 에이전트 Admin 이벤트 로그 · 요약은 프록시 서버에서 Get-AzureADPasswordProtectionSummaryReport (각 DC의 Admin 로그를 원격 조회하므로 로그가 많으면 느리고 DC에 부하)
   - 데이터: 이벤트 10024 (변경) · 10025 (설정) — "거부될 암호였음" · 상관 이벤트 30008/30007(사용자 지정) · 30010/30009(Microsoft) · 30028/30029(결합). 정책 자체가 꺼지면 30019가 한 번 기록됨
   - 해설: 적용 모드 전환 전에 영향을 미리 파악하는 용도입니다. 감사 기간에 DC 승격·강등을 최소 한 번씩 시험해 자동화가 깨지는지도 확인합니다
- 시나리오: 예 ▸ 예 :: 정책 위반에 적용 모드여서 암호 변경 거부
- 시나리오: 예 ▸ 아니오 :: 정책 위반이지만 감사 모드여서 통과 처리
- 시나리오: 아니오 :: 정책 위반이 아니어서 암호 변경 통과

> 교육 포인트: DC는 인터넷에 직접 나가지 않고, 평문 암호는 DC 밖으로 나가지 않습니다. 감사 모드 기간에 이벤트 10024·10025를 모니터링해 영향이 확인되면 적용 모드로 전환합니다.
>
> 주의: 암호 보호는 변경·설정 시점에만 검사하므로 이미 AD에 저장된 약한 암호는 다음 변경 때까지 남습니다. AD의 기존 정책을 대체하는 것이 아니라 추가로 적용됩니다.

### L3 · C · 스마트 잠금 동작 — 실패 카운터 · 잠금 · 해제

#### L4 · 잘못된 암호 반복 → 잠금 → 해제까지

1. [시작] 잘못된 암호로 로그인 시도
   - 주체: 사용자
   - 위치: 로그인 화면 (login.microsoftonline.com)
   - 데이터: UPN · 틀린 암호
   - 해설: 정상 사용자의 오타일 수도, 공격자의 시도일 수도 있습니다. 스마트 잠금은 항상 켜져 있어 별도 구성이 없어도 동작합니다
2. [처리] 직전 잘못된 암호 해시 3개와 비교
   - 주체: Entra ID
   - 위치: Entra 로그인 서비스
   - 데이터: 최근 잘못된 암호 해시 3개 · 같은 암호는 카운터 증가 안 함 (통과 인증은 인증이 온-프레미스에서 일어나 해시 추적 불가 — 같은 암호를 반복해도 카운터가 오를 수 있음)
   - 해설: 같은 오타를 반복하는 정상 사용자가 잠기지 않게 합니다
3. [처리] 실패 카운터 증가 — 위치별로 따로 계산
   - 주체: Entra ID
   - 위치: Entra 로그인 서비스
   - 데이터: 익숙한 위치 · 낯선 위치의 별도 카운터 · 데이터센터 간 동기화로 임계값과 약간 오차 · 시험할 때 요청이 다른 데이터센터로 갈 수 있음
   - 해설: 공격자는 낯선 위치 카운터만 올라 정상 사용자와 구분됩니다. 낯선 위치의 정상 사용자도 올바른 암호를 쓰고 이전 낯선 위치 실패가 적어야 잠금을 피합니다
4. [판단] 실패 횟수가 임계값에 도달했는가?
   - 주체: Entra ID
   - 위치: 보호 › 인증 방법 › 암호 보호 › 사용자 지정 스마트 잠금
   - 데이터: 잠금 임계값 (기본 10 · Azure 정부 3 · 21Vianet 10). 값 변경은 P1 이상이며 21Vianet 테넌트는 불가
   - 해설: 도달하기 전에는 계속 시도할 수 있습니다
   - 예 → 5
   - 아니오 → [끝] 일반 실패 — 카운터 유지, 다시 시도 가능
5. [처리] 계정 잠금
   - 주체: Entra ID
   - 위치: Entra 로그인 서비스 (모든 Entra 데이터센터에 적용)
   - 데이터: 첫 잠금 기본 60초 · 잠금이 풀린 뒤 첫 시도도 실패하면 다시 잠금 · 연속으로 잠기면 기간 증가 (증가율 비공개)
   - 해설: 잠금은 모든 Entra 데이터센터에 함께 적용됩니다
6. [처리] 잠금 중 시도는 암호가 맞아도 거절
   - 주체: Entra ID
   - 위치: 로그인 로그
   - 데이터: AADSTS50053 (IdsLocked) · "계정이 일시적으로 잠겼습니다" 메시지 (영문: Your account is temporarily locked to prevent unauthorized use) · SigninLogs ResultType 50053
   - 해설: IP 트래픽 같은 신호를 분석해 악의적 속성의 로그인은 암호 유효 여부와 무관하게 기본 보호가 막고 같은 50053을 돌려줍니다
7. [판단] 사용자가 SSPR에서 "암호를 잊었습니다"를 선택했는가?
   - 주체: 사용자
   - 위치: https://aka.ms/sspr
   - 데이터: "암호를 알고 있습니다"를 고르면 잠금 타이머가 계속됨. SSPR 사용에는 테넌트의 SSPR 구성과 사용자 등록(aka.ms/ssprsetup)이 선행되어야 합니다
   - 해설: 잊었다고 하고 본인 확인을 통과하면 잠금이 초기화됩니다. 낯선 위치에서 잠겼다면 SSPR로 카운터를 재설정해 볼 수 있습니다
   - 예 → 8
   - 아니오 → 9
8. [처리] 잠금 기간 0초로 초기화
   - 주체: Entra ID
   - 위치: SSPR 흐름 (aka.ms/sspr)
   - 데이터: 잠금 시간 reset · 새 암호 설정 후 로그인
   - 해설: 사용자가 대기 없이 바로 복구합니다
   - 다음 → 10
9. [처리] 기간 만료 또는 암호 변경으로 해제 — 관리자는 대기 없이 해제
   - 주체: 관리자
   - 위치: ID › 사용자 › 모든 사용자 › 사용자 선택 › 암호 재설정 (Entra ID › Users › Reset password)
   - 데이터: 클라우드 계정 잠금 즉시 해제 가능 · 최소 Password Administrator 역할 필요 (다른 역할은 일부 대상만) · 임시 암호가 자동 생성되고 다음 로그인 때 변경 필요 · 동기화된 AD 사용자는 암호 쓰기 저장이 켜지고 관리형 도메인일 때만 재설정 가능 (페더레이션은 온프레미스에서 변경)
   - 해설: 기간을 기다리거나 관리자가 풀어 줄 수 있습니다. 재설정이 안 되면 사용자의 AdminCount가 1인지 확인합니다
10. [끝] 로그인 재개 + 잠금 기록
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 로그인 로그
   - 데이터: SigninLogs ResultType 50053 이력 · 이후 성공 로그인
   - 해설: 잠금 이력으로 공격 시도와 영향을 추적합니다
- 시나리오: 예 ▸ 예 :: 임계값 도달 후 SSPR로 잠금을 풀고 재개
- 시나리오: 예 ▸ 아니오 :: 임계값 도달 후 기간 만료·암호 변경으로 해제
- 시나리오: 아니오 :: 임계값 미달의 일반 실패로 잠금 없음

> 교육 포인트: 하이브리드(PHS·PTA) 환경에서는 Entra 스마트 잠금이 온-프레미스 AD 계정 잠금을 대신 막습니다. 이때 Entra 임계값은 AD 임계값보다 낮게(AD가 2~3배), Entra 잠금 기간은 AD보다 길게 둡니다.
>
> 예시: Entra 잠금 기간 120초, AD 잠금 기간 60초로 두면 Entra가 먼저 공격을 막아 AD 계정이 잠기지 않습니다.
