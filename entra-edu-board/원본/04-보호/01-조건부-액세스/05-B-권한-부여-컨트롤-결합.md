### L3 · B · 권한 부여 컨트롤 결합 — 여러 요구를 AND / OR로 합치는 법

#### L4 · 할당 매칭 → 정책 간 AND → 정책 안 결합(모두 필요 / 하나만 필요) → 허용

1. [시작] 이번 로그인에 걸리는 정책 추리기 — 할당 매칭
   - 주체: Entra ID
   - 위치: Entra ID 내부 평가 (결과는 Sign-in logs › Conditional Access 탭에 정책별 Success · Failure · Not Applied로 나열)
   - 데이터: conditions.users · applications · locations · platforms · clientAppTypes · devices.deviceFilter · signInRiskLevels 일치 여부. Include와 Exclude를 모두 보고 Exclude가 우선
   - 해설: 사용자 · 대상 리소스 · 조건이 모두 맞는 정책만 이번 로그인에 적용됩니다. Client apps는 설정하지 않아도 새 정책은 모든 클라이언트 앱 유형에 적용됩니다
2. [처리] 정책 간 결합 = AND — 모든 정책 충족 필요
   - 주체: Entra ID
   - 위치: Entra ID 내부 평가 (관리자 화면 없음)
   - 데이터: 적용 정책 목록 (예: 정책 1 MFA · 정책 2 준수 기기). 한 정책 안의 모든 할당(사용자 · 대상 리소스 · 조건)도 AND
   - 해설: 적용된 정책이 여러 개면 모두 충족해야 하며 정책끼리는 AND입니다. 예를 들어 한 정책은 MFA를, 다른 정책은 준수 기기를 요구하면 사용자는 둘 다 만족해야 합니다
3. [판단] 정책 안 결합 방식은?
   - 주체: Entra ID
   - 위치: 정책 › Access controls › Grant › Require all the selected controls / Require one of the selected controls
   - 데이터: grantControls.operator (AND 또는 OR, UI 기본값은 모두 필요). 비밀번호 변경(passwordChange)은 Graph에서 mfa와 AND로, risk remediation(riskRemediation)은 authenticationStrength와 AND로 함께 지정해야 하며 둘은 따로 씀
   - 해설: 각 정책이 여러 컨트롤을 어떤 방식으로 묶었는지 확인합니다. passwordChange · riskRemediation은 모든 리소스를 대상으로 하고 users · applications · userRiskLevels 조건만 쓸 수 있습니다
   - AND → 4
   - OR → 5
4. [처리] 모두 필요 (AND, 기본값) — 전부 충족
   - 주체: Entra ID
   - 위치: Require all the selected controls (정책 › Access controls › Grant)
   - 데이터: 선택한 컨트롤 전부의 충족 상태. 예: grantControls.builtInControls = mfa, compliantDevice 에 operator = AND
   - 해설: 여러 컨트롤을 고르면 기본값이 "모두 필요"입니다. 요청 순서는 MFA, 준수 기기, 하이브리드 조인 등 정해진 순서를 따릅니다
   - 다음 → 6
5. [처리] 하나만 필요 (OR) — 정의된 순서로 요청
   - 주체: Entra ID
   - 위치: Require one of the selected controls (정책 › Access controls › Grant)
   - 데이터: 컨트롤 정의 순서 · 하나라도 충족하면 이 정책은 통과. 예: operator = OR 로 mfa, compliantDevice
   - 해설: 정의된 순서대로 프롬프트를 띄우고 하나를 채우면 그 정책은 통과합니다. Kaizala · Skype for Business · Visio는 app protection policy를 지원하지 않아 approved client app을 OR로 묶어도 동작하지 않습니다
   - 다음 → 6
6. [처리] 정책별 충족 결과 기록
   - 주체: Entra ID
   - 위치: Entra ID › Monitoring & health › Sign-in logs › Conditional Access 탭 · Report-only 탭
   - 데이터: appliedConditionalAccessPolicies[].result (success · failure · notApplied · notEnabled · unknown, 보고 전용은 reportOnlySuccess · reportOnlyFailure · reportOnlyNotApplied · reportOnlyInterrupted) · enforcedGrantControls · enforcedSessionControls. reportOnly* 값은 Prefer: include-unknown-enum-members 헤더를 보내야 Graph가 반환
   - 해설: 정책마다 성공 · 실패가 따로 기록되어 어느 정책이 막았는지 알 수 있습니다
7. [처리] 전체 AND 판정 — 모든 정책 통과 확인
   - 주체: Entra ID
   - 위치: Entra ID 내부 평가 (관리자 화면 없음)
   - 데이터: 정책별 결과의 논리곱. 한 정책이라도 failure이면 로그인 전체가 실패
   - 해설: 한 정책이라도 실패하면 전체가 실패로 판정됩니다. 차단(block) 정책은 평가 초반에 이미 멈추므로 이 단계는 차단이 없을 때의 권한 부여 요구에만 해당합니다
8. [끝] 세션 컨트롤 적용 뒤 접근 허용
   - 주체: 로그
   - 위치: Entra ID › Monitoring & health › Sign-in logs › Basic info · Conditional Access 탭 / Graph GET /v1.0/auditLogs/signIns
   - 데이터: conditionalAccessStatus = success (가능한 값 success · failure · notApplied)
   - 해설: 모든 정책의 요구를 채우면 세션 컨트롤을 적용한 뒤 접근이 허용됩니다. 정책 결과를 읽으려면 Security Reader · Global Reader · Conditional Access Administrator 같은 역할이 필요합니다
- 시나리오: AND :: 정책 안 모두 필요(AND)로 결합해 접근 허용
- 시나리오: OR :: 정책 안 하나만 필요(OR)로 결합해 접근 허용

> 예시: 정책 1 MFA 필요 + 정책 2 준수 기기 필요 → 둘 다 충족해야 허용. 한 정책 안에서 "MFA 또는 준수 기기"로 묶으면 둘 중 하나만 충족해도 그 정책은 통과합니다.
>
> 교육 포인트: 할당(사용자 · 리소스 · 조건)끼리도 AND입니다. 하나라도 어긋나면 그 정책은 이번 로그인에 걸리지 않습니다.
