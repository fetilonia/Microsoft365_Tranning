### L3 · 0 · 기능 상태 전이 — 정책 없음 → 보고 전용으로 구성 → 켜기로 강제

#### L4 · ⓪ 비활성 — 조건부 액세스 정책이 없거나 모두 꺼진 상태

1. [시작] 사용자가 앱에 로그인 요청
   - 주체: 사용자
   - 위치: 앱 로그인 화면 → login.microsoftonline.com/{tenant}/oauth2/v2.0/authorize (대화형 로그인은 /authorize, 갱신 토큰으로 조용히 갱신할 때는 /token)
   - 데이터: 사용자 · 기기 · IP · 대상 앱 (대상 앱은 Entra ID가 보는 리소스이며 로그의 ResourceDisplayName 열로 확인)
   - 해설: 어느 위치에서 어떤 기기로든 로그인을 요청합니다. 이 요청은 정책이 없어도 Entra ID 로그인 로그에 한 건으로 남습니다
2. [처리] 적용 대상 정책 0개 — 평가할 정책이 없음
   - 주체: Entra ID
   - 위치: Entra ID › Conditional Access(조건부 액세스) › Policies(정책) — 목록이 비었거나 모든 정책의 Enable policy가 Off. 조회는 Security Reader 이상, 변경은 Conditional Access Administrator 이상
   - 데이터: conditionalAccessPolicy.state = disabled (state 값은 enabled · disabled · enabledForReportingButNotEnforced). Graph: GET /v1.0/identity/conditionalAccess/policies, 권한 Policy.Read.All
   - 해설: 켜진 조건부 액세스 정책이 없어 평가할 대상이 없습니다. 보고 전용 정책은 평가만 되고 강제되지 않으므로 사용자 경험은 이 상태와 같습니다
3. [판단] 보안 기본값이 켜져 있는가?
   - 주체: Entra ID
   - 위치: Entra ID › Overview › Properties › Manage security defaults — Security defaults 토글 Enabled / Disabled (not recommended). 변경은 Conditional Access Administrator 이상
   - 데이터: 보안 기본값 사용 여부 (조건부 액세스 정책으로 대체하려면 보안 기본값을 먼저 Disabled로 바꿔야 함). 2019-10-22 이후 만든 테넌트는 기본으로 켜져 있을 수 있고, 새 테넌트는 켜진 뒤 24시간 유예 뒤부터 강제
   - 해설: 정책이 없는 테넌트에서는 Microsoft가 제공하는 기본 보호가 켜져 있을 수 있습니다. 조건부 액세스 정책이 없고 프리미엄 라이선스가 없으며 레거시 인증 클라이언트를 쓰지 않는 테넌트는 Microsoft가 알림 뒤 자동으로 켭니다
   - 예 → 4
   - 아니오 → 5
4. [처리] 보안 기본값 적용 — MFA 등록 · 관리자 MFA · 레거시 인증 차단
   - 주체: Entra ID
   - 위치: Entra ID › Overview › Properties › Manage security defaults (Enabled 상태)
   - 데이터: 모든 사용자 MFA 등록 요구(Microsoft Authenticator 알림으로만 등록 가능, 2024-07-29부터 14일 유예 없음) · 관리자 역할은 매 로그인 MFA · 필요할 때 사용자 MFA(Microsoft가 위치·기기·역할·작업으로 판단) · 레거시 인증 차단(IMAP · SMTP · POP3 · Exchange ActiveSync 기본 인증 포함) · 디바이스 코드 흐름 차단 · Azure Resource Manager 접근(Azure portal · Entra admin center · Azure PowerShell · Azure CLI) MFA 요구, Entra ID · Microsoft Graph는 제외
   - 해설: 세밀한 조건 없이 고정된 기본 보호만 적용되고 예외를 둘 수 없습니다. Directory Synchronization Accounts 역할 계정(Entra Connect · Cloud Sync)은 제외되고, 사용자에게 열린 MFA 방법을 끄면 테넌트에서 잠길 수 있으므로 끄지 않습니다
   - 다음 → 6
5. [처리] 1차 인증만 확인 — 암호만으로 통과
   - 주체: Entra ID
   - 위치: Entra ID › Monitoring & health › Sign-in logs › 해당 로그인 › Authentication Details 탭
   - 데이터: Log Analytics SigninLogs ConditionalAccessStatus = notApplied (Graph signIn.conditionalAccessStatus는 success · failure · notApplied 중 하나)
   - 해설: 정책도 보안 기본값도 없으면 암호 한 번으로 인증이 끝납니다. 다만 사용자별 MFA 같은 다른 경로가 인증 요구를 만들 수 있으며 그 출처는 SigninLogs AuthenticationRequirementPolicies 열에서 확인합니다
6. [끝] 토큰 발급 — 위치 · 기기와 무관하게 접근 허용
   - 주체: 로그
   - 위치: Entra ID › Monitoring & health › Sign-in logs › Conditional Access 탭 (Reports Reader 이상으로 로그 조회)
   - 데이터: Log Analytics SigninLogs ConditionalAccessPolicies = [] (Graph에서는 signIn.appliedConditionalAccessPolicies 빈 목록) · ConditionalAccessStatus = notApplied. 꺼진 정책이 남아 있으면 로그에 Disabled(notEnabled)로 나열될 수 있음
   - 해설: 누가 어디서 오든 같은 토큰이 발급되고 로그에도 정책 적용 기록이 없습니다. 이 상태는 위치 · 기기 · 위험과 무관하게 접근이 열려 있어 도입 전 기준선으로만 의미가 있습니다
- 시나리오: 예 :: 보안 기본값이 켜져 있어 적용 후 토큰 발급
- 시나리오: 아니오 :: 보안 기본값 없이 1차 인증만 확인하고 토큰 발급

#### L4 · ① 구성 — 보고 전용(Report-only)으로 만들고 영향을 본다

1. [시작] 관리자가 Entra Admin Center에 로그인
   - 주체: 관리자
   - 위치: entra.microsoft.com — Conditional Access Administrator 이상 (Security Reader는 정책 · 로그 · Policy impact 조회만 가능)
   - 데이터: 역할 할당. Graph로 정책을 만들 때는 위임 · 앱 권한 Policy.Read.All + Policy.ReadWrite.ConditionalAccess (알려진 문제로 Application.Read.All 추가 동의가 필요할 수 있음)
   - 해설: 정책을 만들려면 조건부 액세스 관리자 역할이 필요하고, 조건부 액세스 자체는 Entra ID P1 이상 라이선스가 필요합니다
2. [처리] 비상 접근(break-glass) 계정 그룹 준비
   - 주체: 관리자
   - 위치: Entra ID › Groups › New group (비상 계정 멤버 추가)
   - 데이터: 제외 대상 그룹 ID. 모든 사용자 · 모든 리소스 정책을 만들 때 "Don't lock yourself out!" 경고가 뜨고 현재 관리자 제외 옵션이 기본 제공됨
   - 해설: 모든 사용자 정책을 만들기 전에 제외할 비상 계정을 그룹으로 준비합니다. 제외(Exclude)는 포함(Include)보다 우선하며 정책은 중첩 그룹에도 적용됩니다
3. [처리] 새 정책 만들기 — 이름 입력
   - 주체: 관리자
   - 위치: Entra ID › Conditional Access › Policies › New policy (Graph: POST /v1.0/identity/conditionalAccess/policies)
   - 데이터: conditionalAccessPolicy.displayName. 강제되는 정책이 되려면 이름 · 할당(사용자와 대상 리소스) · 액세스 제어(권한 부여 또는 차단)가 최소한 필요
   - 해설: 정책 이름은 조직의 표준 명명 규칙으로 정합니다
4. [처리] 할당 · 사용자 — 포함 그룹 · 제외 비상 계정
   - 주체: 관리자
   - 위치: 새 정책 › Assignments › Users or workload identities › Include · Exclude (Include 선택지: None · All users · Select users and groups)
   - 데이터: conditions.users.includeUsers · includeGroups · includeRoles · excludeGroups. All users는 B2B 게스트 포함, Select users and groups에는 게스트 · 외부 사용자 유형 · Directory roles(기본 제공 역할만) · Users and groups가 있음. 한 사용자가 2,048개를 넘는 그룹에 속하면 접근이 차단될 수 있어 개별 사용자 대신 그룹을 사용
   - 해설: 시험 그룹을 포함하고 비상 계정 그룹은 반드시 제외합니다. 관리 단위 범위 역할과 사용자 지정 역할은 지원되지 않고, 그룹 · 역할 대상 정책은 토큰 발급 시에만 평가되어 새 멤버는 새 토큰을 받기 전까지 적용되지 않습니다
5. [처리] 할당 · 대상 리소스 — 앱 · 사용자 작업 · 인증 컨텍스트
   - 주체: 관리자
   - 위치: 새 정책 › Target resources › Resources (formerly cloud apps) › Include · Exclude (대상 종류: Resources · User actions · Authentication context)
   - 데이터: conditions.applications.includeApplications (All · Office365 · appId 목록) · excludeApplications · includeUserActions (urn:user:registersecurityinfo · urn:user:registerdevice)
   - 해설: 어떤 앱이나 작업에 들어갈 때 이 정책이 걸릴지 고릅니다. 사용자 작업(User actions) 범위 정책은 보고 전용으로 평가할 수 없고, Microsoft 365 서비스는 개별 앱 대신 Office 365 묶음으로 지정해 서비스 종속성 문제를 피합니다
6. [처리] 네트워크 · 조건 — 위치 · 위험 · 플랫폼 · 클라이언트 앱
   - 주체: 관리자
   - 위치: 새 정책 › Network · Conditions (Sign-in risk · Device platforms · Client apps · Filter for devices; 위치는 Entra ID › Conditional Access › Named locations에서 먼저 정의)
   - 데이터: conditions.locations(Any network or location · All trusted networks and locations · All Compliant Network locations · Selected networks and locations) · signInRiskLevels · platforms · clientAppTypes · devices.deviceFilter. Named location은 IPv4/IPv6 범위 · 국가/지역으로 만들며 최대 195개, 위치당 IP 범위 2,000개
   - 해설: 할당은 모두 AND로 결합되어 전부 맞아야 정책이 이 로그인에 걸립니다. 로그인 위험 조건은 ID Protection이 필요하고, 새 정책은 Client apps를 설정하지 않아도 모든 클라이언트 앱 유형에 적용되며, 기기 플랫폼은 변경 가능한 user agent 같은 비검증 정보로 판별됩니다
7. [처리] 액세스 제어 · 권한 부여 — 차단 또는 요구 컨트롤
   - 주체: 관리자
   - 위치: 새 정책 › Access controls › Grant (Block access · Grant access, 여러 개면 Require all the selected controls / Require one of the selected controls)
   - 데이터: grantControls.builtInControls (block · mfa · compliantDevice · domainJoinedDevice · approvedApplication · compliantApplication · passwordChange · riskRemediation) · authenticationStrength · termsOfUse · customAuthenticationFactors · operator (AND 모든 컨트롤 필요 · OR 하나만 필요)
   - 해설: 여러 컨트롤을 고르면 기본은 "모두 필요"이고 "하나만 필요"로 바꿀 수 있습니다. Windows Hello for Business는 MFA 요구를 충족하고, 비밀번호 변경은 All resources · 사용자 위험 조건과만 쓰며 준수 기기 같은 다른 컨트롤과 함께 쓸 수 없고, Require approved client app은 2026년 3월 폐기로 공지되어 새 정책에는 Require app protection policy를 씁니다
8. [처리] 액세스 제어 · 세션 — 로그인 빈도 · CAE · 토큰 보호
   - 주체: 관리자
   - 위치: 새 정책 › Access controls › Session (Use app enforced restrictions · Use Conditional Access App Control · Sign-in frequency · Persistent browser session · Customize continuous access evaluation · Disable resilience defaults · Require token protection for sign-in sessions)
   - 데이터: sessionControls (applicationEnforcedRestrictions · cloudAppSecurity · signInFrequency · persistentBrowser · disableResilienceDefaults, 베타: continuousAccessEvaluation.mode · secureSignInSession). 앱 적용 제한은 Exchange Online · SharePoint Online에서만 동작
   - 해설: 접근을 허용한 뒤의 세션 동작을 제한하는 컨트롤을 선택합니다. CAE의 Disable은 All resources를 선택하고 다른 조건이 없을 때만 선택할 수 있습니다
9. [처리] 정책 사용 = 보고 전용으로 만들기
   - 주체: 관리자
   - 위치: 새 정책 › Enable policy › Report-only › Create
   - 데이터: conditionalAccessPolicy.state = enabledForReportingButNotEnforced
   - 해설: 보고 전용은 로그인마다 정책을 평가만 하고 MFA 요청이나 차단은 하지 않습니다. 준수 기기를 요구하는 보고 전용 정책은 macOS · iOS · Android에서 디바이스 인증서 선택 프롬프트를 반복해 띄울 수 있어 해당 플랫폼을 제외하고, GPS 기반 위치를 쓰면 위치 공유 프롬프트가 뜹니다. 기존 정책을 On에서 Report-only로 바꾸면 강제가 해제됩니다
10. [끝] 영향 확인 — 사용자 영향 없이 결과만 누적
    - 주체: 로그
    - 위치: Entra ID › Monitoring & health › Sign-in logs › Report-only 탭 · Policy impact(미리 보기) · Entra ID › Conditional Access › Insights and reporting (워크북)
    - 데이터: SigninLogs 보고 전용 결과 (Report-only: Success · Failure · User action required · Not applied; Graph result는 reportOnlySuccess · reportOnlyFailure · reportOnlyNotApplied · reportOnlyInterrupted). Policy impact는 대화형 로그인 대상, 최근 24시간 · 7일 · 1개월, Security Reader 이상. 워크북은 P1과 로그인 로그를 받는 Log Analytics 작업 영역이 필요
    - 해설: 켜기 전에 어느 로그인이 막히거나 추가 인증을 요구받았을지 로그에서 미리 봅니다. 기존 정책을 고칠 때는 변경안 복사본을 보고 전용으로 만들어 강제 중인 원본과 결과를 비교합니다

#### L4 · ② 활성 — 정책을 켜기로 바꾼 뒤 로그인이 평가되고 강제된다

1. [시작] 사용자가 앱에 로그인 요청 (정책 상태 = 켜기)
   - 주체: 사용자
   - 위치: 앱 로그인 화면 → /authorize (정책 Enable policy = On)
   - 데이터: 사용자 · 기기 · IP · 대상 앱 (정책은 영향 확인 뒤 정책 사용 = 켜기로 전환됨, state = enabled)
   - 해설: 관리자가 정책 사용을 켜기로 바꾼 뒤 들어오는 요청입니다. 이미 발급된 토큰에는 소급되지 않고 다음 토큰 발급부터 적용됩니다
2. [처리] 1차 인증 — 암호 등 자격 증명 검증
   - 주체: Entra ID
   - 위치: login.microsoftonline.com 로그인 화면 (자격 증명 입력)
   - 데이터: AuthenticationDetails 첫 단계 (예: Password). 로그의 AuthenticationRequirement 열이 모든 단계를 통틀어 필요했던 최고 인증 수준을 보여 줌
   - 해설: 조건부 액세스는 1차 인증이 끝난 뒤에 평가됩니다
3. [처리] Phase 1 · 세션 정보 수집 — 위치 · 기기 · 플랫폼
   - 주체: Entra ID
   - 위치: Entra ID 내부 평가 (관리자 화면 없음, 결과는 Sign-in logs › Device info · Location 탭으로 확인)
   - 데이터: 네트워크 위치 · 디바이스 ID · 플랫폼 · 클라이언트 앱 (켜기와 보고 전용 정책 모두 평가). 브라우저에서는 기기 등록 때 발급된 클라이언트 인증서로 기기를 식별하고 처음에는 인증서 선택 프롬프트가 뜰 수 있음
   - 해설: 정책 평가에 필요한 세션 정보를 먼저 모읍니다
4. [처리] 할당 매칭 — 사용자 · 리소스 · 조건이 모두 맞는 정책만
   - 주체: Entra ID
   - 위치: Entra ID 내부 평가 (결과는 Sign-in logs › Conditional Access 탭에 정책별로 나열)
   - 데이터: conditions 일치 결과 (정책별 적용 / 미적용). Include와 Exclude를 모두 보고 Exclude가 우선하며, 로그의 정책 결과는 Success · Failure · Not Applied · Disabled
   - 해설: 할당 중 하나라도 어긋나는 정책은 이번 로그인에 걸리지 않습니다. 기기 등록 · 기기 준수 확인 같은 부트스트랩 로그인은 순환 의존을 피하려고 평가에서 면제되고 Windows Hello for Business 로그인은 Not Applied로 보입니다
5. [판단] 차단 컨트롤 정책이 걸렸는가?
   - 주체: Entra ID
   - 데이터: grantControls.builtInControls = block. 정책이 여러 개여도 차단 정책이 하나라도 걸리면 평가가 바로 멈추고 사용자는 차단됨(로그 result = failure)
   - 해설: 차단 컨트롤이 하나라도 걸리면 다른 요구와 관계없이 여기서 멈춥니다. 차단은 추가 인증으로 풀리지 않으므로 정책 대상에서 제외하거나 정책을 고쳐야 하고, 켜기 전에 보고 전용과 What If 도구로 검증합니다
   - 예 → [차단] 차단 — 평가 종료
   - 아니오 → 6
6. [판단] 아직 못 채운 권한 부여 요구가 있는가?
   - 주체: Entra ID
   - 데이터: Phase 1 결과로 충족된 요구 vs 정책이 요구하는 컨트롤. 예: 토큰에 유효한 MFA 클레임이 있으면 MFA 요구는 이미 충족, 준수 기기에서 온 요청이면 기기 요구도 충족
   - 해설: 이미 클레임이나 기기 상태로 충족된 요구는 다시 묻지 않습니다. 디바이스 코드 흐름은 기기 상태를 전달할 수 없어 준수 기기 · 하이브리드 조인 요구를 지원하지 않으므로 MFA 요구를 대신 씁니다
   - 예 → 7
   - 아니오 → 8
7. [처리] 사용자가 미충족 요구를 순서대로 충족
   - 주체: 사용자
   - 위치: 로그인 화면 (MFA 프롬프트 · 기기 준수 확인 · 약관 동의 화면 등). Require one of the selected controls 정책은 정의된 순서대로 프롬프트가 뜸
   - 데이터: MFA 클레임 · 기기 준수 상태 · 약관 수락 기록. 토큰에 MFA 클레임이 없으면 로그에 interrupt(MFA 대기)가 먼저 남고 MFA 뒤 두 번째 항목에서 약관 등이 검증되며, 클레임이 이미 있으면 한 항목에 success로 남음
   - 해설: MFA, 준수 기기, 하이브리드 조인 순서로 요구되고 약관은 그 뒤에 요청됩니다. 약관을 이전 로그인에서 수락했어도 MFA가 먼저 중단되면 그 항목에서는 약관이 실패로 보일 수 있습니다
8. [처리] 세션 컨트롤 적용 — 로그인 빈도 · 앱 제어 · CAE
   - 주체: Entra ID
   - 위치: Entra ID 내부 평가 (결과는 Sign-in logs › Conditional Access 탭 › 정책 선택 › Session Controls)
   - 데이터: sessionControls 결과 (signInFrequency · 앱 적용 제한 · 토큰 수명 등)
   - 해설: 요구를 모두 채우면 세션 컨트롤이 토큰 수명과 앱 동작에 반영됩니다. 적용 순서는 앱 적용 제한(App Enforced) · Defender for Cloud Apps 앱 제어 · 토큰 수명 순이며, Sign-in frequency는 CAE 사용 여부와 무관하게 적용됩니다
9. [처리] 토큰 발급 — 평가 결과가 토큰에 반영
   - 주체: Entra ID
   - 데이터: 액세스 토큰 · 갱신 토큰 · 세션 정보. 기본 액세스 토큰 수명은 1시간이고 CAE 지원 클라이언트와 리소스 조합이면 최대 28시간의 장기 토큰
   - 해설: 요구를 채운 요청에만 토큰이 발급되고 리소스는 이 토큰만 확인합니다. 정책이나 그룹 멤버십 변경은 이미 발급된 토큰에 소급되지 않으며 즉시 반영하려면 사용자 세션을 취소합니다
10. [끝] 정책 적용 결과 기록
    - 주체: 로그
    - 위치: Entra ID › Monitoring & health › Sign-in logs › Conditional Access 탭 / Log Analytics SigninLogs · Graph GET /v1.0/auditLogs/signIns (AuditLog.Read.All)
    - 데이터: SigninLogs ConditionalAccessStatus(success · failure · notApplied) · ConditionalAccessPolicies (Graph 이름 appliedConditionalAccessPolicies; 정책별 result · enforcedGrantControls · enforcedSessionControls). Graph에서 이 속성은 Global Reader · Security Reader · Security Administrator · Conditional Access Administrator 역할(앱은 Policy.Read.All 등)이 있어야 반환되고 없으면 응답에서 빠짐
    - 해설: 어떤 정책이 적용되어 어떤 컨트롤을 요구했는지 로그인 로그에 남습니다. Graph에서는 Reports Reader가 로그인 로그는 읽어도 조건부 액세스 정책 결과(appliedConditionalAccessPolicies)는 받지 못합니다
- 시나리오: 예 :: 차단 컨트롤 정책에 걸려 로그인 차단
- 시나리오: 아니오 ▸ 예 :: 미충족 요구를 충족한 뒤 토큰 발급
- 시나리오: 아니오 ▸ 아니오 :: 남은 요구 없이 세션 컨트롤 후 토큰 발급

> 교육 포인트: 켜기 전에 보고 전용으로 영향을 확인하는 것이 안전한 도입 순서입니다. 강제는 리소스가 아니라 Entra가 토큰을 발급할 때 일어납니다.
>
> 주의: 모든 관리자를 대상으로 하는 정책을 켜기 전에 비상 접근(break-glass) 계정을 제외했는지 확인합니다. 사용자 작업 범위의 정책은 보고 전용으로 평가할 수 없습니다. 보안 기본값은 조건부 액세스 정책으로 대체할 때 먼저 끄고, 끈 직후 정책(또는 Microsoft 관리형 정책)으로 같은 보호를 곧바로 채워야 합니다.
