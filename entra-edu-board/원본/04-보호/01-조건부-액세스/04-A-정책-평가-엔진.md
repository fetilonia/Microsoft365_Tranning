### L3 · A · 정책 평가 엔진 — 여러 정책을 어떤 순서로 판정하는가

#### L4 · 2단계 평가 — Phase 1 세션 정보 수집 → Phase 2 강제

1. [시작] 로그인 요청이 Entra ID에 도착
   - 주체: 사용자
   - 위치: /authorize 또는 /token 요청 (클라이언트 → login.microsoftonline.com). 조건부 액세스는 1차 인증 뒤 토큰 발급 단계에서 평가
   - 데이터: 사용자 · 대상 리소스 · 기기 · IP · 클라이언트 앱 · 플랫폼
   - 해설: 사용자가 리소스에 접근하려고 토큰을 요청합니다. 리소스는 이후 발급된 토큰만 확인하므로 평가는 Entra ID에서 끝납니다
2. [처리] Phase 1 · 세션 정보 수집 — 위치 · 기기 ID
   - 주체: Entra ID
   - 위치: Entra ID 내부 평가 (관리자 화면 없음)
   - 데이터: 네트워크 위치 · 디바이스 ID · 플랫폼 · 클라이언트 앱. 플랫폼은 user agent 같은 변경 가능한 비검증 정보로 판별됨
   - 해설: Phase 1은 켜기 정책과 보고 전용 정책 모두에서 수행됩니다. 이 단계에서 이미 충족되는 요구(예: 토큰의 MFA 클레임, 준수 기기)는 Phase 2에서 다시 묻지 않습니다
3. [처리] 보고 전용 정책 평가 — 결과만 기록
   - 주체: Entra ID
   - 위치: Entra ID › Monitoring & health › Sign-in logs › 해당 로그인 › Report-only 탭
   - 데이터: 로그인 로그 보고 전용 탭 (Report-only: Success · Failure · User action required · Not applied; Graph result는 reportOnlySuccess · reportOnlyFailure · reportOnlyNotApplied · reportOnlyInterrupted)
   - 해설: 보고 전용은 Phase 1까지만 평가되고 MFA 요청이나 차단은 하지 않으며, 사용자 작업(User actions) 범위 정책은 평가 대상이 아닙니다. 준수 기기를 요구하는 보고 전용 정책은 macOS · iOS · Android에서 인증서 선택 프롬프트를 띄울 수 있습니다
4. [처리] Phase 2 · 미충족 요구 식별
   - 주체: Entra ID
   - 위치: Entra ID 내부 평가 (관리자 화면 없음)
   - 데이터: Phase 1 결과와 정책 요구의 차이 (켜기 정책만 대상). 예: 정책이 MFA와 준수 기기를 요구하는데 토큰에 MFA 클레임만 있으면 준수 기기가 미충족 목록에 남음
   - 해설: Phase 2는 켜기 상태 정책에서만 일어나며 아직 못 채운 요구를 추립니다
5. [판단] 차단 정책이 있는가?
   - 주체: Entra ID
   - 위치: Entra ID › Conditional Access › Policies › 정책 › Access controls › Grant › Block access
   - 데이터: grantControls.builtInControls = block. 한 정책이라도 걸리면 평가를 멈추고 사용자를 차단하며 정책 result는 failure
   - 해설: 차단 컨트롤 정책이 하나라도 있으면 다른 컨트롤보다 먼저 차단합니다. 차단은 추가 인증으로 풀리지 않으므로 비상 계정 제외와 보고 전용 · What If 검증이 필수입니다
   - 예 → [차단] 차단 — 여기서 평가 종료
   - 아니오 → 6
6. [처리] 권한 부여 요구 — 정해진 순서로 요청
   - 주체: Entra ID
   - 위치: 정책 › Access controls › Grant 에서 고른 컨트롤 (Require multifactor authentication · Require authentication strength · Require device to be marked as compliant · Require Microsoft Entra hybrid joined device · Require approved client app · Require app protection policy · Require password change)
   - 데이터: MFA → 준수 기기 → 하이브리드 조인 → 승인된 앱 → 앱 보호 → 암호 변경 → 약관 → 사용자 지정(미리 보기). 인증 강도 · 신원 확인 컨트롤의 순서 위치는 이 목록에 없음 [확인 필요: 인증 강도 · 신원 확인 컨트롤의 요청 순서]
   - 해설: 차단이 없으면 못 채운 요구를 이 순서로 하나씩 요청하며 MFA가 가장 먼저입니다. Windows Hello for Business는 MFA 요구를 충족합니다
7. [처리] 사용자가 요구를 하나씩 충족
   - 주체: 사용자
   - 위치: 로그인 중 프롬프트 (MFA 프롬프트 · 기기 인증서 선택 · 약관 동의 화면). Require one of the selected controls 정책은 정의된 순서로 프롬프트가 뜸
   - 데이터: 충족된 컨트롤 목록. 토큰에 MFA 클레임이 없으면 로그에 interrupt(MFA 대기)가 먼저 남고 MFA 뒤 두 번째 항목에서 나머지 컨트롤이 검증되며, 클레임이 있으면 한 항목에 success
   - 해설: 모든 정책의 요구가 채워질 때까지 프롬프트가 이어집니다. 디바이스 코드 흐름은 기기 상태를 전달할 수 없어 준수 기기 · 하이브리드 조인 요구를 쓸 수 없습니다
8. [처리] 세션 컨트롤 적용 — 앱 제한 · 앱 제어 · 토큰 수명
   - 주체: Entra ID
   - 위치: 정책 › Access controls › Session (Use app enforced restrictions · Use Conditional Access App Control · Sign-in frequency · Persistent browser session · Customize continuous access evaluation · Disable resilience defaults)
   - 데이터: 앱 적용 제한(Exchange Online · SharePoint Online 한정) · Defender for Cloud Apps 앱 제어 · 로그인 빈도 · CAE 설정. Graph: sessionControls.applicationEnforcedRestrictions · cloudAppSecurity · signInFrequency · persistentBrowser · disableResilienceDefaults
   - 해설: 권한 부여를 다 채운 뒤에 세션 컨트롤이 적용되며 순서는 앱 적용 제한 · Defender for Cloud Apps 앱 제어 · 토큰 수명입니다. 앱 제어는 민감 문서 다운로드 · 잘라내기 · 복사 · 인쇄 차단이나 위험한 세션 모니터링에 쓰입니다
9. [끝] 토큰 발급 — 접근 허용
   - 주체: 로그
   - 위치: Entra ID › Monitoring & health › Sign-in logs › Conditional Access 탭 / Graph GET /v1.0/auditLogs/signIns
   - 데이터: Graph signIn.appliedConditionalAccessPolicies (Log Analytics SigninLogs는 ConditionalAccessPolicies) · conditionalAccessStatus (success · failure · notApplied)
   - 해설: 토큰이 발급되고 정책별 평가 결과가 기록됩니다. 이 토큰은 이후 정책 변경이나 그룹 멤버십 변경에 소급되지 않으므로 즉시 반영이 필요하면 사용자 세션을 취소합니다
- 시나리오: 예 :: 차단 정책에 걸려 로그인이 차단됨
- 시나리오: 아니오 :: 차단 정책 없이 요구 충족 후 토큰 발급

> 교육 포인트: 여러 정책이 걸리면 모두 충족해야 합니다. 차단 정책이 하나라도 있으면 다른 컨트롤보다 먼저 차단됩니다.
>
> 주의: 역할이나 그룹을 대상으로 한 정책은 토큰이 발급될 때만 평가됩니다. 새로 추가된 멤버는 새 토큰을 받기 전까지 정책이 적용되지 않으며, 권한 상승 시점에 평가를 일으키려면 PIM 활성화 시 MFA 요구를 함께 씁니다.
