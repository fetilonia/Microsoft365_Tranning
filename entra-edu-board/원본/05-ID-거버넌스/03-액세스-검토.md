## L2 · 액세스 검토 — 주기적 권한 재확인

- 설정(Control Plane): 검토 대상(그룹·앱·역할·패키지) · 검토자 · 주기 | 미응답 시 동작 · 자동 적용
- 강제(Enforcement): Entra 액세스 검토 서비스 | 거부 결과를 멤버십·앱 할당에 적용
- 증적(Evidence): 검토 결과 · 이력(CSV) | 감사 로그 (Create access review · Apply decision) · Graph accessReviewScheduleDefinition
- 메뉴(Admin Center): ID 거버넌스 > 액세스 검토
- 라이선스(License): Entra ID P2 또는 Entra ID Governance — 기존 P2 GA 기능(그룹·앱·역할 검토)은 P2로 가능하고, 사용자-그룹 소속 권장·활성 사용자를 뺀 비활성 사용자 범위·카탈로그 검토·패키지 정책의 접근 검토 등은 ID Governance 필요 · 검토 대상 사용자와 검토자 사용자 모두 라이선스 대상 · 서비스 주체 검토는 Workload ID Premium 추가

### L3 · 0 · 기능 상태 전이 — 재확인 없음 → 검토 구성 → 결과 적용

#### L4 · ⓪ 비활성 — 권한을 다시 확인하지 않는다

1. [시작] 시간이 지나며 역할·부서·프로젝트가 바뀜
   - 주체: 사용자
   - 데이터: 조직도·프로젝트 변화 (Entra 권한은 그대로) · 부서·관리자 같은 사용자 속성이 바뀌어도 정적 그룹 멤버십과 앱 할당은 자동으로 바뀌지 않음
   - 해설: 조직은 계속 바뀌지만 권한은 자동으로 따라 바뀌지 않습니다
2. [처리] 그룹 멤버와 앱 사용자 목록을 아무도 점검하지 않음
   - 주체: 관리자
   - 위치: 그룹 › 멤버 · 엔터프라이즈 앱 › 사용자 및 그룹
   - 데이터: 멤버십 · 앱 할당 (점검 일정 없음) · 액세스 검토가 없으면 검토 인스턴스·결정 기록(accessReviewInstanceDecisionItem)도 없음
   - 해설: 접근이 정당한지 정기적으로 묻는 절차가 없습니다
3. [처리] 초대한 게스트가 사용하지 않아도 그대로 남음
   - 주체: Entra ID
   - 데이터: 게스트 user 객체 · 마지막 로그인 기록은 있으나 정리 규칙 없음 (Graph: GET /v1.0/users?$select=signInActivity — Entra ID P1/P2 라이선스와 AuditLog.Read.All 권한 필요)
   - 해설: 프로젝트가 끝난 파트너 사용자가 계정을 그대로 유지합니다
4. [끝] 권한 누적 · 감사 시 접근 정당성 증빙 불가
   - 주체: 로그
   - 데이터: 승인·재확인 이력이 비어 있음 · 감사 로그에 Create access review · Approve decision · Apply decision 같은 활동이 없음
   - 해설: 불필요한 접근이 쌓이고 감사 때 근거를 대기 어렵습니다

#### L4 · ① 구성 — 대상 · 검토자 · 주기 · 완료 동작을 정한다

1. [시작] 관리자가 새 액세스 검토를 시작
   - 주체: 관리자
   - 위치: entra.microsoft.com › ID 거버넌스(ID Governance) › 액세스 검토(Access reviews) › 새 액세스 검토(New access review) (최소 Identity Governance Administrator) · 그룹 소유자에게 위임하려면 액세스 검토 › 설정에서 Group owners can create and manage access reviews for groups they own = 예
   - 데이터: 로그인 관리자 역할 · 위임 설정 기본값은 아니오 · Graph 위임 권한 AccessReview.ReadWrite.All
   - 해설: 템플릿 화면에서 "리소스 유형에 대한 접근 검토(Review access to a resource type)"를 고릅니다. 그룹·앱 검토 기능은 Entra ID P2 또는 ID Governance 라이선스가 필요합니다
2. [처리] 검토할 리소스 유형 선택
   - 주체: 관리자
   - 위치: 새 액세스 검토 › 검토할 항목 선택(Select what to review) › Teams + 그룹(Teams + Groups) 또는 애플리케이션(Applications)
   - 데이터: 여러 그룹·앱을 고르면 각각 별도 검토가 만들어짐(그룹 5개 선택 = 검토 5개) · 그룹은 "게스트가 있는 모든 Microsoft 365 그룹"(동적·역할 할당 가능 그룹 제외, 그룹 제외 선택 가능) 또는 선택한 Teams + 그룹 · 중첩 그룹은 평탄화돼 개별 사용자로 보임 · 앱은 사전에 Entra ID에 통합돼 있어야 함
   - 해설: 그룹을 고르면 "게스트가 있는 모든 Microsoft 365 그룹" 옵션도 쓸 수 있습니다. 패키지·Entra 역할·PIM for Groups는 각각 다른 메뉴에서 만듭니다
3. [처리] 검토 범위 지정
   - 주체: 관리자
   - 위치: 범위 › 게스트 사용자만(Guest users only) / 모든 사용자(Everyone) · 그룹 멤버십 검토는 비활성 사용자(테넌트 기준, Inactive users (on tenant level)) + 비활성 일수(Days inactive, 최대 730일)
   - 데이터: 게스트 사용자만 = B2B 게스트만 · 모든 사용자 = 리소스에 연결된 모든 사용자 개체 · 비활성 = 대화형·비대화형 모두 로그인하지 않은 사용자 · 새로 만든 계정은 설정한 비활성 기간(예: 90일)을 채워야 대상이 됨 · 게스트가 있는 모든 M365 그룹을 고르면 게스트 사용자만만 선택 가능
   - 해설: 게스트만, 전체, 또는 오래 로그인하지 않은 사용자만 검토할 수 있습니다. 활성 사용자를 빼고 비활성 사용자만 검토하는 범위는 ID Governance 라이선스 기능입니다
4. [처리] 검토자 선택
   - 주체: 관리자
   - 위치: 검토 탭 › 검토자 선택(Select reviewers) › 그룹 소유자(Group owner(s), 팀·그룹 검토 전용) · 선택한 사용자 또는 그룹 · 사용자가 본인 접근 검토 · 사용자의 관리자
   - 데이터: 관리자·그룹 소유자 선택 시 대체(fallback) 검토자 지정 가능 — 관리자가 없거나 그룹 소유자가 없을 때 검토를 받음 · 그룹 소유자는 검토 시작 시점의 소유자만 검토자(중간 변경은 다음 회차부터 반영)
   - 해설: 관리자나 소유자가 없을 때 검토를 받을 대체 검토자를 둡니다. 초대를 수락하지 않은 게스트 검토자는 검토 메일을 받지 못합니다
5. [처리] 기간과 반복 주기 지정
   - 주체: 관리자
   - 위치: 검토 탭 › 기간(Duration, 일) · 시작 날짜(Start date) · 종료 날짜(End date: 안 함 Never · 특정 날짜 · 횟수)
   - 데이터: accessReviewScheduleDefinition 의 settings.recurrence · instanceDurationInDays (Graph 반복 형식은 weekly · absoluteMonthly 만 지원) · 시작 시각은 시스템 처리로 몇 시간 늦을 수 있음(예: 03:00 UTC 기준 예약이 지연될 수 있음)
   - 해설: 검토가 열려 있는 일수와 반복 주기를 정합니다. 검토는 각 회차 시작 시점의 사용자·리소스·검토자 스냅샷으로 진행되고, 이후 변경은 다음 회차에 반영됩니다
6. [처리] 완료 후 동작 지정
   - 주체: 관리자
   - 위치: 설정 탭 › 완료 시 설정(Upon completion settings) › 리소스에 결과 자동 적용(Auto apply results to resource) · 검토자가 응답하지 않으면(If reviewers don't respond: 변경 없음 · 접근 제거 · 승인 · 권장 사항 적용) · 거부된 게스트 사용자 동작 · 완료 알림 수신자(At end of review, send notification to)
   - 데이터: Graph settings.autoApplyDecisionsEnabled (기본 false) · defaultDecisionEnabled (기본 false) · defaultDecision (Approve · Deny · Recommendation) · 자동 적용 + 접근 제거(또는 권장 사항 적용)를 함께 쓰면 응답이 없을 때 모두 회수될 수 있음 · 미응답 설정은 이미 응답한 대상에는 영향 없음
   - 해설: 응답이 없을 때의 기본 동작이 가장 위험한 설정입니다. 자동 적용을 끄면 마감 후 관리자가 직접 적용해야 합니다
7. [처리] 의사 결정 도우미 켜기
   - 주체: 관리자
   - 위치: 설정 탭 › 검토 결정 도우미 사용(Enable review decision helpers: 30일 내 로그인 없음 No sign-in within 30 days · 사용자-그룹 소속 관계 User-to-Group Affiliation)
   - 데이터: 마지막 로그인 날짜 기반 권장 승인/거부 (대화형·비대화형 로그인 모두 포함, 앱 검토는 앱 로그인 기준) · 사용자-그룹 소속은 관리자 속성과 조직 보고 구조상 거리 기반이라 디렉터리 내 사용자만, 600명 초과 그룹은 미지원, ID Governance 필요 · 30일 내 로그인 없음 권장과 마지막 로그인 날짜는 검토 시작 때 정해져 진행 중 갱신되지 않음 · Graph recommendationsEnabled · recommendationLookBackDuration
   - 해설: 검토자가 판단하기 쉽도록 권장 결정을 보여 줍니다. 소속 거리가 먼 사용자는 그룹 검토에서 거부 권장을 받습니다
8. [처리] 고급 설정
   - 주체: 관리자
   - 위치: 설정 탭 › 고급 설정(Advanced settings: 사유 필수 Justification required · 이메일 알림 Email notifications · 미리 알림 Reminders · 검토자 메일 추가 내용 Additional content for reviewer email)
   - 데이터: 미리 알림은 검토 기간의 중간 시점에 응답 여부와 무관하게 발송 · 이메일 알림은 검토 시작 시 검토자, 종료 시 관리자에게 · Graph justificationRequiredOnApproval · mailNotificationsEnabled · reminderNotificationsEnabled (모두 기본 false)
   - 해설: 검토자에게 가는 메일과 사유 요구를 정합니다. 추가 내용에 안내문이나 연락처를 적으면 초대·미리 알림 메일에 함께 들어갑니다
9. [끝] 이름을 붙이고 만들기
   - 주체: 관리자
   - 위치: 검토 + 만들기 탭 › 이름 · 설명 › 만들기 · API: POST /identityGovernance/accessReviews/definitions · PowerShell: New-MgIdentityGovernanceAccessReviewDefinition
   - 데이터: accessReviewScheduleDefinition · 감사 활동 Create access review (범주 Policy) · 메일 알림이 켜져 있으면 시작 때 검토자에게 발송(지연될 수 있음)
   - 해설: 검토 일정이 등록되고 시작 시점에 검토자에게 알림이 갑니다

#### L4 · ② 활성 — 검토 결과가 접근에 반영된다

1. [시작] 검토 인스턴스 시작 — 검토자에게 알림
   - 주체: Entra ID
   - 데이터: accessReviewInstance (반복 검토면 회차마다 1개, 여러 그룹을 검토하면 그룹마다 1개) · 검토자 이메일 · 시작 때 사용자·리소스·검토자 스냅샷 · 알림 받은 검토자는 contactedReviewers API로 조회
   - 해설: 검토가 시작되면 검토자에게 메일이 갑니다. 메일은 최대 24시간 지연될 수 있어 MSSecurity-noreply@microsoft.com 을 안전한 발신자로 등록해 두고, 초대를 수락하지 않은 게스트 검토자에게는 메일이 가지 않습니다
2. [처리] 검토자가 내 액세스에서 검토 목록을 연다
   - 주체: 사용자
   - 위치: 메일의 검토 시작(Start review) 링크 또는 myaccess.microsoft.com › 왼쪽 메뉴 액세스 검토(Access reviews) / 그룹 및 앱(Groups and Apps)
   - 데이터: 검토 이름(Name) · 마감일(Due) · 리소스(Resource) · 진행률(Progress, 검토한 수/전체) · 본인 접근 검토(self-review)면 화면 구성이 다름
   - 해설: 검토자는 마감일과 진행률을 보고 이름을 눌러 시작합니다. 마감일이 지나면 거부된 사용자는 리소스에서 제거될 수 있습니다
3. [처리] 권장 결정 확인
   - 주체: 사용자
   - 데이터: 마지막 로그인 · 소속 거리 기반 권장 · 30일 이상 로그인하지 않았으면 거부 권장(앱 검토는 앱 사용 기준) · 사용자-그룹 소속은 조직 구조에서 멀수록 거부 권장
   - 해설: 의사 결정 도우미가 켜져 있으면 권장 결정이 함께 표시됩니다. 권장은 참고용이며 검토자가 그대로 수락하거나 직접 결정할 수 있습니다
4. [판단] 검토자가 마감 전에 결정했는가?
   - 주체: 사용자
   - 해설: 응답하지 않은 대상은 완료 시 "미응답 처리" 설정을 따릅니다. 마감일(Due) 전까지는 응답을 바꿀 수 있습니다
   - 예 → 5
   - 아니오 → 6
5. [처리] 승인 · 거부 · 모름 선택
   - 주체: 사용자
   - 위치: 사용자(원 표시) 하나 이상 선택 › 승인(Approve) · 거부(Deny) · 모름(Don't know) › 사유(Reason) › 제출(Submit) · 또는 시스템 권장 수락
   - 데이터: accessReviewInstanceDecisionItem · 모름은 접근 유지 + 감사 기록 · 마감 전에는 변경 가능(거부했던 사용자를 다시 승인 가능) · 감사 활동 Approve decision · Deny decision · Don't know decision (일괄은 Bulk ... decisions)
   - 해설: 사유를 남길 수 있고, 사유는 다른 검토자에게도 보입니다. 관리자가 사유를 필수로 지정하지 않았어도 입력할 수 있습니다
   - 다음 → 7
6. [처리] 미응답 처리 설정 적용
   - 주체: Entra ID
   - 데이터: 변경 없음 · 접근 제거 · 승인 · 권장 사항 적용 중 설정값 (Graph defaultDecision: Approve · Deny · Recommendation, defaultDecisionEnabled 기본 false)
   - 해설: 응답하지 않은 대상만 이 설정을 따릅니다. 자동 적용이 켜져 있고 접근 제거나 권장 사항 적용이면 검토자가 응답하지 않을 때 리소스 접근이 전부 회수될 수 있습니다
7. [판단] 결과 자동 적용이 켜져 있는가?
   - 주체: Entra ID
   - 데이터: autoApplyDecisionsEnabled (자동 적용 옵션, 기본 false)
   - 해설: 켜져 있으면 검토 인스턴스 기간이 끝날 때(검토자 응답 여부와 무관), 또는 관리자가 인스턴스를 수동으로 중지할 때 바로 반영됩니다
   - 예 → 9
   - 아니오 → 8
8. [처리] 관리자가 결과를 수동 적용
   - 주체: 관리자
   - 위치: 액세스 검토 › {검토} › 시리즈(Series) › 검토 기록(Review history) › 해당 회차 선택 › 적용(Apply) · API: POST /identityGovernance/accessReviews/definitions/{id}/instances/{id}/applyDecisions
   - 데이터: 회차 상태 Completed → Applying → Result applied (PIM 역할 검토는 Applied)
   - 해설: 자동 적용이 꺼져 있으면 관리자가 직접 적용해야 접근이 제거됩니다. 거부된 사용자는 몇 분 안에 제거됩니다
9. [처리] 거부된 사용자의 멤버십·앱 할당 제거
   - 주체: Entra ID
   - 데이터: 그룹 멤버십 삭제 · 앱 역할 할당 삭제 (몇 분 소요) · 중첩 그룹은 평탄화돼 보이지만 중첩 그룹 자체에서는 제거되지 않고 직접 멤버십만 제거됨 · 동적 그룹은 결정으로 바뀌지 않고 규칙을 따름
   - 해설: 온프레미스에서 동기화한 그룹·메일 사용 그룹 등은 적용되지 않을 수 있어 결과를 내려받아 원천에서 직접 조정해야 합니다
10. [끝] 결정·적용 감사 + 결과 다운로드
   - 주체: 로그
   - 위치: 액세스 검토 › {검토} › 결과(Results) › 검색(표시 이름·UPN) · 다운로드(Download, UTF-8 CSV) · 감사 로그
   - 데이터: 감사 활동 Create access review · Approve decision · Deny decision · Don't know decision · Apply decision · Access review ended (범주 Policy) · Apply review (범주 UserManagement) · GET /v1.0/identityGovernance/accessReviews/definitions/{id}/instances/{id}/decisions (AccessReview.Read.All, 기본 페이지 100건)
   - 해설: 누가 무엇을 결정했고 언제 적용했는지 이력이 남습니다
- 시나리오: 예 ▸ 예 :: 마감 전 결정, 자동 적용으로 거부자 제거
- 시나리오: 예 ▸ 아니오 :: 마감 전 결정, 관리자가 수동 적용
- 시나리오: 아니오 ▸ 예 :: 미결정은 미응답 설정 적용 뒤 자동 적용
- 시나리오: 아니오 ▸ 아니오 :: 미결정은 미응답 설정 적용 뒤 수동 적용

> 교육 포인트: 액세스 검토는 한 번 정리하는 도구가 아니라 "주기적으로 다시 묻는" 도구입니다. 반복 주기와 미응답 시 동작이 핵심 설정입니다.

### L3 · A · 검토 대상 유형 — 그룹 · 앱 · Entra 역할 · 액세스 패키지

#### L4 · 무엇을 검토하느냐에 따라 만드는 곳이 다르다

1. [시작] 검토할 대상이 무엇인지 정한다
   - 주체: 관리자
   - 위치: 목적에 따라 ID 거버넌스 › 액세스 검토(그룹·앱) 또는 PIM(Entra 역할) 또는 권한 관리(패키지 정책의 수명 주기 탭)
   - 데이터: 검토 대상 리소스와 범위 (사용자 · 그룹 · 서비스 주체) · 필요한 최소 역할: 그룹·앱 Identity Governance Administrator, Entra 역할 Privileged Role Administrator, Azure 리소스 Owner 또는 User Access Administrator, 패키지 Identity Governance Administrator
   - 해설: 대상에 따라 생성 메뉴와 필요한 역할이 달라집니다. 카탈로그 전체를 한 번에 검토하는 카탈로그 액세스 검토(미리 보기)와 PIM for Groups 검토는 별도 흐름입니다
2. [판단] 대상 유형은?
   - 주체: 관리자
   - 해설: 유형별로 선택 가능한 범위와 검토자 유형이 다릅니다. 같은 서비스지만 생성 화면이 네 곳으로 갈립니다
   - 그룹 → 3
   - 앱 → 4
   - Entra 역할 → 5
   - 액세스 패키지 → 6
3. [처리] Teams + 그룹 검토
   - 주체: 관리자
   - 위치: ID 거버넌스 › 액세스 검토 › 새 액세스 검토 › Teams + 그룹 › 게스트가 있는 모든 Microsoft 365 그룹(All Microsoft 365 groups with guest users) 또는 Teams + 그룹 선택(Select Teams + groups)
   - 데이터: 게스트가 있는 모든 Microsoft 365 그룹(동적·역할 지정 그룹 제외, 개별 그룹 제외 선택 가능) 또는 선택한 그룹 · 그룹마다 인스턴스가 따로 생김(instanceEnumerationScope) · 공유 채널의 B2B direct connect 사용자·팀은 단일 단계 검토에만 포함되고 "게스트가 있는 모든 M365 그룹" 옵션에는 포함되지 않음
   - 해설: 게스트 정리는 "게스트가 있는 모든 M365 그룹" 옵션으로 한 번에 만들 수 있습니다
   - 다음 → 7
4. [처리] 애플리케이션 검토
   - 주체: 관리자
   - 위치: 새 액세스 검토 › 애플리케이션(Applications) 선택 · 앱 사전 준비: 앱이 Entra ID에 통합돼 있어야 함
   - 데이터: 앱 할당 사용자 (권장 결정은 앱 마지막 로그인 기준, 최대 30일 look-back) · 앱이 그룹 할당 방식이면 그 그룹의 멤버는 검토 결과로 제거되지 않음
   - 해설: 앱을 여러 개 고르면 앱마다 검토가 따로 만들어집니다
   - 다음 → 7
5. [처리] Microsoft Entra 역할 검토
   - 주체: 관리자
   - 위치: ID 거버넌스 › Privileged Identity Management › Microsoft Entra 역할 › 관리(Manage)의 Microsoft Entra 역할 › 액세스 검토(Access reviews) › 새로 만들기(New) (최소 Privileged Role Administrator)
   - 데이터: 적격·활성 할당 구성원 (사용자 · 그룹 · 서비스 주체) · 사용자 범위(Users and Groups — 직접 할당 사용자와 역할 할당 가능 그룹 포함) 또는 서비스 주체 · 할당 유형 적격만 · 활성만 · 모두 · 빈도 일회성(기본, 1개월 뒤 종료) · 매주 · 매월 · 분기 · 반기 · 연 · 월 검토 기간 최대 27일 · 서비스 주체는 Workload ID Premium 추가 필요
   - 해설: 역할 할당은 PIM의 액세스 검토에서 만들고, 만드는 데 필요한 역할이 따로 있습니다. 역할 할당 가능 그룹은 확장되지 않고 그룹 하나로 표시돼 승인·거부하면 그룹 전체의 역할 할당이 유지·제거됩니다
   - 다음 → 7
6. [처리] 액세스 패키지 할당 검토
   - 주체: 관리자
   - 위치: 권한 관리 › 액세스 패키지 › 정책 › 수명 주기(Lifecycle) 탭 › 액세스 검토 필요(Require access reviews) = 예 · 시작일(Starting on) · 검토 빈도(Annually · Bi-annually · Quarterly · Monthly) · 기간(Duration) · 검토자(Self-review · Specific reviewer(s) · Manager + 폴백)
   - 데이터: 패키지 할당 사용자 (검토는 정책에 포함되어 정의) · 정책마다 독립된 검토 일정 가능 · 패키지 정책의 접근 검토에는 ID Governance 라이선스 필요
   - 해설: 패키지 정책 안에서 주기적 재확인을 함께 정의합니다. 관리자를 검토자로 두면 관리자를 찾지 못할 때를 위한 폴백 검토자를 지정해야 합니다
7. [처리] 검토자 유형 제약 확인
   - 주체: 관리자
   - 위치: 검토 탭 › 검토자 선택
   - 데이터: 본인 검토 · 관리자 검토는 사용자 범위만 · 그룹 소유자는 그룹에만 · PIM 그룹 소유자 검토는 대체 검토자 필수(활성 소유자만 검토자가 되고 적격 소유자는 제외) · PIM 역할 검토의 본인(Members self) 검토는 Users 범위에서만 가능하고 역할 할당 가능 그룹은 제외 · 관리자·그룹 소유자 유형의 대체 검토자는 제거할 수 없음
   - 해설: 선택한 범위에서 쓸 수 없는 검토자 유형이 있습니다
8. [끝] 정의 저장 — Graph로도 생성 가능
   - 주체: 관리자
   - 위치: POST /identityGovernance/accessReviews/definitions · PowerShell New-MgIdentityGovernanceAccessReviewDefinition
   - 데이터: accessReviewScheduleDefinition · 권한 AccessReview.ReadWrite.All(위임 또는 애플리케이션) · 정의 status: Initializing · NotStarted · Starting · InProgress · Completing · Completed · AutoReviewing · AutoReviewed · 인스턴스는 회차 × 리소스마다 1개
   - 해설: 포털 설정은 검토 정의로 저장되고 같은 정의를 API로도 만들 수 있습니다
- 시나리오: 그룹 :: 그룹 대상은 Teams + 그룹 검토로 정의 저장
- 시나리오: 앱 :: 앱 대상은 애플리케이션 검토로 정의 저장
- 시나리오: Entra 역할 :: Entra 역할 대상은 역할 검토로 정의 저장
- 시나리오: 액세스 패키지 :: 액세스 패키지 대상은 할당 검토로 정의 저장

> 교육 포인트: 같은 "액세스 검토"라도 역할은 PIM, 패키지는 권한 관리에서도 접근합니다. 메뉴는 달라도 서비스는 같습니다.

### L3 · B · 검토 진행 · 결과 적용 — 관리자 쪽 운영

#### L4 · 진행 확인에서 적용·한계까지

1. [시작] 관리자가 검토 현황을 연다
   - 주체: 관리자
   - 위치: ID 거버넌스 › 액세스 검토 › {검토} › 개요(Overview) (현재 Current · 시리즈 Series)
   - 데이터: 진행 중 인스턴스 진행률 · 이전 회차 정보 · 활성 인스턴스가 없으면 직전 인스턴스 정보가 보임 · 다단계 검토 상태는 시리즈의 View status of multi-stage review(미리 보기)
   - 해설: 현재 인스턴스가 열려 있는 동안만 현재 항목을 볼 수 있습니다. 검토가 끝나기 전에는 디렉터리의 접근이 바뀌지 않습니다
2. [처리] 결과를 조회하거나 내려받는다
   - 주체: 관리자
   - 위치: 결과(Results) 페이지 › 검색(표시 이름·UPN) · 다운로드(Download, UTF-8 CSV) · 반복 검토의 지난 회차는 검토 기록(Review history)에서 회차 선택
   - 데이터: GET /v1.0/identityGovernance/accessReviews/definitions/{id}/instances/{id}/decisions (다단계는 stage의 decisions API) · 권한 AccessReview.Read.All 또는 ReadWrite.All · 기본 페이지 100건 · PowerShell Get-MgIdentityGovernanceAccessReviewDefinitionInstanceDecision
   - 해설: 사용자별 결정과 사유를 확인하고 CSV로 내려받습니다. 읽기는 Global Reader · Security Reader · User Administrator · Identity Governance Administrator · Security Administrator(그룹·앱), Entra 역할 검토는 Security Reader · Identity Governance Administrator · Privileged Role Administrator · Security Administrator가 할 수 있습니다
3. [판단] 마감 전에 검토를 끝낼 것인가?
   - 주체: 관리자
   - 해설: 중지하면 검토자가 더 응답할 수 없고 다시 시작할 수 없습니다
   - 예 → 4
   - 아니오 → 5
4. [처리] 해당 회차를 중지(Stop)
   - 주체: 관리자
   - 위치: 결과 › 중지(Stop) (회차 단위 · 반복 시리즈는 시리즈 설정에서 종료 날짜 편집) · 다단계 검토는 결과 › 현재 단계 중지(Stop current stage)로 다음 단계를 바로 시작 · 결과 페이지에는 초기화(Reset) · 삭제(Delete)도 있음
   - 데이터: 중지 시 자동 적용이 켜져 있으면 그 시점에 적용 · 중지한 회차는 재시작 불가
   - 해설: 반복 검토 전체를 멈추려면 시리즈의 종료 날짜를 고칩니다
5. [처리] 현재 회차와 시리즈 설정을 구분해 수정
   - 주체: 관리자
   - 위치: 액세스 검토 › {검토} › 설정 › 현재 / 시리즈
   - 데이터: 현재 변경은 이번 회차만, 시리즈 변경은 이후 모든 회차에 적용 · 주 검토자는 제거할 수 있지만 대체 검토자는 제거할 수 없음 · 대체 검토자는 검토자 유형이 관리자·그룹 소유자일 때만 추가 가능
   - 해설: 검토자 추가·미리 알림 켜기 같은 변경 범위를 구분해야 합니다. 미리 알림을 켜면 기간 중간에 응답 여부와 무관하게 알림이 갑니다
6. [판단] 자동 적용이 꺼져 있어 수동 적용이 필요한가?
   - 주체: 관리자
   - 위치: 시리즈 › 검토 기록(Review history) › 회차 선택
   - 해설: 자동 적용이 꺼져 있으면(기본값) 마감 뒤 적용을 눌러야 합니다
   - 예 → 7
   - 아니오 → 8
7. [처리] 적용(Apply) 선택
   - 주체: 관리자
   - 위치: 검토 기록 › 회차 › 적용(Apply) · API: POST .../instances/{id}/applyDecisions
   - 데이터: 상태 Completed → Applying → Result applied
   - 해설: 거부된 사용자의 멤버십이나 앱 할당이 몇 분 안에 제거됩니다
   - 다음 → 8
8. [처리] 적용되지 않는 경우를 점검
   - 주체: Entra ID
   - 데이터: 온프레미스 AD 동기화 그룹 · 메일 사용 그룹 · 중첩 그룹 경유 멤버십 · 그룹 할당된 앱 · 동적 그룹은 결과 적용이 사용자를 못 지움 · 사용자를 찾지 못하는 등 기타 오류도 적용 불가가 될 수 있음 · Azure 리소스 역할에 보안 그룹으로 할당된 사용자는 거부해도 그룹에서 제거되지 않아 관리자가 직접 반영
   - 해설: 이런 경우는 결과를 내려받아 원천에서 직접 조정해야 합니다. 온프레미스 그룹은 다운로드한 결과를 온프레미스 디렉터리의 그룹에 반영합니다
9. [끝] 최종 상태와 감사 확인
   - 주체: 로그
   - 데이터: 감사 활동 Apply decision (범주 Policy) · Apply review (UserManagement) · 회차 상태 Result applied
   - 해설: 적용 결과가 상태와 감사 로그로 확인됩니다
- 시나리오: 예 ▸ 예 :: 회차를 중지하고 수동 적용까지 진행
- 시나리오: 예 ▸ 아니오 :: 회차를 중지하고 자동 적용으로 상태 점검
- 시나리오: 아니오 ▸ 예 :: 중지 없이 끝까지 두고 수동 적용
- 시나리오: 아니오 ▸ 아니오 :: 중지 없이 끝까지 두고 자동 적용 점검

> 교육 포인트: "검토 완료 = 접근 제거"가 아닙니다. 자동 적용 여부와 적용 불가 사례를 함께 확인해야 합니다.
>
> 출처: https://learn.microsoft.com/entra/id-governance/complete-access-review

### L3 · C · 다단계 · 게스트 검토 — 단계 전달과 거부된 게스트 처리

#### L4 · 다단계 검토와 게스트 정리 옵션

1. [시작] 게스트 접근을 정리하려 한다
   - 주체: 관리자
   - 위치: ID 거버넌스 › 액세스 검토 › 새 액세스 검토 › Teams + 그룹 (최소 Identity Governance Administrator, 공유 채널 팀 검토는 User Administrator도 가능)
   - 데이터: 게스트 사용자 (B2B direct connect 사용자와 공유 채널 접근 팀은 팀(Teams 사용 M365 그룹) 검토에서 별도 포함 — 단일 단계 검토에만 포함되고 다단계에서는 제외, 모든 M365 그룹 옵션에서도 제외)
   - 해설: 파트너나 외부 협업자의 불필요한 접근을 줄이는 대표 사례입니다. 본인·관리자 검토자 유형이면 B2B direct connect 사용자는 스스로 검토할 수 없고 팀 소유자가 대신 검토합니다
2. [처리] 범위를 게스트로 한정
   - 주체: 관리자
   - 위치: 범위 › 게스트 사용자만(Guest users only, 게스트가 있는 모든 M365 그룹 선택 시 이 옵션만 가능) · 공유 채널 팀 검토는 모든 사용자 선택 시 내부 사용자 · B2B 협업 사용자 · B2B direct connect 사용자 · 공유 채널 접근 팀을 모두 포함
   - 데이터: 사용자 범위 필터 (게스트 사용자만 = Microsoft Entra B2B 게스트)
   - 해설: 내부 직원은 검토 대상에서 제외합니다
3. [처리] 다단계 검토 켜기
   - 주체: 관리자
   - 위치: 검토 탭 › 다단계 검토(Multi-stage review) 확인란 (기본 2단계 · + 단계 추가(Add a stage)로 최대 3단계)
   - 데이터: Graph stageSettings (최대 3개, dependsOn으로 순서 지정, durationInDays) · stage별 reviewers · 단계 기간(일) · 단계는 순차적이며 이전 단계 결정이 기록된 뒤 다음 단계가 열림
   - 해설: 예를 들어 1단계는 그룹 소유자, 2단계는 보안 담당이 이어서 확인합니다. 단일 단계에서는 마지막 검토자의 결정이 적용되지만 다단계는 단계별 독립 판단입니다
4. [처리] 단계별 검토자와 기간 지정
   - 주체: 관리자
   - 위치: 첫 번째 단계 검토 · 두 번째 단계 검토 › 검토자 선택 · 대체 검토자(그룹 소유자·관리자 선택 시) · 단계 기간(Stage duration, 일)
   - 데이터: 반복 한 회차의 기간 = 단계 기간의 합 · 반복 주기는 이 합보다 길거나 같아야 함 · 단계마다 대체 검토자 지정 가능
   - 해설: 주간 반복이면 단계 기간의 합이 최대 7일이어야 합니다
5. [처리] 다음 단계로 넘길 대상 지정
   - 주체: 관리자
   - 위치: 다음 단계로 이동할 검토 대상 지정(Specify reviewees to go to next stage)
   - 데이터: 승인됨(Approved) · 거부됨(Denied) · 검토 안 됨(Not reviewed) · 모름(Don't know) · 모두(All) 중 하나 이상
   - 해설: 예를 들어 1단계에서 "모름"과 "검토 안 됨"만 2단계로 보낼 수 있습니다. 결정이 났어도 단계 기간이 남았으면 결과 페이지의 현재 단계 중지로 다음 단계를 앞당길 수 있습니다
6. [처리] 이전 단계 결정 공개 여부
   - 주체: 관리자
   - 위치: 결과 공개(Reveal review results) › 이전 단계 결정을 다음 단계 검토자에게 표시(Show previous stage(s) decisions to later stage reviewers)
   - 데이터: 확인란 (기본은 비공개) · Graph settings.decisionHistoriesForReviewersEnabled (기본 false)
   - 해설: 이전 판단이 영향을 주지 않게 하려면 공개를 끕니다
7. [판단] 거부된 게스트를 어떻게 처리할 것인가?
   - 주체: 관리자
   - 위치: 설정 탭 › 거부된 게스트 사용자에 적용할 동작(Action to apply on denied guest users) (게스트만 범위일 때 표시 · 게스트가 있는 모든 M365 그룹 검토에서는 선택 불가로 기본값 적용 · PIM 역할 검토에서는 편집 불가, 항상 접근 제거)
   - 데이터: Graph settings.applyActions — removeAccessApplyAction(기본) · disableAndDeleteUserApplyAction(차단 후 삭제일 때만 지정)
   - 해설: 리소스에서만 제거하거나, 로그인을 막고 시간이 지나 삭제할 수 있습니다
   - 리소스에서만 제거 → 8
   - 로그인 차단 후 삭제 → 9
8. [끝] 검토 대상 리소스에서만 멤버십 제거
   - 주체: Entra ID
   - 데이터: 기본값 · 게스트는 테넌트에 로그인할 수 있고 다른 접근은 유지 · 거부된 B2B direct connect 사용자·팀은 해당 팀의 모든 공유 채널 접근을 잃음
   - 해설: 이 리소스 접근만 사라지고 다른 리소스 접근은 영향이 없습니다
9. [끝] 로그인 차단 → 30일 뒤 테넌트에서 삭제
   - 주체: Entra ID
   - 데이터: 테넌트 전체 로그인 차단(다른 리소스 접근 여부와 무관) · 30일 안에 관리자가 복구 가능 · 30일 후 삭제 · Global Administrator는 최근 삭제 사용자를 앞당겨 영구 삭제할 수 있음 · 삭제된 게스트 데이터는 진행 중 검토에서 사라지고 감사 로그에는 남음
   - 해설: 잘못 거부했다면 30일 안에 접근을 복구할 수 있습니다
- 시나리오: 리소스에서만 제거 :: 거부된 게스트를 리소스에서만 제거
- 시나리오: 로그인 차단 후 삭제 :: 거부된 게스트를 로그인 차단 후 30일 뒤 삭제

> 교육 포인트: 게스트 검토의 핵심 결정은 "이 리소스에서만 빼느냐, 테넌트에서 정리하느냐"입니다.
>
> 주의: 검토자로 지정한 게스트가 초대를 수락하지 않았다면 검토 메일을 받지 못합니다.
