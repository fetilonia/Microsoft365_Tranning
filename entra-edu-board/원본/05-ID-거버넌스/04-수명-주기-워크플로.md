## L2 · 수명 주기 워크플로 — 입사 · 이동 · 퇴사 자동화

- 설정(Control Plane): 워크플로 템플릿 · 범위 규칙 | 트리거 (예: employeeHireDate 기준 오프셋) · 태스크
- 강제(Enforcement): Entra 수명 주기 워크플로 서비스 | 예약 또는 온디맨드 실행으로 태스크 자동 수행
- 증적(Evidence): 워크플로 실행·사용자·태스크 기록 | 감사 로그 TaskManagement · WorkflowManagement
- 메뉴(Admin Center): ID 거버넌스 > 수명 주기 워크플로
- 라이선스(License): Entra ID Governance 또는 Entra Suite

### L3 · 0 · 기능 상태 전이 — 수동 절차 → 템플릿·범위·트리거 구성 → 이벤트 시점 자동 실행

#### L4 · ⓪ 비활성 — 입·퇴사 절차를 사람이 처리한다

1. [시작] 입사·이동·퇴사가 HR에서 확정됨
   - 주체: 외부
   - 위치: HR 시스템 (Workday · SuccessFactors 등)
   - 데이터: 입사일 (Workday StatusHireDate · SuccessFactors startDate) · 퇴사일 (Workday StatusTerminationDate · SuccessFactors endDate) · 부서·직무 변경
   - 해설: HR 이벤트가 발생하지만 IT 절차는 자동으로 이어지지 않습니다. HR 기반 프로비저닝은 계정 생성과 속성 갱신까지만 맡고, 그 뒤의 후속 작업(임시 액세스 패스 발급 · 그룹 정리 등)은 수명 주기 워크플로가 담당하므로 워크플로가 없으면 사람이 처리합니다
2. [처리] 담당자에게 체크리스트가 전달됨
   - 주체: 관리자
   - 위치: 메일 · 티켓 · 엑셀 체크리스트
   - 데이터: 일정 · 대상자 · 처리 항목이 사람 손에 의존
   - 해설: 누가 언제 무엇을 할지 사람이 추적합니다
3. [처리] 계정·그룹·라이선스를 시스템마다 수동 처리
   - 주체: 관리자
   - 위치: Entra 관리 센터 사용자 · 그룹 · 라이선스 화면 · Teams 관리 화면
   - 데이터: 시스템별로 따로 바뀌는 상태 (계정 활성 여부 · 그룹 멤버십 · 할당 라이선스 · Teams 소속)
   - 해설: 같은 사람에 대해 여러 곳을 일일이 바꿉니다. 한 곳이라도 빠지면 계정 상태와 접근 권한이 서로 어긋납니다
4. [처리] 입사 첫날 접근 지연 또는 퇴사일 처리 누락
   - 주체: 사용자
   - 데이터: 비활성 상태로 남은 신규 계정 · 퇴사 후 활성인 계정
   - 해설: 사람이 놓치면 첫날 업무가 막히거나 퇴사자 계정이 남습니다
5. [끝] 퇴사자 계정 잔존 — 보안 공백
   - 주체: 로그
   - 데이터: 퇴사일 이후에도 로그인 가능한 계정 · 그룹 멤버십 잔존 (사용자 accountEnabled=true 유지)
   - 해설: 처리가 늦은 시간만큼 보안 공백이 생깁니다. 로그인 로그에 퇴사일 이후의 성공 로그인이 남는지로 공백 규모를 확인할 수 있습니다

#### L4 · ① 구성 — 템플릿 · 범위 · 트리거 · 태스크를 정한다

1. [시작] 관리자가 수명 주기 워크플로를 연다
   - 주체: 관리자
   - 위치: entra.microsoft.com › ID Governance(ID 거버넌스) › Lifecycle workflows(수명 주기 워크플로) › Workflows (최소 Lifecycle Workflows Administrator)
   - 데이터: 로그인 관리자 역할 · 라이선스 Entra ID Governance 또는 Entra Suite · 한도: 테넌트당 워크플로 100개 · 워크플로당 태스크 25개 · 워크플로당 관리 범위(administrative scope) 5개
   - 해설: 워크플로 관리는 Lifecycle Workflows Administrator 이상으로 합니다. Graph로 위임 호출할 때도 같은 최소 역할이 필요하고, 필요한 Graph 권한은 Lifecycle workflows permissions 문서를 따릅니다
2. [처리] 트리거 속성이 채워지는지 선행 확인
   - 주체: 관리자
   - 위치: HR 인바운드 프로비저닝 · Microsoft Entra Cloud Sync · Microsoft Entra Connect (Entra Connect Sync) — 세 방식 모두 두 속성 동기화를 지원
   - 데이터: user.employeeHireDate · user.employeeLeaveDateTime (DateTimeOffset, Graph 입력 형식 YYYY-MM-DDThh:mm:ssZ). 온프레미스 AD에는 대응 속성이 없어 문자열 속성을 골라 yyyyMMddHHmmss.fZ 형식으로 변환해 매핑 (예: Workday FormatDateTime([StatusHireDate], ,"yyyy-MM-ddzzz", "yyyyMMddHHmmss.fZ") · Cloud Sync 직접 매핑 msDS-cloudExtensionAttribute1 → employeeHireDate)
   - 해설: 날짜 속성이 비어 있으면 예약 실행이 일어나지 않습니다. 시간 부분도 맞춰야 해서 입사일은 하루 시작(예: 오전 1시·5시), 퇴사일은 하루 끝(예: 오후 9시·11시)으로 넣고, 워크플로는 속성 시각보다 일찍 실행되지 않지만 평가 주기(기본 3시간) 때문에 늦어질 수 있습니다. 클라우드 전용 사용자의 employeeLeaveDateTime을 수동으로 넣으려면 별도 권한이 필요합니다
3. [처리] 템플릿으로 워크플로 만들기 시작
   - 주체: 관리자
   - 위치: 수명 주기 워크플로 › 워크플로 만들기(Create workflow) › 워크플로 선택(Choose a workflow) — 템플릿 선택 또는 "Clone an existing workflow" 카드 › Browse workflows (복제는 관리 센터에서만 가능)
   - 데이터: 내장 템플릿 16개 (범주 Joiner · Mover · Leaver, 신원 확인 템플릿 2개는 미리 보기) · 예: Onboard pre-hire employee
   - 해설: 포털에서는 템플릿이나 기존 워크플로 복제로 시작하고, 템플릿 없이 처음부터 만들려면 Microsoft Graph를 씁니다. 복제를 고르면 검토 + 만들기 탭으로 바로 이동하며, 다른 탭을 눌러 값을 고친 뒤 만들 수도 있습니다
4. [처리] 기본 사항 입력
   - 주체: 관리자
   - 위치: 기본 사항(Basics) 탭 › 고유한 표시 이름 · 설명 · 관리 범위(administrative scope)
   - 데이터: workflow.displayName · description · 관리 범위는 워크플로당 최대 5개 (신원 확인 템플릿은 이 탭에서 트리거 유형도 선택)
   - 해설: 이름과 설명, 위임 범위를 정합니다. 신원 확인 템플릿(미리 보기)은 purpose가 all 또는 onboarding인 ID 확인 프로필을 별도 탭에서 골라야 합니다
5. [처리] 트리거 지정
   - 주체: 관리자
   - 위치: 범위 구성(Configure scope) 탭 › 트리거 유형 (시간 기반 특성 · 특성 변경 · 그룹 멤버십 변경 · 로그인 비활동 — 템플릿에 따라 선택 가능 범위가 다르고, 온디맨드 전용 템플릿은 On-demand only)
   - 데이터: 시간 기반이면 연산자(Equal to · Between · Within) · 이벤트 기준 일수(Days from event, Between은 Days to event도 입력) · 이벤트 시점(Before · After · On) · 이벤트 사용자 특성 (employeeHireDate · employeeLeaveDateTime · createdDateTime 및 DateTime 형식 디렉터리 확장 특성). 날짜는 UTC 기준으로 비교하며 일치하는 날은 00:00 UTC에 시작. 예: 입사 7일 전 = Equal to · 7 · Before (규칙 구문 employeeHireDate eq (system.now plus P7D), 템플릿 문서 표에는 -7로 표기). [확인 필요: 허용 일수 — 실행 조건 문서는 0~365일, 서비스 한도 문서는 offsetInDays -180~180일로 서로 다름]
   - 해설: 날짜 속성에서 얼마나 떨어진 시점인지 정합니다. 여러 시간대에 걸친 조직은 UTC 하루의 시작이 사용자 현지 시각으로 전날일 수 있음에 유의하세요. 특성 변경 트리거는 트리거 특성·연산자·값, 그룹 멤버십 변경은 Added to group / Removed from group, 로그인 비활동은 비활동 일수(Days of inactivity)를 입력합니다
6. [처리] 범위 규칙 지정
   - 주체: 관리자
   - 위치: 범위 구성 탭 › 규칙(Rule) › 속성 · 연산자 · 값 (예: department eq Sales) · 규칙 구문 보기(View rule syntax)에서 Graph 필터 구문 확인·여러 규칙 붙여넣기. 그룹 멤버십 트리거는 범위 유형이 그룹 기반(Group based)이라 대상 그룹을 선택
   - 데이터: executionConditions.scope (ruleBasedSubjectSet) — 지원 사용자 속성 한정. 규칙 평가는 대소문자를 구분합니다
   - 해설: 트리거 조건을 만족하는 사용자 중 누구에게 적용할지 좁힙니다. 값을 대소문자까지 정확히 맞추지 않으면 대상에서 빠집니다
7. [처리] 태스크 검토·추가
   - 주체: 관리자
   - 위치: 태스크 검토(Review tasks) 탭 › 태스크 추가(Add task) · 사용(Enable) · 사용 안 함(Disable) · 제거(Remove) (예: Generate TAP And Send Email)
   - 데이터: workflow.tasks (taskDefinitionId · arguments · continueOnError · isEnabled) · 워크플로당 최대 25개 · 사용자 지정 태스크 확장도 추가 가능 (테넌트당 100개). 만든 뒤 태스크나 범위를 바꾸면 새 워크플로 버전이 생겨 로그에 별도로 보고됩니다
   - 해설: 템플릿이 주는 기본 태스크를 조정하고 순서를 정합니다. 이메일 태스크 본문에는 {{user.displayName}} 같은 변수를 넣을 수 있습니다
8. [처리] 검토 + 만들기 — 예약은 비워 둠
   - 주체: 관리자
   - 위치: 검토 및 만들기(Review and create) 탭 › 예약 사용 확인란 비움 › 만들기
   - 데이터: 포털 생성 기준 isEnabled=true · isSchedulingEnabled=false (API로 만들 때는 두 값을 명시적으로 지정 — 포털 기본값을 가정하지 않음)
   - 해설: 새 워크플로는 켜진 상태이지만 예약은 꺼져 있어 온디맨드로 먼저 시험할 수 있습니다. 신원 확인 태스크 3개(미리 보기)는 Graph /beta에서만 만들 수 있습니다
9. [끝] 시험 후 예약 사용으로 전환
   - 주체: 관리자
   - 위치: 워크플로 › 속성(Properties) 페이지 › Enable Schedule 확인란 · 평가 주기는 수명 주기 워크플로 › 워크플로 설정(Workflow settings)
   - 데이터: isSchedulingEnabled=true · 평가 주기 기본 3시간 (설정 범위 1~24시간, 테넌트 전체 공통). 선택 사항: Workflow settings 또는 워크플로 Settings › Enable execution threshold — 사용자 비율·고정 인원 한도 (둘 다 지정하면 OR)
   - 해설: 예약을 켜면 조건에 맞는 사용자를 정해진 주기마다 처리합니다. 예약 실행 중 한도를 넘으면 워크플로가 격리(quarantine)되고 Lifecycle Workflows 관리자에게 메일이 가며, 관리자가 Approve execution 하기 전에는 다시 실행되지 않습니다 (온디맨드 실행은 한도 대상 아님)

#### L4 · ② 활성 — 트리거 시점에 태스크가 실행된다

1. [시작] 예약 평가 주기가 돌아옴
   - 주체: Entra ID
   - 데이터: 평가 주기 (기본 3시간, 1~24시간 설정) · 워크플로 사용 설정과 예약이 모두 켜진 워크플로만 평가
   - 해설: 서비스가 예약된 워크플로를 주기마다 평가합니다. 워크플로 목록의 Scheduled 열로 예약 여부를 확인합니다
2. [처리] 트리거 조건 평가
   - 주체: Entra ID
   - 데이터: 사용자의 employeeHireDate 와 오프셋 비교 (같음 · 사이 · 이내) — UTC 날짜 기준, 일치하는 날 00:00 UTC부터 첫 평가에서 대상이 됨. 새 시간 기반 워크플로의 Equal to는 일치하는 UTC 날짜에만 해당하며 3일 보정 창(catch-up)이 없고, 기존 워크플로는 보정 동작을 유지
   - 해설: 기준 날짜가 조건에 해당하는 사용자를 찾습니다. 속성 값이 그 날이 지난 뒤에 채워지면 놓친 오프셋은 처리되지 않으므로 지연이 예상되면 Between 또는 Within으로 기간을 줍니다
3. [판단] 범위 규칙에 맞는 사용자인가?
   - 주체: Entra ID
   - 데이터: 규칙 예: department eq 'Sales' (대소문자 구분)
   - 해설: 조건에 맞지만 범위 밖인 사용자는 처리하지 않습니다. 워크플로 개요의 실행 사용자 범위(execution user scope)에서 다음 실행 때 처리될 사용자 목록을 미리 볼 수 있고, 이 목록은 마지막 평가 기준이라 조건을 막 바꿨다면 최신이 아닐 수 있습니다
   - 예 → 4
   - 아니오 → [차단] 제외 — 범위 밖 사용자는 건너뜀
4. [처리] 사용자 처리 작업 생성
   - 주체: Entra ID
   - 데이터: 사용자 처리 결과 (상태 Queued → In Progress) · 처리 시작 직전에 실행 조건을 다시 평가해 그 사이 속성이 바뀌어 조건을 벗어난 사용자는 Canceled 처리
   - 해설: 대상 사용자마다 실행 작업이 만들어집니다. 워크플로가 삭제·비활성화되거나 예약이 꺼지면 대기 중이던 사용자도 취소됩니다
5. [처리] 태스크를 순서대로 실행
   - 주체: Entra ID
   - 데이터: 예: 계정 활성화 · 그룹 추가 · 환영 메일 (퇴사 템플릿은 계정 비활성화 · 그룹·Teams 제거). 계정 활성화·비활성화·삭제 태스크는 Entra 역할이 할당된 사용자와 역할 할당 가능 그룹의 구성원·소유자를 지원하지 않으며, 동기화된 온프레미스 사용자에는 enableOnPremisesAccount·disableOnPremisesAccount·deleteOnPremisesAccount 인수를 따로 지정
   - 해설: 정의된 태스크를 순서대로 수행합니다. 태스크별 continueOnError 설정이 실패 시 다음 태스크로 넘어갈지를 정합니다
6. [판단] 태스크가 성공했는가?
   - 주체: Entra ID
   - 데이터: 태스크 처리 결과 Completed · Failed — continueOnError=false 태스크가 실패하면 사용자 상태 Failed, continueOnError=true 태스크만 실패하면 Completed with errors
   - 해설: 실패한 태스크는 기록에 남아 확인이 필요합니다
   - 예 → 7
   - 아니오 → [차단] 실패 — Failed 또는 Completed with errors 표시
7. [처리] 실행 이력 기록
   - 주체: 로그
   - 위치: 수명 주기 워크플로 › 워크플로 › {워크플로} › 워크플로 기록(Workflow history) (사용자 · 실행 · 태스크) · CSV 다운로드 가능
   - 데이터: 사용자 요약(전체·성공·실패) · 태스크 요약 · 상태 Completed · In Progress · Queued · Canceled · Completed with errors · Failed · 필터 날짜(24시간~30일) · 상태 · 실행 유형(Scheduled/on-demand)
   - 해설: 사용자별·실행별·태스크별로 결과를 볼 수 있습니다. 개요의 My Feed에서도 다음 예약 실행·처리 사용자·실패 태스크 수를 요약해 보여줍니다
8. [끝] 감사 로그에도 남음
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 감사 로그 (서비스 Lifecycle Workflows · 범주 TaskManagement · WorkflowManagement · 사용자 지정 태스크는 Other)
   - 데이터: 활동별 상태 · 상태 사유 · 대상(개체 ID) · 시작한 주체 (최대 30일, 날짜 필터 24시간~30일, 테넌트 현지 시각 또는 UTC 선택)
   - 해설: 워크플로가 한 일은 감사 로그에서도 추적됩니다
- 시나리오: 예 ▸ 예 :: 범위에 맞고 태스크가 성공해 이력과 감사 로그 기록
- 시나리오: 예 ▸ 아니오 :: 범위에 맞지만 태스크가 실패해 실패로 끝남
- 시나리오: 아니오 :: 범위 규칙에 맞지 않는 사용자라 제외

> 교육 포인트: 워크플로는 "HR 이벤트 → Entra 계정 처리"를 자동화합니다. HR 기반 프로비저닝이 계정을 만들고 속성을 맞추면, 워크플로가 그 위에서 TAP 발급·그룹 추가·계정 비활성화 같은 후속 작업을 합니다.
>
> 주의: 날짜 속성이 없거나 늦게 채워지면 예약 실행이 어긋납니다. 새 워크플로의 시간 기반 트리거는 3일 보정 창이 없을 수 있으므로 사이/이내 범위를 설정해 지연을 흡수합니다.

### L3 · A · 워크플로 구성 요소 — 트리거 유형 · 범위 · 태스크

#### L4 · 워크플로를 이루는 세 부분과 트리거 선택

1. [시작] 워크플로 = 일반 정보 + 태스크 + 실행 조건
   - 주체: 관리자
   - 위치: 수명 주기 워크플로 › 워크플로 › {워크플로} (개요: Basic Information · My Feed · Quick Action)
   - 데이터: displayName · tasks · executionConditions (trigger · scope)
   - 해설: 실행 조건은 누구에게(범위) 언제(트리거) 돌릴지를 정합니다. 개요의 Quick Action에서 온디맨드 실행 · 태스크 편집 · 기록 보기를 바로 할 수 있습니다
2. [처리] 템플릿은 범주별로 태스크를 안내
   - 주체: 관리자
   - 위치: 워크플로 만들기 › 워크플로 선택
   - 데이터: 내장 16개 — Onboard pre-hire · Onboard new hire · Post-onboarding · Real-time change · Real-time termination · Pre-offboarding · Offboard · Post-offboarding · Employee group membership changes · Employee job profile change · Pre-Offboard inactive users · Offboard inactive users · Transition agent sponsorships (when a sponsor leaves / changes roles, Microsoft Agent 365 라이선스 테넌트) · 신원 확인 템플릿 2개(미리 보기)
   - 해설: 템플릿이 기본 트리거와 사용할 수 있는 태스크를 정해 줍니다. 템플릿 범주(Joiner·Mover·Leaver)는 바꿀 수 없고, 온디맨드 전용 템플릿(Real-time 계열)은 실행 조건이 없습니다
3. [판단] 어떤 트리거 유형을 쓸 것인가?
   - 주체: 관리자
   - 해설: 이벤트 성격에 맞는 트리거를 골라야 합니다. 템플릿에 따라 쓸 수 있는 트리거가 제한되며, 트리거마다 범위 유형(규칙 기반 · 그룹 기반)이 정해집니다
   - 시간 기반 특성 → 4
   - 특성 변경 → 5
   - 그룹 멤버십 → 6
   - 로그인 비활동 → 7
4. [처리] 시간 기반 특성(Time based attribute)
   - 주체: Entra ID
   - 위치: 범위 구성 › 이벤트 사용자 특성 · 이벤트 기준 일수 · 이벤트 시점
   - 데이터: 같음 · 사이 · 이내 비교 (employeeHireDate · employeeLeaveDateTime · createdDateTime 등) · 예: Within · 7 · After → employeeHireDate ge (system.now minus P7D) and employeeHireDate le system.now. 범위 유형은 규칙 기반
   - 해설: 날짜 속성 기준으로 며칠 전·당일·이후에 실행합니다. 날짜(UTC)만 비교하며 시각은 평가 주기에 따라 결정됩니다. 이 트리거는 워크플로와 예약이 모두 켜져 있어야 평가됩니다
   - 다음 → 8
5. [처리] 특성 변경(Attribute changes)
   - 주체: Entra ID
   - 위치: 범위 구성 › 트리거 특성 · 연산자 · 값
   - 데이터: 지정한 속성 값이 바뀐 사용자 (규칙 기반, 규칙 평가는 대소문자 구분) · 사용자 지정 특성 트리거는 미리 보기
   - 해설: 예를 들어 부서나 직무 속성이 바뀌면 이동 워크플로가 실행됩니다
   - 다음 → 8
6. [처리] 그룹 멤버십 변경
   - 주체: Entra ID
   - 위치: 범위 구성 › 그룹에 추가됨(Added to group) / 그룹에서 제거됨(Removed from group)
   - 데이터: 그룹 기반 범위 (선택한 그룹 하나를 기준으로 판단)
   - 해설: 사용자가 특정 그룹에 들어오거나 나가는 순간에 실행합니다. 평가 주기마다 변경분을 확인하므로 즉시 실행은 아닙니다
   - 다음 → 8
7. [처리] 로그인 비활동(Sign-in inactivity)
   - 주체: Entra ID
   - 위치: 범위 구성 › 비활동 일수(Days of inactivity)
   - 데이터: 지정 기간 동안 로그인 없는 사용자 (규칙 기반) · 템플릿 기본값: Pre-Offboard inactive users 90일, Offboard inactive users 120일 (이벤트 특성 lastSuccessfulSignInDateTime)
   - 해설: 오래 쓰지 않는 계정을 정리하는 용도로 씁니다. 두 템플릿 모두 기본 태스크는 계정 비활성화와 비활동 알림 메일입니다
8. [처리] 범위 규칙 지정
   - 주체: 관리자
   - 위치: 범위 구성 › 규칙 › 속성 · 연산자 · 값 · 규칙 구문 보기
   - 데이터: Graph ruleBasedSubjectSet 의 지원 사용자 속성 · 그룹 멤버십 트리거는 규칙 대신 그룹 선택
   - 해설: 트리거에 맞는 사용자 중 적용 대상을 속성 조건으로 좁힙니다. 대소문자가 다르면 일치하지 않습니다
9. [처리] 태스크 구성
   - 주체: 관리자
   - 위치: 태스크 검토 › 태스크 추가 · 사용 · 사용 안 함 · 제거 · 사용자 지정 태스크 확장
   - 데이터: Add User To Group · Enable User Account · Send Welcome Email · Disable User Account · Remove user from all groups · Remove user from all Teams · Delete User Account · Generate TAP And Send Email · 워크플로당 최대 25개 · 사용자 지정 태스크 확장은 테넌트당 100개
   - 해설: 입사·퇴사별 기본 태스크를 조합하고, 필요하면 사용자 지정 태스크로 확장합니다. 어떤 태스크를 쓸 수 있는지는 템플릿 범주가 정합니다
10. [끝] 예약 사용과 평가 주기
   - 주체: 관리자
   - 위치: 워크플로 › 속성(Properties) › Enable Schedule 확인란 · 평가 주기는 수명 주기 워크플로 › Workflow settings
   - 데이터: isSchedulingEnabled · 평가 주기 기본 3시간 (1~24시간)
   - 해설: 예약을 켜야 트리거 평가가 시작됩니다. Real-time 입사·이동·퇴사 계열의 온디맨드 전용 템플릿은 설계상 예약을 켤 수 없습니다
- 시나리오: 시간 기반 특성 :: 시간 기반 특성 트리거로 예약·평가 주기 설정
- 시나리오: 특성 변경 :: 특성 변경 트리거로 예약·평가 주기 설정
- 시나리오: 그룹 멤버십 :: 그룹 멤버십 트리거로 예약·평가 주기 설정
- 시나리오: 로그인 비활동 :: 로그인 비활동 트리거로 예약·평가 주기 설정

> 교육 포인트: 트리거는 "언제", 범위는 "누구에게", 태스크는 "무엇을"입니다. 세 가지를 따로 정하면 같은 템플릿을 부서별로 복제해 쓸 수 있습니다.

### L3 · B · 온디맨드 실행 · 실행 이력 — 즉시 실행과 확인

#### L4 · 온디맨드로 실행하고 결과를 확인한다

1. [시작] 예약을 기다리지 않고 즉시 실행이 필요
   - 주체: 관리자
   - 위치: 수명 주기 워크플로 › 워크플로 › {워크플로} (최소 Lifecycle Workflows Administrator)
   - 데이터: 시험 실행 또는 긴급 퇴사 같은 즉시 처리 요구
   - 해설: 예약 전 시험이나 갑작스런 퇴사 처리에 씁니다. 온디맨드 전용 템플릿(Real-time employee termination 등)은 이 방식으로만 실행됩니다
2. [판단] 워크플로가 사용 설정되어 있는가?
   - 주체: Entra ID
   - 데이터: isEnabled — false면 예약 실행도 온디맨드도 막힘
   - 해설: 사용 설정이 꺼진 워크플로는 즉시 실행도 할 수 없습니다. 사용 설정을 끄면 대기 중이던 예약 사용자도 Canceled가 됩니다
   - 예 → 3
   - 아니오 → [차단] 차단 — 비활성 워크플로는 온디맨드 실행 불가
3. [처리] 온디맨드 실행 선택
   - 주체: 관리자
   - 위치: 워크플로 › 온디맨드 실행(Run on demand) — 개요 화면의 Quick Action에서도 시작
   - 데이터: API: POST /identityGovernance/lifecycleWorkflows/workflows/{id}/activate (workflow: activate)
   - 해설: 개요 화면의 빠른 작업에서도 시작할 수 있습니다. 평가 주기는 기본 3시간이지만 온디맨드는 기다리지 않고 바로 처리합니다
4. [처리] 대상 사용자 추가
   - 주체: 관리자
   - 위치: 사용자 선택(Select users) 탭 › 사용자 추가(Add users) › 추가(Add)
   - 데이터: 한 번에 최대 10명 (온디맨드 선택 한도)
   - 해설: 시험은 소수의 사용자로 시작하는 것이 좋습니다. 대상이 더 많으면 10명씩 나눠 실행하거나 예약 실행을 씁니다
5. [처리] 확인 후 워크플로 실행
   - 주체: 관리자
   - 위치: 선택 확인 › 워크플로 실행(Run workflow)
   - 데이터: 실행 요청 (사용자 · 워크플로 ID)
   - 해설: 실행 요청이 접수되고 사용자별 처리가 시작됩니다. 이력에서는 실행 유형이 on-demand로 구분됩니다
6. [처리] 실행 조건과 무관하게 태스크 적용
   - 주체: Entra ID
   - 데이터: 온디맨드 실행은 트리거·범위 조건 충족 여부를 보지 않음 · 실행 한도(execution threshold)와 격리(quarantine) 검사 대상도 아님
   - 해설: 선택한 사용자에게 태스크가 그대로 적용되므로 대상 선택이 중요합니다. 격리된 워크플로도 온디맨드로는 실행할 수 있습니다
7. [처리] 사용자 요약 확인
   - 주체: 관리자
   - 위치: 워크플로 › 워크플로 기록(Workflow history) › 사용자(Users) (날짜 · 상태 · 이름 필터 · 실행 유형 · 완료 날짜)
   - 데이터: 전체 처리 · 성공 · 실패 · 전체 태스크 · 실패 태스크 · 날짜 범위는 24시간~30일
   - 해설: 사용자별로 성공과 실패 건수를 봅니다. 결과는 CSV 파일로 내려받을 수 있습니다
8. [처리] 실행·태스크 요약 확인
   - 주체: 관리자
   - 위치: 워크플로 기록 › 실행(Runs) · 태스크(Tasks) (최대 30일 범위)
   - 데이터: 상태 Completed · In Progress · Queued · Canceled · Completed with errors · Failed (Completed with errors = continueOnError=true 태스크 실패, Failed = continueOnError=false 태스크 실패)
   - 해설: 어느 태스크에서 실패했는지 좁혀 확인합니다
9. [끝] 감사 로그로 상세 확인
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 감사 로그 (서비스 Lifecycle Workflows · 날짜 필터 24시간~30일)
   - 데이터: 범주 Other(사용자 지정 태스크) · TaskManagement · WorkflowManagement · 상태 사유 · 대상(개체 ID) · 시작한 주체
   - 해설: 실패한 항목은 상태 사유와 대상 개체 ID로 원인을 추적합니다
- 시나리오: 예 :: 사용 설정돼 온디맨드 실행 후 감사 로그 확인
- 시나리오: 아니오 :: 사용 설정이 안 돼 즉시 실행이 차단됨

> 교육 포인트: 시험은 온디맨드로 소수 사용자에게 먼저 돌린 뒤 예약을 켭니다.
>
> 주의: 온디맨드 실행은 범위 조건을 무시하므로 잘못 선택한 사용자에게도 태스크가 적용됩니다.

### L3 · C · 입사 · 이동 · 퇴사 시나리오 — 템플릿별 흐름

#### L4 · 입사 전에서 퇴사 후까지 템플릿 흐름

1. [시작] 입사 7일 전 — Onboard pre-hire employee
   - 주체: Entra ID
   - 위치: 템플릿 Onboard pre-hire employee (범주 Joiner)
   - 데이터: 이벤트 사용자 특성 employeeHireDate · 이벤트 기준 일수 7 (템플릿 문서 표에는 -7로 표기) · 이벤트 시점 Before · 이벤트 시점은 변경 불가, 일수는 변경 가능 · 기본 태스크 Generate TAP And Send Email
   - 해설: 입사일 전에 계정 준비를 위한 태스크를 실행합니다
2. [처리] 임시 액세스 패스를 만들어 메일 전송
   - 주체: Entra ID
   - 데이터: 태스크 Generate TAP And Send Email · 인수 tapLifetimeInMinutes(10~43200분) · tapIsUsableOnce · 기본 수신자는 관리자이며 사용자에게 보내려면 To recipient=User · 수신 주소 속성 otherMails. 선행 조건: 관리자 수신이면 사용자 manager 관계와 관리자 mail 값, TAP 테넌트 정책 사용 및 허용 범위 내 값
   - 해설: 첫 로그인용 임시 액세스 패스를 발급해 안내합니다. TAP 시작 시각은 입사일(hire date)이며 이미 지났다면 현재 시각이라, 활성 기간을 입사일 시각에 맞춰 두어야 첫날에 만료되지 않습니다. 다른 인증 방법·로그인 기록·Entra 역할 할당이 이미 있는 사용자는 이 태스크가 동작하지 않으며, 외부 게스트에는 리소스 테넌트에서 TAP을 발급할 수 없습니다
3. [처리] 입사 당일 — Onboard new hire employee
   - 주체: Entra ID
   - 데이터: 이벤트 기준 일수 0 · On · employeeHireDate 또는 createdDateTime · 태스크 Add User To Group · Enable User Account · Send Welcome Email
   - 해설: 입사일에 계정을 켜고 그룹을 붙이고 환영 메일을 보냅니다. 입사 후 7일 시점에는 Post-Onboarding 템플릿(Add User To Group · Add user to selected teams, 기본 7일 After)을 이어서 쓸 수 있습니다
4. [처리] 이동 — 직무 변경 · 그룹 멤버십 변경
   - 주체: Entra ID
   - 데이터: 템플릿 Employee job profile change (기본 태스크: 관리자에게 이동 알림 메일 · 모든 액세스 패키지 할당 제거(기본 15일 후 제거 예약) · 선택한 그룹·Teams에서 제거 · 액세스 패키지 할당 요청) · Employee group membership changes (모든 액세스 패키지 할당 제거(기본 15일) · 선택한 Teams에서 제거 · 관리자에게 이동 알림 메일). 트리거는 특성 변경 또는 그룹 멤버십 변경 · 이동 알림 메일은 사용자 manager와 관리자 mail 값이 필요
   - 해설: 부서나 직무 속성이 바뀌면 이동 시나리오 워크플로가 실행됩니다. 즉시 처리가 필요하면 Real-time employee change(온디맨드 전용)를 씁니다
5. [처리] 퇴사 예정 — Pre-offboarding of an employee
   - 주체: Entra ID
   - 데이터: 퇴사일(employeeLeaveDateTime) 7일 전(Before)에 실행하는 템플릿 · 기본 태스크 Remove user from selected groups · Remove user from selected Teams · 이벤트 시점은 변경 불가
   - 해설: 퇴사일 전에 필요한 사전 정리 작업을 실행합니다
6. [처리] 퇴사 당일 — Offboard an employee
   - 주체: Entra ID
   - 데이터: employeeLeaveDateTime · 이벤트 기준 일수 0 · On · 태스크 Disable User Account · Remove user from all groups · Remove user from all Teams · 계정 비활성화는 Entra 역할 할당 사용자와 역할 할당 가능 그룹 구성원을 지원하지 않음
   - 해설: 퇴사일에 계정을 막고 그룹·Teams 접근을 제거합니다. 퇴사 시각까지 반영하려면 employeeLeaveDateTime의 시간 부분을 하루 끝(예: 오후 9시)으로 넣어 둡니다
7. [판단] 즉시 퇴사 처리가 필요한가?
   - 주체: 관리자
   - 해설: 긴급 퇴사는 예약일을 기다리지 않고 바로 처리합니다
   - 예 → 8
   - 아니오 → 9
8. [끝] Real-time employee termination — 온디맨드
   - 주체: 관리자
   - 위치: 템플릿 Real-time employee termination (트리거: 온디맨드)
   - 데이터: 태스크 Remove user from all groups · Delete User Account · Remove user from all Teams · 예약을 켤 수 없고 한 번에 최대 10명 · 삭제 태스크는 Entra 역할 할당 사용자와 역할 할당 가능 그룹 구성원을 지원하지 않음 [확인 필요: 삭제 후 복구 기간 — 태스크 문서에 미기재]
   - 해설: 선택한 사용자에게 즉시 퇴사 태스크를 실행합니다. 계정 삭제는 되돌리기 어려우므로 대상 선택을 한 번 더 확인합니다
9. [끝] Post-offboarding of an employee — 퇴사 후 정리
   - 주체: Entra ID
   - 데이터: 퇴사일(employeeLeaveDateTime) 이후 실행하는 템플릿 · 기본 태스크 Remove all licenses for user · Remove user from all Teams · Delete User Account [확인 필요: 기본 오프셋 — 템플릿 표에 미기재]
   - 해설: 퇴사 후 일정 시간이 지난 뒤 남은 정리 작업을 실행합니다
- 시나리오: 예 :: 즉시 퇴사가 필요해 Real-time 템플릿으로 종료
- 시나리오: 아니오 :: 즉시 퇴사가 아니라 Post-offboarding으로 종료

> 교육 포인트: 입사는 "사전 준비 → 당일 활성화", 퇴사는 "당일 비활성화 → 필요 시 후속 삭제" 순서로 나눠 설계합니다.
>
> 주의: 퇴사 워크플로는 날짜 속성(employeeLeaveDateTime)이 정확해야 합니다. 클라우드 전용 사용자에게 값을 수동으로 넣으려면 별도 권한이 필요합니다.
