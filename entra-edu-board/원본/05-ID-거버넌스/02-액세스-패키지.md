## L2 · 액세스 패키지 — 권한 관리(Entitlement Management)

- 설정(Control Plane): 카탈로그 · 액세스 패키지 | 요청·승인·기간 정책 · 커넥티드 조직
- 강제(Enforcement): Entra 권한 관리 서비스 | 승인 후 리소스 할당 · 만료 시 자동 제거
- 증적(Evidence): 액세스 패키지 요청 · 할당 기록 | 감사 로그 EntitlementManagement
- 메뉴(Admin Center): ID 거버넌스 > 권한 관리
- 라이선스(License): Entra ID Governance 또는 Entra ID P2 — P2는 기존 GA 기능(요청·승인·만료·외부 사용자 수명 주기·분리 의무 등)만, 자동 할당 정책·Verified ID 연동·사용자 프로필 스폰서 승인자·ID Protection 연동 등은 ID Governance 필수 (조직의 멤버 사용자 기준)

### L3 · 0 · 기능 상태 전이 — 수동 요청 → 패키지·정책 구성 → 요청·승인·할당·만료

#### L4 · ⓪ 비활성 — 접근을 메일·티켓으로 요청해 수동 부여

1. [시작] 사용자가 접근이 필요해 담당자에게 메일·티켓 요청
   - 주체: 사용자
   - 위치: 메일 · 티켓 시스템 (Entra 밖)
   - 데이터: 요청 사유와 필요한 리소스 설명 (정형 필드 없음) · Entra의 요청 기록(accessPackageAssignmentRequest)이나 감사 범주 EntitlementManagement 에는 남지 않음
   - 해설: 어떤 접근이 필요한지 사람에게 설명하는 데서 시작합니다. 요청·승인 근거가 Entra 밖 메일과 티켓에만 흩어집니다
2. [처리] 담당자가 승인자를 찾아 전달
   - 주체: 관리자
   - 위치: 메일 · 메신저
   - 데이터: 승인 여부와 근거가 메일 스레드에 흩어짐 · 사용자 프로필의 Manager · Sponsors 속성을 승인자 선정에 쓰는 자동 규칙이 없음
   - 해설: 누가 승인해야 하는지 모르는 경우가 많아 지연됩니다. 액세스 패키지는 Manager·Sponsors 속성이나 지정 승인자·대체 승인자로 이 단계를 정책화합니다
3. [처리] 관리자가 그룹·앱·사이트에 각각 수동 추가
   - 주체: 관리자
   - 위치: 그룹 멤버 · 엔터프라이즈 앱 사용자 및 그룹 · SharePoint 사이트 권한
   - 데이터: 리소스마다 따로 남는 할당 기록 · 그룹은 클라우드 생성 보안 그룹·M365 그룹만 Entra에서 멤버 변경 가능(온프레미스 AD 동기화 그룹·Exchange 배포 그룹은 Entra에서 변경 불가)
   - 해설: 한 업무에 필요한 권한을 여러 곳에 하나씩 붙입니다. 하나라도 빠뜨리면 업무가 막히고, 회수 때도 각각 찾아 지워야 합니다
4. [처리] 만료일 없이 권한이 유지
   - 주체: Entra ID
   - 데이터: 만료·재확인 일정이 없는 그룹 멤버십 · 앱 할당 (액세스 패키지 정책은 만료를 날짜·일수(0~3660)·시간·없음 중에서 정함)
   - 해설: 프로젝트가 끝나도 아무도 회수하지 않습니다
5. [끝] 외부 사용자의 접근도 회수되지 않고 쌓임
   - 주체: 로그
   - 데이터: 초대된 게스트 계정과 권한이 계속 남음 · Guests can invite 가 허용돼 있으면 게스트가 다른 게스트를 직접 초대하는 경로도 거버넌스 밖에서 생김
   - 해설: 접근이 필요한 만큼만, 필요한 기간만 유지되지 않습니다. 액세스 패키지는 마지막 할당이 끝나면 게스트를 차단하고 30일 뒤 삭제하는 기본 수명 주기를 제공합니다

#### L4 · ① 구성 — 카탈로그 · 액세스 패키지 · 정책을 만든다

1. [시작] 관리자가 권한 관리를 연다
   - 주체: 관리자
   - 위치: entra.microsoft.com › ID 거버넌스(ID Governance) › 권한 관리(Entitlement management) › 액세스 패키지(Access package) (최소 Identity Governance Administrator)
   - 데이터: 로그인 관리자 역할 (카탈로그 소유자·액세스 패키지 관리자도 자기 카탈로그 안에서 일부 작업 가능 · Global Administrator도 전체 관리 가능) · Graph 위임 권한 EntitlementManagement.ReadWrite.All
   - 해설: 패키지는 Identity Governance Administrator나 위임된 관리자가 만듭니다. User Administrator는 더 이상 카탈로그 생성이나 남의 카탈로그의 패키지 관리를 할 수 없으므로 Identity Governance Administrator를 줍니다
2. [처리] 카탈로그 만들기
   - 주체: 관리자
   - 위치: ID 거버넌스 › 카탈로그(Catalogs) › 새 카탈로그(New catalog) (이름 · 설명 · Enabled · Enabled for external users) — 최소 Identity Governance Administrator 또는 Catalog creator
   - 데이터: accessPackageCatalog — 지정하지 않으면 General 카탈로그에 들어감 · Enabled=Yes여야 요청 가능 · Enabled for external users 는 새 카탈로그에서 기본 허용이며 외부 사용자의 셀프 요청만 제어(관리자 직접 할당과는 무관) · 만든 사람이 비관리자면 첫 카탈로그 소유자
   - 해설: 카탈로그는 패키지에 넣을 수 있는 리소스의 범위를 정하는 컨테이너입니다. 이미 만든 패키지를 다른 카탈로그로 옮길 수는 없습니다
3. [처리] 카탈로그에 리소스 추가
   - 주체: 관리자
   - 위치: 카탈로그 › {카탈로그} › 리소스(Resources) › 리소스 추가 (그룹 · Teams · 앱 · SharePoint 사이트) — 패키지 생성 중에는 리소스 역할 탭의 See all 로도 추가
   - 데이터: accessPackageResource (클라우드 생성 보안 그룹 · Microsoft 365 그룹 · 엔터프라이즈 앱 · SharePoint Online 사이트·사이트 컬렉션) · 제외: 온프레미스 AD 동기화 그룹·Exchange 배포 그룹(멤버 변경 불가), Exchange Online·SharePoint Online 서비스 자체, 개인 Microsoft 계정 전용 앱 · 동적 멤버십 그룹은 소유자 역할만 선택 가능
   - 해설: 관리자가 소유하거나 관리하는 리소스를 카탈로그에 모읍니다. 액세스 패키지 관리자는 소유 리소스라도 카탈로그에 추가할 수 없어 카탈로그 소유자에게 요청합니다
4. [처리] 액세스 패키지 기본 정보 입력
   - 주체: 관리자
   - 위치: 권한 관리 › 액세스 패키지 › 새 액세스 패키지(New access package) › 기본 사항(Basics) (이름 · 설명 · 카탈로그 — 새 카탈로그 만들기도 가능)
   - 데이터: accessPackage (displayName · description · catalog) · 사용자가 요청할 때 이 이름과 설명이 보임 · 생성 API는 EntitlementManagement.ReadWrite.All (PowerShell: Microsoft.Graph.Identity.Governance 모듈)
   - 해설: 패키지를 만들 카탈로그를 고르거나 새 카탈로그를 만듭니다. 본인이 패키지를 만들 권한이 있는 카탈로그만 목록에 보입니다
5. [처리] 패키지에 리소스 역할 지정
   - 주체: 관리자
   - 위치: 새 액세스 패키지 › 리소스 역할(Resource roles) 탭 › 그룹과 팀 · 애플리케이션 · SharePoint 사이트 · Microsoft Entra 역할(미리 보기) · API 권한(미리 보기) 선택 › 역할(Role) 지정
   - 데이터: accessPackageResourceRoleScope · 앱 역할이 여럿인 앱에서 둘 이상을 담으면 담은 역할이 모두 부여됨 · PIM 관리 그룹은 활성·적격 역할을 모두 선택 가능 · 만들 때 생략하고 나중에 추가해도 기존 할당자가 추가 리소스를 자동으로 받음
   - 해설: 요청자는 패키지에 담긴 모든 리소스 역할을 한 번에 받습니다. 역할 조합이 다르면 패키지를 나눕니다
6. [처리] 요청 정책의 대상 지정
   - 주체: 관리자
   - 위치: 요청(Requests) 탭 › 접근 권한이 있는 사람(Who can get access) — 디렉터리 내 사용자·에이전트·서비스 주체: 특정 사용자 및 그룹 · 모든 멤버(게스트 제외) · 모든 사용자(게스트 포함) 등 / 디렉터리 밖 사용자: 특정 커넥티드 조직 · 모든 커넥티드 조직 · 모든 사용자 / 없음(관리자 직접 할당만)
   - 데이터: accessPackageAssignmentPolicy (allowedTargetScope · specificAllowedTargets · requestorSettings) · 모든 서비스 주체·모든 에이전트 선택지는 Entra Agent ID 필요 · 모든 사용자(커넥티드 조직 + 새 외부 사용자) 정책은 먼저 이메일 일회용 암호(OTP)를 켜야 함
   - 해설: 정책 하나가 누가 요청할 수 있는지 정의합니다. 처음에 요청 방식이 불확실하거나 자동 할당을 쓸 계획이면 관리자 직접 할당 정책으로 시작합니다
7. [처리] 승인 요구와 승인자 지정
   - 주체: 관리자
   - 위치: 요청 탭 › 승인 필요(Require approval) = 예 › 요청자 사유 필수 · 단계 수(1~3) › 첫 승인자(관리자 · 스폰서 · 특정 승인자 선택 / 외부 요청은 내부 스폰서 · 외부 스폰서) · 폴백 승인자 · "며칠 안에 결정해야 하는가"(Decision must be made in how many days?) · 승인자 사유 필수 · 고급 요청 설정 › 대체 승인자(If no action taken, forward to alternate approvers)
   - 데이터: 승인 단계 · 결정 기한(일) · 폴백 승인자 · 승인자는 한 명만 승인하면 되고 먼저 응답한 사람의 결정이 적용됨 · 기한 안에 결정이 없으면 요청이 자동 거부 · 대체 승인자 전달은 요청 기간의 절반이 지난 다음 날부터 마지막 날 전까지만 가능해 결정 기한을 4일 이상으로 둬야 함
   - 해설: 승인자를 못 찾는 경우를 위해 폴백 승인자를 둡니다. 관리자(Manager) 승인자는 사용자 프로필의 Manager 속성으로, 스폰서 승인자는 Sponsors 속성으로 찾습니다. 사용자 프로필 스폰서 승인자는 ID Governance 라이선스가 필요하고, 관리자·지정 승인자·다단계 승인은 P2로도 가능합니다. 디렉터리 밖 사용자가 요청하는 정책은 승인을 요구합니다
8. [처리] 요청자 정보 · 검증된 ID 요구
   - 주체: 관리자
   - 위치: 요청자 정보(Requestor information) 탭 › 질문(Questions: 표시 문자열 · 현지화 · 답변 형식 · 필수) · 속성(Attributes) / 요청 탭 › 검증된 ID 추가(+ Add issuer · 자격 증명 유형) — Global Administrator만 추가 가능
   - 데이터: 요청자의 응답(accessPackageAnswer) · Verified ID 발급자와 자격 증명 유형 · 한 발급자의 여러 유형이나 여러 발급자를 넣으면 요청자가 전부 제시해야 하므로 선택적으로 받으려면 정책을 나눔
   - 해설: 요청 시 받을 정보와 요구할 자격 증명을 정합니다. Identity Governance Administrator·User Administrator·카탈로그 소유자·액세스 패키지 관리자는 아직 검증된 ID 요구를 추가할 수 없고, Verified ID 연동은 ID Governance 라이선스 기능입니다
9. [처리] 수명 주기 설정
   - 주체: 관리자
   - 위치: 수명 주기(Lifecycle) 탭 › 액세스 패키지 할당 만료(날짜 · 일 수 · 시간 · 안 함) · 사용자가 특정 기간 요청 허용 · 고급 만료 설정 › 연장 허용(Allow users to extend access) · 연장에 승인 필요 · 액세스 검토 요구(Require access reviews: 빈도 Annually · Bi-annually · Quarterly · Monthly)
   - 데이터: expiration (type · duration) — 일 수는 0~3660 · 연장 요청은 정책 만료일 이내여야 하고, 연장에 승인이 필요하면 요청 탭의 승인 설정을 그대로 사용 · 정책에 접근 검토를 넣으려면 ID Governance 라이선스
   - 해설: 만료 14일 전과 1일 전에 연장 안내 메일이 갑니다. 사용자는 연장 시점에도 정책 범위 안에 있어야 합니다
10. [끝] 검토 + 만들기
   - 주체: 관리자
   - 위치: 검토 + 만들기(Review + create) 탭 › 만들기(Create) · 이후 액세스 패키지 › 편집에서 숨김(Hidden) 설정 변경
   - 데이터: accessPackage + 초기 accessPackageAssignmentPolicy · 감사 범주 EntitlementManagement · 숨김 기본값은 아니오 · 숨김=예여도 요청 링크를 가진 사용자는 요청할 수 있음 · 코드로는 카탈로그 리소스 확인 → accessPackage → resourceRoleScope → assignmentPolicy 순서로 생성
   - 해설: 패키지와 첫 정책이 만들어지고 사용자가 요청할 수 있게 됩니다. 요청 링크를 받은 사람에게만 노출하려면 숨김을 예로 바꾸고 링크를 공유하며, 이후 정책 추가나 비호환 패키지(분리 의무) 설정도 할 수 있습니다

#### L4 · ② 활성 — 요청 → 승인 → 할당 → 만료

1. [시작] 사용자가 내 액세스 포털에서 패키지 요청
   - 주체: 사용자
   - 위치: myaccess.microsoft.com › 액세스 패키지(Access packages) › 요청(Request) — 숨김 패키지는 요청 링크로 진입
   - 데이터: accessPackageAssignmentRequest (requestType=userAdd) · 상태 Submitted (Graph state=submitted) · 감사 활동 User requests access package assignment
   - 해설: 요청이 제출되며 요청 기록이 만들어집니다. 카탈로그 Enabled가 아니거나 비호환 패키지 보유 등으로 막히면 요청할 수 없습니다
2. [처리] Entra ID가 요청자가 정책 대상인지 확인
   - 주체: Entra ID
   - 데이터: 정책의 요청자 범위 (디렉터리 내 사용자 · 커넥티드 조직 · 특정 사용자·그룹) · 패키지에 정책이 여러 개면 요청자를 포함하는 정책을 찾아 그 정책의 승인·기간 규칙을 적용
   - 해설: 정책에 정의된 요청 가능 대상과 요청자를 대조합니다. 카탈로그 Enabled(외부는 Enabled for external users) · 패키지 비호환 목록 · 정책 설정이 함께 요청 가능 여부를 정합니다
3. [판단] 요청자가 정책 대상인가?
   - 주체: Entra ID
   - 해설: 대상이 아니면 패키지가 보이지 않거나 요청이 거부됩니다. 숨김 패키지는 목록에 안 보여도 링크가 있고 정책 대상이면 요청할 수 있습니다
   - 예 → 4
   - 아니오 → [차단] 차단 — 정책 요청 대상이 아님
4. [처리] 요청 정보 수집
   - 주체: 사용자
   - 위치: 요청 화면 › 질문 응답 · 사유(정책이 Require requestor justification 일 때) · (요구 시) Verified ID 제시 · 사용자가 특정 기간 요청이 허용된 정책이면 시작·종료 일시
   - 데이터: 요청자 답변(accessPackageAnswer) · 검증된 자격 증명 클레임 · 요청자가 필수 질문에 답하지 않으면 제출 불가
   - 해설: 정책이 요구한 정보를 요청에 함께 담습니다. 승인자에게 이 답변이 함께 보여 판단 근거가 됩니다
5. [판단] 승인이 필요한가?
   - 주체: Entra ID
   - 데이터: 정책의 Require approval 값 (아니오면 자동 승인 — 감사 활동 Auto approve access package assignment request)
   - 해설: 승인이 필요 없으면 곧바로 할당 단계로 갑니다. 승인이 필요 없는 정책이라도 외부 사용자가 요청할 수 있으면 디렉터리 유입 감독이 사라지므로 주의합니다
   - 예 → 6
   - 아니오 → 8
6. [처리] 승인 대기 — 승인자에게 알림
   - 주체: Entra ID
   - 위치: 승인자: 내 액세스 포털 › 승인(Approvals) · 메일 제목 예: Action required: Approve or deny request by [날짜]
   - 데이터: 요청 상태 Pending approval · 승인자 이메일 · 다단계 승인(최대 3단계, 단계마다 한 명만 승인) · 감사 활동 Create request approval · Add approver to request approval (범주 UserManagement) · 대체 승인자가 있으면 기한 중간 이후 전달 메일(Approve or deny forwarded request)
   - 해설: 승인자(관리자·스폰서·지정 사용자)가 요청을 검토합니다. 승인자는 전원이 아니라 먼저 응답한 한 명의 결정으로 처리됩니다
7. [판단] 승인자가 기한 안에 승인했는가?
   - 주체: 관리자
   - 데이터: 상태 Approved · Denied · Expired (결정 기한 초과) · 감사 활동 Approve access package assignment request · Deny access package assignment request · Access package assignment request timed out (no approver action taken) · Graph 요청 state 값(submitted · pendingApproval · delivering · delivered · deliveryFailed · denied · scheduled · canceled · partiallyDelivered)에는 expired가 없어 시한 초과는 감사 활동으로 확인
   - 해설: 기한 안에 승인이 없으면 요청이 만료돼 사용자가 다시 요청해야 합니다. 요청자에게는 거부 또는 만료 메일이 갑니다
   - 예 → 8
   - 아니오 → [차단] 거부·만료 — 승인되지 않아 할당 없음
8. [처리] 리소스에 한 번에 할당
   - 주체: Entra ID
   - 데이터: 그룹 멤버십 추가 · 엔터프라이즈 앱 역할 할당 · SharePoint 사이트 멤버 추가 (상태 Delivering → Delivered) · 감사 활동 Ready to fulfill access package assignment request → Fulfill access package assignment
   - 해설: 패키지에 담긴 리소스 역할이 동시에 부여되고, 서비스마다 반영에 시간이 걸릴 수 있습니다. 대량 변경은 하루 여러 번 일괄 처리돼 최대 24시간이 걸릴 수 있고(소수 객체면 보통 몇 분), 이후 SaaS·Microsoft 서비스로 전파되는 시간이 더해집니다. 진행은 감사 로그·프로비저닝 로그·SharePoint 사이트 감사 로그로 확인합니다
9. [처리] 만료 전 연장 안내
   - 주체: Entra ID
   - 데이터: 연장이 허용된 정책은 14일 전·1일 전 메일 · 연장 시 상태 Access extended · 연장 요청 날짜는 정책 만료일 이내 · 연장에 승인이 필요하면 요청 탭 승인 설정 재사용 · Graph requestType=userUpdate
   - 해설: 사용자는 정책 범위 안에 있을 때만 연장을 요청할 수 있습니다. 연장된 사용자는 연장 날짜 이후에는 해당 패키지를 새로 요청할 수 없습니다
10. [끝] 기간 만료 → 자동 제거 + 기록
   - 주체: 로그
   - 위치: 권한 관리 › 액세스 패키지 › {패키지} › 요청 · 할당(Assignments › Download) / ID Governance › Entitlement management › 감사 로그(Audit logs) › Category = EntitlementManagement 또는 UserManagement
   - 데이터: 상태 Access expired (Graph 할당 state=expired · expiredDateTime) · 감사 활동 Remove access package assignment (만료·사용자 취소·관리자 제거 공통) · AuditLogs 범주 EntitlementManagement · UserManagement · 같은 그룹·팀이 다른 패키지에도 담겨 있고 그 할당이 유효하면 그룹·팀에서는 제거되지 않음
   - 해설: 기한이 지나면 접근이 자동으로 회수되고 요청 이력이 남습니다. 다시 필요하면 새 요청이 필요합니다
- 시나리오: 예 ▸ 예 ▸ 예 :: 승인자가 기한 안에 승인해 할당되고 만료 시 제거
- 시나리오: 예 ▸ 예 ▸ 아니오 :: 승인 대기 중 기한 안에 승인이 없어 거부·만료
- 시나리오: 예 ▸ 아니오 :: 승인 없이 바로 할당되고 만료 시 자동 제거
- 시나리오: 아니오 :: 정책 대상이 아닌 요청자라 차단

> 교육 포인트: 패키지는 "접근을 사람에게 일일이 붙이는 일"을 "정책에 맞는 사람이 요청 → 승인 → 기간 한정 부여"로 바꿉니다.

### L3 · A · 카탈로그 · 액세스 패키지 · 정책 — 구성 요소의 관계

#### L4 · 카탈로그 > 패키지 > 정책 구조와 위임

1. [시작] 카탈로그가 패키지에 넣을 리소스 범위를 정함
   - 주체: 관리자
   - 위치: ID 거버넌스 › 권한 관리 › 카탈로그(Catalogs) · 카탈로그 설정 편집: Enabled · Enabled for external users
   - 데이터: accessPackageCatalog — 패키지는 카탈로그 안에서만 리소스를 가져옴 · 리소스는 카탈로그 소유자 또는 Identity Governance Administrator가 카탈로그에 추가(액세스 패키지 관리자는 불가) · 패키지는 만든 뒤 다른 카탈로그로 이동 불가
   - 해설: 카탈로그 밖의 리소스는 그 카탈로그 패키지에 넣을 수 없습니다. 카탈로그를 만든 비관리자는 첫 카탈로그 소유자가 됩니다
2. [처리] 관리할 수 있는 리소스 유형
   - 주체: Entra ID
   - 데이터: 클라우드 생성 보안 그룹 · Microsoft 365 그룹과 Teams · 엔터프라이즈 앱 · SharePoint Online 사이트 (Microsoft Entra 역할 · SAP IAG 비즈니스 역할은 미리 보기, 에이전트 ID용 API 권한은 Agent 365 라이선스) · 온프레미스 AD 동기화 그룹·Exchange 배포 그룹·동적 그룹의 멤버 변경은 지원되지 않음 · M365 그룹은 소유자 100명 제한 등 그룹 제약을 따름
   - 해설: 그룹에 라이선스나 Azure 역할을 묶어 두면 간접적으로 더 많은 권한을 패키지로 줄 수 있습니다. Exchange Online·SharePoint Online은 앱이 아니라 서비스라 직접 담을 수 없어 그룹 기반 라이선스로 줍니다
3. [처리] 비관리자에게 패키지 관리 위임
   - 주체: 관리자
   - 위치: ID 거버넌스 › 카탈로그 › {카탈로그} › 역할 및 관리자(Roles and administrators) › 소유자 추가(Add owners) (카탈로그 소유자 · 액세스 패키지 관리자)
   - 데이터: 카탈로그별 역할 할당 · 역할 4종: Catalog creator(ba92d953-d8e0-4e39-a797-0cbedb0a89e8) · Catalog owner(ae79f266-94d4-4dab-b730-feca7e132178) · Access package manager(7f480852-ebdc-47d4-87de-0d8498384a83) · Access package assignment manager(e2182095-804a-4656-ae11-64734e9b7ae5, 사용자 할당·제거만 가능) · 카탈로그 소유자로는 사용자·그룹·애플리케이션 서비스 주체도 추가 가능
   - 해설: 부서 담당자가 자기 카탈로그 안에서 패키지를 만들고 정책을 정하게 합니다. Global Administrator와 Identity Governance Administrator는 기본으로 전체를 관리하며, 위임 대상자가 외부 사용자 요청 정책을 열 수 있다는 점을 미리 알립니다
4. [처리] 패키지는 리소스 역할의 묶음
   - 주체: Entra ID
   - 데이터: accessPackageResourceRoleScope 여러 개 · 이미 그 리소스 역할에 있던 사용자는 패키지 할당이 없으면 자동으로 패키지에 들어오지 않고(직접 할당 필요), 패키지 할당 후에 만료되면 그 역할에서 제거됨
   - 해설: 요청자는 개별 리소스가 아니라 묶음 단위로 접근을 받습니다. 앱에 역할이 여럿이고 일부만 주려면 패키지를 나눕니다
5. [처리] 한 패키지에 정책을 여러 개 둔다
   - 주체: 관리자
   - 위치: 액세스 패키지 › {패키지} › 정책(Policies) › 정책 추가 (패키지는 정책이 최소 1개 있어야 할당 가능)
   - 데이터: accessPackageAssignmentPolicy 1..N (예: 내부 직원용 · 파트너용) · 요청이 오면 요청자를 포함하는 정책(requestorSettings 대조)을 찾아 승인·기간·접근 검토 규칙을 적용 · 정책마다 독립된 접근 검토 일정 가능
   - 해설: 같은 리소스 묶음을 대상별로 다른 승인·기간 규칙으로 제공합니다. 서로 호환되지 않는 패키지(분리 의무)는 비호환으로 표시해 둘을 함께 받지 못하게 합니다
6. [처리] 정책 유형 구분
   - 주체: 관리자
   - 위치: 액세스 패키지 › {패키지} › 정책 (요청 정책 · 직접 할당 정책 · 자동 할당 정책 추가) · 수명 주기 워크플로 › 워크플로 › 작업 "Request user access package assignment"
   - 데이터: 요청 정책 · 관리자 직접 할당(요청 설정 없음) · 속성 기반 자동 할당(automaticRequestSettings 가 있는 정책, ID Governance 또는 Suite 라이선스) · 수명 주기 워크플로로 할당 — 워크플로가 실행되면 패키지 할당 요청이 자동 생성되며 설정 시 Identity Governance Administrator와 Lifecycle Workflows Administrator 역할이 모두 필요
   - 해설: 요청 기반이 아니어도 속성 규칙이나 워크플로로 할당할 수 있습니다. 워크플로 작업이 요청할 때 패키지 승인 설정을 따르게 하려면 Enforce policy approval setting for admin direct assignments 설정을 켭니다
7. [끝] 자동 할당 정책은 속성이 바뀌면 접근도 회수
   - 주체: Entra ID
   - 위치: 액세스 패키지 › {패키지} › 정책(Policies) › 자동 할당 정책 추가(Add auto-assignment policy) › 규칙 편집(Edit) › 규칙 빌더 또는 규칙 구문 텍스트 상자 · 최소 Identity Governance Administrator (카탈로그 소유자·액세스 패키지 관리자는 만들 수 없음)
   - 데이터: 동적 멤버십 그룹과 같은 규칙 문법의 사용자 속성 규칙 (예: (user.department -eq "Sales")) · 정책당 규칙 대상 최대 15,000명 · 범위를 벗어난 뒤 접근을 유지할 시간·일 지정 가능 · 정책마다 EM이 동적 보안 그룹을 자동 생성(수정·재사용 금지) · memberOf 연산자 규칙은 2026-11-03부터 격리돼 할당 처리가 멈춤
   - 해설: 부서나 코스트 센터가 바뀌면 자동으로 할당과 제거가 이어지며, 속성 변경 반영에는 몇 분이 걸립니다. 한 패키지에 자동 할당 정책은 하나를 권장하고, 둘 이상이면 대상이 겹치지 않아야 합니다. 규칙 검증에는 Groups Administrator 역할이 필요합니다

> 교육 포인트: 카탈로그는 "무엇을 담을 수 있나", 패키지는 "무엇을 한 번에 주나", 정책은 "누가·어떻게·얼마나"를 정합니다.

### L3 · B · 요청 상태 — 요청부터 만료까지

#### L4 · 요청 상태 전이 — Submitted 에서 Access expired 까지

1. [시작] Submitted — 사용자가 요청을 제출
   - 주체: 사용자
   - 위치: 내 액세스 포털(myaccess.microsoft.com) › 액세스 패키지
   - 데이터: accessPackageAssignmentRequest 생성 (requestType=userAdd · Graph state=submitted) · 감사 활동 User requests access package assignment
   - 해설: 요청이 접수되면 정책이 승인을 요구하는지 확인합니다. 관리자가 직접 할당한 경우에는 활동이 Administrator directly assigns user to access package 로 남고 요청자 메일은 가지 않습니다
2. [판단] 정책이 승인을 요구하는가?
   - 주체: Entra ID
   - 데이터: 정책 승인 설정 (Require approval 예/아니오 · 승인자 · 결정 기한)
   - 해설: 승인 요구가 없으면 곧바로 Approved로 갑니다 (감사 활동 Auto approve access package assignment request)
   - 예 → 3
   - 아니오 → 5
3. [처리] Pending approval — 승인 대기
   - 주체: Entra ID
   - 데이터: 승인 단계 · 승인자 알림 · 결정 기한 · Graph state=pendingApproval · 감사 활동 Create request approval · Add approver to request approval (UserManagement)
   - 해설: 승인자가 결정할 때까지 요청이 대기합니다. 대체 승인자를 켜면 기한 절반이 지난 다음 날부터 대체 승인자에게도 전달됩니다
4. [판단] 승인자의 결정은?
   - 주체: 관리자
   - 위치: 승인자: 내 액세스 포털 › 승인(Approvals)
   - 해설: 시한 안에 승인하면 진행하고, 거부하거나 시한이 지나면 종료합니다. 거부는 Deny access package assignment request, 시한 초과는 Access package assignment request timed out (no approver action taken) 로 감사 로그에 남고 요청자에게 메일이 갑니다
   - 승인 → 5
   - 거부 → [차단] Denied — 승인자가 거부, 다시 요청해야 함
   - 시한 초과 → [차단] Expired — 승인 시한 안에 결정 없음
5. [처리] Approved — 할당 시작
   - 주체: Entra ID
   - 데이터: accessPackageAssignment 생성 (state) · 리소스 할당 작업 시작 · 감사 활동 Approve access package assignment request → Ready to fulfill access package assignment request
   - 해설: 승인되거나 자동 승인되면 리소스 할당이 시작됩니다. 할당 변경은 하루 여러 번 일괄 처리됩니다
6. [판단] 모든 리소스 역할이 바로 할당됐는가?
   - 주체: Entra ID
   - 데이터: 외부 사용자는 디렉터리 첫 접근·동의 프롬프트 수락 전일 수 있음 · 서비스 전파 지연(대량이면 최대 24시간 이상)
   - 해설: 일부가 아직 반영되지 않으면 Delivering 또는 Partially Delivered 상태가 됩니다
   - 예 → 8
   - 아니오 → 7
7. [처리] Delivering — 할당이 진행 중
   - 주체: Entra ID
   - 데이터: 상태 Delivering / Partially Delivered (Graph 할당 state=delivering · partiallyDelivered · 실패는 deliveryFailed) · 멈춘 요청은 reprocess API로 재시도 가능
   - 해설: 외부 사용자의 초대 수락이나 서비스 반영을 기다립니다. 어느 리소스가 막혔는지 요청 세부와 감사·프로비저닝 로그에서 확인합니다
   - 다음 → 8
8. [처리] Delivered — 모든 리소스 할당 완료
   - 주체: Entra ID
   - 데이터: 전달 이메일 · 상태 Delivered (Graph 할당 state=delivered) · 감사 활동 Fulfill access package assignment (ActorUserPrincipalName = 접근을 받은 사용자)
   - 해설: 사용자는 패키지의 모든 리소스에 접근할 수 있습니다. 접근 보고서는 액세스 패키지 › 할당(Assignments) › 다운로드(Download)로 받을 수 있습니다
9. [판단] 만료 전에 연장했는가?
   - 주체: 사용자
   - 데이터: 연장이 허용된 정책 · 연장 승인 필요 여부 (상태 Access extended) · 연장 날짜는 정책 만료일 이내 · 할당 status 에 NearExpiry1DayNotificationTriggered · ExpiredNotificationTriggered 가 표시될 수 있음
   - 해설: 연장하면 만료일이 늦춰지고, 아니면 만료로 진행합니다. 연장 요청 때도 사용자가 정책 범위 안에 있어야 합니다
   - 예 → 8
   - 아니오 → 10
10. [끝] Access expired — 접근이 자동 제거됨
   - 주체: 로그
   - 데이터: 상태 Access expired (Graph 할당 state=expired · expiredDateTime) · 감사 활동 Remove access package assignment · 다시 받으려면 새로 요청
   - 해설: 접근이 끝나고, 다시 필요하면 새 요청을 제출해야 합니다. 요청자 본인 취소·관리자 제거도 같은 감사 활동으로 남습니다
- 시나리오: 예 ▸ 승인 ▸ 예 ▸ 아니오 :: 승인 후 역할 바로 할당, 연장 없이 만료
- 시나리오: 예 ▸ 승인 ▸ 아니오 ▸ 아니오 :: 승인 후 역할이 바로 안 붙고 연장 없이 만료
- 시나리오: 예 ▸ 거부 :: 승인자가 거부해 Denied로 종료
- 시나리오: 예 ▸ 시한 초과 :: 승인 시한 초과로 Expired 종료
- 시나리오: 아니오 ▸ 예 ▸ 아니오 :: 승인 없이 바로 전달, 연장 없이 만료
- 시나리오: 아니오 ▸ 아니오 ▸ 아니오 :: 승인 없이 역할이 바로 안 붙고 연장 없이 만료

> 교육 포인트: 문제 요청은 Delivering·Partially Delivered 에서 멈추는 경우가 많습니다. 어느 리소스가 안 됐는지 요청 세부와 감사 로그를 봅니다.

### L3 · C · 외부 사용자 요청 — 커넥티드 조직 · 게스트 생성 · 수명 주기

#### L4 · 외부 조직 사용자가 요청하고 접근이 끝날 때까지

1. [시작] 커넥티드 조직 추가
   - 주체: 관리자
   - 위치: ID 거버넌스 › 권한 관리 › 커넥티드 조직(Connected organizations) › 커넥티드 조직 추가(Add connected organization) › 기본 사항(Basics) · 디렉터리 + 도메인(Directory + domain) · 스폰서(Sponsors) (최소 Identity Governance Administrator)
   - 데이터: connectedOrganization (state=configured · identitySources — 다른 Entra 테넌트(같은·다른 클라우드) · 도메인 · SAML/WS-Fed 페더레이션 · Microsoft 계정) · 검색은 조직 이름만 가능하고 도메인명으로는 불가 · 도메인 조직은 이메일 일회용 암호(OTP)를 켜야 인증 가능
   - 해설: 패키지를 요청할 수 있는 파트너 조직을 먼저 등록합니다. 같은 테넌트의 확인된 도메인(서브도메인 포함)의 사용자는 모두 요청 대상이 되며 B2B 허용·차단 목록이 우선합니다
2. [처리] 정책에 외부 대상 지정
   - 주체: 관리자
   - 위치: 액세스 패키지 › 정책 › 요청 탭 › 접근 권한이 있는 사람 = 디렉터리 밖 사용자(For users not in your directory) › 특정 커넥티드 조직 · 모든 커넥티드 조직 · 모든 사용자(모든 커넥티드 조직 + 새 외부 사용자) 중 선택 · 전제: 카탈로그의 Enabled for external users = 예
   - 데이터: 정책의 allowedTargetScope (specificConnectedOrganizationUsers · allConfiguredConnectedOrganizationUsers · allExternalUsers 등) + specificAllowedTargets 에 연결된 조직 · 모든 사용자를 고르면 요청자의 커넥티드 조직이 자동으로 새로 만들어짐(proposed)
   - 해설: 어느 조직 사용자가 요청할 수 있는지 정책이 한정합니다. 모든 사용자 범위는 인터넷의 누구나 요청할 수 있는 범위이므로 승인을 반드시 설정합니다
3. [처리] 내부·외부 스폰서를 승인자로 지정
   - 주체: 관리자
   - 위치: 정책 › 승인 › 첫 승인자 = 내부 스폰서(Internal sponsor) · 외부 스폰서(External sponsor) · 특정 승인자 · 폴백 승인자 / 스폰서 지정은 커넥티드 조직 › 스폰서(Sponsors) 탭
   - 데이터: 승인자 목록 (외부 요청은 승인 요구를 권장) · 내부 스폰서 = 디렉터리의 멤버 사용자, 외부 스폰서 = 이미 초대된 해당 조직 게스트 · 두 단계 이상이면 각 단계에서 한 명만 승인하면 됨
   - 해설: 외부 사용자가 들어올 때 감독할 사람을 정합니다. 파트너의 핵심 담당자를 게스트로 초대해 외부 스폰서 승인자로 두면 누가 필요한지 가장 잘 아는 사람이 승인합니다
4. [처리] 외부 사용자가 패키지를 요청
   - 주체: 사용자
   - 위치: 파트너 사용자: 패키지 요청 링크(숨김 패키지는 링크로만 진입) › 홈 디렉터리 계정으로 로그인 (My Access 포털)
   - 데이터: 요청자 이메일 · 홈 테넌트 정보 · 로그인 방식은 커넥티드 조직의 인증 유형(Entra · 페더레이션 · 이메일 OTP · Microsoft 계정)을 따름
   - 해설: 아직 디렉터리에 없는 사용자도 정책에 맞으면 요청할 수 있습니다. 링크는 외부 조직 담당자에게 보내 그가 같은 조직 사용자에게 공유하게 합니다
5. [판단] 승인자가 요청을 승인했는가?
   - 주체: 관리자
   - 데이터: 승인 상태 · 결정 기한 초과 시 요청 자동 거부 · 승인이 필요 없는 정책이면 이 단계 없이 바로 초대
   - 해설: 승인되어야 B2B 초대가 만들어집니다
   - 예 → 6
   - 아니오 → [차단] 거부 — 게스트 계정이 만들어지지 않음
6. [처리] B2B 초대로 게스트 계정 생성
   - 주체: Entra ID
   - 데이터: user (userType=Guest) · 허용/차단 도메인 목록이 있으면 먼저 적용 (도메인이 허용되지 않으면 초대·할당 불가) · 초대 메일은 가지 않고 할당 전달 때 메일이 감
   - 해설: 승인되면 B2B 초대 절차로 게스트가 자동 생성됩니다. 게스트가 다른 게스트를 초대하는 경로(Guests can invite)는 아니오로 두는 것이 권장됩니다
7. [처리] 리소스 할당 + 전달 안내 메일
   - 주체: Entra ID
   - 데이터: 패키지 리소스 할당 · 외부 사용자에게 Delivered 메일 · 리소스별 전제: SharePoint 조직 외부 공유 = Anyone 또는 New and existing guests · M365 그룹 게스트 허용 켬 · Teams 게스트 액세스 켬 · CA 정책에서 Entitlement Management 앱을 게스트 대상에서 제외
   - 해설: 메일의 링크나 리소스 직접 접근으로 초대 수락을 마칩니다. 전제가 맞지 않거나 CA가 게스트를 막으면 My Access 로그인이나 리소스 접근이 차단될 수 있습니다
8. [처리] 기간이 지나면 접근 제거
   - 주체: Entra ID
   - 데이터: 만료 시 패키지 리소스 접근 회수 · 연장이 허용된 정책은 14일 전·1일 전 안내 메일 · 정책 만료 설정(날짜·일 수 0~3660·시간·안 함)
   - 해설: 정책에 만료일이 있으면 그날 접근 권한이 자동으로 제거됩니다. 만료 설정이 없으면 외부 사용자 접근이 계속 남습니다
9. [끝] 마지막 패키지가 끝나면 외부 사용자 정리
   - 주체: 로그
   - 위치: ID 거버넌스 › 권한 관리 › 제어 구성(Control Configurations) › 외부 사용자 수명 주기(Lifecycle of external users) › 설정 보기(View settings) (최소 Identity Governance Administrator)
   - 데이터: 외부 사용자 제거(Remove external user) · 디렉터리 로그인 차단(Block external user from signing in) · 제거 전 대기 일수(Number of days before removing) — 기본: 로그인 차단 후 30일 뒤 삭제, 0이면 즉시 삭제 · 대상은 패키지로 초대됐거나 governed로 전환한 게스트만 · 계정 삭제 알림은 없음
   - 해설: 할당이 모두 사라진 외부 사용자는 기본적으로 로그인이 차단되고 30일 뒤 삭제됩니다. 차단하면 그 사용자는 다른 패키지도 새로 요청할 수 없고, 설정 변경은 이후 마지막 할당을 잃는 사용자에게만 적용됩니다
- 시나리오: 예 :: 승인되어 게스트 생성, 종료 후 외부 사용자 정리
- 시나리오: 아니오 :: 승인자가 거부해 요청 종료

> 교육 포인트: 외부 사용자 계정을 "만든 사람이 기억해서 지우는" 대신, 패키지 할당이 끝나면 계정도 정리하도록 수명 주기를 정책으로 둡니다.
>
> 주의: 외부 사용자 수명 주기 설정을 "삭제하지 않음"으로 바꾸면 게스트 계정이 남습니다. 액세스 검토로 보완합니다.
