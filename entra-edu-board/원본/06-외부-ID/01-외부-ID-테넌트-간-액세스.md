## L2 · 외부 ID · 테넌트 간 액세스 — B2B 협업 · 신뢰 설정

- 설정(Control Plane): 테넌트 간 액세스 설정(기본·조직별 인바운드/아웃바운드) | 신뢰 설정 · 테넌트 제한 v2
- 강제(Enforcement): 리소스 테넌트 CA 평가 | 파트너 MFA · 준수 기기 클레임 신뢰 여부
- 증적(Evidence): 로그인 로그 (게스트) | 감사 로그 CrossTenantAccessSettings
- 메뉴(Admin Center): 외부 ID > 테넌트 간 액세스 설정
- 라이선스(License): 기본 설정은 Free · 신뢰 설정과 특정 사용자·그룹·앱 지정은 Entra ID P1 필요 [확인 필요: 고객 라이선스]

### L3 · 0 · 기능 상태 전이 — 기본 설정만 → 조직별 설정·신뢰 → 홈 테넌트 인증 + 리소스 테넌트 판정

#### L4 · ⓪ 비활성 — 기본 설정만 있는 상태

1. [시작] 외부 조직 사용자가 우리 리소스에 접근하려 함
   - 주체: 외부
   - 위치: 파트너 사용자의 홈 테넌트 계정 · 우리 앱 또는 초대 링크 · 일반 앱 URL(예: myapps.microsoft.com)에서 로그인 옵션 › 조직에 로그인
   - 데이터: 외부 사용자 UPN · 홈 테넌트 ID · 게스트 userType=Guest
   - 해설: 파트너 사용자가 게스트로 접근을 시도합니다. 게스트는 홈 조직의 로그인 페이지로 이동해 홈 테넌트 브랜딩으로 인증한 뒤 우리 테넌트로 돌아옵니다
2. [처리] 조직별 설정이 없어 기본 설정이 적용
   - 주체: Entra ID
   - 위치: Entra ID › External Identities(외부 ID) › Cross-tenant access settings(테넌트 간 액세스 설정) › Default settings(기본 설정) 탭 (최소 Security Administrator)
   - 데이터: 기본값: B2B 협업은 허용(내부 사용자 전체, 인바운드·아웃바운드 모두) · B2B direct connect는 차단 · 크로스 테넌트 동기화로 들어온 사용자 없음
   - 해설: 조직 설정이 하나도 없으면 모든 외부 Entra 조직이 B2B 협업에 허용됩니다. 이 기본값은 같은 Azure 클라우드 안의 Entra 조직에 적용되며 다른 Microsoft 클라우드와의 협업은 별도의 클라우드 설정이 필요합니다
3. [처리] 모든 외부 테넌트가 같은 규칙을 받음
   - 주체: Entra ID
   - 데이터: Organizational settings 목록이 비어 있음 (추가할 수 있는 조직 수에는 제한 없음)
   - 해설: 파트너별로 다르게 열거나 막을 수 있는 구분이 없습니다
4. [처리] 파트너가 이미 한 MFA·기기 검증을 인정하지 않음
   - 주체: Entra ID
   - 데이터: 기본값: 다른 Entra 조직의 MFA·준수 기기·하이브리드 조인 기기 클레임을 신뢰하지 않음
   - 해설: 파트너에서 MFA를 마쳐도 우리 CA가 다시 MFA를 요구할 수 있습니다
5. [끝] 파트너별 통제 · 신뢰 · 가시성이 없음
   - 주체: 로그
   - 데이터: 어느 조직과 오가는지 로그인 로그에서 직접 찾아야 함 (일부 로그는 보관 30일)
   - 해설: 누구에게 무엇을 열어 뒀는지 설계 근거가 없습니다. 차단·제한을 걸기 전에 실제 접근 현황부터 파악해야 합니다

#### L4 · ① 구성 — 파트너 조직별 설정과 신뢰를 정한다

1. [시작] 관리자가 테넌트 간 액세스 설정을 연다
   - 주체: 관리자
   - 위치: entra.microsoft.com › Entra ID › External Identities › Cross-tenant access settings (최소 Security Administrator 또는 사용자 지정 역할)
   - 데이터: 로그인 관리자 역할 · 라이선스: 신뢰 설정 · 기본 리디렉션 순서 변경 · 특정 사용자·그룹·앱 지정은 구성하는 테넌트에 Entra ID P1 필요 (B2B direct connect는 양쪽 테넌트 모두 P1)
   - 해설: 설정은 Security Administrator 이상으로 변경합니다. 이 설정을 바꾸는 작업은 보호된 작업이라 조건부 액세스로 추가 보호할 수 있습니다
2. [처리] 현재 교차 테넌트 로그인 현황을 먼저 파악
   - 주체: 관리자
   - 위치: 모니터링 및 상태 › 로그인 로그 · Azure Monitor의 Cross-tenant access activity workbook · PowerShell Get-MgAuditLogSignIn · MSIdentityTools Get-MSIDCrossTenantAccessActivity · SIEM
   - 데이터: 외부 조직 · 앱 · 사용자별 로그인 (일부 로그 30일 보관) · 외부 조직의 앱 ID도 로그인 로그에서 찾을 수 있음
   - 해설: 차단·제한 전에 실제 쓰는 접근을 먼저 확인합니다. 로그 보관이 30일뿐인 경우가 있어 업무 담당자에게도 필요한 접근을 확인합니다
3. [처리] 기본 설정 확인·수정
   - 주체: 관리자
   - 위치: 테넌트 간 액세스 설정 › 기본 설정 탭 › Edit inbound defaults(인바운드 기본값 편집) · Edit outbound defaults(아웃바운드 기본값 편집)
   - 데이터: 모든 외부 조직에 적용되는 기본 정책 — 기본값을 차단으로 바꾸면 기존 접근이 끊길 수 있음 · 기본 설정에서는 특정 외부 사용자·그룹을 지정할 수 없음
   - 해설: 조직별 설정이 없는 모든 외부 조직에 기본 설정이 적용됩니다
4. [처리] 파트너 조직 추가
   - 주체: 관리자
   - 위치: 테넌트 간 액세스 설정 › 조직 설정(Organizational settings) › 조직 추가(Add organization) › 도메인 이름 전체 또는 테넌트 ID 입력 › 검색 결과 선택 › 추가
   - 데이터: crossTenantAccessPolicyConfigurationPartner (tenantId) — 처음에는 기본 설정을 상속(목록에 Inherited from default 링크로 표시)
   - 해설: 추가 직후에는 기본 설정 상속 상태이고, 이후 인바운드/아웃바운드를 각각 사용자 지정합니다. 조직 설정은 기본 설정보다 우선합니다
5. [처리] 인바운드 B2B 협업 설정
   - 주체: 관리자
   - 위치: 조직 설정 › 인바운드 액세스 링크 › B2B collaboration › Customize settings › 외부 사용자 및 그룹 탭 · 애플리케이션 탭 › 액세스 상태(Allow access · Block access) · 적용 대상(Applies to)
   - 데이터: 특정 외부 사용자·그룹·앱 지정은 P1 필요이며 파트너에게 받은 사용자·그룹 개체 ID와 앱 ID가 필요 · 사용자 설정과 앱 설정이 서로 모순되면 저장 불가 (외부 사용자·그룹 전체 차단 시 앱도 전체 차단) · 크로스 테넌트 동기화를 쓰면 외부 사용자 전체 차단이 동기화를 막을 수 있음
   - 해설: 파트너의 어떤 사용자가 우리 어떤 앱에 접근할 수 있는지 정합니다. SharePoint·OneDrive의 B2B 통합 공유를 쓰면 외부 협업 설정에도 해당 외부 도메인을 추가하지 않으면 그 앱에서 보내는 초대가 실패할 수 있습니다
6. [처리] 인바운드 신뢰 설정
   - 주체: 관리자
   - 위치: 조직 설정 › 인바운드 액세스 › 신뢰 설정(Trust settings) 탭 › 사용자 지정 설정(Customize settings)
   - 데이터: Trust multifactor authentication from Microsoft Entra tenants · Trust compliant devices · Trust Microsoft Entra hybrid joined devices (체크박스 3개). MFA 클레임이 없으면 홈 테넌트에서 MFA를 요구하고, GDAP로 로그인하는 서비스 공급자 기술자에게는 적용되지 않음
   - 해설: 파트너가 이미 검증한 MFA·기기 신호를 우리 CA가 인정하게 합니다. 외부 사용자의 MFA를 신뢰할 계획이라면 ID Protection의 MFA 등록 정책에서 외부 사용자를 제외하는 것을 고려하세요. 두 정책이 함께 있으면 외부 사용자가 요구 사항을 충족하지 못할 수 있습니다
7. [처리] 초대 자동 수락 설정
   - 주체: 관리자
   - 위치: 신뢰 설정 탭 › 테넌트와 초대를 자동으로 사용(Automatically redeem invitations with the tenant) — 조직 설정에서만 보이는 확인란
   - 데이터: 인바운드(리소스 테넌트)와 아웃바운드(홈 테넌트)를 모두 켜야 첫 접근 동의 화면이 생략됨 · 초대 메일은 가지 않고 B2B 협업 사용자는 알림 메일만 받음 · 크로스 테넌트 동기화에는 필수 · Graph: crossTenantAccessPolicyConfigurationPartner 업데이트
   - 해설: 같은 조직 그룹 같은 신뢰 관계에서 동의 프롬프트를 줄입니다. 생략되는 것은 첫 접근의 동의 화면(Review permissions)뿐이고 앱 동의 경험에는 영향이 없습니다
8. [처리] 아웃바운드 설정
   - 주체: 관리자
   - 위치: 조직 설정 › 아웃바운드 액세스 › B2B collaboration › 사용자 및 그룹 · 애플리케이션 · (자동 수락은 신뢰 설정 탭)
   - 데이터: 우리 사용자가 외부 조직 앱에 접근하는 규칙 (예: MFA 등록·약관 앱 허용). 앱을 모두 차단하면 암호화 메일(OME) 읽기가 실패하므로 앱 ID 00000012-0000-0000-c000-000000000000을 허용 · 아웃바운드에서 사용자를 허용하면 앱도 최소 하나는 허용해야 함
   - 해설: 우리 사용자가 파트너 쪽 리소스를 쓰는 방향도 따로 통제합니다. 아웃바운드는 포털에서 다른 애플리케이션 추가(Add other applications)로 앱 ID를 직접 입력할 수 있습니다
9. [끝] 저장 — 변경이 감사 로그로 남음
   - 주체: 로그
   - 위치: 저장 · 모니터링 및 상태 › 감사 로그 (범주 CrossTenantAccessSettings)
   - 데이터: Graph: GET /v1.0/policies/crossTenantAccessPolicy/partners (단건은 partners/{tenantId}, 기본 설정은 .../crossTenantAccessPolicy/default)
   - 해설: 교차 테넌트 설정 변경은 보호된 작업으로 취급해 CA로 추가 보호할 수 있습니다

#### L4 · ② 활성 — 홈 테넌트 인증 + 리소스 테넌트 판정

1. [시작] 게스트가 우리 리소스에 접근
   - 주체: 사용자
   - 위치: 우리 앱 · 내 앱 포털(myapps.microsoft.com) · 초대 메일 링크 · 테넌트 지정 링크(https://myapps.microsoft.com/?tenantid=<테넌트 ID>)
   - 데이터: 게스트 user 개체 (userType=Guest)
   - 해설: 게스트가 초대 링크나 앱 URL로 접근합니다. 테넌트 정보가 없는 공용 URL에서는 로그인 옵션 › 조직에 로그인에서 우리 조직 도메인을 입력해 우리 테넌트로 들어옵니다
2. [처리] 초대 시점에 허용/차단 목록과 조직 설정을 확인
   - 주체: Entra ID
   - 데이터: 도메인 허용·차단 목록 + 테넌트 간 액세스 설정 (초대 때 둘 다 검사) · 이미 수락한 사용자에게는 목록이 적용되지 않고, 대기 중인 초대는 이후 목록이 막으면 수락에 실패
   - 해설: 차단 목록에 걸리면 조직 설정과 무관하게 초대할 수 없습니다
3. [판단] 초대할 수 있는가?
   - 주체: Entra ID
   - 해설: 도메인이 허용 목록에 있어도 조직 설정에서 명시적으로 차단되면 초대되지 않습니다. 어느 목록에도 없으면 테넌트 간 액세스 설정으로 판정합니다
   - 예 → 4
   - 아니오 → [차단] 차단 — 도메인 목록 또는 조직 설정이 초대를 막음
4. [처리] 게스트 개체 생성과 초대 수락
   - 주체: 사용자
   - 위치: 초대 메일(Microsoft Invitations 발신) › Accept invitation(초대 수락) · 동의 화면 Review permissions → 사용 약관(구성한 경우) → 내 앱(My Apps)
   - 데이터: 동의 상태 PendingAcceptance → 수락 완료 (사용자 속성 Invitation accepted=Yes) · 자동 수락 설정이 양쪽에 있으면 동의 생략
   - 해설: 수락 방식에 따라 홈 테넌트나 대체 ID 공급자로 인증이 이어집니다. 초대 메일의 별칭 주소로 들어오는 게스트는 직접 링크가 아니라 메일의 수락 링크를 써야 합니다
5. [처리] 홈 테넌트에서 인증
   - 주체: 사용자
   - 위치: 파트너 Microsoft Entra
   - 데이터: 홈 테넌트 로그인 · MFA는 홈 테넌트에서 수행
   - 해설: 인증은 사용자의 홈 테넌트에서 이뤄집니다. 인증 후 게스트는 우리 테넌트로 돌아와 로그인을 마칩니다
6. [판단] 인바운드 설정이 이 사용자와 앱을 허용하는가?
   - 주체: Entra ID
   - 데이터: 조직 설정 > 인바운드 > B2B 협업 (사용자·그룹 · 애플리케이션 액세스 상태)
   - 해설: 리소스 테넌트가 조직별 규칙을 확인합니다
   - 예 → 7
   - 아니오 → [차단] 차단 — 인바운드 설정이 외부 사용자 또는 앱을 막음
7. [처리] 리소스 테넌트 CA 평가 — 신뢰한 클레임 인정
   - 주체: Entra ID
   - 데이터: 신뢰 설정이 켜져 있으면 파트너 MFA·준수 기기·하이브리드 조인 클레임 인정, 없으면 홈 테넌트에서 MFA 요구
   - 해설: 신뢰 설정이 있으면 파트너의 MFA를 그대로 인정해 이중 MFA를 줄입니다. 우리 MFA 정책은 외부 사용자에게도 그대로 적용되며, 홈에서 이미 MFA를 마친 클레임이 있으면 다시 묻지 않을 뿐입니다
8. [끝] 접근 허용 + 양쪽 로그인 로그 기록
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 로그인 로그 (필터: 사용자 유형 게스트)
   - 데이터: SigninLogs 의 HomeTenantId · ResourceTenantId · CrossTenantAccessType (예: b2bCollaboration)
   - 해설: 홈 테넌트와 리소스 테넌트 양쪽에 로그인 로그가 생깁니다. 로그에는 앱 · 이메일 주소 · 홈과 리소스 테넌트 이름·ID가 함께 남습니다
- 시나리오: 예 ▸ 예 :: 초대 가능, 인바운드 허용해 접근 허용·양쪽 로그
- 시나리오: 예 ▸ 아니오 :: 초대는 되나 인바운드 설정이 막아 차단
- 시나리오: 아니오 :: 초대 시점에 허용·차단 목록에 걸려 차단

> 교육 포인트: 인증은 홈 테넌트가, 접근 판정은 리소스 테넌트가 합니다. 그래서 신뢰 설정이 없으면 파트너에서 MFA를 마쳐도 우리 CA가 다시 요구할 수 있습니다.

### L3 · A · B2B 협업 초대 · 게스트 인증 — 누가 초대하고 어떻게 로그인하나

#### L4 · 초대 정책에서 게스트 로그인까지

1. [시작] 누가 게스트를 초대할 수 있는지 정함
   - 주체: 관리자
   - 위치: Entra ID › External Identities › External collaboration settings(외부 협업 설정) › Guest invite settings (Global Administrator 또는 External Identity Provider Administrator)
   - 데이터: authorizationPolicy.allowInvitesFrom — 선택지: 조직의 모든 사용자(게스트 포함) · 멤버 사용자와 특정 관리자 역할 · 특정 관리자 역할만(User Administrator · Guest Inviter) · 아무도 안 함(관리자 포함)
   - 해설: 초대 권한 범위는 가장 열린 설정부터 가장 제한된 설정까지 있습니다. 기본값은 게스트를 포함한 모든 사용자가 초대할 수 있으며, Guest Inviter 역할을 받은 사용자는 "특정 관리자 역할만" 상태에서도 초대할 수 있습니다
2. [처리] 초대 가능한 도메인 제한
   - 주체: 관리자
   - 위치: 외부 협업 설정 › 협업 제한(Collaboration restrictions) — 모든 도메인 허용(기본) · 지정 도메인 초대 거부 · 지정 도메인에만 초대 허용
   - 데이터: 허용 목록 또는 차단 목록 중 한 종류만 만들 수 있고 조직당 정책은 하나 · 정책 전체 크기 최대 25KB(약 25,000자) · 목록을 바꿔 전환하면 기존 정책이 사라짐
   - 해설: 목록에 있는 도메인만 허용하거나 특정 도메인을 막을 수 있습니다. 차단된 도메인으로 초대하면 초대자에게 차단 도메인 메시지가 보이며, SharePoint·OneDrive의 공유 허용/차단 목록은 별개로 관리합니다
3. [처리] 초대를 보낸다
   - 주체: 관리자
   - 위치: 포털 사용자 초대 · API: POST /v1.0/invitations (최소 권한 User.Invite.All)
   - 데이터: invitation (invitedUserEmailAddress · invitedUserDisplayName · inviteRedirectUrl · sendInvitationMessage)
   - 해설: 초대 시 게스트 개체가 만들어지고 초대 메일이 발송됩니다. onmicrosoft.com 기본 도메인 발신 초대 메일은 Exchange Online 발송 한도를 받으므로 많이 보낸다면 사용자 지정 도메인을 고려합니다
4. [처리] 게스트 개체가 대기 상태로 생성됨
   - 주체: Entra ID
   - 데이터: user (userType=Guest) · 동의 상태 PendingAcceptance · 초대 이메일과 같은 연락처(contact) 개체가 있으면 게스트의 proxyAddresses는 비워 둠
   - 해설: 사용자가 초대를 수락하기 전까지 대기 상태로 남습니다
5. [처리] 수락 시 사용할 ID 공급자 순서 결정
   - 주체: Entra ID
   - 위치: 테넌트 간 액세스 설정 › 기본 설정 › Edit inbound defaults › B2B collaboration › 리디렉션 순서(Redemption order) 탭 (Entra ID P1 필요)
   - 데이터: 주 ID 공급자(Entra · 페더레이션) → 대체 ID 공급자(Microsoft 계정 · 이메일 일회용 암호) — 대체 공급자 둘 다 끌 수는 없음. 기본 순서: 관리형 Entra 사용자 → SAML/WS-Fed → Google(gmail.com · googlemail.com) → 기존 Microsoft 계정 → 이메일 일회용 암호(꺼져 있으면 Microsoft 계정 생성). Graph: invitationRedemptionIdentityProviderConfiguration (/beta/policies/crossTenantAccessPolicy/default)
   - 해설: 초대를 수락하는 사용자가 어떤 계정으로 로그인할지 순서가 정해집니다. Microsoft 계정을 끄면 이메일 일회용 암호를 켜 둬야 하고, 이미 Microsoft 계정으로 수락한 게스트는 상환 상태를 초기화해야 새 설정이 적용됩니다. 이메일 일회용 암호는 새 테넌트에서 기본으로 켜져 있습니다
6. [처리] 일반 앱 URL에서 로그인
   - 주체: 사용자
   - 위치: myapps.microsoft.com › 로그인 옵션 › 조직에 로그인 › 조직 도메인 입력
   - 데이터: 테넌트별 엔드포인트로 리디렉션 · 테넌트 지정 직접 링크 예: https://myapps.microsoft.com/?tenantid=<테넌트 ID> · https://entra.microsoft.com/<테넌트 ID>
   - 해설: 공용 URL에서도 게스트가 우리 테넌트로 인증을 시작할 수 있습니다. 직접 링크로 들어와도 처음에는 동의 화면을 거칩니다
7. [판단] 사용자의 홈 ID 공급자가 Microsoft Entra인가?
   - 주체: Entra ID
   - 데이터: 도메인의 주 ID 공급자 매칭 여부 — 관리형(managed) Entra 테넌트의 사용자만 상환에 쓸 수 있고, UPN이 Entra 계정과 개인 Microsoft 계정에 모두 일치하면 사용자가 선택
   - 해설: 일치하지 않으면 대체 ID 공급자가 사용됩니다
   - 예 → 8
   - 아니오 → 9
8. [끝] 홈 Entra에서 인증 후 우리 테넌트로 접근
   - 주체: 사용자
   - 데이터: 홈 테넌트 토큰 → 리소스 테넌트 판정 (신뢰 설정이 있으면 MFA 클레임 인정)
   - 해설: 파트너의 보안 수준을 그대로 활용합니다
9. [끝] 대체 ID 공급자로 인증
   - 주체: 사용자
   - 데이터: Microsoft 계정 또는 이메일 일회용 암호 (Google·SAML/WS-Fed 페더레이션을 구성한 도메인이면 해당 공급자)
   - 해설: 홈이 Entra가 아니면 대체 방식으로 로그인하며, 우리 CA와 MFA 정책이 그대로 적용됩니다. 기존 SSO 세션이 있는 Entra 사용자가 이메일 일회용 암호를 써야 하면 다른 계정 사용을 선택해 사용자 이름을 다시 입력해야 합니다
- 시나리오: 예 :: 홈 Entra 인증으로 우리 테넌트에 접근
- 시나리오: 아니오 :: Entra가 아닌 대체 ID 공급자로 인증

> 교육 포인트: 초대 정책(누가 부르는가), 도메인 제한(누구를 부르는가), 테넌트 간 액세스(어떻게 접근하는가)는 서로 다른 설정입니다.

### L3 · B · 인바운드 · 아웃바운드 · 신뢰 설정 — 적용 우선순위와 충돌 규칙

#### L4 · 설정이 어떤 순서로 평가되고 어떤 제약이 있나

1. [시작] 기본 설정과 조직별 설정이 함께 존재
   - 주체: Entra ID
   - 위치: 테넌트 간 액세스 설정 › 기본 설정 · 조직 설정
   - 데이터: crossTenantAccessPolicy default · partners
   - 해설: 조직 설정은 기본 설정보다 우선합니다
2. [판단] 이 외부 조직에 대한 조직 설정이 있는가?
   - 주체: Entra ID
   - 데이터: partners 목록에 tenantId 존재 여부
   - 해설: 조직 설정이 없으면 기본 설정이 그대로 적용됩니다
   - 예 → 3
   - 아니오 → 4
3. [처리] 조직 설정 적용
   - 주체: Entra ID
   - 위치: 조직 설정 › 인바운드 액세스 · 아웃바운드 액세스 (기본 설정 또는 사용자 지정 설정 선택)
   - 데이터: 인바운드·아웃바운드 각각 독립적으로 사용자 지정 가능 — 기본 설정으로 되돌리면 기존 사용자 지정 설정이 모두 기본값으로 교체됨(확인에서 예 선택)
   - 해설: 방향별로 기본값을 따르거나 조직 전용 규칙을 씁니다
   - 다음 → 5
4. [처리] 기본 설정 적용
   - 주체: Entra ID
   - 데이터: 기본값: B2B 협업 허용 · direct connect 차단 · 신뢰 안 함
   - 해설: 조직별 설정이 없는 모든 외부 조직이 같은 규칙을 받습니다
5. [처리] 사용자·그룹과 앱 설정이 서로 모순되지 않는지 확인
   - 주체: Entra ID
   - 데이터: 인바운드에서 모든 외부 사용자 차단 시 내부 앱도 모두 차단해야 하고, 아웃바운드에서 사용자를 허용하면 앱도 최소 하나는 허용해야 함 (인바운드에서 앱을 모두 차단하면 외부 사용자·그룹도 모두 차단)
   - 해설: 모순된 조합은 저장되지 않고 경고가 뜹니다
6. [처리] 신뢰 설정 평가
   - 주체: Entra ID
   - 데이터: 외부 사용자 토큰의 MFA·준수 기기·하이브리드 조인 클레임 — MFA 클레임이 없으면 홈 테넌트에서 MFA 요구
   - 해설: GDAP로 로그인한 서비스 공급자 기술자는 홈 테넌트에서 항상 MFA를 요구하고 리소스 테넌트가 항상 신뢰합니다. B2B direct connect와 MFA를 요구하는 CA를 함께 쓰려면 파트너의 MFA 클레임 신뢰를 반드시 설정해야 합니다
7. [처리] 우리 CA 정책이 신뢰된 클레임을 소비
   - 주체: Entra ID
   - 위치: 보호 › 조건부 액세스 › 정책 › 권한 부여(MFA 필요 · 준수 기기 필요 등)
   - 데이터: 게스트 또는 외부 사용자 범위 CA 정책의 부여 통제
   - 해설: 신뢰 설정이 있을 때만 파트너의 신호로 부여 통제가 충족됩니다
8. [처리] 필수 예외 앱 허용
   - 주체: 관리자
   - 위치: 아웃바운드(홈 테넌트)·인바운드(리소스 테넌트) › 다른 애플리케이션 추가
   - 데이터: MFA 등록용 Microsoft App Access Panel 0000000c-0000-0000-c000-000000000000 · 사용 약관 d52792f4-ba38-424d-8140-ada5b883f293 · RMS/OME 00000012-0000-0000-c000-000000000000 (인바운드는 UI 한계로 Graph로 설정). 허용 목록 방식이면 My Apps 2793995e-0a7d-40d7-bd35-6968ba142197 · My Profile 8c59ead7-d703-4a27-9e55-c96a0054c8d2 · My Sign-ins 19db86c3-b2b9-44cc-b339-36da233a3be2도 함께 허용
   - 해설: 앱 전체를 막으면 MFA 등록·약관 동의·암호화 메일 읽기가 실패합니다. Graph PATCH는 기존에 설정한 앱 목록을 덮어쓰므로 먼저 GET으로 현재 값을 확인해 함께 보내야 하고, Microsoft 관리 포털 앱 그룹은 포털에서 추가할 수 없어 앱별로 Graph로 지정합니다
9. [끝] 변경 감사와 보호
   - 주체: 로그
   - 위치: 감사 로그 (범주 CrossTenantAccessSettings) · 보호된 작업(Protected actions)
   - 데이터: 설정 변경 기록 · 변경 작업에 CA 보호 적용 가능 · 관리용 사용자 지정 역할도 만들 수 있음
   - 해설: 이 설정은 외부 접근 범위를 바꾸므로 변경 자체도 보호합니다
- 시나리오: 예 :: 외부 조직 설정이 있는 경우의 설정 평가와 감사
- 시나리오: 아니오 :: 외부 조직 설정이 없는 경우의 설정 평가와 감사

> 교육 포인트: 신뢰 설정은 "파트너가 이미 한 검증을 인정"하는 것이고, 접근 허용/차단은 "누가 무엇에 접근하나"입니다. 둘은 서로 다른 효과를 냅니다.

### L3 · C · 테넌트 제한 v2 — 외부 계정 사용 통제

#### L4 · 관리 기기에서 외부 계정 사용을 막는 흐름

1. [시작] 목적: 우리 기기에서 외부 계정 사용을 통제
   - 주체: 관리자
   - 데이터: 알 수 없는 테넌트에서 만든 계정 · 다른 조직이 우리 사용자에게 준 계정 · 선행 조건: Entra ID P1 또는 P2 · 정책 구성 최소 Security Administrator
   - 해설: 인바운드·아웃바운드 설정은 우리 계정에만 적용되므로 외부 계정은 따로 통제해야 합니다. 외부 협업이 필요하면 외부 계정 사용을 막고 B2B 협업으로 유도하세요
2. [처리] 기본 테넌트 제한 정책 만들기
   - 주체: 관리자
   - 위치: 외부 ID › 테넌트 간 액세스 설정 › 기본 설정 › 테넌트 제한 기본값 편집(Edit tenant restrictions defaults) › 정책 만들기(Create policy, Policy ID 옆 링크)
   - 데이터: 테넌트 ID · 정책 ID (복사해 두었다가 Windows·프록시 설정에 사용). 정책 ID는 /crosstenantaccesspolicy/default 가 돌려주는 id 값
   - 해설: 정책 ID는 강제 신호에 넣는 값입니다
3. [처리] 외부 사용자 및 외부 앱 액세스 지정
   - 주체: 관리자
   - 위치: 테넌트 제한 › 외부 사용자 및 그룹 · 외부 애플리케이션 탭 › 액세스 상태 · 적용 대상(모든 외부 애플리케이션 · 외부 애플리케이션 선택)
   - 데이터: 기본값은 개별 사용자·그룹 지정 불가 · 앱 선택은 이름 또는 앱 ID(클라이언트 앱 ID·리소스 앱 ID) 검색
   - 해설: 두 탭 모두에서 차단을 설정해야 외부 앱이 막힙니다. 모든 외부 앱을 막으려면 두 탭에서 Block access와 모든 외부 애플리케이션을, 일부만 막으려면 외부 애플리케이션 선택을 고릅니다
4. [처리] 파트너 예외 추가
   - 주체: 관리자
   - 위치: 조직 설정 › 조직 추가 › 테넌트 제한 › 사용자 지정 설정 › 액세스 허용 (최소 Security Administrator 또는 Conditional Access Administrator)
   - 데이터: 조직별 정책 ID 별도 · 허용할 사용자·그룹·앱 지정 · 조직 설정이 기본 설정보다 우선
   - 해설: 협력사 테넌트만 허용하고 나머지는 막는 식으로 구성합니다. 예를 들어 기본은 차단하되 사용자가 자기 Microsoft 계정으로 Microsoft Learn에 접근하도록 허용할 수 있습니다
5. [판단] 강제 신호를 어떻게 주입할 것인가?
   - 주체: 관리자
   - 해설: 환경에 따라 범용 신호, 프록시 헤더, Windows 장치 정책 중 고릅니다
   - 범용 테넌트 제한 → 6
   - 프록시 헤더 → 7
   - Windows 관리 기기 → 8
6. [처리] 범용 테넌트 제한(Global Secure Access)
   - 주체: 관리자
   - 위치: Global Secure Access › Settings › Session Management › Universal Tenant Restrictions 탭 › "Enable Tenant Restrictions for Microsoft Entra ID and Microsoft Graph" 켜기 (Global Secure Access Administrator 역할)
   - 데이터: OS · 브라우저 · 기기 종류와 무관 · 인증 평면 보호 (데이터 평면은 Microsoft Graph에 한함) · Global Secure Access 클라이언트와 Microsoft 트래픽 프로필로 연결한 사용자에 적용
   - 해설: 프록시 없이 모든 트래픽에 테넌트 제한 신호를 붙입니다
   - 다음 → 9
7. [처리] 회사 프록시에서 헤더 삽입
   - 주체: 관리자
   - 위치: 프록시 설정 — login.live.com · login.microsoft.com · login.microsoftonline.com · login.windows.net 으로 가는 요청에 헤더 삽입
   - 데이터: 헤더 sec-Restrict-Tenant-Access-Policy: <TenantId>:<policyGuid> · 로그인 URL 복호화(break and inspect) 필요 · 인증 평면만 보호 · 예전 restrict-msa 헤더를 login.live.com으로 보내던 설정은 중단해야 충돌하지 않음
   - 해설: 프록시 방식은 데이터 평면까지는 막지 못하고, 복호화를 지원하지 않는 플랫폼에서는 동작하지 않습니다. 그런 플랫폼은 관리·준수 기기 조건부 액세스, 게스트 CA, 아웃바운드 규칙, 앱 동의 제한 같은 다른 통제로 보완합니다
   - 다음 → 9
8. [처리] Windows 관리 기기에 정책 적용 (미리 보기)
   - 주체: 관리자
   - 위치: 그룹 정책 편집기 › 컴퓨터 구성 › 관리 템플릿 › Windows 구성 요소 › Tenant Restrictions › Cloud Policy Details — Microsoft Entra Directory ID에 테넌트 ID, Policy GUID에 정책 ID 입력, 나머지 칸은 비움 [확인 필요: Intune으로 배포할 때의 설정 이름]
   - 데이터: 인증 평면 + 데이터 평면 보호(SharePoint Online · Exchange Online · Microsoft Graph) · 프록시 불필요 · Windows 10/11 최신 업데이트 필요 · .NET 스택 · Chrome · Firefox는 보호되지 않음
   - 해설: 회사 소유 Windows 기기는 리소스 접근 시점에도 정책이 적용됩니다. 동작 확인은 이벤트 뷰어 › 응용 프로그램 및 서비스 로그 › Microsoft › Windows › TenantRestrictions › Operational에서 합니다
9. [끝] 로그인 로그로 확인
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 로그인 로그 · 감사 로그
   - 데이터: 테넌트 제한 v2 정책이 적용된 로그인 · B2B 사용자는 홈·리소스 테넌트 양쪽에 로그 생성 · 서비스 주체 로그인이 TRv2로 차단되면 요청을 받은 테넌트에만 로그가 남음
   - 해설: 어떤 외부 계정 접근이 막혔는지 로그인 로그에서 확인합니다. TRv2를 켠 뒤 Entra 관리 센터가 "Access denied"를 보이면 주소 끝에 ?feature.msaljs=true&exp.msaljsexp=true 를 붙여 접근을 복구합니다
- 시나리오: 범용 테넌트 제한 :: 범용 테넌트 제한으로 신호를 주입해 로그 확인
- 시나리오: 프록시 헤더 :: 회사 프록시 헤더로 신호를 주입해 로그 확인
- 시나리오: Windows 관리 기기 :: Windows 관리 기기 정책으로 신호를 주입해 확인

> 교육 포인트: 테넌트 제한 v2는 "우리 사용자가 외부 계정을 쓰는 것"을 통제하고, 인바운드·아웃바운드 설정과는 독립적으로 동작합니다. 외부 협업은 B2B로 유도합니다.
>
> 주의: 프록시는 로그인 도메인 복호화가 필요하고 익명 접근(Teams 회의 참여 등)은 막지 못합니다.
