## L2 · 인증 방법 — MFA · 패스키 · Windows Hello

- 설정(Control Plane): 인증 방법 정책 (방법별 사용 · 대상 그룹) | 인증 강도 · 등록 캠페인 · 임시 액세스 패스(TAP) 설정
- 강제(Enforcement): Entra ID 로그인 단계 (방법 등록 · 인증) | 조건부 액세스 "인증 강도 필요" 컨트롤이 토큰 발급 전 평가
- 증적(Evidence): SigninLogs AuthenticationDetails | GET /v1.0/auditLogs/signIns · AuditLogs (방법 정책 변경)
- 메뉴(Admin Center): Entra ID > 인증 방법 (Authentication methods) > 정책 · 인증 강도 · 등록 캠페인
- 라이선스(License): 인증 방법 정책 · TAP · 등록 캠페인의 라이선스 요건은 [확인 필요: 고객 라이선스] | 인증 강도는 조건부 액세스 기능이라 Entra ID P1 필요

### L3 · 0 · 기능 상태 전이 — 정책 미설정 → 방법 사용 · 인증 강도 생성 → 조건부 액세스가 강도를 강제

#### L4 · ⓪ 비활성 — 방법 정책과 인증 강도를 손대지 않은 기본 상태

1. [시작] 사용자가 암호로 로그인 요청
   - 주체: 사용자
   - 위치: 앱의 로그인 화면 → login.microsoftonline.com/{tenant}/oauth2/v2.0/authorize
   - 데이터: 요청 파라미터 client_id · scope · 사용자 UPN · 이 시점에는 어떤 조건부 액세스 평가도 방법의 강도를 따지지 않음
   - 해설: 사용자가 사용자 이름과 암호를 입력해 로그인을 시작합니다
2. [처리] 인증 방법 정책 확인 — 강한 방법을 대상 그룹에 열지 않음
   - 주체: Entra ID
   - 위치: Entra ID › 인증 방법 (Authentication methods) › 정책 (Policies) — 문서에 따라 Entra ID › Security › Authentication methods › Policies로도 표기 · 수정은 최소 Authentication Policy Administrator
   - 데이터: authenticationMethodsPolicy 안의 방법별 구성 state (enabled · disabled) · includeTargets · excludeTargets [확인 필요: 테넌트 기본값은 Microsoft 관리 기본 사용 설정에 따라 다름] · 정책은 통합 등록 환경(combined registration)만 인식하며, 레거시 MFA·SSPR 정책에서 방법을 켠 사용자도 그 방법을 쓸 수 있음(어느 한 정책에서라도 켜져 있으면 사용 가능)
   - 해설: 패스키나 Authenticator 같은 방법이 이 사용자 그룹에 열려 있지 않으면 등록할 수도 없습니다. 방법을 막으려면 모든 정책에서 꺼야 합니다
3. [처리] 사용자 등록 상태 확인 — 약한 방법만 등록됨
   - 주체: Entra ID
   - 위치: 사용자 › {사용자} › 인증 방법 (Graph: GET /v1.0/users/{id}/authentication/methods) — 사용 가능한 방법이 먼저, 사용 불가 방법이 뒤에 표시
   - 데이터: 등록된 방법 목록 (암호 · 전화 번호 등) · 만료된 TAP이나 증명에 실패한 FIDO2 키처럼 사용 불가가 된 방법은 사유와 함께 표시
   - 해설: 등록된 방법이 암호나 SMS 정도라면 피싱에 취약한 요소만 남아 있습니다
4. [처리] 요구 인증 강도 없음 — 어떤 방법이든 통과
   - 주체: Entra ID
   - 위치: Entra ID › 조건부 액세스 › 정책 (인증 강도를 요구하는 정책 0개)
   - 데이터: grantControls.authenticationStrength 설정 없음 · 인증 강도는 조건부 액세스 기능이라 Entra ID P1 필요
   - 해설: 인증 강도를 요구하는 조건부 액세스 정책이 없어서 방법의 강도를 따지지 않습니다
5. [끝] 토큰 발급 — 피싱 가능 방법으로도 접근 허용
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 로그인 로그 › 인증 세부 정보 (Authentication Details)
   - 데이터: SigninLogs AuthenticationDetails의 authenticationMethod = Password · SMS 등 · 요구 사항(Requirement) 열에 인증 강도 이름이 없음
   - 해설: 약한 방법으로 인증해도 토큰이 발급되고, 로그에는 사용한 방법만 남습니다

#### L4 · ① 구성 — 관리자가 방법을 켜고 인증 강도를 만든다

1. [시작] 관리자가 Entra Admin Center에 로그인
   - 주체: 관리자
   - 위치: entra.microsoft.com — 방법 정책 수정은 Authentication Policy Administrator 이상, 사용자 지정 인증 강도 생성은 Security Administrator 이상(패스키 문서는 Conditional Access Administrator로 표기), 사용자에게 TAP 발급은 Authentication Administrator 이상
   - 데이터: 역할 할당 (roleAssignments) · Graph로 방법 정책을 고칠 때는 Policy.Read.All · Policy.ReadWrite.AuthenticationMethod 권한 동의 · 인증 강도는 Entra ID P1, 패스키(FIDO2)는 모든 Entra ID 에디션에서 추가 라이선스 없이 사용
   - 해설: 방법 정책을 고치려면 인증 정책 관리자 역할이 필요합니다
2. [처리] 인증 방법 정책 열기 — 방법 목록 확인
   - 주체: 관리자
   - 위치: Entra ID › 인증 방법 (Authentication methods) › 정책 (Policies) — 문서에 따라 Entra ID › Security › Authentication methods › Policies로도 표기
   - 데이터: authenticationMethodsPolicy (GET https://graph.microsoft.com/v1.0/policies/authenticationMethodsPolicy) · 정책 크기 한도 20 KB라 대상 그룹이 많으면 저장이 안 될 수 있어 방법별로 그룹 하나로 통합 권장 · 개별 사용자 지정은 더 이상 지원하지 않고 그룹으로 지정
   - 해설: 방법별 사용 여부와 대상 그룹을 한 정책에서 관리합니다. 레거시 MFA·SSPR 정책에서의 방법 관리는 2025년 9월 30일부터 불가하므로 인증 방법 정책으로 이전(관리 마이그레이션: Pre-migration → Migration in Progress → Migration Complete)합니다
3. [처리] 패스키(FIDO2) 사용 — 대상 그룹 · 패스키 프로필
   - 주체: 관리자
   - 위치: 정책 › 패스키(FIDO2) › 사용 › 대상 선택 · 구성 탭 › 자체 서비스 설정 허용 (Allow self-service set up) · 패스키 프로필 추가 (+ Add passkey profile) › 증명 적용 (Enforce attestation) · 패스키 유형 (Passkey types: Device-bound · Synced) · 키 제한 적용 (Enforce key restrictions, AAGUID 허용/차단)
   - 데이터: fido2AuthenticationMethodConfiguration (state · includeTargets · excludeTargets · isSelfServiceRegistrationAllowed · keyRestrictions) · 패스키 프로필은 한 번 옵트인하면 되돌릴 수 없고 기본 프로필 포함 최대 3개 · 사용자가 여러 프로필 대상이면 그중 하나만 만족해도 허용 · 제외 그룹은 포함 그룹보다 우선 · 증명 적용은 등록 시점에만 적용
   - 해설: 패스키를 허용할 그룹과 장치 고정형·동기화형 같은 종류를 정합니다. 자체 서비스 설정을 No로 두면 패스키가 켜져 있어도 내 보안 정보에서 등록할 수 없습니다. 게스트 사용자는 패스키 등록을 지원하지 않습니다
4. [처리] Microsoft Authenticator 사용 — 푸시 인증 모드
   - 주체: 관리자
   - 위치: 정책 › Microsoft Authenticator › 사용 · 구성 (인증 모드 Any · Push · Passwordless · 앱 이름과 위치 표시)
   - 데이터: microsoftAuthenticatorAuthenticationMethodConfiguration · featureSettings.displayAppInformationRequiredState · displayLocationInformationRequiredState (기능별로 단일 대상 그룹만 지정) · 인증 모드는 그룹마다 기본값 Any(푸시 + 암호 없는 휴대폰 로그인)이며 Authenticator는 모드가 Any 또는 Push일 때만 통합 등록으로 등록 가능
   - 해설: 앱 이름과 위치를 보여 줘서 실수 승인을 줄이는 옵션도 여기서 켭니다. Authenticator를 사용으로 켠 사용자에게만 앱 이름·위치가 보입니다
5. [처리] 임시 액세스 패스(TAP) 사용 — 수명 · 일회용 설정
   - 주체: 관리자
   - 위치: 정책 › 임시 액세스 패스 › 사용 › 대상 포함/제외 · 구성 (최소 · 최대 · 기본 수명 · 길이 · 일회용) · 저장
   - 데이터: temporaryAccessPassAuthenticationMethodConfiguration (기본: 최소 1시간 · 최대 8시간 · 기본 수명 1시간 · 길이 8 · 일회용 False / 허용 범위 수명 10~43,200분(30일), 길이 8~48자) · 일회용을 True로 강제하면 테넌트의 모든 TAP이 일회용
   - 해설: 방법이 없는 사용자가 패스키를 처음 등록할 때 쓰는 시간 제한 코드를 허용합니다. TAP은 대상 정책에 포함된 사용자만 로그인에 쓸 수 있고, 발급은 정책에 없는 사용자에게도 가능합니다
6. [처리] 인증 강도 만들기 — 허용 조합 묶음 선택
   - 주체: 관리자
   - 위치: Entra ID › 인증 방법 › 인증 강도 (Authentication strengths) › 새 인증 강도 (New authentication strength) (이름 · 설명 · 허용 방법 선택 · 다음 · 검토 · 만들기) — 예: 현장 직원에게 QR 코드만 허용하려면 단일 요소 (Single factor authentication) 아래 QR 코드 선택
   - 데이터: authenticationStrengthPolicy.allowedCombinations (사용자 지정은 최대 15개) · POST /beta/identity/conditionalAccess/authenticationStrength/policies · 패스키는 고급 옵션(Advanced options)에서 AAGUID, 인증서 기반 인증은 발급자(최대 5개)·정책 OID(최대 5개)로 더 좁힐 수 있음
   - 해설: 기본 제공 강도로 부족하면 허용할 방법 조합을 직접 묶어 둡니다. 정책이 참조하는 사용자 지정 강도는 삭제할 수 없고 수정 시 확인이 필요합니다
7. [처리] 등록 캠페인 설정 — 더 강한 방법 등록 유도
   - 주체: 관리자
   - 위치: Entra ID › 인증 방법 › 등록 캠페인 (Registration campaign) › 편집 (Edit) (상태 Enabled · Microsoft managed · Disabled · 대상 방법 Authenticator/Passkey · 연기 일수 0~14 · 대상 포함/제외) — 최소 Authentication Policy Administrator
   - 데이터: authenticationMethodsPolicy.registrationEnforcement.authenticationMethodsRegistrationCampaign (state enabled·disabled·default · snoozeDurationInDays 0~14 기본 1 · enforceRegistrationAfterAllowedSnoozes 기본 true · includeTargets.targetedAuthenticationMethod = microsoftAuthenticator 또는 fido2) · 캠페인은 한 번에 방법 하나만 대상 · 사전 조건: Authenticator는 인증 모드 Any/Push, 패스키는 자체 서비스 설정 허용
   - 해설: 로그인 때 패스키나 Authenticator 등록을 안내하도록 대상 그룹과 연기 한도를 정합니다. Microsoft managed 상태에서는 방법과 연기 설정을 Microsoft가 정하고 포함·제외 대상만 직접 지정합니다
8. [끝] 저장 — 사용자 등록 대기 (아직 강제 아님)
   - 주체: 관리자
   - 위치: 각 설정 화면의 저장 버튼
   - 데이터: AuditLogs의 정책 변경 활동 — 방법 정책은 Authentication Methods Policy Update, 인증 강도는 Authentication Strength Policy Create · Update · Delete (ApplicationManagement 범주) · 등록 캠페인 변경이 어느 활동으로 남는지는 [확인 필요: 활동 이름]
   - 해설: 저장하면 사용자가 방법을 등록할 수 있지만 강제는 조건부 액세스가 맡습니다

#### L4 · ② 활성 — 조건부 액세스가 인증 강도를 요구하고 로그인이 검증된다

1. [시작] 사용자가 보호 대상 앱에 로그인
   - 주체: 사용자
   - 위치: 앱 로그인 화면 (예: 관리 포털) → /authorize
   - 데이터: client_id · 사용자 · 기기 · IP · 조건부 액세스 정책은 앱·사용자·조건이 모두 맞을 때만 인증 강도를 요구
   - 해설: 인증 강도를 요구하는 조건부 액세스 정책이 걸린 앱에 접근합니다
2. [처리] 1차 인증 — 암호 등 초기 인증
   - 주체: 사용자
   - 위치: Entra 로그인 화면
   - 데이터: SigninLogs AuthenticationDetails 첫 단계 (authenticationMethod = Password)
   - 해설: 정책은 1차 인증 뒤에 평가되므로 인증 강도가 초기 인증을 막지는 않습니다
3. [처리] 조건부 액세스가 "인증 강도 필요" 매칭
   - 주체: Entra ID
   - 위치: 조건부 액세스 평가 엔진 (서비스 내부) — 정책의 Entra ID › 조건부 액세스 › 정책 › 액세스 제어 › 권한 부여 › 인증 강도 필요
   - 데이터: grantControls.authenticationStrength (예: 피싱 방지 MFA 강도) · 여러 강도 정책이 적용되면 모든 강도를 충족해야 하고, 강도가 서로 다르면 여러 방법을 써야 할 수 있음
   - 해설: 사용자 · 앱 · 조건이 맞는 정책에서 필요한 강도를 가져옵니다
4. [판단] 이 세션이 이미 강도를 충족했는가?
   - 주체: Entra ID
   - 위치: 토큰 클레임 · 로그인 로그 인증 세부 정보
   - 데이터: 토큰 클레임에 남은 이전 인증 결과 (AuthenticationDetails의 authenticationMethod = Previously satisfied 또는 Satisfied by token)
   - 해설: 같은 세션에서 이미 허용 조합으로 인증했다면 다시 묻지 않습니다. 예를 들어 암호+문자 메시지로 로그인했다면 MFA 강도 리소스는 추가 프롬프트가 없지만 피싱 방지 MFA 강도 리소스에서는 새 방법을 요구합니다
   - 예 → 8
   - 아니오 → 5
5. [판단] 허용 조합에 해당하는 방법을 쓸 수 있는가?
   - 주체: Entra ID
   - 위치: 사용자 › {사용자} › 인증 방법 (등록 목록) · 인증 방법 정책
   - 데이터: 사용자 등록 방법 ∩ 방법 정책이 켠 방법 ∩ 강도의 허용 조합 · 사용자는 강도를 충족하는 방법을 하나만 등록하면 되며, 등록하지 않았다면 통합 등록의 중단 모드(interrupt mode)로 이동 · 강도에 사용자가 등록·사용할 수 있는 방법이 없으면 로그인 차단 · Authenticator 휴대폰 로그인 · 인증서 기반 인증 · Windows Hello for Business는 중단 모드에서 등록할 수 없고 패스키는 관리 모드로 미리 등록해야 함
   - 해설: 사용자가 등록했고 방법 정책에서 켜져 있으며 강도가 허용하는 방법이 필요합니다. 신규 직원 부트스트랩은 "보안 정보 등록" 사용자 작업을 대상으로 TAP을 허용하는 별도 강도·정책으로 풀 수 있습니다
   - 예 → 6
   - 아니오 → [차단] 차단 — 허용 방법 등록 필요 (TAP으로 부트스트랩)
6. [처리] 사용자가 허용된 방법으로 추가 인증
   - 주체: 사용자
   - 위치: 로그인 옵션 (Sign-in options)에서 방법 선택 (패스키 · Windows Hello for Business · 인증서 기반 인증)
   - 데이터: FIDO2 서명 응답 또는 Hello 자격 증명 · 지원되지 않는 보안 키로 로그인하면 "You can't get there from here" 메시지가 나오고 세션을 다시 시작해야 함 · 인증서 기반 인증은 브라우저 세션당 인증서 하나만 사용
   - 해설: 암호로 시작했다면 로그인 옵션에서 강도가 요구하는 방법을 직접 고릅니다
7. [처리] 자격 증명 검증 — 방법별 검증 수행
   - 주체: Entra ID
   - 위치: 인증 서비스 (서비스 내부)
   - 데이터: 등록된 공개 키 · 챌린지 서명 검증 결과 · 패스키에 AAGUID 키 제한이 걸려 있으면 허용되지 않은 모델은 등록뿐 아니라 로그인에도 쓸 수 없음
   - 해설: 토큰을 내주기 전에 선택한 방법의 자격 증명을 검증합니다
8. [처리] 정책 충족 확인 후 토큰 발급
   - 주체: Entra ID
   - 위치: 토큰 엔드포인트 (서비스 내부)
   - 데이터: 액세스 · 갱신 토큰 (인증 방법 클레임 amr 포함, 예: ["mfa","rsa","pwd"] — mfa는 MFA 사용을 뜻하며 다른 인증 방법을 포함) · 강도 정책의 requirementsSatisfied 속성이 MFA 클레임 부여 여부를 나타냄(mfa 또는 none)
   - 해설: 인증 강도를 충족한 요청에만 토큰이 발급됩니다
9. [끝] 사용한 방법과 결과가 로그인 로그에 기록
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 로그인 로그 › 인증 세부 정보 (Authentication Details) 탭의 요구 사항(Requirement) 열 · 조건부 액세스 탭 › 정책 이름 › 권한 부여 컨트롤 (Grant Controls)
   - 데이터: SigninLogs AuthenticationDetails · appliedConditionalAccessPolicies · Requirement 열에 적용된 인증 강도 정책 이름이 표시
   - 해설: 어떤 방법으로 어떤 정책을 충족했는지 로그인 로그에서 확인합니다
- 시나리오: 예 :: 이미 강도를 충족해 바로 토큰 발급
- 시나리오: 아니오 ▸ 예 :: 허용 방법으로 검증 후 토큰 발급
- 시나리오: 아니오 ▸ 아니오 :: 허용 조합 방법이 없어 로그인 차단

> 교육 포인트: 방법 정책은 "무엇을 쓸 수 있나", 인증 강도는 "무엇이면 충분한가"입니다. 강제는 조건부 액세스의 권한 부여 컨트롤에서 일어납니다.

> 주의: 인증 강도는 초기 인증을 제한하지 않고, 조건부 액세스는 1차 인증 뒤에 평가됩니다. 암호로 로그인한 사용자가 Windows Hello for Business를 요구받으면 세션을 다시 시작해 로그인 옵션에서 방법을 골라야 합니다.

### L3 · A · 인증 강도 — 어떤 방법 조합이면 충분한가

#### L4 · 기본 제공 · 사용자 지정 강도 → 허용 조합 대조 → 충족 판정

1. [시작] 로그인이 "인증 강도 필요" 정책에 매칭
   - 주체: Entra ID
   - 위치: Entra ID › 조건부 액세스 › 정책 › 액세스 제어 › 권한 부여 › 인증 강도 필요 (Require authentication strength)
   - 데이터: conditionalAccessPolicy.grantControls.authenticationStrength · 필요 라이선스는 Entra ID P1 · 같은 정책에서 "다단계 인증 필요"와 함께 쓸 수 없음
   - 해설: 권한 부여 컨트롤이 어떤 강도를 요구하는지에서 시작합니다. 민감한 작업(인증 컨텍스트), 위험 사용자, 외부 네트워크, 게스트 접근 같은 시나리오별로 다른 강도를 걸 수 있습니다
2. [판단] 어떤 종류의 강도인가?
   - 주체: Entra ID
   - 위치: Entra ID › 인증 방법 › 인증 강도 (정책 종류 열)
   - 데이터: authenticationStrengthPolicy.policyType (builtIn 또는 custom) · 목록은 GET /beta/identity/conditionalAccess/authenticationStrength/policies?$filter=policyType eq 'builtIn'으로 조회
   - 해설: 기본 제공 세 가지 또는 관리자가 만든 사용자 지정 강도(최대 15개) 중 하나입니다
   - 기본 제공 → 3
   - 사용자 지정 → 4
3. [처리] 기본 제공 강도 — MFA · 암호 없는 MFA · 피싱 방지 MFA
   - 주체: Entra ID
   - 위치: 인증 강도 목록의 Multifactor authentication strength · Passwordless MFA strength · Phishing-resistant MFA strength
   - 데이터: Microsoft가 정의한 고정 조합 (수정 불가, 새 방법이 나오면 Microsoft가 갱신) · 세 강도 모두 FIDO2 보안 키 · Windows Hello for Business(또는 플랫폼 자격 증명) · 인증서 기반 인증(다중 요소) 허용 · MFA 강도와 암호 없는 MFA는 Authenticator 휴대폰 로그인도 허용 · MFA 강도만 TAP(일회용·다회용) · 암호 + 보유 요소(문자 · 음성 · 푸시 · OATH) · 페더레이션 조합 허용 · 어느 강도에도 없는 방법은 암호 단독 · SMS 로그인 · 인증서 단일 요소 · QR 코드 · 페더레이션 단일 요소
   - 해설: 피싱 방지 MFA는 Windows Hello · FIDO2 · 인증서 기반 인증(다중 요소)만 허용합니다. MFA 강도는 "다단계 인증 필요" 컨트롤과 같은 조합 집합입니다
   - 다음 → 5
4. [처리] 사용자 지정 강도 — 관리자가 고른 조합
   - 주체: 관리자
   - 위치: 인증 강도 › 새 인증 강도 · 단일 요소 아래 QR 코드 같은 방법 선택 · 패스키는 고급 옵션 › AAGUID 추가 · 인증서 기반 인증은 고급 옵션 › 발급자 · 정책 OID
   - 데이터: allowedCombinations 예: fido2 · windowsHelloForBusiness · x509CertificateMultiFactor · qrCodePin (authenticationMethodModes 열거형 값, qrCodePin은 Prefer: include-unknown-enum-members 헤더 필요) · POST /beta/identity/conditionalAccess/authenticationStrength/policies · 인증서 발급자(SKI)·정책 OID는 각각 최대 5개 · Email one-time pass(Guest)는 조합에 쓸 수 없음 · 생성은 최소 Security Administrator
   - 해설: 현장 직원에게 QR 코드 로그인만 허용하는 식으로 조합을 직접 정합니다
   - 다음 → 5
5. [처리] 허용 조합 집합 로드 — 하나만 충족하면 됨
   - 주체: Entra ID
   - 위치: 인증 강도 정책 평가 (서비스 내부)
   - 데이터: 허용 조합 목록 (예: FIDO2 보안 키 / Hello 또는 플랫폼 자격 증명 / CBA 다중 요소) · 조합 중 하나로 인증하면 충족
   - 해설: 목록의 조합 중 어느 하나로 인증하면 강도를 충족한 것으로 봅니다. 여러 강도 정책이 함께 적용되면 모든 강도를 충족해야 하므로 방법 집합이 다르면 방법을 여러 개 써야 합니다
6. [판단] 해당 방법이 방법 정책에서 켜져 있는가?
   - 주체: Entra ID
   - 위치: Entra ID › 인증 방법 › 정책
   - 데이터: 방법 구성 state = enabled ∩ includeTargets에 사용자 포함 · 사용자가 방법 정책이나 레거시 MFA 설정 중 한쪽에서만 켜져 있어도 로그인에 쓸 수 있음
   - 해설: 강도가 허용해도 방법 정책에서 꺼져 있거나 대상이 아니면 쓸 수 없습니다. 예를 들어 Authenticator 모드를 Any로 열어 두고 민감 앱에만 암호 없는 MFA 강도를 걸 수 있습니다
   - 예 → 7
   - 아니오 → [차단] 차단 — 방법 정책에서 해당 방법 비활성
7. [처리] 사용자가 허용 조합 중 하나로 인증
   - 주체: 사용자
   - 위치: 로그인 화면 › 로그인 옵션
   - 데이터: 선택한 방법의 자격 증명 · Windows Hello for Business가 1차 인증이 아니면 자동 프롬프트가 없어 세션을 다시 시작해 로그인 옵션에서 직접 선택해야 함
   - 해설: 사용자가 허용된 조합 가운데 하나를 골라 인증을 마칩니다
8. [처리] 충족 결과를 세션에 반영 — 재사용 가능
   - 주체: Entra ID
   - 위치: 세션 토큰 (서비스 내부)
   - 데이터: 토큰에 남는 인증 결과 (이후 같은 강도 요구에는 Previously satisfied) · 같은 세션 안에서는 이전에 쓴 방법이 새 강도를 충족하는지만 다시 평가
   - 해설: 같은 세션의 다음 요구에서는 다시 묻지 않고 이전 충족 결과를 씁니다
9. [끝] 강도 충족 — 토큰 발급과 기록
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 로그인 로그 › 인증 세부 정보 · 조건부 액세스 탭
   - 데이터: SigninLogs AuthenticationDetails · appliedConditionalAccessPolicies · 요구 사항(Requirement) 열에 강도 이름 · 정책 변경은 감사 로그의 Authentication Strength Policy Create · Update · Delete
   - 해설: 충족한 방법과 정책 결과가 로그인 로그에 남습니다
- 시나리오: 기본 제공 ▸ 예 :: 기본 제공 강도를 방법 정책이 허용해 충족
- 시나리오: 기본 제공 ▸ 아니오 :: 기본 제공 강도인데 방법이 꺼져 있어 차단
- 시나리오: 사용자 지정 ▸ 예 :: 사용자 지정 강도를 방법 정책이 허용해 충족
- 시나리오: 사용자 지정 ▸ 아니오 :: 사용자 지정 강도인데 방법이 꺼져 있어 차단

### L3 · B · 등록 캠페인 · TAP — 강한 방법을 등록시키는 두 경로

#### L4 · MFA 가능 사용자는 캠페인으로 유도 → 방법 없는 사용자는 TAP으로 부트스트랩

1. [시작] 사용자가 대화형 로그인
   - 주체: 사용자
   - 위치: Entra 로그인 화면
   - 데이터: 로그인 요청 · 사용자 등록 방법 · 보안 정보 등록을 제한하는 조건부 액세스 정책이 있으면 그 정책이 먼저 적용됨
   - 해설: 등록 유도는 사용자가 MFA를 마치는 대화형 로그인 중에 일어납니다
2. [판단] MFA에 쓸 수 있는 방법이 이미 있는가?
   - 주체: Entra ID
   - 위치: 사용자 › {사용자} › 인증 방법 (Graph: GET /v1.0/users/{id}/authentication/methods)
   - 데이터: /users/{id}/authentication/methods 등록 목록 · 사용 불가(예: 만료된 TAP)로 표시된 방법은 쓸 수 없음
   - 해설: 방법이 있으면 캠페인으로 유도하고, 하나도 없으면 TAP 같은 우회 경로가 필요합니다
   - 예 → 3
   - 아니오 → 8
3. [판단] 캠페인 대상이고 자격 조건을 충족하는가?
   - 주체: Entra ID
   - 위치: Entra ID › 인증 방법 › 등록 캠페인
   - 데이터: 상태(Enabled · Microsoft managed) · 대상 그룹 · 방법 정책 사용 · Authenticator 푸시 미등록 · Microsoft managed Authenticator 캠페인은 문자·음성으로 MFA한 사용자만 대상이고 Enabled는 어떤 MFA 방법이든 대상 · 패스키 캠페인은 Microsoft managed에서 적합한 패스키 프로필에 속한 사용자만, Enabled에서는 모든 패스키 프로필 사용자 · Authenticator 모드가 Passwordless면 대상 제외 · 패스키는 OS·브라우저 조합별로 로컬 패스키 유무를 평가하며 Linux 사용자는 안내받지 않음
   - 해설: 대상 그룹이면서 목표 방법을 아직 갖지 않은 사용자만 안내 대상입니다
   - 예 → 4
   - 아니오 → [끝] 안내 없음 — 정상 로그인 진행
4. [처리] 등록 안내 화면 표시 — 지금 설정 또는 연기
   - 주체: Entra ID
   - 위치: 로그인 중 등록 안내 화면 (다음 · 지금은 건너뛰기 Skip for now)
   - 데이터: 목표 방법 (Authenticator 또는 패스키) · 연기 한도 · 보안 기본값이나 SSPR 같은 다른 기능도 별도로 등록을 요구할 수 있음
   - 해설: 등록을 안내하는 화면에서 사용자가 바로 설정할지 미룰지 고릅니다
5. [판단] 사용자가 연기를 선택했는가?
   - 주체: 사용자
   - 위치: 안내 화면의 Skip for now

   - 해설: 연기 횟수 제한을 켜 두면 일정 횟수 뒤에는 등록이 필수가 됩니다

   - 주체: 사용자
   - 위치: 내 보안 정보 (mysignins.microsoft.com/security-info)
   - 데이터: 새 인증 방법 (패스키 · Microsoft Authenticator) · 패스키 등록 전 최근 5분 이내 MFA 완료 필요 · 패스키는 이름 지정 후 완료 · 패스키 자체 서비스 설정(Allow self-service set up)이 No이면 등록 불가
   - 해설: 안내 화면에서 이어지는 등록 절차를 마치면 강한 방법이 추가됩니다
7. [끝] 등록 기록 — 인증 강도 충족 가능
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 감사 로그 (UserManagement 범주)
   - 데이터: AuditLogs 방법 등록 활동 — 문서의 인증 방법 감사 활동 목록에 User registered security info · User registered all required security info가 있음 [확인 필요: 캠페인 등록 시 실제 기록 이름]
   - 해설: 등록이 끝나면 이후 인증 강도 정책을 충족할 수 있습니다
8. [처리] 관리자가 TAP 발급 — 방법이 없는 사용자용
   - 주체: 관리자
   - 위치: Entra ID › 사용자 › {사용자} › 인증 방법 › 인증 방법 추가 (Add authentication method) › 임시 액세스 패스 (활성화 시간 · 기간) — 최소 Authentication Administrator (관리자 계정용은 Privileged Authentication Administrator), 본인 TAP은 발급 불가
   - 데이터: temporaryAccessPassMethod (isUsableOnce · lifetimeInMinutes 10~43,200 · startDateTime) — 코드는 발급 직후 한 번만 표시 · PowerShell New-MgUserAuthenticationTemporaryAccessPassMethod -UserId <UPN> -BodyParameter · 사용자당 TAP은 하나이고 새로 만들면 기존 것을 덮어씀 · 내부 게스트는 가능하지만 외부 게스트는 오류
   - 해설: Authentication Administrator 이상이 멤버 사용자에게 시간 제한 코드를 만들어 전달합니다. TAP으로 로그인하려면 사용자가 방법 정책의 TAP 대상에 포함돼 있어야 합니다. Global Reader는 코드 없이 TAP 세부 정보만 볼 수 있습니다
9. [처리] 사용자가 TAP으로 로그인해 패스키 등록
   - 주체: 사용자
   - 위치: 로그인 화면 › TAP 입력 → 내 보안 정보 (mysignins.microsoft.com/security-info)
   - 데이터: TAP 로그인 세션 · 토큰 수명은 TAP 만료 시각으로 제한 · 페더레이션 도메인에서도 TAP이 우선해 Entra ID에서 인증이 끝남 · SSPR 또는 ID Protection MFA 등록 정책 대상자는 브라우저에서 중단 모드 등록으로 넘어가는데 이 경험은 FIDO2·휴대폰 로그인 등록을 지원하지 않음 · NPS 확장과 AD FS 어댑터에서는 TAP 사용 불가
   - 해설: 일회용 TAP이면 로그인 후 10분 안에 패스키 등록을 끝내야 합니다. 다회용 TAP은 이 제한이 없고 TAP 추가·만료는 복제에 몇 분 걸릴 수 있습니다
10. [끝] 암호 없는 방법 확보 — TAP 만료
    - 주체: 로그
    - 위치: 사용자 › {사용자} › 인증 방법 (세부 정보 열에 TAP 만료 시각 · 만료된 TAP은 삭제 가능)
    - 데이터: 사용자 인증 방법에 패스키 추가 · TAP은 사용 불가로 표시 (methodUsabilityReason = Expired · OneTimeUsed) · 만료·삭제된 TAP은 대화형·비대화형 인증 모두 불가
    - 해설: 이제 TAP 없이 패스키로 로그인하고 강한 인증 강도도 충족합니다. TAP 만료가 이미 만들어진 세션을 소급해 끊지는 않으므로 로그인 빈도 정책으로 접근 시간을 제한하고, 분실한 방법을 대체하는 경우 이전 방법은 삭제하도록 안내합니다
- 시나리오: 예 ▸ 예 ▸ 예 :: 이미 방법이 있고 캠페인 안내를 연기
- 시나리오: 예 ▸ 예 ▸ 아니오 :: 이미 방법이 있고 안내에 따라 등록해 기록
- 시나리오: 예 ▸ 아니오 :: 방법은 있으나 캠페인 대상이 아니라 안내 없음
- 시나리오: 아니오 :: 방법이 없어 TAP으로 패스키 등록해 암호 없는 방법 확보

> 교육 포인트: TAP은 "방법이 하나도 없는 사용자"의 첫 등록용입니다. TAP은 MFA 강도는 충족하지만 암호 없는 MFA나 피싱 방지 강도는 충족하지 못합니다.
>
> 주의: 등록 정보 업데이트를 제한하는 조건부 액세스 정책(예: 내부 네트워크에서만)이 있으면 그 조건을 통과한 사용자에게만 등록 안내가 뜹니다. 외부 게스트에는 TAP을 만들 수 없습니다.
