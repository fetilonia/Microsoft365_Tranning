## L2 · 애플리케이션 프록시 — 사내 웹 앱 게시

- 설정(Control Plane): 외부 URL · 내부 URL · 사전 인증 · 커넥터 그룹 | 사용자·그룹 할당 · SSO 방식 (IWA/KCD 등)
- 강제(Enforcement): Application Proxy 서비스 (사전 인증 · 조건부 액세스) | 커넥터 → 내부 웹 앱 (아웃바운드 전용)
- 증적(Evidence): 로그인 로그 (앱 접근 · 조건부 액세스 결과) | 커넥터 서버 이벤트 로그 (Microsoft Entra private network connector)
- 메뉴(Admin Center): 애플리케이션 > 엔터프라이즈 앱 > 애플리케이션 프록시
- 라이선스(License): Entra ID P1 또는 P2 필요, 커넥터는 Private Access와 같은 것을 사용 [확인 필요: 고객 라이선스]

### L3 · 0 · 기능 상태 전이 — 인바운드 포트 · DMZ 노출 → 커넥터 게시 → 사전 인증 후 접근

#### L4 · ⓪ 비활성 — 사내 웹 앱을 인바운드 포트와 DMZ 프록시로 연다

1. [시작] 외부 직원이 사내 웹 앱에 접속하려 한다
   - 주체: 사용자
   - 위치: 인터넷 → 회사 공개 주소 (또는 VPN 클라이언트)
   - 데이터: 사내 웹 앱 URL · 사용자 기기 · VPN을 쓰면 VPN 클라이언트 배포·구성이 필요
   - 해설: 재택·출장 직원이 사내 전용 웹 앱을 써야 하는 상황입니다. 기존 방식은 VPN이나 경계(DMZ) 리버스 프록시로 이 연결을 받습니다
2. [처리] 방화벽 인바운드 포트와 DMZ 리버스 프록시로 노출
   - 주체: 온프레미스
   - 위치: 경계 방화벽 · DMZ 서버 (또는 VPN 게이트웨이)
   - 데이터: 외부에서 들어오는 인바운드 443 개방 · DMZ 서버 패치 · 포트 모니터링 부담 · DMZ의 도메인 가입 서버가 외부 공격에 노출될 수 있음
   - 해설: 외부 연결을 받으려면 인바운드 포트와 DMZ 장비를 직접 운영해야 합니다. 하드웨어 비용과 지속적인 보안 패치·포트 감시가 따라옵니다
3. [처리] 인증이 엣지 또는 앱 서버에서 처리된다
   - 주체: 온프레미스
   - 위치: DMZ 서버 · 웹 앱 자체 로그인
   - 데이터: 앱 자체 인증 (Entra 조건부 액세스 · MFA 정책과 무관)
   - 해설: 인증을 통과하기 전의 트래픽도 내부 쪽 서버까지 들어옵니다. 사용자는 엣지 또는 DMZ의 웹 서버에서 인증하는 구조입니다
4. [처리] 인증 전 요청이 내부 서버에 도달
   - 주체: 온프레미스
   - 데이터: 익명 요청 · 취약점 스캔 · 무차별 대입 시도
   - 해설: 인증되지 않은 트래픽이 공개 경로에 그대로 노출됩니다
5. [끝] 위험 기반 · 기기 기반 통제 불가 — 로그가 Entra에 없음
   - 주체: 로그
   - 위치: DMZ · 앱 서버 로그 (Entra 로그인 로그에는 없음)
   - 데이터: 접속 기록은 DMZ · 앱 서버 로그에만 존재 (Entra 로그인 로그 없음)
   - 해설: Entra의 조건부 액세스와 위험 신호(ID Protection)를 이 앱에 쓸 수 없습니다

#### L4 · ① 구성 — 커넥터를 설치하고 사내 앱을 게시한다

1. [시작] 커넥터 서버 준비 — Windows Server · TLS 1.2 · HTTP/2 비활성화
   - 주체: 관리자
   - 위치: 사내 Windows Server (레지스트리 HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Internet Settings\WinHttp 의 EnableDefaultHTTP2 = 0 후 재시작, 서버 2019 이상)
   - 데이터: Windows Server 2016 이상 · .NET 4.7.2 이상 · TLS 1.2 사용(설치 전에 활성화하고 재시작) · 아웃바운드 80(CRL 확인)/443(서비스 통신) · *.msappproxy.net · *.servicebus.windows.net 등 허용 URL · 고가용성은 서버 2대 이상 권장
   - 해설: 인바운드 포트 없이 서버에서 바깥으로 나가는 연결만 허용되면 됩니다. HTTP/2 비활성화는 Application Proxy로 웹 앱을 게시할 때만 필요하고(Private Access만 쓰면 불필요), 방화벽·프록시는 커넥터와 서비스 사이 아웃바운드 TLS를 검사·종단(inline inspection)하지 않아야 합니다
2. [처리] 커넥터 다운로드 · 설치 · 등록
   - 주체: 관리자
   - 위치: Global Secure Access › 연결 › 커넥터 › 커넥터 서비스 다운로드 → 설치 마법사 (Global Secure Access › Connect › Connectors › Download connector service)
   - 데이터: Application Administrator 자격 증명으로 테넌트에 등록 · 설치되는 Windows 서비스 2개(Microsoft Entra private network connector · 자동 업데이트용 updater)
   - 해설: 커넥터는 Application Proxy와 Private Access가 함께 쓰는 에이전트입니다. 설치 후 포털의 커넥터 목록에서 초록색 '활성' 표시와 services.msc의 두 서비스 실행 상태를 확인합니다. Password Protection Proxy와는 같은 서버에 설치하지 않습니다
3. [처리] 커넥터 그룹 만들기
   - 주체: 관리자
   - 위치: Global Secure Access › 연결 › 커넥터 › 새 커넥터 그룹 (Entra ID › Enterprise apps › Application proxy에서도 가능)
   - 데이터: 그룹 이름 · 포함할 커넥터 (앱이 있는 네트워크·리전별로 묶음) · 새 커넥터는 자동으로 Default 그룹에 들어감
   - 해설: 어떤 커넥터가 어떤 앱을 맡을지 정하는 단위입니다. 대규모 배포에서는 앱을 Default 그룹에 할당하지 않는 것이 좋습니다. 새 커넥터는 활성 그룹으로 옮기기 전까지 실제 트래픽을 받지 않으므로 점검용으로 대기시킬 수 있습니다
4. [처리] 온-프레미스 애플리케이션 추가 시작
   - 주체: 관리자
   - 위치: 애플리케이션 › 엔터프라이즈 앱 › 새 애플리케이션 › 온-프레미스 애플리케이션 추가 (Entra ID › Enterprise apps › New application › Add an on-premises application) · 필요 역할 Application Administrator 이상
   - 데이터: 표시 이름 · 유지 관리 모드 (선택, 켜면 모든 사용자의 접근이 임시로 막힘) · 전제 조건 Entra ID P1/P2 · 사용자 ID는 온프레미스 디렉터리와 동기화되었거나 Entra에서 직접 만든 것이어야 함
   - 해설: 게시할 사내 웹 앱 하나가 엔터프라이즈 앱 하나가 됩니다. 이름은 My Apps와 관리 센터에 그대로 보입니다
5. [처리] 내부 URL · 외부 URL 입력
   - 주체: 관리자
   - 위치: 온-프레미스 애플리케이션 추가 › 내부 URL · 외부 URL (사용자 지정 도메인은 외부 URL에서 도메인을 선택한 뒤 PFX 인증서 업로드)
   - 데이터: Internal URL (사내 주소, 경로 게시 가능 — 경로를 게시하면 이미지·스크립트·스타일시트가 있는 경로까지 포함해야 함) · External URL (기본 yourtenant.msappproxy.net 형태 또는 사용자 지정 도메인) · URL은 http/https로 시작해 "/"로 끝나고 IP가 아닌 도메인 이름이어야 하며 내부·외부 URL 모두 고유해야 함
   - 해설: 외부 사용자가 쓸 주소와 커넥터가 호출할 사내 주소를 짝지어 줍니다. 사용자 지정 도메인에는 Entra에서 확인된 사용자 지정 도메인과 개인 키가 포함된 PFX 인증서(중간 인증서 포함)가 필요하고, 와일드카드 인증서는 와일드카드가 외부 URL과 일치할 때 쓸 수 있습니다. 포털이 알려 주는 CNAME을 DNS에 msappproxy.net으로 연결합니다(IP나 서버 DNS 이름으로 연결하지 않음)
6. [처리] 사전 인증과 커넥터 그룹 선택
   - 주체: 관리자
   - 위치: 온-프레미스 애플리케이션 추가 › 사전 인증 · 커넥터 그룹
   - 데이터: Microsoft Entra ID(기본값, 권장) 또는 Passthrough · 커넥터 그룹 (기본은 Default) · WebSocket을 쓰는 앱은 그룹 안 모든 커넥터가 1.5.612.0 이상이어야 함
   - 해설: Entra ID 사전 인증을 골라야 조건부 액세스와 MFA를 쓸 수 있고 Microsoft Defender for Cloud Apps로 앱을 모니터링할 수도 있습니다. Passthrough는 Entra 인증 없이 통과시키며 인증 요구는 백엔드 앱에서 따로 설정합니다
7. [처리] 추가 설정 검토 — 시간 제한 · 쿠키 · 헤더 · TLS 검증
   - 주체: 관리자
   - 위치: 온-프레미스 애플리케이션 추가 › 추가 설정
   - 데이터: 백엔드 시간 제한 (기본 85초 / 긴 값 180초) · HTTP-Only 쿠키 · 영구 쿠키(선택 해제 유지) · 헤더 URL 변환(기본 선택) · 본문 URL 변환(기본 해제, 하드코딩된 링크가 있을 때만) · 백엔드 TLS 인증서 검증
   - 해설: 대부분 기본값을 유지하고 앱 특성이 있을 때만 바꿉니다. 시간 제한을 '긴 값'으로 바꾸는 경우는 앱이 인증·연결에 시간이 오래 걸릴 때뿐입니다. 영구 쿠키는 프로세스 간 쿠키를 공유하지 못하는 앱에만 씁니다
8. [처리] User.Read 관리자 동의 부여
   - 주체: 관리자
   - 위치: 엔터프라이즈 앱 › {앱} › 권한 › 관리자 동의 부여 (Permissions › Grant admin consent for {tenant}) · 필요 역할 Cloud Application Administrator 이상 · PowerShell은 Connect-MgGraph -Scopes Application.ReadWrite.All, DelegatedPermissionGrant.ReadWrite.All 후 New-MgOauth2PermissionGrant
   - 데이터: oauth2PermissionGrant (AllPrincipals · User.Read, Microsoft Graph 위임 권한) — 2026-06-30 이후 신규 앱은 자동 부여되지 않음 (기존 앱은 영향 없음)
   - 해설: 새로 만든 게시 앱은 이 동의를 직접 눌러야 로그인이 이어집니다. 동의 뒤 권한 화면에서 User.Read가 관리자 동의 · 위임 형식으로 보이는지 확인합니다
9. [처리] 사용자 · 그룹 할당
   - 주체: 관리자
   - 위치: 엔터프라이즈 앱 › {앱} › 사용자 및 그룹 › 사용자 또는 그룹 추가 (시작 가이드 › Assign a user for testing)
   - 데이터: appRoleAssignment (할당된 사용자만 사전 인증 후 접근) · 사전 인증을 쓰는 Application Proxy 앱에도 '할당 필요' 설정이 적용됨 · 미할당 사용자는 AADSTS50105
   - 해설: 사내에서 이미 접근 가능한 사용자인지 확인한 뒤 할당합니다. 그룹 할당은 Entra ID P1/P2가 필요합니다
10. [끝] 애플리케이션 테스트 실행 — 진단 보고서 확인
   - 주체: 관리자
   - 위치: 엔터프라이즈 앱 › {앱} › 애플리케이션 프록시 › 애플리케이션 테스트
   - 데이터: 구성 점검 결과 · 진단 보고서 (해결 안내 포함)
   - 해설: 앱을 열어 보고 진단 보고서로 구성 오류를 바로 확인합니다. 앱 생성 단계 오류는 화면 오른쪽 위 알림에 표시되며 대부분 해결 방법이 함께 나옵니다

#### L4 · ② 활성 — 사전 인증 후에만 커넥터가 사내 앱으로 전달한다

1. [시작] 사용자가 외부 URL로 접속
   - 주체: 사용자
   - 위치: 외부 URL (msappproxy.net 또는 사용자 지정 도메인) · My Apps
   - 데이터: 브라우저 요청 (토큰 없음)
   - 해설: 사용자는 VPN 없이 일반 웹 주소로 앱에 들어옵니다. My Apps 타일로도 시작할 수 있습니다
2. [처리] 토큰 없는 요청을 Entra 로그인으로 — Proxy 서비스가 차단 후 이동
   - 주체: Entra ID
   - 위치: Application Proxy 서비스 (클라우드)
   - 데이터: 사전 인증 = Microsoft Entra ID → 유효한 토큰 없는 트래픽은 내부로 전달하지 않음 · 서비스는 웹 크롤러에 robots.txt(User-agent: * Disallow: /)로 응답해 색인을 막음
   - 해설: 인증 전 요청은 클라우드에서 끝나 내부 네트워크에 닿지 않습니다. 모든 트래픽이 클라우드에서 종단되는 리버스 프록시라서 백엔드 서버는 HTTP 트래픽에 직접 노출되지 않고, 게시한 앱은 Microsoft의 DDoS 보호도 받습니다
3. [판단] 로그인 · 앱 할당 · 조건부 액세스를 충족하는가?
   - 주체: Entra ID
   - 위치: 보호 › 조건부 액세스 › 정책 (Entra ID › Conditional Access › Policies, 대상 리소스 = 게시한 앱)
   - 데이터: 사용자 할당 · MFA · 기기 · 위치 · 위험 평가 결과 · 미할당 사용자는 AADSTS50105
   - 해설: 정책을 통과한 사용자에게만 토큰이 발급됩니다. 위치·인증 강도·사용자 위험으로 제한할 수 있고 Defender for Cloud Apps 액세스·세션 정책으로 실시간 모니터링도 연결할 수 있습니다
   - 예 → 4
   - 아니오 → [차단] 차단 — 토큰 미발급으로 내부 연결 없음
4. [처리] 토큰을 Proxy 서비스로 전달 — UPN · SPN 추출
   - 주체: Entra ID
   - 위치: 사용자 브라우저 → Application Proxy 서비스
   - 데이터: 사용자 토큰 → 서비스가 UPN · SPN 추출
   - 해설: 서비스는 토큰을 검증해 누가 요청했는지 읽고, 커넥터가 이중 인증된 보안 채널로 UPN과 SPN을 가져가도록 넘깁니다
5. [처리] 서비스가 요청을 커넥터로 전달
   - 주체: 온프레미스
   - 위치: Application Proxy 서비스 ↔ 커넥터 (커넥터가 먼저 바깥으로 연 아웃바운드 채널)
   - 데이터: 포트 80/443 · *.msappproxy.net · *.servicebus.windows.net 연결 · 커넥터는 클라이언트 인증서로 서비스에 인증하고 모든 통신은 TLS
   - 해설: 인바운드 포트 없이 커넥터가 서비스에서 요청을 가져가는 방식입니다. 서비스와 커넥터 사이 흐름은 커넥터 설정 시, 구성 정보를 가져올 때, 사용자가 앱에 접근할 때 만들어집니다
6. [처리] 커넥터가 사용자 대신 SSO 수행 (설정한 경우)
   - 주체: 온프레미스
   - 위치: 커넥터 서버 → Active Directory (Kerberos 위임 등)
   - 데이터: 설정된 SSO 방식 (IWA/KCD · 헤더 · 암호 보관 · SAML)
   - 해설: 사내 앱이 요구하는 로그인 방식으로 사용자를 대신 인증합니다. 방식 선택은 앱이 백엔드에서 쓰는 인증 방식이 정합니다
7. [처리] 커넥터가 내부 URL의 앱으로 요청 전달
   - 주체: 온프레미스
   - 위치: 커넥터 서버 → 내부 웹 앱 (내부 URL)
   - 데이터: 변환된 헤더 · 클라이언트 IP 헤더 (선택한 설정에 따름) · 백엔드 시간 제한 기본 85초
   - 해설: 커넥터는 사내에서 앱을 직접 호출하고 응답을 기다립니다. 백엔드 TLS 인증서 검증을 켰다면 앱 서버 인증서가 유효해야 합니다
8. [처리] 응답이 커넥터 → 서비스 → 사용자로 돌아감
   - 주체: 앱
   - 위치: 앱 서버 → 커넥터 → Application Proxy 서비스 → 사용자 브라우저
   - 데이터: 앱 응답 (HTTP) — 세션은 클라우드 서비스에서 종단 후 재수립
   - 해설: 사용자 트래픽은 서비스에서 끝나고 내부 서버는 직접 노출되지 않습니다. 사용자가 서비스에 붙고, 커넥터가 서비스에 붙고, 커넥터가 앱에 붙는 세 구간으로 흐릅니다
9. [끝] 로그인 로그에 접근 결과 기록
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 로그인 로그
   - 데이터: SigninLogs — 앱 · 사용자 · 조건부 액세스 결과 · 상태
   - 해설: 허용과 차단 모두 일반 SaaS 앱처럼 로그인 로그에서 확인합니다. 커넥터 쪽 연결 문제는 커넥터 서버의 이벤트 로그와 함께 봅니다
- 시나리오: 예 :: 사전 인증을 충족해 커넥터가 사내 앱에 전달
- 시나리오: 아니오 :: 사전 인증 조건 미충족으로 접근 차단

> 교육 포인트: 핵심은 "인증이 먼저, 연결은 나중"입니다. Entra ID 사전 인증을 쓰면 인증되지 않은 트래픽은 사내 네트워크에 도달하지 못합니다.
>
> 주의: Passthrough는 Entra 인증 없이 통과시키므로 조건부 액세스와 사전 인증의 이점이 사라집니다.
>
> 주의: Application Proxy는 원격 사용자용입니다. 사내 사용자가 굳이 거치면 성능 문제가 생길 수 있습니다.

### L3 · A · 백엔드 SSO — 통합 Windows 인증(KCD)과 다른 방식

#### L4 · 사내 앱의 로그인 방식에 맞춰 SSO를 구성한다

1. [시작] 사내 앱이 쓰는 로그인 방식을 확인
   - 주체: 관리자
   - 위치: 앱 문서 · 웹 서버(IIS 등) 인증 설정
   - 데이터: 통합 Windows 인증 · 폼/헤더 기반 · 암호 기반 · SAML
   - 해설: 앱의 기본 인증 방식이 SSO 구성 방법을 결정합니다. Application Proxy가 지원하는 SSO는 암호 기반 · 통합 Windows 인증(KCD) · 헤더 기반 · SAML 네 가지입니다
2. [판단] 앱이 통합 Windows 인증을 쓰는가? — IWA · Kerberos
   - 주체: 관리자
   - 위치: 앱 서버 인증 설정 (IWA · Kerberos 사용 여부)
   - 데이터: 앱이 Kerberos 티켓을 요구하는지 여부 · 앱에 SPN이 등록되어 있어야 함 · 커넥터 서버와 앱 서버는 같은 도메인이거나 신뢰하는 도메인이어야 함
   - 해설: Kerberos 앱은 커넥터가 사용자 대신 티켓을 얻도록 위임을 설정합니다
   - 예 → 3
   - 아니오 → 9
3. [처리] AD에서 커넥터 서버에 위임 권한 부여
   - 주체: 관리자
   - 위치: 온프레미스 Active Directory › 사용자 및 컴퓨터 › 커넥터 서버 컴퓨터 개체 › 속성 › 위임(Delegation) › 지정된 서비스에 대해서만 이 컴퓨터를 위임용으로 트러스트 › 모든 인증 프로토콜 사용
   - 데이터: 커넥터가 대상 SPN에 위임 자격 증명을 보낼 수 있는 허용 목록(KCD) · 커넥터와 앱이 다른 도메인이면 앱 서비스 계정의 PrincipalsAllowedToDelegateToAccount를 설정(Set-ADComputer 또는 Set-ADUser, Windows Server 2012 R2 이상 DC에서 실행, 계정은 플랫 이름 사용) · 커넥터 서버가 사용자의 TokenGroupsGlobalAndUniversal을 읽을 수 있어야 하며 막혀 있으면 Windows Authorization Access 그룹에 추가
   - 해설: 커넥터가 사용자를 가장해 앱 서비스 티켓을 요청할 수 있게 합니다. 서로 신뢰가 없는 여러 포리스트라면 커넥터 하나로 모두 처리할 수 없으므로 포리스트별로 커넥터 그룹을 나눕니다
4. [처리] SSO 모드를 통합 Windows 인증으로 선택
   - 주체: 관리자
   - 위치: 엔터프라이즈 앱 › {앱} › 싱글 사인온 › 통합 Windows 인증
   - 데이터: 사전 인증은 Microsoft Entra ID여야 함
   - 해설: Entra에서 앱이 Kerberos 방식임을 알려 줍니다
5. [처리] 내부 애플리케이션 SPN 입력
   - 주체: 관리자
   - 위치: 통합 Windows 인증 › 내부 애플리케이션 SPN
   - 데이터: 예: http/www.contoso.com (커넥터가 위임 받을 수 있는 SPN 목록에 있어야 함)
   - 해설: 앱 서버의 서비스 주체 이름이 위임 허용 목록과 같아야 동작합니다
6. [처리] 위임 로그인 ID 선택
   - 주체: 관리자
   - 위치: 통합 Windows 인증 › 위임 로그인 ID (Delegated Login Identity)
   - 데이터: 선택지 — UPN · 대체 UPN · UPN의 사용자 이름 부분 · 대체 UPN의 사용자 이름 부분 · 온-프레미스 SAM 계정 이름 (클라우드와 온프레미스 계정 이름이 다를 때 사용, 앱별 설정)
   - 해설: Entra 사용자와 AD 계정을 이어 줄 식별자를 정합니다. SAM 계정 이름을 쓰면 커넥터 호스트가 사용자 계정이 있는 도메인에 가입돼 있어야 하고, 위임 로그인 ID 값이 도메인·포리스트 전체에서 유일하지 않다면 앱을 커넥터 그룹을 달리해 두 번 게시합니다
7. [처리] 커넥터가 AD에서 사용자 대신 Kerberos 티켓 획득
   - 주체: 온프레미스
   - 위치: 커넥터 서버 ↔ 도메인 컨트롤러
   - 데이터: 서비스 티켓 (사용자 대신 요청)
   - 해설: 사용자는 로그인 화면 없이 앱의 티켓을 커넥터가 대신 받습니다
8. [처리] 커넥터가 티켓과 함께 앱에 요청
   - 주체: 온프레미스
   - 위치: 커넥터 서버 → 내부 웹 앱
   - 데이터: Kerberos 티켓이 담긴 요청 · 비Windows 서버는 SPNEGO 토큰을 기대하는 경우가 많으며 커넥터에서 UseSpnegoAuthentication 레지스트리를 1로 설정(기본 해제, 표준 Kerberos와 SPNEGO는 한 커넥터에서 동시에 쓸 수 없음)
   - 해설: 앱은 도메인 사용자가 접속한 것으로 보고 세션을 엽니다. SPNEGO를 켜면 같은 커넥터 그룹의 모든 커넥터를 같은 방식으로 맞추고, 표준 Kerberos 토큰을 기대하는 앱은 다른 그룹으로 보냅니다
   - 다음 → 10
9. [처리] 다른 방식 선택 — 헤더 · 암호 보관 · SAML
   - 주체: 관리자
   - 위치: 엔터프라이즈 앱 › {앱} › 싱글 사인온
   - 데이터: 헤더 기반(PingAccess 파트너 서비스) · 암호 기반(첫 로그인 후 Entra가 대신 입력) · SAML 2.0 · WS-Federation
   - 해설: IWA가 아니면 앱의 인증 방식에 맞는 SSO 항목을 고릅니다. PingAccess를 쓰려면 PingAccess와 Entra ID P1/P2 라이선스가 모두 필요합니다
10. [끝] 사용자는 앱 로그인 화면 없이 접속
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 로그인 로그 · 커넥터 서버 이벤트 뷰어(Application Proxy 세션 로그)
   - 데이터: 로그인 로그 (앱 · 사용자 · 결과) · 앱이 예상과 다른 HTTP 응답을 주면 커넥터의 세션 로그에서 이벤트 24029의 user 필드로 위임에 쓰인 ID를 확인 (이벤트 뷰어 › 보기 › 분석 및 디버그 로그 표시)
   - 해설: Entra 로그인 한 번으로 사내 앱 세션까지 이어집니다
- 시나리오: 예 :: 통합 Windows 인증 앱에 Kerberos 위임 SSO
- 시나리오: 아니오 :: 다른 로그인 방식 앱에 맞춰 SSO 구성

> 교육 포인트: Application Proxy의 SSO는 Entra 사전 인증을 전제로 합니다. 앱이 요구하는 인증 방식(Kerberos·헤더·SAML 등)에 맞춰 커넥터나 Entra가 대신 로그인해 줍니다.
>
> 주의: KCD의 SPN과 위임 허용 목록이 어긋나면 로그인이 실패합니다. 서버·도메인 구성은 앱별로 다르니 AD 관리자와 함께 확인합니다.

### L3 · B · 커넥터 · 커넥터 그룹 — 아웃바운드 연결과 라우팅

#### L4 · 커넥터가 연결을 만들고 요청이 그룹으로 라우팅된다

1. [시작] 커넥터가 서비스로 아웃바운드 연결을 연다
   - 주체: 온프레미스
   - 위치: 커넥터 서버 → Application Proxy 서비스
   - 데이터: 포트 80/443 · 채널은 보안 연결 (인바운드 포트 없음) · 접속 호스트는 항상 *.msappproxy.net 또는 *.servicebus.windows.net이지만 DNS 응답은 CNAME 체인으로 다른 이름을 거칠 수 있어 고정된 DNS 목록은 없음
   - 해설: 방화벽에서 바깥으로만 나가면 연결이 만들어집니다. 커넥터 서버·방화벽·아웃바운드 프록시가 체인의 모든 레코드를 풀고 그 IP로의 연결을 허용해야 하며, 방화벽이 도메인 접미사 규칙을 못 쓰면 Azure IP 범위·서비스 태그(매주 갱신)를 허용합니다
2. [처리] 커넥터는 상태 비저장 — 필요한 정보를 클라우드에서 가져옴
   - 주체: 온프레미스
   - 데이터: 커넥터 구성 · 앱 정보 (로컬에는 서비스 연결 설정과 인증 인증서만 저장, 구성은 몇 분마다 갱신)
   - 해설: 서버를 추가·교체해도 클라우드 구성이 그대로 이어집니다. 커넥터는 Windows 서비스 두 개(커넥터 · updater)로 구성되며 둘 다 항상 실행 중이어야 합니다
3. [처리] 앱을 커넥터 그룹에 할당
   - 주체: 관리자
   - 위치: 엔터프라이즈 앱 › {앱} › 애플리케이션 프록시 › 커넥터 그룹
   - 데이터: 앱 ↔ 커넥터 그룹 연결 (미선택 시 Default 그룹) · 게시할 때 지정하고 이후 언제든 변경 가능
   - 해설: 같은 네트워크에 있는 앱과 커넥터를 한 그룹에 묶습니다. 그룹 구성 예: 데이터센터별 · 격리 네트워크 · IaaS · 포리스트별 · 재해 복구 사이트별
4. [처리] 요청이 오면 서비스가 앱의 커넥터 그룹을 확인
   - 주체: Entra ID
   - 데이터: 앱의 그룹 설정 · 그룹 안 커넥터 상태
   - 해설: 서비스는 앱에 지정된 그룹의 커넥터에게만 요청을 보냅니다
5. [판단] 그룹에 연결된 활성 커넥터가 있는가?
   - 주체: Entra ID
   - 위치: Global Secure Access › 연결 › 커넥터 (그룹 · 커넥터 상태)
   - 데이터: 커넥터 활성 · 비활성 상태 (초록 '활성' 표시여도 네트워크 문제로 메시지를 못 받을 수 있음)
   - 해설: 활성 커넥터가 없으면 사내 앱까지 요청이 가지 못합니다. 커넥터 서버에서 브라우저로 앱에 직접 접근해 보는 식으로 커넥터에서 앱까지의 경로를 확인합니다
   - 예 → 6
   - 아니오 → [차단] 연결 실패 — 활성 커넥터 없음 (서버·네트워크 점검)
6. [처리] 그룹 안 커넥터로 요청이 분산
   - 주체: Entra ID
   - 위치: 앱의 트래픽 라우팅 설정 (Global Secure Access 앱 · Graph onPremisesPublishing)
   - 데이터: 같은 그룹의 커넥터는 고가용성·부하 분산 단위 · 라우팅 방식 Random(기본) · Session persistence(같은 사용자·기기를 한 커넥터로) · Performance(RTT가 가장 낮은 커넥터, 미리 보기)
   - 해설: 서버가 여러 대면 한 대가 멈춰도 다른 커넥터가 이어받습니다. 커넥터 송신 IP로 인증하거나 ACL을 쓰는 앱은 Session persistence가 맞습니다. 평균 사양 서버 한 대는 일반 웹 트래픽 기준 초당 약 2,000 요청을 처리하며, 최소 4코어·8 GiB이고 CPU·메모리 사용률이 지속적으로 70%를 넘으면 커넥터를 늘립니다
7. [처리] 커넥터 그룹마다 가까운 서비스 리전 선택
   - 주체: 관리자
   - 위치: 엔터프라이즈 앱 › 애플리케이션 프록시 › 새 커넥터 그룹 › 고급 설정 › 특정 지역에 대한 최적화(Optimize for a specific region) (Entra ID › Enterprise apps › Application proxy)
   - 데이터: 지역이 다른 커넥터는 그룹을 나눠 가까운 리전에 지정 · 커넥터 버전 1.5.1975.0 이상 · 기본값은 테넌트와 같거나 가장 가까운 리전 · 기본 리전 그룹의 커넥터만 다른 그룹으로 옮길 수 있음
   - 해설: 지역별 커넥터를 그룹으로 나눠야 트래픽 경로가 짧아집니다. 리전을 지정한 그룹의 커넥터는 지정한 리전의 Application Proxy 서비스에 연결합니다
8. [처리] 점검 시 유지 보수 전용 그룹으로 이동
   - 주체: 관리자
   - 위치: Global Secure Access › 연결 › 커넥터 › 새 커넥터 그룹 (테스트 앱 하나만 할당)
   - 데이터: 점검할 커넥터를 임시 그룹으로 이동 → 작업 후 원래 그룹 복귀 · 이동한 커넥터는 새 연결을 받지 않고 진행 중인 연결은 정상 종료될 때까지 유지
   - 해설: 새 트래픽을 보내지 않으면서 진행 중인 세션은 마무리됩니다. 대기 시간은 앱 세션 특성에 따라 정하고, 패치·재부팅 뒤 두 서비스가 정상 실행되는지 테스트 앱으로 확인한 후 원래 그룹으로 돌립니다. 자동 업데이트는 그룹에서 커넥터 한 대씩 적용됩니다
9. [끝] 커넥터 상태 확인 — 포털과 서버 이벤트 로그
   - 주체: 로그
   - 위치: Global Secure Access › 연결 › 커넥터 / 서버 이벤트 뷰어 › 응용 프로그램 및 서비스 로그 › Microsoft › Microsoft Entra private network › Connector (Admin · Session)
   - 데이터: 커넥터 · 그룹 상태 · 등록 실패 사유 이벤트 · Admin 로그는 주요 이벤트·오류, Session 로그는 모든 트랜잭션 세부(분석 및 디버그 로그 표시 후 활성화, 평소엔 꺼 둠)
   - 해설: 등록·연결 문제는 포털 상태와 서버 이벤트 로그로 함께 봅니다. 한 커넥터 서버 장애는 같은 그룹의 다른 커넥터가 이어받으므로 그룹에 정상 서버를 추가해 용량을 복구합니다
- 시나리오: 예 :: 활성 커넥터가 있어 요청 처리, 상태 확인
- 시나리오: 아니오 :: 활성 커넥터가 없어 연결 실패

> 교육 포인트: 커넥터는 "서버 한 대"가 아니라 "그룹"으로 설계합니다. 앱이 있는 네트워크·리전·용도별로 그룹을 나눕니다.
>
> 주의: Password Protection Proxy와 한 서버에 설치하지 않습니다(에이전트 업데이터가 호환되지 않음).

### L3 · C · Private Access와의 구분 — 어떤 서비스로 열 것인가

#### L4 · 앱 종류와 접근 방식으로 서비스를 고른다

1. [시작] 사내 앱을 원격 사용자에게 열어야 한다
   - 주체: 관리자
   - 위치: 설계 단계 (애플리케이션 프록시 · Global Secure Access › 애플리케이션)
   - 데이터: 앱 종류 · 프로토콜 · 사용자 기기 관리 여부
   - 해설: 같은 커넥터를 쓰지만 서비스가 다르므로 먼저 앱 성격을 봅니다. 라이선스도 서비스마다 다릅니다(Application Proxy는 Entra ID P1/P2, Private Access는 Private Access 라이선스)
2. [판단] 브라우저로 쓰는 웹 앱(HTTP/HTTPS)인가?
   - 주체: 관리자
   - 데이터: 앱 프로토콜 (웹 vs RDP · SMB · SSH 등)
   - 해설: 웹 이외 프로토콜은 Application Proxy가 다루지 못합니다
   - 예 → 3
   - 아니오 → 6
3. [판단] 클라이언트 설치 없이 외부 URL로 접근시켜야 하는가?
   - 주체: 관리자
   - 데이터: 비관리 기기 · 협력사 · 일회성 접근 여부
   - 해설: 에이전트를 깔 수 없는 사용자에게는 URL만으로 접근시키는 쪽이 맞습니다
   - 예 → 4
   - 아니오 → 6
4. [처리] Application Proxy로 게시
   - 주체: 관리자
   - 위치: 애플리케이션 › 엔터프라이즈 앱 › 애플리케이션 프록시
   - 데이터: 외부 URL · 사전 인증 · 조건부 액세스 · SSO (IWA/KCD 등)
   - 해설: 웹 앱 단위로 외부 URL을 만들어 사전 인증과 SSO까지 묶습니다. 앱 코드를 바꿀 필요가 없고 방화벽 인바운드 연결도 열지 않습니다
5. [끝] 사용자는 설치 없이 브라우저로 접속
   - 주체: 사용자
   - 위치: 외부 URL · My Apps
   - 데이터: 외부 URL · My Apps (원격 사용자 전용, 사내 사용자 우회 불필요)
   - 해설: 앱 단위 게시이며 사용자에게 클라이언트를 배포할 필요가 없습니다
6. [처리] Private Access로 게시 — Global Secure Access
   - 주체: 관리자
   - 위치: Global Secure Access › 애플리케이션 › Quick access / 엔터프라이즈 애플리케이션 (Global Secure Access › Applications › Quick access · Enterprise applications) · 필요 역할 Global Secure Access Administrator + Application Administrator
   - 데이터: 앱 세그먼트 (FQDN(와일드카드 포함) · IP · IP 범위(CIDR · IP-IP) · 포트 — 예 RDP 3389 · SMB 445 · SSH 22), 앱당 최대 500 세그먼트 · 세그먼트는 앱 사이에 겹칠 수 없음(Quick Access와의 겹침만 예외이며 엔터프라이즈 앱 쪽이 우선) · NetBIOS 이름은 미지원
   - 해설: 웹이 아닌 포트·프로토콜도 앱 세그먼트로 열 수 있습니다. 앱별 접근은 사용자·그룹 할당(중첩 그룹 미지원)과 조건부 액세스로 제어하며, 설정 변경이 클라이언트에 반영되기까지 약 15분을 둡니다. Quick Access에서 엔터프라이즈 앱으로 세그먼트를 옮기면 할당이 자동 이전되지 않아 기존 사용자가 막힐 수 있습니다. 커넥터는 Private Access 기준 1.5.3417.0 이상이 필요합니다
7. [처리] 사용자 기기에 GSA 클라이언트 필요 — 설치 대상
   - 주체: 사용자
   - 위치: 사용자 기기 (클라이언트 설치)
   - 데이터: 클라이언트가 사설 FQDN · IP 트래픽을 에지로 보냄 · 클라이언트 지원 OS: Windows · macOS · Android · iOS · Windows 기기는 Entra 조인·하이브리드 조인 또는 등록 필요(미등록이면 클라이언트가 첫 로그인에서 등록)
   - 해설: 클라이언트가 VPN 없이 사설 리소스로 가는 트래픽을 가져옵니다. 클라이언트는 경량 필터(LWF) 드라이버로 트래픽을 획득해 다른 VPN 솔루션과 공존할 수 있습니다
8. [끝] 두 서비스는 같은 커넥터를 공유할 수 있다
   - 주체: 온프레미스
   - 위치: 사내 Windows Server (커넥터 설치 서버)
   - 데이터: Microsoft Entra private network connector (Application Proxy · Private Access 공용)
   - 해설: 커넥터 설치는 한 번이고 어떤 서비스로 열지는 앱마다 선택합니다. 커넥터 그룹 관리에는 Application Administrator 역할과 Entra ID P1/P2가 필요합니다
- 시나리오: 예 ▸ 예 :: 웹 앱을 설치 없이 Application Proxy로 게시
- 시나리오: 예 ▸ 아니오 :: 웹 앱이지만 클라이언트로 Private Access 게시
- 시나리오: 아니오 :: 웹 앱이 아니라 Private Access로 게시

> 교육 포인트: Private Access는 Application Proxy의 기능 위에 모든 사설 리소스·포트·프로토콜로 범위를 넓힌 것입니다. 웹 앱만 URL로 빠르게 열면 Application Proxy, 그 밖의 접근은 Private Access로 구분합니다.
>
> 예시: 사내 인트라넷 웹 포털은 Application Proxy, 파일 서버(SMB)나 RDP는 Private Access.
