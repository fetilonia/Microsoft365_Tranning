## L2 · 앱 동의 관리 — OAuth 권한 부여 통제

- 설정(Control Plane): 사용자 동의 설정 | 권한 분류(낮은 영향) · 관리자 동의 워크플로
- 강제(Enforcement): Entra OAuth 동의 단계 (/authorize) | 앱 동의 정책(permissionGrantPolicy) 평가
- 증적(Evidence): 감사: Consent to application | GET /v1.0/oauth2PermissionGrants · appRoleAssignments
- 메뉴(Admin Center): 애플리케이션 > 엔터프라이즈 앱 > 동의 및 권한
- 라이선스(License): 동의 설정 · 관리자 동의 워크플로 모두 Entra ID Free 포함 [확인 필요: 고객 라이선스]

### L3 · 0 · 기능 상태 전이 — 사용자 동의 방치 → 사용자 동의 제한 + 관리자 동의 워크플로 → 정책 기반 동의

#### L4 · ⓪ 비활성 — 사용자 동의를 제한하지 않은 상태 (legacy 정책)

1. [시작] 사용자가 처음 보는 타사 앱에 Microsoft 계정으로 로그인
   - 주체: 사용자
   - 위치: 타사 앱의 "Microsoft로 로그인" 버튼 → login.microsoftonline.com/{tenant}/oauth2/v2.0/authorize
   - 데이터: 요청 파라미터 client_id · scope (예: User.Read Mail.Read offline_access)
   - 해설: 사용자가 처음 보는 앱에 Microsoft 계정으로 로그인을 시도합니다. 기본 설정에서는 관리자 동의가 필요 없는 권한이면 사용자가 직접 동의할 수 있어, 자기 메일함 접근은 허용되지만 조직 전체 파일을 읽고 쓰는 권한은 허용되지 않습니다
2. [처리] Entra ID가 앱이 요청한 권한을 해석 — 위임된 권한인지 · 관리자 동의가 필요한 권한인지
   - 주체: Entra ID
   - 위치: Entra 동의 단계 (서비스 내부)
   - 데이터: 권한별 "관리자 동의 필요" 속성 · 앱의 서비스 주체 · 게시자 확인(verified publisher) 여부
   - 해설: Entra가 요청된 권한이 사용자 동의로 허용되는 권한인지 확인합니다
3. [판단] 관리자 동의가 필요한 권한이 포함되어 있는가?
   - 주체: Entra ID
   - 데이터: 권한 정의의 admin consent required 값 · 사용자 할당이 필수인 앱은 사용자 동의 정책이 허용해도 관리자 동의가 필요
   - 해설: 관리자 동의가 필요한 권한이 있으면 사용자는 직접 동의할 수 없습니다. 이 상태에서는 사용자가 막혀도 관리자에게 보낼 요청 경로가 없습니다
   - 예 → [차단] 사용자 동의 불가 — 요청 경로가 없어 앱 사용이 막힘 (관리자 동의 워크플로 꺼짐)
   - 아니오 → 4
4. [처리] 사용자가 동의 화면에서 [수락] 선택
   - 주체: 사용자
   - 위치: Entra 동의 화면 (요청 권한 목록 + 게시자 표시)
   - 데이터: 사용자 선택 한 번 — 관리자 검토 없음 · 정책 microsoft-user-default-legacy (관리자 동의가 필요 없는 권한이면 모든 앱 허용)
   - 해설: 사용자 한 명의 수락만으로 권한이 부여됩니다
5. [처리] Entra ID가 동의 기록 생성 — 이 사용자에 한정된 위임 권한 부여
   - 주체: Entra ID
   - 데이터: oauth2PermissionGrant (clientId · consentType=Principal · principalId · scope)
   - 해설: 부여 기록이 oauth2PermissionGrants에 저장되고 감사 로그(서비스 Core Directory · 범주 ApplicationManagement · 활동 Consent to application)가 남습니다
6. [처리] 앱이 토큰으로 사용자 데이터에 접근
   - 주체: 앱
   - 위치: Microsoft Graph 등 리소스 API
   - 데이터: 액세스 토큰의 scp 클레임 = 부여된 위임 권한
   - 해설: 앱이 사용자 권한 범위 안에서 메일·파일 같은 데이터에 접근합니다. 이후 로그인에서는 같은 범위에 대해 다시 동의를 묻지 않습니다
7. [끝] 악성 앱(동의 피싱)도 사용자 한 명의 수락으로 데이터 접근 — 사전 검토 없음
   - 주체: 로그
   - 데이터: 감사 로그 "Consent to application"은 남지만 승인 절차 · 알림은 없음 (사용자 동의는 ConsentContext.IsAdminConsent=false 로 구분)
   - 해설: 기록은 남지만 막을 장치가 없어 사후에야 발견됩니다. 동의 활동을 모니터링하려면 이 활동에서 IsAdminConsent=false 인 건을 확인합니다
- 시나리오: 예 :: 관리자 동의 필요 권한이라 사용자 동의 불가
- 시나리오: 아니오 :: 관리자 동의 불필요라 한 명 수락으로 데이터 접근

#### L4 · ① 구성 — 사용자 동의를 제한하고 관리자 동의 워크플로를 연다

1. [시작] 관리자가 Entra Admin Center에 로그인
   - 주체: 관리자
   - 위치: entra.microsoft.com — 사용자 동의 설정: 관리 센터는 Global Administrator, Graph·PowerShell은 Privileged Role Administrator · 관리자 동의 워크플로 켜기: Global Administrator · 권한 분류: Cloud Application Administrator 또는 Application Administrator
   - 데이터: 역할 할당 (roleAssignments) · Graph 권한 Policy.ReadWrite.Authorization (읽기 전용은 Policy.Read.All)
   - 해설: 설정 변경에 필요한 역할로 로그인합니다. 사용자 동의 설정은 조직 전체 사용자에게 한 번에 적용됩니다
2. [처리] 현재 사용자 동의 설정 확인
   - 주체: 관리자
   - 위치: 엔터프라이즈 앱 › 동의 및 권한(Consent and permissions) › 사용자 동의 설정(User consent settings)
   - 데이터: authorizationPolicy.defaultUserRolePermissions.permissionGrantPoliciesAssigned (GET /v1.0/policies/authorizationPolicy) · 정책 목록 GET /v1.0/policies/permissionGrantPolicies
   - 해설: 지금 어떤 정책이 사용자 동의를 허용하는지부터 확인합니다. 값을 바꾸기 전에 현재 목록을 먼저 읽어 두어야 ManagePermissionGrantsForOwnedResource.* 같은 기존 정책(개발자의 자기 앱 권한 관리 등)을 잃지 않습니다
3. [처리] 낮은 영향 권한 분류
   - 주체: 관리자
   - 위치: 동의 및 권한 › 권한 분류(Permission classifications) › 분류 탭 › 권한 추가(Add permissions) › API 선택 후 위임 권한 선택
   - 데이터: delegatedPermissionClassification = low (예: openid · profile · email · offline_access — 로그인에 필요한 최소 세트). 분류 등급은 Low · Medium(미리 보기) · High(미리 보기)이고, 관리자 동의가 필요 없는 위임 권한만 분류할 수 있음
   - 해설: 사용자가 직접 동의해도 되는 "낮은 영향" 권한만 골라 둡니다. 분류하지 않은 권한은 사용자 동의 대상이 되지 못합니다
4. [처리] 사용자 동의 설정 선택 — 확인된 게시자 · 선택한 권한만 허용
   - 주체: 관리자
   - 위치: 동의 및 권한 › 사용자 동의 설정 › "확인된 게시자의 앱에 대해, 선택한 권한만 사용자 동의 허용" (Allow user consent for apps from verified publishers, for selected permissions)
   - 데이터: 정책 microsoft-user-default-low (나머지 선택지: 사용자 동의 허용 안 함 / 모든 앱 허용 = microsoft-user-default-legacy). Graph: PATCH /v1.0/policies/authorizationPolicy 의 permissionGrantPoliciesAssigned 에 managePermissionGrantsForSelf.microsoft-user-default-low 지정
   - 해설: 확인된 게시자의 앱 또는 내 테넌트에 등록된 앱이면서 낮은 영향 권한일 때만 사용자 동의를 허용합니다. 정책을 바꿔도 이미 부여된 동의는 그대로이며 이후 동의에만 적용됩니다
5. [처리] 관리자 동의 요청 켜기
   - 주체: 관리자
   - 위치: 동의 및 권한 › 관리자 동의 설정(Admin consent settings) › 관리자 동의 요청 › "사용자가 동의할 수 없는 앱에 대해 관리자 동의를 요청할 수 있음" = 예 (Users can request admin consent to apps they are unable to consent to)
   - 데이터: adminConsentRequestPolicy.isEnabled = true (테넌트당 정책 하나, Graph: Update adminConsentRequestPolicy)
   - 해설: 사용자가 막혔을 때 관리자에게 승인을 요청할 수 있게 합니다. 켜면 사용자에게는 "승인 필요(Approval required)" 창이 표시됩니다
6. [처리] 검토자 지정
   - 주체: 관리자
   - 위치: 관리자 동의 설정 › "관리자 동의 요청을 검토할 수 있는 사람" (사용자 · 그룹 · 역할)
   - 데이터: adminConsentRequestPolicy.reviewers · 검토자는 요청을 보고 차단·거부할 수 있고, Microsoft Graph 앱 역할(애플리케이션 권한) 요청의 승인은 Global Administrator만 가능
   - 해설: 요청을 볼 검토자를 정합니다. 검토자로 지정해도 권한이 올라가지는 않으며, 승인하려면 그 앱의 권한을 직접 부여할 수 있는 역할이 필요합니다. 새 검토자는 지정 이전에 만들어진 요청을 처리할 수 없고, 목록에서 빠진 검토자도 이전 요청은 계속 볼 수 있습니다
7. [처리] 알림 · 만료 기간 설정
   - 주체: 관리자
   - 위치: 관리자 동의 설정 › 이메일 알림 · 만료 미리 알림 · "동의 요청 만료 기간(일)" (Consent request expires after (days))
   - 데이터: notifyReviewers · remindersEnabled · requestDurationInDays
   - 해설: 검토자 알림 메일과 요청 유효 기간을 정합니다. 알림 메일을 끄면 요청자에게 가는 접수·결과 메일도 함께 꺼지고, 만료 미리 알림의 첫 메일은 설정한 기간의 중간쯤 발송됩니다
8. [끝] 저장 — 워크플로가 켜지기까지 최대 1시간
   - 주체: 관리자
   - 위치: 저장 버튼
   - 데이터: 정책 저장 + 감사 로그 (정책 변경)
   - 해설: 저장 후 설정이 반영되기까지 최대 1시간이 걸릴 수 있습니다

#### L4 · ② 활성 — 정책이 동의를 허용 · 요청 · 거부로 나눈다

1. [시작] 사용자가 앱에 로그인 요청
   - 주체: 사용자
   - 위치: /authorize 요청
   - 데이터: client_id · scope
   - 해설: 같은 앱에 로그인을 시도합니다
2. [처리] Entra ID가 요청 권한을 해석
   - 주체: Entra ID
   - 데이터: 위임 권한 목록 · 앱 게시자 확인 여부 · 권한 분류 (Low로 분류된 위임 권한인지)
   - 해설: 권한 종류와 게시자 확인 상태를 계산합니다
3. [판단] 이미 부여된 동의가 있는가?
   - 주체: Entra ID
   - 데이터: oauth2PermissionGrants 조회 (clientId · principalId 또는 AllPrincipals)
   - 해설: 이전에 부여된 동의가 요청 범위를 모두 덮으면 동의 화면 없이 넘어갑니다. 앱이 새 권한을 추가로 요청하면 관리자 동의가 이미 있어도 다시 동의 프롬프트가 뜰 수 있습니다
   - 예 → 10
   - 아니오 → 4
4. [판단] 사용자 동의 설정이 이 앱·권한을 허용하는가?
   - 주체: Entra ID
   - 데이터: 정책 microsoft-user-default-low — 확인된 게시자(또는 내 테넌트 등록 앱) + 낮은 영향 분류인가 · 사용자 할당 필수 앱은 정책과 무관하게 관리자 동의 필요 · 사용자 동의를 끈 설정이면 동의 프롬프트 자체가 나오지 않음
   - 해설: 앱 동의 정책이 허용 조건을 평가합니다
   - 예 → 5
   - 아니오 → 6
5. [처리] 사용자가 동의 화면에서 수락
   - 주체: 사용자
   - 위치: Entra 동의 화면
   - 데이터: 사용자 단위 위임 권한 부여
   - 해설: 허용 범위 안이라 사용자가 직접 수락할 수 있습니다
   - 다음 → 9
6. [판단] 관리자 동의 워크플로가 켜져 있는가?
   - 주체: Entra ID
   - 데이터: adminConsentRequestPolicy.isEnabled
   - 해설: 사용자가 직접 동의할 수 없을 때 요청 경로가 있는지 확인합니다. 켜져 있으면 사용자에게 "승인 필요" 창이 나오고, 꺼져 있으면 요청 없이 접근만 막힙니다
   - 예 → 7
   - 아니오 → [차단] 차단 — "관리자 승인 필요"만 표시, 요청 경로 없음
7. [처리] 관리자 동의 요청 생성 · 검토자에게 메일 발송
   - 주체: Entra ID
   - 위치: 검토자: 엔터프라이즈 앱 › 관리자 동의 요청 › 내 보류 중(My Pending)
   - 데이터: adminConsentRequest (앱 · 요청 권한 · 요청자 · 만료 시각) · 만료 기간(일) 안에 처리되지 않으면 자동 만료
   - 해설: 요청이 검토자에게 전달되고 사용자에게는 대기 안내가 나옵니다. 알림 메일 설정을 켜 두었다면 검토자에게 메일이 가고 처리 결과는 요청자에게 통보됩니다
8. [판단] 검토자가 만료 전에 승인했는가?
   - 주체: 관리자
   - 위치: 요청 상세 › 권한 검토 및 동의 / 거부 / 차단
   - 데이터: 승인 시 관리자 동의 부여 · 앱 역할(application permission)은 Global Administrator만 승인 가능 · 그 외 권한은 검토자가 해당 권한을 부여할 수 있는 역할(Privileged Role Administrator · Cloud Application Administrator · Application Administrator 등)이어야 함
   - 해설: 검토자가 권한과 게시자를 보고 결정합니다. 조직 전체 동의는 민감한 작업이므로 앱과 게시자를 신뢰할 수 있는지 확인한 뒤에만 승인합니다
   - 예 → 9
   - 아니오 → [차단] 거부 · 차단 · 만료 — 앱 사용 불가
9. [처리] Entra ID가 동의 기록 생성 + 감사 로그 기록
   - 주체: Entra ID
   - 데이터: oauth2PermissionGrant (consentType=Principal 또는 AllPrincipals) · 감사 "Consent to application" (서비스 Core Directory · 범주 ApplicationManagement)
   - 해설: 부여 기록이 저장되고 누가 승인했는지 감사 로그에 남습니다
10. [끝] 토큰 발급 — 앱은 부여된 범위 안에서만 API 호출
   - 주체: 앱
   - 데이터: 액세스 토큰 scp 클레임
   - 해설: 부여된 권한만 토큰에 담겨 앱에 전달됩니다
- 시나리오: 예 :: 이미 부여된 동의가 있어 바로 토큰 발급
- 시나리오: 아니오 ▸ 예 :: 사용자 동의 허용으로 수락 후 토큰 발급
- 시나리오: 아니오 ▸ 아니오 ▸ 예 ▸ 예 :: 관리자 동의 요청이 승인되어 토큰 발급
- 시나리오: 아니오 ▸ 아니오 ▸ 예 ▸ 아니오 :: 관리자 동의 요청이 거부·만료되어 차단
- 시나리오: 아니오 ▸ 아니오 ▸ 아니오 :: 사용자·관리자 동의 모두 불가해 차단

> 교육 포인트: 동의는 "앱이 사용자의 데이터에 접근해도 된다"는 승인입니다. 기본 설정을 그대로 두면 사용자 한 명의 클릭이 데이터 접근 권한이 됩니다. 낮은 영향 권한 + 확인된 게시자로 좁히고, 나머지는 관리자 검토로 보내는 것이 권장 구성입니다.
>
> 주의: 정책을 바꿔도 이미 부여된 동의는 사라지지 않습니다. 아래 L3 B로 기존 부여를 별도로 점검합니다.

### L3 · A · 동의 종류 — 위임 권한 · 앱 권한 · 사용자 동의 · 관리자 동의

#### L4 · 요청 권한 종류에 따라 누가 동의하고 어디에 저장되는가

1. [시작] 앱이 권한을 요청
   - 주체: 앱
   - 데이터: 요청 scope (위임) 또는 .default + 앱 역할 (앱 권한)
   - 해설: 앱이 사용자 대신 동작할지, 앱 단독으로 동작할지에 따라 권한 종류가 갈립니다
2. [판단] 요청된 권한 종류는?
   - 주체: Entra ID
   - 해설: 위임 권한은 로그인한 사용자와 함께, 앱 권한은 사용자 없이 동작합니다. 위임 권한은 사용자나 관리자가 동의할 수 있고, 앱 권한은 관리자만 동의할 수 있습니다
   - 위임 → 3
   - 앱 권한 → 6
3. [판단] 사용자 동의로 허용되는 권한인가?
   - 주체: Entra ID
   - 데이터: 권한의 관리자 동의 필요 여부 + 앱 동의 정책 결과
   - 해설: 관리자 동의가 필요 없고 정책이 허용하면 사용자가 동의할 수 있습니다. 사용자 동의가 꺼져 있거나 허용 범위 밖이면 사용자는 동의 프롬프트를 받지 않습니다
   - 예 → 4
   - 아니오 → 5
4. [처리] 사용자 동의 — 그 사용자에게만 적용
   - 주체: 사용자
   - 데이터: oauth2PermissionGrant · consentType=Principal · principalId=사용자
   - 해설: 동의한 사용자의 세션에서만 앱이 권한을 씁니다. 이후 같은 앱에 로그인할 때 보통 다시 동의하지 않습니다
   - 다음 → 7
5. [처리] 관리자 동의 — "조직을 대신하여 동의"
   - 주체: 관리자
   - 위치: 엔터프라이즈 앱 › {앱} › 권한 › 관리자 동의 부여 · 또는 동의 화면의 "조직을 대신하여 동의" · 앱 등록 › API 권한 › 관리자 동의 부여 · URL https://login.microsoftonline.com/{tenant}/adminconsent?client_id={client-id}
   - 데이터: oauth2PermissionGrant · consentType=AllPrincipals · 필요 역할: Privileged Role Administrator(모든 API의 모든 권한) · Cloud Application Administrator · Application Administrator · AI Administrator(Microsoft Graph 앱 역할 제외) · 권한 부여를 허용한 사용자 지정 역할
   - 해설: 조직 전체 사용자에게 같은 범위가 한 번에 적용됩니다. 기본적으로 모든 사용자가 그 앱에 접근할 수 있으므로 제한하려면 앱 속성에서 사용자 할당을 필수로 하고 사용자·그룹을 할당합니다. 테넌트 전체 동의를 다시 부여하면 그 앱에 이미 부여한 테넌트 전체 권한이 철회될 수 있고, 사용자가 개별로 부여한 권한은 영향을 받지 않습니다
   - 다음 → 7
6. [처리] 앱 권한 동의 — 사용자는 동의 불가, 관리자만 가능
   - 주체: 관리자
   - 위치: 엔터프라이즈 앱 › {앱} › 권한 › 관리자 동의 부여
   - 데이터: appRoleAssignment (서비스 주체에 리소스의 앱 역할 할당) · Microsoft Graph 앱 역할은 Privileged Role Administrator 역할로 부여 (Cloud Application Administrator · Application Administrator · AI Administrator는 불가)
   - 해설: 앱 권한은 사용자 없이 동작하므로 반드시 관리자가 동의합니다. 사용자 컨텍스트가 없어 앱이 받은 범위 전체가 그대로 유효합니다
7. [끝] 부여 기록 저장 + 감사 로그
   - 주체: 로그
   - 데이터: 감사 로그 "Consent to application" · GET /v1.0/oauth2PermissionGrants · /servicePrincipals/{id}/appRoleAssignments · 활동명: Add delegated permission grant · Add app role assignment to service principal (서비스 Core Directory · 범주 ApplicationManagement)
   - 해설: 위임 권한은 oauth2PermissionGrants에, 앱 권한은 appRoleAssignments에서 조회합니다
- 시나리오: 위임 ▸ 예 :: 위임 권한이 사용자 동의로 허용돼 사용자가 동의
- 시나리오: 위임 ▸ 아니오 :: 위임 권한이 사용자 동의 불가라 관리자가 동의
- 시나리오: 앱 권한 :: 앱 권한 요청이라 앱 권한 동의로 처리

> 교육 포인트: 위임 권한의 실제 접근 범위는 "앱이 받은 권한 ∩ 로그인한 사용자 본인의 권한"입니다. 앱 권한은 사용자와 무관하게 앱이 가진 범위 전체입니다.
>
> 출처: https://learn.microsoft.com/entra/identity/enterprise-apps/user-admin-consent-overview
>
> 출처: https://learn.microsoft.com/entra/identity/enterprise-apps/grant-admin-consent
>
> 출처: https://learn.microsoft.com/entra/identity/enterprise-apps/app-perms-audit-logs

### L3 · B · 사후 점검 — 이미 부여된 동의 찾기 · 회수

#### L4 · 부여된 동의 목록 → 위험 판별 → 회수

1. [시작] 관리자가 정기 점검을 시작
   - 주체: 관리자
   - 위치: 엔터프라이즈 앱 › 모든 애플리케이션 (필터: 애플리케이션 종류 · 게시자) · 앱 선택 후 권한(Permissions) 페이지의 관리자 동의(Admin consent) · 사용자 동의(User consent) 탭 (최소 Cloud Application Administrator 또는 Application Administrator)
   - 데이터: 서비스 주체 목록 · 게시자 확인 여부 · 관리자 동의 탭은 조직 전체 부여, 사용자 동의 탭은 사용자·그룹별 부여
   - 해설: 동의 정책 변경 전에 부여된 앱까지 포함해 점검합니다. 서비스 주체 소유자는 관리자가 아니어도 새로 고침 토큰을 무효화할 수 있습니다
2. [처리] 위임 권한 부여 목록 조회
   - 주체: 관리자
   - 위치: Microsoft Graph — GET /v1.0/oauth2PermissionGrants · 앱별 GET /v1.0/servicePrincipals/{id}/oauth2PermissionGrants
   - 데이터: clientId · consentType · principalId · scope · PowerShell 조회 시 권한 DelegatedPermissionGrant.ReadWrite.All
   - 해설: 어떤 앱이 어떤 위임 권한을 받았는지 모읍니다
3. [처리] 앱 권한 부여 목록 조회
   - 주체: 관리자
   - 위치: Microsoft Graph — GET /v1.0/servicePrincipals/{id}/appRoleAssignments
   - 데이터: resourceId · appRoleId · PowerShell 조회 시 권한 AppRoleAssignment.ReadWrite.All
   - 해설: 사용자 없이 동작하는 앱 권한도 함께 봅니다
4. [판단] 과도한 권한이거나 게시자 확인이 안 된 앱인가?
   - 주체: 관리자
   - 데이터: 예: Mail.ReadWrite · Files.ReadWrite.All 같은 고위험 범위 · *.All 형태나 Mail.* 같은 넓은 권한이 앱에 부여됐는지 감사 로그 "Add app role assignment to service principal" 로도 확인 [판단]
   - 해설: 위험 기준은 조직이 정합니다
   - 예 → 5
   - 아니오 → 6
5. [처리] 권한 회수 또는 앱 차단
   - 주체: 관리자
   - 위치: 엔터프라이즈 앱 › {앱} › 권한 › 관리자 동의 탭 › 권한 옆 "..." › 권한 취소(Revoke permission) · 사용자 동의 탭 권한은 포털에서 취소할 수 없어 Graph·PowerShell 사용 / 속성 › "사용자에게 로그인 설정 사용?"(Enabled for users to sign in?) = 아니요
   - 데이터: DELETE /v1.0/oAuth2PermissionGrants/{id} (위임) · DELETE /v1.0/servicePrincipals/{resource-sp-id}/appRoleAssignedTo/{assignment-id} (앱 권한) · servicePrincipal.accountEnabled=false (토큰 미발급, 앱 권한 접근도 제한)
   - 해설: 부여를 취소하거나 앱 로그인을 막습니다. 취소해도 앱이 동적 동의로 다시 요청하면 사용자가 재동의할 수 있으므로 동의 설정으로 함께 막습니다. 액세스 토큰 기본 수명은 60~90분의 무작위 값이며 이미 발급된 토큰이 취소 즉시 무효가 되는지는 [확인 필요: 문서 미기재]. 취소한 권한은 복원할 수 있습니다
6. [끝] 점검 결과 기록 + 감사 로그 확인
   - 주체: 로그
   - 데이터: 감사 로그 ApplicationManagement — 동의 부여 · 취소 활동 (Consent to application · Add delegated permission grant · Remove delegated permission grant · Add / Remove app role assignment to service principal)
   - 해설: 점검과 회수 이력이 감사 로그로 남습니다. 특정 리소스 앱(예: Microsoft Graph)의 엔터프라이즈 앱 › 활동 › 감사 로그에서 최근 30일의 부여 이력을 볼 수 있습니다 (최소 Reports Reader)
- 시나리오: 예 :: 위험 앱은 권한 회수·차단 후 결과 기록
- 시나리오: 아니오 :: 문제 앱이 없어 점검 결과만 기록

> 주의: 동의 점검은 정책 설정과 별개의 정기 작업입니다. 새 정책은 앞으로의 동의만 막습니다.
