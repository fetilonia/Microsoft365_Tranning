## L2 · 로그 · 모니터링 — 진단 설정 · 보관 · 분석

- 설정(Control Plane): 진단 설정(로그 범주 선택) | 전송 대상: Log Analytics · Storage · Event Hub · 파트너 솔루션
- 강제(Enforcement): Entra 로그 파이프라인 | 로그인 · 감사 · 프로비저닝 로그 수집·전달
- 증적(Evidence): 로그인 로그 · 감사 로그 · 프로비저닝 로그 | KQL: SigninLogs · AuditLogs
- 메뉴(Admin Center): 모니터링 및 상태 > 로그인 로그 · 감사 로그 · 진단 설정
- 라이선스(License): 로그인·감사 로그 기본 보관은 Free 7일, P1/P2 30일. 프로비저닝 로그 · Graph 활동 로그 · 사용 현황 · 워크북은 P1 이상 [확인 필요: 고객 라이선스 · Azure 대상 요금 별도]

### L3 · 0 · 기능 상태 전이 — 포털 기본 보관 → 진단 설정 → 장기 분석

#### L4 · ⓪ 비활성 — 포털의 기본 보관 기간만 쓴다

1. [시작] 보안 사고 발생 — 40일 전 로그인 기록이 필요
   - 주체: 관리자
   - 위치: Entra 관리 센터 › Entra ID › 모니터링 및 상태(Monitoring & health) › 로그인 로그(Sign-in logs)
   - 데이터: 조회 기간 필터 (조사 대상 시점이 기본 보관 기간을 넘어서는지 확인)
   - 해설: 사고 조사 중 몇 주 전의 로그인 기록을 확인해야 하는 상황입니다. 로그를 열람하는 최소 역할은 Reports Reader입니다
2. [처리] 포털에서 기본 보관분만 조회
   - 주체: Entra ID
   - 위치: Entra ID › 모니터링 및 상태 › 감사 로그(Audit logs) · 로그인 로그(Sign-in logs)
   - 데이터: 로그인·감사 로그 기본 보관: Free 7일 · P1/P2 30일 · MFA 사용량 30일(전 에디션) · 위험한 로그인 7일(Free) · 30일(P1) · 90일(P2) · Graph 활동 로그는 진단 설정으로 내보내지 않으면 보관되지 않음(P1/P2 전용)
   - 해설: 포털은 라이선스에 따른 기본 보관 기간만큼의 기록만 보여 줍니다. Free는 Entra ID를 처음 열거나 보고 API를 쓸 때부터, P1/P2는 구독 시점부터 수집이 시작됩니다
3. [판단] 조회하려는 기간이 보관 기간 안인가?
   - 주체: 로그
   - 데이터: 로그 보관 기간 vs 조사 대상 시점 · Free에서 Premium으로 올려도 보관 기간 변경은 소급되지 않아 무료 보관 기간(최대 7일) 안의 데이터만 남음
   - 해설: 보관 기간이 지난 기록은 별도로 내보내 두지 않았다면 복구할 수 없습니다. 업그레이드 전에 쌓인 데이터가 없었다면 보고서에 데이터가 나타나기까지 최대 3일 걸릴 수 있습니다
   - 예 → 4
   - 아니오 → [차단] 조회 불가 — 보관 기간이 지나 기록이 사라짐
4. [처리] 포털 필터로 수동 검색 — 상관 분석과 경보 불가
   - 주체: 관리자
   - 위치: 로그인 로그 · 감사 로그 · 프로비저닝 로그의 필터와 다운로드(Download) 단추(JSON/CSV)
   - 데이터: 단일 화면 필터 결과 (다른 Azure 로그와 조인 불가) · 포털·Graph 조회가 HTTP 429로 제한되면 결과가 비어 보일 수 있음(시스템 수요에 따라 달라짐)
   - 해설: 일회성 조사에는 충분하지만 반복 분석이나 경보에는 한계가 있습니다. 결과가 비면 조회 기간을 더 작게 나눠 다시 조회하고, 계속되면 Log Analytics 작업 영역으로 로그를 보내 조회합니다
5. [끝] 장기 추세 분석·경고·SIEM 연동 없음
   - 주체: 로그
   - 데이터: 내보내기 설정 없음, 업그레이드해도 소급 불가 · Microsoft 365 통합 감사 로그(UAL)는 Entra 로그와 별개로 Purview Audit이 보관 관리
   - 해설: 장기 보관과 자동 탐지를 하려면 미리 진단 설정으로 내보내야 합니다
- 시나리오: 예 :: 보관 기간 안이라 수동 검색만 가능
- 시나리오: 아니오 :: 보관 기간을 벗어나 조회 불가

#### L4 · ① 구성 — 진단 설정으로 대상을 정한다

1. [시작] 관리자가 Entra 관리 센터에 로그인 — Security Administrator
   - 주체: 관리자
   - 위치: entra.microsoft.com — 진단 설정을 만들려면 최소 Security Administrator, 사용자 지정 보안 특성 로그는 Attribute Log Administrator
   - 데이터: Entra 역할 할당 · 진단 설정을 쓰려면 Azure 구독이 필요 · 사용자 지정 보안 특성 로그를 내보내려면 Attribute Log Administrator와 Security Administrator 둘 다 필요
   - 해설: 로그 열람은 Reports Reader로 가능하지만 내보내기 설정은 더 높은 역할이 필요합니다. 사용자 지정 보안 특성 감사 로그는 속성 할당이 노출되지 않도록 디렉터리 감사 로그와 분리해 두기를 권장합니다
2. [처리] 내보낼 대상 리소스를 먼저 준비
   - 주체: 관리자
   - 위치: Azure 포털 › Log Analytics 작업 영역 · 스토리지 계정 · 이벤트 허브(네임스페이스 + 이벤트 허브) 만들기 · 파트너 솔루션은 Azure Native ISV 서비스(Marketplace)
   - 데이터: 구독 · 리소스 그룹 · 대상 리소스 ID · 스토리지는 범용 계정 권장(Blob 스토리지 계정 아님)이며 ListKeys 권한이 있어야 함
   - 해설: 대상이 먼저 있어야 진단 설정 화면에서 고를 수 있습니다
3. [처리] 진단 설정 추가 화면 열기
   - 주체: 관리자
   - 위치: Entra ID › 모니터링 및 상태(Monitoring & health) › 진단 설정(Diagnostic settings) › + 진단 설정 추가(Add diagnostic setting) (감사·로그인 로그 화면의 '내보내기 설정(Export Settings)'으로도 이동)
   - 데이터: 진단 설정 이름 (수정 시 이름은 변경 불가) · 기본은 '일반(General)' 설정, 사용자 지정 보안 특성 로그는 별도 '사용자 지정 보안 특성' 설정
   - 해설: 하나의 테넌트에 진단 설정을 여러 개 만들어 대상별로 나눌 수 있습니다
4. [처리] 로그 범주 선택
   - 주체: 관리자
   - 위치: 진단 설정 › 로그(Categories)
   - 데이터: AuditLogs · SignInLogs · NonInteractiveUserSignInLogs · ServicePrincipalSignInLogs · ManagedIdentitySignInLogs · ProvisioningLogs · ADFSSignInLogs · RiskyUsers · UserRiskEvents · MicrosoftGraphActivityLogs(P1/P2 전용) · NetworkAccessTrafficLogs 등
   - 해설: 조사 목적에 필요한 범주만 골라 비용과 잡음을 줄입니다. 일부 범주는 미리 보기라 선택해도 기능이 일반 공급되기 전에는 데이터가 없을 수 있고, NetworkAccessTrafficLogs는 Global Secure Access(Internet/Private Access)를 쓸 때만 로그가 쌓입니다. MicrosoftServicePrincipalSignInLogs(미리 보기)는 Microsoft 자체 서비스 간 인증을 담은 대용량 로그로 선택(opt-in)이며 조사에 꼭 필요하지 않고 이를 근거로 앱을 비활성화하면 안 됩니다
5. [처리] 대상 선택: Log Analytics 작업 영역
   - 주체: 관리자
   - 위치: 대상 세부 정보(Destination details) › Log Analytics 작업 영역으로 보내기(Send to Log Analytics workspace) › 구독·작업 영역 › 저장(Save)
   - 데이터: 테이블 SigninLogs · AuditLogs · AADNonInteractiveUserSignInLogs · AADServicePrincipalSignInLogs · AADManagedIdentitySignInLogs · AADProvisioningLogs 등, Microsoft Sentinel Entra 커넥터 자동 활성화 · 작업 영역 데이터에 접근할 권한이 있어야 함
   - 해설: KQL 분석, 워크북, 경고를 쓰려면 작업 영역으로 보내는 것이 기본 선택입니다
6. [처리] 대상 선택: Storage · Event Hub
   - 주체: 관리자
   - 위치: 대상 세부 정보 › 스토리지 계정에 보관(Archive to a storage account) / 이벤트 허브로 스트림(Stream to an event hub)
   - 데이터: 스토리지는 JSON 보관(진단 설정의 스토리지 보존 일수 기능은 지원 중단되어 2025-09-30에 모든 환경에서 비활성화 → 스토리지 수명 주기 관리 사용), 이벤트 허브는 Splunk · SumoLogic 등 SIEM 연동
   - 해설: 거의 조회하지 않는 장기 보관은 스토리지, 외부 SIEM 연동은 이벤트 허브를 씁니다. 이전에 보존 일수를 설정한 진단 설정을 편집하면 해당 항목이 여전히 보이지만 보존 기능은 동작하지 않습니다
7. [처리] 저장 후 로그 도착 확인
   - 주체: 관리자
   - 위치: 진단 설정 › 저장 → 작업 영역 › 로그
   - 데이터: 첫 로그가 대상에 보이기까지 최대 3일 지연될 수 있음
   - 해설: 저장 직후 비어 있어도 오류로 단정하지 않고 지연 시간을 고려합니다. Graph 활동 로그는 진단 설정에서 해당 범주를 켠 시점부터 수집이 시작됩니다
8. [처리] 대상 쪽 보관 기간 정책 설정
   - 주체: 관리자
   - 위치: Azure 포털 › Log Analytics 작업 영역 › 설정(Settings) › 사용량 및 예상 비용(Usage and estimated costs) › 데이터 보존(Data Retention) · 테이블별은 Tables › 테이블 관리 · 스토리지는 Azure Storage 수명 주기 관리 정책
   - 데이터: Analytics 테이블 기본 보존 30일(일부 로그 테이블은 90일) · 분석 보존은 최대 2년(730일), 총 보존은 최대 12년(4,383일) · 31일 분석 보존은 수집 가격에 포함 · 보존 설정 변경은 Log Analytics Contributor 수준 권한 필요
   - 해설: Entra 기본 보관과 별개로 대상 서비스에서 보관 기간과 비용을 관리합니다. 보존이 30일인 작업 영역도 데이터를 31일까지 둘 수 있으므로 정확히 30일만 보관해야 하면 API로 immediatePurgeDataOn30Days를 설정합니다
9. [끝] 열람·분석 권한 부여
   - 주체: 관리자
   - 위치: Azure RBAC (Log Analytics Reader · Monitoring Reader — 열람 / Log Analytics Contributor · Monitoring Contributor — 설정 변경) + Entra 역할 (Reports Reader · Security Reader · Global Reader — 열람 / Security Administrator — 진단 설정 변경)
   - 데이터: 작업 영역 접근 권한 · Entra 역할 할당
   - 해설: 작업 영역에 접근할 수 있어야 로그를 조회하고 워크북을 볼 수 있습니다

#### L4 · ② 활성 — 로그가 대상에 쌓이고 질의된다

1. [시작] 사용자가 앱에 로그인
   - 주체: 사용자
   - 위치: 브라우저 · 앱 → login.microsoftonline.com
   - 데이터: 로그인 요청 (앱 · 자격 증명 · 클라이언트 정보 · IP)
   - 해설: 로그인 요청이 Entra ID에 도착하면서 기록 대상 이벤트가 시작됩니다
2. [처리] Entra ID가 인증과 조건부 액세스를 평가
   - 주체: Entra ID
   - 데이터: 결과 코드(ResultType 문자열 "0" = 성공, 그 외 5~6자리 오류 코드) · ConditionalAccessStatus(success · failure · notApplied) · 위험 수준(RiskLevelDuringSignIn은 P2 고객만 값이 채워지고 그 외는 hidden)
   - 해설: 인증 결과가 성공이든 실패든 이후 로그에 기록됩니다. 오류 코드는 login.microsoftonline.com/error에서 조회할 수 있습니다
3. [처리] 로그인 로그 이벤트가 만들어짐
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 로그인 로그 (대화형 · 비대화형 · 서비스 주체 · 관리 ID 탭)
   - 데이터: SigninLogs: UserPrincipalName · AppDisplayName · IPAddress · ResultType · ConditionalAccessStatus · CorrelationId · IsInteractive
   - 해설: 로그인 종류별로 서로 다른 로그 범주와 테이블이 쓰입니다. 포털은 같은 CorrelationId의 재시도(예: MFA 실패 후 성공)를 하나의 로그인으로 합쳐 최종 결과를 보여 주지만 Log Analytics에는 요청마다 한 행씩 쌓입니다
4. [처리] 관리자가 사용자·정책·앱을 변경
   - 주체: 관리자
   - 데이터: 변경 대상(사용자 · 그룹 · 앱 · 정책 · 라이선스) · 변경 내용
   - 해설: 포털이나 Graph로 한 구성 변경은 감사 대상이 됩니다
5. [처리] 감사 로그 이벤트가 만들어짐
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 감사 로그 (그룹·라이선스 등 각 영역의 감사 로그 바로가기는 범주 필터가 자동 설정, 예: GroupManagement)
   - 데이터: AuditLogs: ActivityDisplayName · OperationName · InitiatedBy · TargetResources · Result(success · failure · timeout) · ResultType(Success · Failure) · LoggedByService · AADOperationType(Add · Update · Delete · Other)
   - 해설: 누가 무엇을 언제 바꿨는지가 감사 로그 한 행으로 남습니다
6. [처리] 로그 파이프라인이 진단 설정에 따라 라우팅
   - 주체: Entra ID
   - 데이터: 선택한 로그 범주 → 설정된 대상으로 복제 (설정 저장 후 첫 로그는 최대 3일 지연)
   - 해설: 포털 보관과 별개로 진단 설정에 지정된 대상에도 같은 이벤트가 전달됩니다. 진단 설정이 여러 개면 대상마다 복제됩니다
7. [처리] Log Analytics 작업 영역에 테이블로 적재
   - 주체: 리소스
   - 위치: Log Analytics 작업 영역 › 테이블 SigninLogs · AuditLogs · AADNonInteractiveUserSignInLogs · AADServicePrincipalSignInLogs · AADManagedIdentitySignInLogs
   - 데이터: TimeGenerated · CorrelationId 등 열을 가진 행 (AuditLogs는 Basic 테이블 플랜 미지원)
   - 해설: 적재된 행은 KQL로 조회하고 다른 Azure 로그와 함께 분석할 수 있습니다
8. [처리] KQL 조회 · 워크북 · 경고 · Sentinel로 활용
   - 주체: 관리자
   - 위치: Entra ID › 모니터링 및 상태 › Log Analytics · 워크북 (최소 Reports Reader)
   - 데이터: KQL 결과 · 경고 규칙 · Sentinel 분석 규칙
   - 해설: 집계·시각화·탐지를 같은 데이터로 수행해 조사 속도를 높입니다. Log Analytics 화면은 LogManagement 범주의 기본 쿼리 목록과 스키마를 함께 보여 줍니다
9. [끝] Storage · Event Hub 대상으로도 병행 전달

   - 데이터: JSON blob(장기 보관) · 이벤트 허브 스트림(SIEM)
   - 해설: 같은 이벤트가 장기 보관과 외부 SIEM에도 함께 전달됩니다

### L3 · B · KQL 조회 — SigninLogs · AuditLogs 실제 열로 분석

#### L4 · 로그인 실패 → CA 결과 → 변경 이력 순으로 파고든다

1. [시작] Log Analytics에서 쿼리 화면 열기
   - 주체: 관리자
   - 위치: Entra ID › 모니터링 및 상태(Monitoring & health) › Log Analytics (또는 Azure 포털의 작업 영역 › 로그) — 열람 최소 Reports Reader, 기본 쿼리가 실행되고 LogManagement 범주에 쿼리 목록이 있음
   - 데이터: SigninLogs · AuditLogs 테이블이 작업 영역에 있어야 함 · Entra ID P1/P2 라이선스와 작업 영역 접근 권한 필요
   - 해설: 진단 설정으로 데이터가 적재된 작업 영역에서만 쿼리할 수 있습니다
2. [처리] 실패한 로그인 요약
   - 주체: 관리자
   - 데이터: SigninLogs | where ResultType != "0" | summarize count() by ResultType, ResultDescription (ResultType은 문자열 오류 코드 5~6자리, 0 = 성공)
   - 해설: 어떤 오류 코드가 가장 많은지 보고 원인을 좁힙니다. 코드 의미는 login.microsoftonline.com/error에서 찾습니다
3. [처리] 조건부 액세스 결과 확인
   - 주체: 관리자
   - 데이터: SigninLogs: ConditionalAccessStatus(success · failure · notApplied) · ConditionalAccessPolicies(dynamic) · AppliedConditionalAccessPolicies(string)
   - 해설: 어떤 정책이 적용돼 성공·실패했는지 로그인 한 건 단위로 확인합니다
4. [처리] 위험·인증 요구 조건 확인
   - 주체: 관리자
   - 데이터: SigninLogs: RiskLevelDuringSignIn · RiskState · AuthenticationRequirement(로그인 성공에 필요했던 최고 인증 수준) · AuthenticationDetails · AuthenticationMethodsUsed · AuthenticationRequirementPolicies(조건부 액세스 · 사용자별 MFA · ID 보호 · 보안 기본값)
   - 해설: MFA가 요구됐는지, 어떤 방법으로 통과했는지를 함께 봅니다. 위험 관련 열은 P2 고객만 값이 채워지고 그 외에는 hidden으로 반환됩니다
5. [처리] GSA 경유 로그인 식별
   - 주체: 관리자
   - 데이터: SigninLogs: IsThroughGlobalSecureAccess(bool) · GlobalSecureAccessIpAddress(string) · 네트워크 로그는 NetworkAccessTrafficLogs
   - 해설: Global Secure Access를 거친 로그인만 골라 네트워크 로그와 맞춰 볼 수 있습니다
6. [처리] 감사 로그에서 변경 주체·대상 확인
   - 주체: 관리자
   - 데이터: AuditLogs | where TimeGenerated > ago(7d) | where Result == "failure" | project TimeGenerated, ActivityDisplayName, InitiatedBy, TargetResources (Result 값: success · failure · timeout · unknownFutureValue)
   - 해설: 실패한 관리 작업과 누가 시도했는지를 한 번에 확인합니다. InitiatedBy와 TargetResources는 dynamic 열이라 필요하면 parse_json으로 펼칩니다
7. [처리] 서비스별로 좁히기 — Verified ID 활동 예
   - 주체: 관리자
   - 데이터: AuditLogs | where LoggedByService == "Verified ID" | summarize count() by ActivityDisplayName (LoggedByService 값 예: Self-service Password Management · Core Directory · B2C · Invited Users · Privileged Identity Management)
   - 해설: LoggedByService 열로 서비스별 감사 활동만 모아 집계할 수 있습니다
8. [처리] CorrelationId로 두 테이블 연결
   - 주체: 관리자
   - 데이터: SigninLogs · AuditLogs 모두 CorrelationId 열 보유 · 같은 로그인의 재시도 행은 CorrelationId로 묶어 최종 상태를 봄 (summarize arg_max(TimeGenerated, ResultType, ConditionalAccessStatus) by CorrelationId, UserPrincipalName)
   - 해설: 같은 요청 흐름에서 생긴 이벤트를 한 묶음으로 추적합니다. 로그인 로그의 CorrelationId는 클라이언트가 로그인을 시작할 때 보낸 식별자이고 감사 로그에서는 클라이언트가 넘긴 선택 GUID입니다
9. [처리] 쿼리를 경고 규칙으로 저장
   - 주체: 관리자
   - 위치: Log Analytics › 경고 규칙 만들기 / Microsoft Sentinel 분석 규칙 (Entra 로그를 작업 영역에 보내면 Sentinel의 Microsoft Entra 데이터 커넥터가 자동 활성화)
   - 데이터: 쿼리 · 평가 주기 · 임계값 [확인 필요: 경고 규칙 만들기에 필요한 최소 역할 · 평가 주기 범위]
   - 해설: 반복 조회하는 쿼리는 경고로 만들어 사람이 열어 보지 않아도 탐지하게 합니다
10. [끝] 결과를 쿼리 팩이나 워크북으로 공유
   - 주체: 관리자
   - 위치: Entra ID › 모니터링 및 상태 › 워크북 · Azure Monitor 쿼리 팩 [확인 필요: 쿼리 팩 메뉴 · 권한]
   - 해설: 팀이 같은 쿼리를 재사용해 조사 품질을 일정하게 유지합니다

> 교육 포인트: SigninLogs의 ResultType은 문자열이고 0이 성공입니다. 숫자 0이 아니라 "0"과 비교해야 합니다.
>
> 주의: AuditLogs의 ResultType은 Success/Failure이고 Result는 success/failure 등 별도 열이어서 로그인 로그와 값 체계가 다릅니다. Log Analytics에는 한 번의 로그인이 재시도마다 여러 행으로 쌓이므로 CorrelationId로 묶어 최종 상태를 봅니다.

1. [시작] 정기 점검 요구 — 레거시 인증 · MFA 공백
   - 주체: 관리자
   - 데이터: 점검 주제 예: 레거시 인증 로그인 · MFA 미적용 로그인
   - 해설: 매번 쿼리를 새로 쓰기보다 템플릿으로 반복 점검하려는 상황입니다
2. [처리] 사전 조건 확인
   - 주체: 관리자
   - 위치: Azure 포털 › Log Analytics 작업 영역(접근 권한) · Entra 관리 센터 › 역할 및 관리자
   - 데이터: Entra ID P1 + Log Analytics 작업 영역과 접근 권한 + Azure Monitor 역할(열람: Monitoring Reader · Log Analytics Reader / 수정: Monitoring Contributor · Log Analytics Contributor) + Entra 역할(열람: Reports Reader · Security Reader · Global Reader / 진단 설정 변경: Security Administrator)
   - 해설: 워크북은 작업 영역 데이터를 읽어 그리므로 진단 설정이 먼저 있어야 하고, 작업 영역은 워크북을 쓰기 전에 만들어 두어야 합니다
3. [처리] 워크북 갤러리 열기
   - 주체: 관리자
   - 위치: Entra ID › 모니터링 및 상태(Monitoring & health) › 워크북(Workbooks) › 공개 템플릿(Public Templates) (탭: Workbooks · Public Templates · My Templates · '갤러리 전체 찾아보기(Browse across galleries)'로 Entra 외 템플릿도 조회)
   - 데이터: Workbooks · Public Templates · My Templates · 열람 최소 Reports Reader
   - 해설: 자주 쓰는 시나리오가 미리 만들어진 템플릿으로 제공되며 이름으로 검색할 수 있고 로딩에 시간이 걸릴 수 있습니다
4. [처리] 점검용 템플릿 선택
   - 주체: 관리자
   - 위치: 워크북 갤러리의 '사용(Usage)' 섹션 — 'MFA 공백'은 템플릿이 아니라 GitHub의 JSON을 + 새로 만들기(New) › 고급 편집기(Advanced Editor)에 붙여 넣고 적용(Apply)
   - 데이터: 템플릿 예: Sign-ins using legacy authentication(필터: 시간 범위 최대 90일 · UPN · 애플리케이션 · 성공/실패) · Authentication prompts analysis · 가져오기: Multifactor Authentication Gaps(MultiFactorAuthenticationGaps.workbook)
   - 해설: 레거시 인증을 꺼도 안전한지, MFA 요구가 적용되지 않은 로그인은 어디인지(앱·사용자·OS·위치별) 즉시 볼 수 있습니다. 레거시 워크북은 'Exchange ActiveSync'처럼 구체적 프로토콜·클라이언트 이름으로 보이는 로그인만 다루고 브라우저·최신 클라이언트는 현대 인증입니다
5. [판단] 작업 영역에 해당 기간의 데이터가 있는가?
   - 주체: 로그
   - 데이터: 진단 설정 연결 상태 · 데이터 적재 지연(첫 로그 최대 3일)
   - 해설: 비어 있으면 워크북 문제가 아니라 대부분 진단 설정·권한 문제입니다
   - 예 → 6
   - 아니오 → [끝] 빈 결과 — 진단 설정과 권한을 점검
6. [처리] 편집 후 내 워크북으로 저장
   - 주체: 관리자
   - 위치: 워크북 › 편집(Edit) › 각 요소의 편집 › 편집 완료(Done editing) › 저장(Save) — 제목(Title) · 구독 · 리소스 그룹 · 위치(Location) › 적용(Apply)
   - 데이터: 워크북 리소스 (선택 시 스토리지 계정에 저장) · 선택한 리소스 그룹에 워크북을 저장할 수 있는 권한 필요
   - 해설: 조직 기준에 맞게 조건을 고쳐 저장하면 팀이 같은 화면을 공유합니다. 처음부터 만들려면 + 새로 만들기(New)에서 요소를 추가합니다
7. [처리] 사용 현황 보고서로 앱·인증 방법 추세 확인
   - 주체: 관리자
   - 위치: Entra ID › 모니터링 및 상태 › 사용량 및 인사이트(Usage & insights) [확인 필요: 한글 메뉴명]
   - 데이터: 애플리케이션 활동(미리 보기) · AD FS 애플리케이션 활동(최근 30일) · 인증 방법 활동(등록·사용 탭) · 서비스 주체 로그인 활동(미리 보기) · 애플리케이션 자격 증명 활동(미리 보기) — P1/P2 필요
   - 해설: 앱 로그인 성공률과 사용자가 선호하는 인증 방법 추세를 한눈에 확인합니다. 최소 역할은 Reports Reader이고 Security Reader·Security Administrator도 볼 수 있으며 Graph에서는 beta 엔드포인트(/reports)를 씁니다
8. [끝] 결과로 정책 조정
   - 주체: 관리자
   - 해설: 레거시 인증 의존이 없음이 확인되면 조건부 액세스의 '레거시 인증 차단(Block legacy authentication)' 정책을 켜는 식으로 조치에 연결합니다
- 시나리오: 예 :: 데이터가 있어 워크북 저장 후 추세로 정책 조정
- 시나리오: 아니오 :: 데이터가 없어 빈 결과로 끝남

> 교육 포인트: 워크북은 읽기용 시각화이고 자료의 원천은 진단 설정으로 쌓은 작업 영역입니다. 진단 설정이 없으면 워크북은 비어 있습니다.

> 주의: 템플릿 이름과 메뉴 이름은 변경될 수 있어 교육 전에 포털 화면과 대조합니다 [확인 필요: 한글 메뉴명 · 템플릿 이름]. 'MFA 공백(Multifactor Authentication Gaps)'은 현재 템플릿이 아니라 GitHub JSON 가져오기로 씁니다.
