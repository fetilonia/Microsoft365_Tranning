## L2 · 애플리케이션 — 앱 검색 · Private DNS · 엔터프라이즈 앱 연결

- 설정(Control Plane): Application discovery (Quick Access 트래픽에서 앱 세그먼트 후보 도출 → Add to new application · Add to an existing application) | Quick Access › Private DNS (DNS 접미사) · 엔터프라이즈 애플리케이션 (커넥터 그룹 · 앱 세그먼트 · 사용자/그룹 할당 · Properties) · 앱별 조건부 액세스 연결
- 강제(Enforcement): Global Secure Access 클라이언트 (NRPT 규칙 · 앱 세그먼트 전달 규칙 · synthetic IP) | SSE 에지 DNS 프록시 → 개인 네트워크 커넥터 → 사내 DNS · Entra ID (앱 할당 · 앱별 조건부 액세스)
- 증적(Evidence): Application discovery 표 (Users · Transactions · Devices · First/Last access) · Entra Recommendations · GSA 트래픽 로그 | KQL: NetworkAccessTraffic (AppSegmentId · ApplicationObjectId · DnsQueryName · DnsResponseOrigin)
- 메뉴(Admin Center): Global Secure Access > 애플리케이션 > Application discovery · Quick Access (Private DNS 탭) · 엔터프라이즈 애플리케이션 (Users and groups · Network access properties · Conditional Access)
- 라이선스(License): Private Access 라이선스(Entra Suite 포함) + 사용자당 Entra ID P1/P2, 커넥터 그룹 관리에도 P1/P2 필요 [확인 필요: 고객 라이선스 · Application discovery · Private DNS 전용 라이선스 문구는 확인한 문서에 별도로 없음]

### L3 · 0 · 기능 상태 전이 — 앱 후보를 모르는 Quick Access 단독 → 앱 검색 · Private DNS · 앱 등록 구성 → 이름 확인과 앱별 판정

#### L4 · ⓪ 비활성 — 앱 검색 · Private DNS · 앱별 등록이 없으면 사내 앱이 한 묶음으로 보인다

1. [시작] 사용자가 접미사 없는 짧은 이름으로 사내 앱에 접속 — 예: https://benefits
   - 주체: 사용자
   - 위치: 브라우저 주소창 → 사내 웹 앱 (예: 10.8.0.5)
   - 데이터: 단일 레이블 이름 benefits · 포트 443. 앱은 FQDN이 아니라 IP 범위(예: 10.8.0.0–10.8.255.255)로만 Quick Access에 게시돼 있다고 가정합니다
   - 해설: 사내에서는 짧은 이름만 쳐도 열리던 앱을 재택 사용자가 같은 방식으로 열어 봅니다
2. [처리] Private DNS 접미사가 없음 — 클라이언트가 이름 질의를 가로챌 근거가 없음
   - 주체: GSA 클라이언트
   - 위치: Global Secure Access › Applications › Quick access › Private DNS 탭 — 체크박스 미선택 · 접미사 0건
   - 데이터: Private DNS를 쓰지 않으면 클라이언트는 질의를 장치의 DNS 서버(보통 DHCP로 받은 가정 DNS)로 그대로 보냅니다. 접미사별 NRPT 규칙(Name Resolution Policy Table)과 단일 레이블용 globalsecureaccess.local 규칙도 만들어지지 않습니다
   - 해설: 이름을 사내 DNS로 풀게 하는 장치는 Private DNS 접미사 등록뿐입니다
3. [처리] 가정 DNS는 내부 이름을 모름 — 주소를 얻지 못함
   - 주체: 외부
   - 위치: 가정 라우터 · ISP의 DNS 서버
   - 데이터: 응답 없음 또는 이름 없음. IP 범위 세그먼트가 있어도 주소를 알아야 그 범위로 접속을 시도할 수 있습니다
   - 해설: 앱 세그먼트가 열려 있어도 이름이 풀리지 않으면 클라이언트가 터널링할 접속 자체가 생기지 않습니다 [판단: 문서는 이 경우를 Private DNS 도입 이유로 설명]
4. [처리] 앱 후보를 알 수 없음 — Application discovery를 보지 않고 Quick Access를 크게 열어 둠
   - 주체: 관리자
   - 위치: Global Secure Access › Applications › Application discovery (조회하지 않음) · Quick Access 앱 세그먼트 (넓은 IP 범위 · 와일드카드 FQDN)
   - 데이터: Quick Access는 VPN을 빨리 대체하는 전환 단계용으로, 넓은 IP 범위와 *.contoso.com 같은 와일드카드를 게시합니다. 어떤 세그먼트를 몇 명이 쓰는지는 Application discovery 표를 봐야 드러납니다
   - 해설: 누가 어떤 앱을 쓰는지 모른 채로는 앱 단위로 쪼갤 기준이 없습니다
5. [처리] 사용자 할당과 조건부 액세스가 Quick Access 앱 하나에 공통으로 걸림
   - 주체: Entra ID
   - 위치: Global Secure Access › Applications › Quick access › Edit application settings › Users and groups · Conditional Access
   - 데이터: Quick Access는 단일 엔터프라이즈 앱 하나에 여러 세그먼트가 들어 있고 모든 세그먼트가 같은 조건부 액세스 정책을 공유합니다. 정책을 바꾸면 모든 세그먼트에 영향이 갑니다
   - 해설: 중요한 앱에만 MFA나 규정 준수 디바이스를 더 요구하고 싶어도 세그먼트별로 나눌 수 없습니다
6. [끝] 사내 앱 가시성 · 최소 권한이 모두 부족한 상태가 남음
   - 주체: 로그
   - 위치: Global Secure Access › Monitor › Traffic logs (Private access 필터) — AccessType = QuickAccess 행만 나옴
   - 데이터: NetworkAccessTraffic의 AccessType이 QuickAccess로만 기록되어 앱 단위로 쪼개 본 통계가 없고, Application discovery 표 기반의 앱 전환 추천도 쓰지 못합니다
   - 해설: 이름은 안 풀리고, 앱은 한 덩어리이며, 누가 무엇을 쓰는지 근거가 없는 상태에서 VPN 대체가 멈춥니다

> 교육 포인트: 이 L2의 세 기능은 "Quick Access에서 per-app으로 옮겨 가는 길"을 돕습니다 — Application discovery가 어떤 앱을 쓰는지 보여 주고, 엔터프라이즈 앱이 앱 단위 할당·조건부 액세스를 걸게 하며, Private DNS가 내부 이름을 풀어 줍니다.
>
> 주의: Application discovery는 Quick Access로 흐른 트래픽만 집계합니다. Quick Access가 없거나 사용자가 그 경로를 쓴 적이 없으면 표가 비는 것이 정상입니다.

#### L4 · ① 구성 — Private DNS 접미사를 등록하고 검색 결과로 앱을 만들어 할당 · 조건부 액세스를 건다

1. [시작] 관리자가 Entra 관리 센터에 로그인 — 역할 · 사전 조건 확인
   - 주체: 관리자
   - 위치: entra.microsoft.com — Global Secure Access Administrator (Application discovery 보기·앱 생성) · Application Administrator (앱 · 커넥터 그룹) · Conditional Access Administrator (정책)
   - 데이터: Quick Access가 이미 구성돼 있어야 하고 활성 커넥터 1개 이상(최소 버전 1.5.3417.0), 클라이언트가 설치된 장치(Windows · macOS · Android · iOS)가 필요합니다. 커넥터 그룹 관리는 Entra ID P1/P2가 필요합니다
   - 해설: Application discovery는 Quick Access 트래픽을 보는 기능이라 Quick Access와 클라이언트가 먼저 있어야 합니다
2. [처리] Private DNS 켜기 — Quick Access 앱의 탭
   - 주체: 관리자
   - 위치: Global Secure Access › Applications › Quick access › Private DNS 탭 › enable private DNS 체크박스 선택
   - 데이터: Graph PATCH /beta/applications/{appObjectId}/onPremisesPublishing → isDnsResolutionEnabled = true (Quick Access 유형 앱에서만 사용 가능)
   - 해설: Private DNS는 별도 메뉴가 아니라 Quick Access 앱 안의 탭이며, 엔터프라이즈 앱 쪽에는 이 스위치가 없습니다
3. [처리] DNS 접미사 추가 — 사내 이름 공간 등록
   - 주체: 관리자
   - 위치: Private DNS 탭 › Add DNS suffix › 접미사 입력 › Add › Save
   - 데이터: 예: contoso.local. Kerberos SSO를 쓰려면 최소한 사용자를 동기화하는 Active Directory 포리스트의 최상위 접미사를 넣습니다. Graph: POST …/onPremisesPublishing/segmentsConfiguration/microsoft.graph.ipSegmentConfiguration/applicationSegments — destinationHost "app1.dns.com" · destinationType "dnsSuffix"
   - 해설: 이 접미사로 끝나는 이름은 클라이언트가 사내 DNS로 풀도록 보내며, 엔터프라이즈 앱 세그먼트의 FQDN을 풀 때도 같은 경로를 탑니다
4. [처리] Application discovery에서 최근 30일 사용 세그먼트를 확인
   - 주체: 관리자
   - 위치: Global Secure Access › Applications › Application discovery (기본 정렬 = Users 내림차순 · 시간 범위 · 사용자별 필터 · Search로 FQDN/IP/포트)
   - 데이터: 열: Destination FQDN · Destination IP · Transport protocol · Destination port · Users · Transactions · Devices · Sent bytes · Received bytes · Last access · First access
   - 해설: 사람들이 실제로 쓰는 세그먼트가 위에 올라오므로 앱으로 분리할 순서를 정하기 쉽습니다
5. [처리] 새 앱으로 전환 — 선택한 세그먼트로 Global Secure Access 앱 생성
   - 주체: 관리자
   - 위치: Application discovery 목록에서 세그먼트 선택 › Add to new application › Create Global Secure Access application › Name · Connector Group 선택 › Save (세그먼트 수동 추가·삭제 가능)
   - 데이터: 한 앱이 한 세그먼트인 경우(예: filesrv.contoso.com TCP 445)와 여러 포트·서버를 묶는 경우(예: AD DS) 모두 가능. 기존 앱에 넣으려면 Add to an existing application › Edit Global Secure Access application(새 세그먼트 Pending · 기존 Success) › Save
   - 해설: 앱을 하나 만들면 Private Access용 엔터프라이즈 앱 객체가 생기고, 그 앱 단위로 할당과 조건부 액세스를 걸 수 있게 됩니다
6. [처리] 엔터프라이즈 앱 속성 확인 — 로그인 허용 · 할당 필요 · 가시성
   - 주체: 관리자
   - 위치: Global Secure Access › Applications › Enterprise applications › {앱} › Properties (필터를 모두 지우고 앱 검색)
   - 데이터: Enabled for users to sign in? (서비스 주체 accountEnabled) · Assignment required · Visible to users · Homepage URL · Notes. Graph 사설 앱 생성 예제의 서비스 주체는 appRoleAssignmentRequired: true로 반환됩니다 [확인 필요: 포털에서 Private Access 앱의 Assignment required · Visible to users 기본값]
   - 해설: Enabled for users to sign in?이 No이면 할당되어 있어도 토큰이 발급되지 않습니다
7. [처리] 사용자·그룹 할당 조정 — 최소 권한으로 다시 좁힘
   - 주체: 관리자
   - 위치: Enterprise applications › {앱} › Users and groups › Add user/group (Quick Access는 Edit application settings › Users and groups)
   - 데이터: 앱 역할 User를 사용자에게 직접 또는 그룹으로 할당하며 중첩 그룹은 지원되지 않습니다. discovery로 만든 새 앱은 생성 시 Quick Access의 할당을 상속하므로 검증 뒤 그 앱에 필요한 사용자만 남깁니다. Application discovery 세그먼트 상세의 Users 탭(최근 30일 사용자)이 근거가 됩니다. Graph: POST /beta/servicePrincipals/{id}/appRoleAssignments
   - 해설: 상속된 넓은 할당을 그대로 두면 앱을 쪼개고도 최소 권한이 되지 않습니다
8. [처리] 앱별 조건부 액세스 정책 연결
   - 주체: 관리자
   - 위치: Enterprise applications › {앱} › Conditional Access › New policy (대상 리소스에 해당 앱이 자동 지정) 또는 Entra ID › Conditional Access › Policies › + Create new policy
   - 데이터: 대상 사용자 Include All users · Exclude 비상 접근(break-glass) 계정. 부여 제어 예: Require multifactor authentication · Require device to be marked as compliant · Require Microsoft Entra hybrid joined device. Enable policy는 Report-only로 먼저 검증한 뒤 On으로 전환합니다
   - 해설: 앱마다 다른 조건을 걸 수 있다는 점이 Quick Access와 가장 크게 다릅니다
9. [끝] Private access 프로필 켜기 · 반영 대기
   - 주체: 관리자
   - 위치: Global Secure Access › Connect › Traffic forwarding › Private access profile 토글
   - 데이터: 프로필이 켜져야 클라이언트가 앱 세그먼트 트래픽을 에지로 보냅니다. 새 앱 정의가 클라이언트에 나타나기까지 약 5~10분, 할당 등 구성 변경은 클라이언트와 약 15분 걸려 동기화됩니다. Graph: PATCH /beta/networkAccess/forwardingProfiles/{id} {"state":"enabled"}
   - 해설: 구성이 끝나도 클라이언트 반영 대기 시간이 있어 바로 안 되면 15분 정도 기다린 뒤 점검합니다

> 교육 포인트: 순서는 "접미사 등록(이름) → 후보 확인(검색) → 앱 생성 → 할당 → 조건부 액세스 → 프로필"입니다. 앱을 만든 뒤 할당을 다시 좁히는 단계가 최소 권한의 핵심입니다.
>
> 주의: Private DNS 접미사를 등록하면 그 접미사로 끝나는 모든 질의가 Private DNS로 풀립니다. 범위를 넓게 잡을수록 영향도 커집니다.

#### L4 · ② 활성 — 사내 이름을 풀고 앱 세그먼트로 일치시킨 뒤 앱별로 판정한다

1. [시작] 사용자가 사내 이름으로 앱에 접속 — 예: app.contoso.local 또는 benefits
   - 주체: 사용자
   - 위치: 브라우저 · 원격 데스크톱 · 파일 탐색기 → 사내 앱 이름
   - 데이터: 목적지 이름 · 포트 · 프로토콜
   - 해설: 사용자는 VPN 없이 평소 이름 그대로 접속합니다
2. [판단] 이름이 등록된 Private DNS 접미사와 일치하는가?
   - 주체: GSA 클라이언트
   - 위치: 클라이언트가 만든 NRPT 규칙 (Get-DnsClientNrptPolicy로 확인) · 단일 레이블용 <appid>.globalsecureaccess.local
   - 데이터: 접미사마다 NRPT 규칙이 있어 일치한 질의는 synthetic IP(보통 6.6.255.254)로 향합니다
   - 해설: 접미사에 걸리면 이름 확인이 사내 DNS로 가고, 걸리지 않으면 장치의 원래 DNS로 갑니다
   - 접미사 일치 → 3
   - 접미사 불일치 → 4
3. [처리] DNS 프록시 경유로 사내 DNS에서 이름을 풀어 옴
   - 주체: SSE 에지
   - 위치: GSA 에지의 DNS 프록시 → (캐시가 없으면) Quick Access에 지정한 커넥터 그룹의 커넥터 → 커넥터 서버의 OS DNS 설정
   - 데이터: 캐시된 응답이 있으면 바로 반환하고 없으면 커넥터가 사내 DNS 서버에 질의합니다. 클라이언트는 받은 내부 IP를 보관하고 앱에는 synthetic IP를 돌려줍니다
   - 해설: 이름 확인은 사용자 PC가 아니라 에지와 커넥터를 거쳐 사내망 안에서 일어납니다
   - 다음 → 5
4. [판단] 장치 DNS의 응답이 FQDN 앱 세그먼트와 일치하는가?
   - 주체: GSA 클라이언트
   - 위치: 앱 세그먼트(FQDN) 규칙 · 클라이언트가 DNS 응답을 가로챔
   - 데이터: FQDN 세그먼트와 이름이 일치하면 응답 결과와 상관없이(집에서는 풀리지 않아도) 질의 응답을 동적 synthetic IP로 바꿉니다
   - 해설: Private DNS가 없어도 FQDN으로 등록한 앱은 이 방식으로 에지로 들어옵니다
   - 세그먼트 일치 → 5
   - 세그먼트 없음 → [차단] 터널링되지 않음 — 규칙에 없어 직접 전송(Bypassed)
5. [처리] 클라이언트가 앱 세그먼트 규칙(대상 · 포트 · 프로토콜)에 맞춰 에지로 터널링
   - 주체: GSA 클라이언트
   - 위치: GSA 클라이언트 › Advanced Diagnostics › Forwarding profile (Priority 열 · Policy tester)
   - 데이터: 개별 엔터프라이즈 앱 세그먼트가 Quick Access 세그먼트보다 우선합니다. 앱의 클라이언트 쪽 접근 사용(Enable access) 체크를 끄면 그 세그먼트는 터널링되지 않습니다
   - 해설: 같은 대역이 Quick Access에도 있더라도 앱으로 옮긴 세그먼트의 트래픽은 앱 설정으로만 처리됩니다
6. [판단] 사용자가 그 앱에 할당되어 있고 앱별 조건부 액세스를 통과하는가?
   - 주체: Entra ID
   - 위치: SSE 에지 → Entra ID (앱 역할 할당 · 앱에 연결된 조건부 액세스 정책)
   - 데이터: 앱 역할 할당 여부 · MFA · 디바이스 준수 등 부여 제어 결과
   - 해설: 할당이 없거나 조건을 못 채우면 에지에서 끝납니다. Private Access 트래픽 전체에 대한 CA는 미지원이라 앱 단위로만 평가됩니다
   - 통과 → 7
   - 미할당 → [차단] 앱 할당 없음 — 에지에서 거부
   - CA 미충족 → [차단] 앱별 조건부 액세스 요구 미충족
7. [처리] Entra ID가 해당 앱용 토큰을 발급하고 Private Access 서비스가 커넥터 그룹으로 중계
   - 주체: 커넥터
   - 위치: Private Access 서비스 → 앱에 지정한 커넥터 그룹의 커넥터 (중계 · 라우팅 상세는 Private Access 기능 참조)
   - 데이터: 해당 엔터프라이즈 앱 대상 토큰 · 앱 세그먼트 · 커넥터 그룹 매핑
   - 해설: 앱마다 커넥터 그룹을 달리 지정해 네트워크·커넥터 단위로 앱을 격리할 수 있습니다
8. [처리] 커넥터가 사내 DNS로 대상 서버 IP를 확인하고 서버로 전달
   - 주체: 커넥터
   - 위치: 커넥터 → 사내 DNS 서버 → 대상 서버:포트
   - 데이터: 앱 세그먼트로 허용된 대상·포트로만 연결이 열립니다
   - 해설: 이름 확인은 끝까지 사내에서 하고 허용된 앱·포트만 닿습니다
9. [끝] 트래픽 로그 기록 — 앱 단위로 식별
   - 주체: 로그
   - 위치: Global Secure Access › Monitor › Traffic logs (Private access 필터) · Application discovery (Quick Access 경유 시)
   - 데이터: NetworkAccessTraffic: AccessType(QuickAccess/PrivateAccess) · AppSegmentId · ApplicationObjectId · ConnectorGroupId · Action(Allowed/Denied) · DnsQueryName · DnsResponseOrigin(Cache/Onprem) · DnsResponseTime [확인 필요: Private DNS 질의에 DNS 열이 채워지는 조건]
   - 해설: 어느 앱 세그먼트로 누가 허용 또는 거부됐는지 앱 단위로 남습니다
- 시나리오: 접미사 일치 ▸ 통과 :: 사내 DNS로 풀려 앱 할당·CA 통과 후 전달
- 시나리오: 접미사 일치 ▸ 미할당 :: 이름은 풀렸지만 앱 미할당으로 거부
- 시나리오: 접미사 일치 ▸ CA 미충족 :: 이름은 풀렸지만 앱별 CA 미충족으로 거부
- 시나리오: 접미사 불일치 ▸ 세그먼트 일치 ▸ 통과 :: FQDN 세그먼트로 가로채 앱 판정 통과 후 전달
- 시나리오: 접미사 불일치 ▸ 세그먼트 일치 ▸ 미할당 :: FQDN 세그먼트로 들어왔지만 앱 미할당 거부
- 시나리오: 접미사 불일치 ▸ 세그먼트 일치 ▸ CA 미충족 :: FQDN 세그먼트로 들어왔지만 CA 미충족 거부
- 시나리오: 접미사 불일치 ▸ 세그먼트 없음 :: 규칙에 없어 터널링되지 않고 직접 전송

> 교육 포인트: 이름 확인과 앱 판정은 두 단계입니다. Private DNS는 "어느 DNS가 이름을 푸는가"를 정하고, 앱 세그먼트와 엔터프라이즈 앱은 "그 대상에 누가 닿는가"를 정합니다.
>
> 주의: DNS 응답을 가로채 synthetic IP로 바꾸는 동작 때문에 NSLOOKUP은 NRPT 규칙을 따르지 않습니다. 점검은 Resolve-DnsName을 쓰고, NSLOOKUP으로 터널을 통과시키려면 서버로 6.6.255.254를 지정합니다.

### L3 · A · 앱 검색에서 앱 세그먼트까지

#### L4 · 검색 표 읽기 — Application discovery에서 앱으로 만들 후보를 고른다

1. [시작] 관리자가 Application discovery 화면을 연다 — 최근 30일 기준
   - 주체: 관리자
   - 위치: Global Secure Access › Applications › Application discovery (Global Secure Access Administrator 이상)
   - 데이터: 표 범위 = 최근 30일 동안 Global Secure Access 클라이언트로 Quick Access를 통해 접근한 앱 세그먼트
   - 해설: 이 표는 지금 Quick Access 안에서 실제로 쓰이는 세그먼트만 보여 줍니다
2. [판단] 표에 행이 있는가?
   - 주체: 관리자
   - 위치: Application discovery 표
   - 데이터: 행 0건이면 Quick Access가 구성되지 않았거나 사용자가 Quick Access로 접근한 적이 없는 것입니다
   - 해설: 빈 화면은 제품 오류가 아니라 정상적인 빈 상태입니다
   - 행 있음 → 3
   - 빈 표 → [차단] 데이터 없음 — Quick Access 구성과 사용자 트래픽이 먼저 필요
3. [처리] 정렬 · 필터로 후보를 좁힘
   - 주체: 관리자
   - 위치: Application discovery › 시간 범위 · 필터 추가 · 열 정렬 · filter by user · Search (FQDN · IP · 포트)
   - 데이터: 기본 정렬 = Users 내림차순. 특정 사용자가 접근한 세그먼트만 따로 볼 수도 있습니다
   - 해설: 많은 사람이 쓰는 세그먼트를 위에서부터 앱 후보로 검토합니다
4. [처리] 열을 읽어 사용 규모를 판단
   - 주체: 관리자
   - 위치: Application discovery 표의 열
   - 데이터: Destination FQDN · Destination IP · Transport protocol(TCP/UDP) · Destination port · Users · Transactions(연결 수) · Devices · Sent bytes · Received bytes · Last access · First access
   - 해설: 사용자 수와 연결 수를 함께 봐야 자주 쓰는 앱과 한두 번 쓴 대상을 구분할 수 있습니다
5. [처리] 세그먼트 상세에서 사용 추이와 사용자 목록 확인
   - 주체: 관리자
   - 위치: Destination FQDN 또는 Destination IP 선택 › Usage 탭 (Users · Transactions · Devices · Bytes sent · Bytes received, Timespan 조정) · Users 탭
   - 데이터: Users 탭 = 최근 30일에 그 세그먼트에 접근한 사용자 목록
   - 해설: 이 사용자 목록이 나중에 앱에 할당할 사용자·그룹을 정하는 근거입니다
6. [판단] 하나의 앱이 세그먼트 하나로 끝나는가?
   - 주체: 관리자
   - 위치: 후보 세그먼트들의 FQDN · 포트 · 프로토콜
   - 데이터: 대부분 한 앱 = 한 세그먼트이지만 여러 포트 · 프로토콜 · 서버에 걸친 앱도 있습니다
   - 해설: 앱 경계를 어디로 잡느냐가 나중의 할당·조건부 액세스 단위가 됩니다
   - 단일 세그먼트 → 7
   - 여러 세그먼트 → 8
7. [처리] 세그먼트 하나를 앱 하나로 — 예: 파일 서버 · 사내 포털
   - 주체: 관리자
   - 위치: Application discovery 목록 › 세그먼트 한 건 선택
   - 데이터: filesrv.contoso.com · TCP · 445 / internalportal.contoso.com · TCP · 443
   - 해설: 서버·포트가 하나인 앱은 세그먼트 하나로 충분합니다
   - 다음 → 9
8. [처리] 여러 세그먼트를 한 앱으로 묶음 — 예: AD DS
   - 주체: 관리자
   - 위치: Application discovery 목록 › 세그먼트 여러 건 선택 (필요하면 수동 추가)
   - 데이터: dc1.contoso.com · dc2.contoso.com 에 TCP 88 · 135 · 137 · 138 · 389 · 445 · 464 · 636 · 3268 · 3269 와 UDP 88 · 123 · 389 · 464 (고정 high port 포함)
   - 해설: 한 앱이 여러 포트와 서버를 쓰면 선택한 세그먼트를 한 앱으로 묶어 만들고 부족한 것은 직접 추가합니다
9. [끝] 앱으로 만들 후보 세그먼트 선정 완료
   - 주체: 관리자
   - 위치: Application discovery 목록 (선택 상태)
   - 데이터: 선택한 세그먼트 · 대상 사용자 목록
   - 해설: 다음 단계는 Add to new application 또는 Add to an existing application입니다
- 시나리오: 행 있음 ▸ 단일 세그먼트 :: 세그먼트 하나를 앱 하나로 전환할 후보로 선정
- 시나리오: 행 있음 ▸ 여러 세그먼트 :: 여러 포트·서버 세그먼트를 한 앱으로 묶을 후보로 선정
- 시나리오: 빈 표 :: Quick Access 트래픽이 없어 표가 비어 있음

> 교육 포인트: Application discovery는 "추측으로 앱을 쪼개지 않게" 하는 도구입니다. 사용 규모는 Users · Transactions · Devices로, 누가 쓰는지는 Users 탭으로 확인합니다.
>
> 주의: 이 표는 Quick Access를 통과한 트래픽만 담습니다. 이미 per-app으로 옮긴 세그먼트는 Quick Access를 거치지 않으므로, 앱으로 만든 뒤에도 사용자가 새 앱에 접근할 때까지 표에 남을 수 있습니다.
>
> 출처: https://learn.microsoft.com/entra/global-secure-access/how-to-application-discovery

#### L4 · 앱 만들기와 세그먼트 입력 — 대상 유형 · 포트 · 겹침 제한을 지킨다

1. [시작] Recommendations 카드에서 전환할 세그먼트를 확인 — Onboard new discovered application segments to enterprise applications
   - 주체: 관리자
   - 위치: Microsoft Entra 관리 센터 › Identity › Overview › Recommendations 탭 › 해당 권장 사항 › Action plan
   - 데이터: 추천 이름: Onboard new discovered application segments to enterprise applications. 이 기능은 현재 Australia와 Africa에서 사용할 수 없다고 안내됩니다
   - 해설: 추천은 새로 발견된 세그먼트를 엔터프라이즈 앱으로 옮기라고 알려 줍니다
2. [판단] 새 앱으로 만드는가, 기존 앱에 더하는가?
   - 주체: 관리자
   - 위치: Application discovery 목록에서 세그먼트 선택 후 상단 버튼
   - 데이터: Add to new application / Add to an existing application
   - 해설: 이미 같은 앱 성격의 Global Secure Access 앱이 있으면 거기에 더하는 쪽이 앱 수를 줄입니다
   - 새 앱 → 3
   - 기존 앱 → 4
3. [처리] 새 앱 생성 — 이름 · 커넥터 그룹 지정
   - 주체: 관리자
   - 위치: Add to new application › Create Global Secure Access application › Name · Connector Group › Save
   - 데이터: 활성 커넥터가 1개 이상인 커넥터 그룹이 필요합니다. 생성 시 Quick Access에 할당된 사용자·그룹이 새 앱으로 상속됩니다
   - 해설: 상속으로 기존 사용자의 접근이 갑자기 끊기지 않고, 이후에 앱에 맞게 좁힙니다
   - 다음 → 5
4. [처리] 기존 앱 수정 — 선택 세그먼트는 Pending으로 표시
   - 주체: 관리자
   - 위치: Add to an existing application › 앱 선택 › Edit Global Secure Access application › Name · Connector Group · 세그먼트 수정 › Save
   - 데이터: 선택한 세그먼트 = Pending, 이미 구성된 세그먼트 = Success
   - 해설: 저장해야 Pending이 앱 구성으로 반영됩니다
5. [처리] 대상 유형 선택 — IP · FQDN · CIDR · 범위
   - 주체: 관리자
   - 위치: 앱 › Add application segment (Quick Access는 Add Quick Access application segment) › Create application segment 패널 › Destination type
   - 데이터: IP address(IPv4, 예: 192.168.2.1) · Fully qualified domain name (와일드카드 FQDN은 *.contoso.com 형식) · IP address range (CIDR, 예: 192.168.2.0/24) · IP address range (IP to IP, 예: 192.168.2.1–192.168.2.10). Graph destinationType: ipAddress · ipRange · ipRangeCidr · fqdn · dnsSuffix
   - 해설: 유형을 고르면 입력 칸이 그에 맞게 바뀝니다. dnsSuffix는 Private DNS 접미사 등록에 쓰는 유형입니다
6. [처리] 포트 · 프로토콜 입력
   - 주체: 관리자
   - 위치: Create application segment 패널 › 포트 입력 › Apply › Save
   - 데이터: 포트는 쉼표로 구분하고 범위는 하이픈(예: 400-500, 80, 443), 공백은 적용 시 제거됩니다. 프로토콜은 TCP/UDP. 자주 쓰는 포트: 22 SSH · 80 HTTP · 443 HTTPS · 445 SMB · 3389 RDP. Graph: ports ["445-445"] · protocol "tcp" | "udp" | "tcp,udp"
   - 해설: 세그먼트는 대상 · 포트 · 프로토콜 3가지로 정의되며, 같은 3가지가 겹치면 겹침 세그먼트로 취급됩니다
7. [판단] 세그먼트가 지원 제한을 지키는가?
   - 주체: 관리자
   - 위치: 앱 세그먼트 목록 · 알려진 제한 문서
   - 데이터: 앱당 최대 500개 · Private Access 앱 사이 FQDN/IP/범위 겹침 금지(Quick Access와의 겹침만 예외) · NetBIOS 이름 미지원(contoso/app1 대신 contoso.local/app1) · 단말 로컬 서브넷 안의 IP 대상은 터널링되지 않음
   - 해설: 제한을 어기면 의도한 대로 동작하지 않으므로 저장 전에 점검합니다
   - 제한 충족 → 8
   - 제한 위반 → [차단] 지원되지 않는 구성 — 겹침 · NetBIOS 이름 · 로컬 서브넷 IP
8. [처리] 클라이언트가 가져가는 우선순위 확인 — 앱 세그먼트가 Quick Access보다 먼저
   - 주체: GSA 클라이언트
   - 위치: GSA 클라이언트 › Advanced Diagnostics › Forwarding profile › Priority 열 (작은 숫자가 우선) · Policy tester
   - 데이터: Enterprise App 세그먼트(예: 10.1.1.1:3389)가 Quick Access 세그먼트(예: 10.1.1.0/24:3389)와 겹치면 Enterprise App이 우선이며 그 대상으로 가는 트래픽은 Quick Access에서 처리되지 않습니다
   - 해설: 모범 사례는 앱으로 옮긴 세그먼트를 Quick Access에서 빼고, 큰 서브넷은 작은 범위로 쪼개 제외하는 것입니다
9. [끝] 앱 구성이 클라이언트에 반영됨 — 할당·조건부 액세스는 다음 L3에서
   - 주체: GSA 클라이언트
   - 위치: GSA 클라이언트 › Advanced Diagnostics › Forwarding profile (새 규칙 표시)
   - 데이터: 새 앱 정의는 약 5~10분, 구성 변경은 약 15분 뒤 클라이언트에 동기화됩니다
   - 해설: 반영 전에 접속해 보고 실패했다고 판단하지 않도록 시간을 둡니다
- 시나리오: 새 앱 ▸ 제한 충족 :: 새 앱 생성 후 유형·포트를 지켜 규칙이 반영됨
- 시나리오: 새 앱 ▸ 제한 위반 :: 새 앱 세그먼트가 겹침·NetBIOS 등 제한을 어김
- 시나리오: 기존 앱 ▸ 제한 충족 :: 기존 앱에 세그먼트를 더해 Pending이 Success로 반영
- 시나리오: 기존 앱 ▸ 제한 위반 :: 기존 앱에 더한 세그먼트가 제한을 어김

> 교육 포인트: 새 앱은 생성 시 Quick Access의 할당을 상속하고, 앱 세그먼트는 Quick Access보다 우선합니다. 그래서 "만들기 → 할당 좁히기 → Quick Access에서 빼기" 순서로 옮기면 끊김이 적습니다.
>
> 주의: AD DS 도메인 컨트롤러를 게시할 때는 와일드카드 FQDN을 쓰지 말고 특정 IP나 FQDN만 넣습니다(Kerberos SSO 문서). 운영 가이드는 destinationType이 dnsSuffix이거나 0.0.0.0/0 같은 넓은 대상을 가진 세그먼트를 점검 대상으로 봅니다.

### L3 · B · Private DNS 이름 확인

#### L4 · 질의 경로 — 접미사 등록에서 내부 IP 응답까지

1. [시작] 관리자가 Quick Access에 Private DNS 접미사를 등록
   - 주체: 관리자
   - 위치: Global Secure Access › Applications › Quick access › Private DNS 탭 › enable private DNS › Add DNS suffix › Save
   - 데이터: 접미사 예: contoso.local. Graph: isDnsResolutionEnabled(Quick Access 앱만) · destinationType "dnsSuffix"
   - 해설: 접미사 등록이 클라이언트 쪽 정책 변경으로 이어집니다
2. [처리] 클라이언트에 NRPT 규칙이 생기고 전달 프로필이 갱신됨
   - 주체: GSA 클라이언트
   - 위치: Windows 클라이언트 › 로컬 NRPT (PowerShell: Get-DnsClientNrptPolicy)
   - 데이터: 접미사마다 NRPT 항목이 하나씩 생기고, 질의는 synthetic IP(보통 6.6.255.254)로 향하도록 설정됩니다
   - 해설: 이후 해당 접미사 질의는 장치의 DNS 서버가 아니라 GSA로 갑니다
3. [처리] 사용자 앱이 접미사로 끝나는 FQDN을 질의
   - 주체: 디바이스
   - 위치: 앱의 DNS 질의 → Windows DNS 클라이언트 → NRPT
   - 데이터: 예: app.contoso.local 질의가 로컬 캐시에 없으면 GSA 에지의 DNS 프록시로 전달됩니다
   - 해설: 이름 공간이 일치한 질의만 에지로 올라갑니다
4. [판단] 에지 DNS 프록시에 캐시된 결과가 있는가?
   - 주체: SSE 에지
   - 위치: GSA 에지의 DNS 프록시 캐시
   - 데이터: 캐시 히트 여부 (로그의 DnsResponseOrigin이 Cache인지 Onprem인지로 사후 확인 [확인 필요: Private DNS 질의 기록 조건])
   - 해설: 캐시가 있으면 커넥터까지 가지 않고 바로 답합니다
   - 캐시 적중 → 7
   - 캐시 없음 → 5
5. [처리] 에지가 질의를 Quick Access에 지정한 커넥터 그룹으로 전달
   - 주체: SSE 에지
   - 위치: DNS 프록시 → Quick Access 앱의 커넥터 그룹
   - 데이터: 커넥터 그룹 = Quick Access 앱 생성 시 선택한 그룹. 이 그룹의 활성 커넥터를 거쳐야 이름이 풀립니다
   - 해설: Private DNS의 해석 경로는 Quick Access 앱의 커넥터 그룹에 묶여 있습니다
6. [처리] 커넥터가 서버 OS에 설정된 DNS 서버로 질의하고 응답을 돌려줌
   - 주체: 커넥터
   - 위치: 커넥터 서버의 OS DNS 설정 (사내 DNS 서버)
   - 데이터: 커넥터는 자기 서버에 설정된 DNS 서버(와 검색 접미사)로 질의하고 응답을 에지로 전달합니다
   - 해설: 사내 DNS 서버 주소를 사용자에게 알릴 필요가 없습니다
7. [처리] DNS 프록시가 내부 IP를 응답하고 클라이언트가 synthetic IP를 앱에 돌려줌
   - 주체: GSA 클라이언트
   - 위치: GSA 클라이언트 DNS 처리
   - 데이터: 내부 IP는 클라이언트가 보관하고 앱에는 synthetic IP가 반환되며, 그 IP로 향하는 트래픽이 에지로 조종됩니다
   - 해설: 앱은 가짜 IP로 연결하지만 실제 연결은 에지와 커넥터를 거쳐 내부 IP로 이어집니다
8. [끝] DNS 질의 결과가 트래픽 로그에 남음
   - 주체: 로그
   - 위치: Global Secure Access › Monitor › Traffic logs · 진단 설정으로 내보낸 Log Analytics의 NetworkAccessTraffic
   - 데이터: DnsQueryName · DnsRecordType · DnsResponseCode · DnsResponseOrigin(Cache/Onprem) · DnsResponseTime · DnsTtl [확인 필요: Private DNS 질의에 이 열이 기록되는 조건과 값]
   - 해설: 캐시에서 답했는지 사내 DNS에서 답했는지를 DnsResponseOrigin으로 구분할 수 있습니다
- 시나리오: 캐시 적중 :: 에지 캐시가 바로 응답해 커넥터까지 가지 않음
- 시나리오: 캐시 없음 :: 커넥터를 거쳐 사내 DNS에서 풀어 응답

> 교육 포인트: Private DNS 접미사가 등록되면 그 접미사로 끝나는 모든 FQDN 질의가 Private DNS로 풀립니다. 엔터프라이즈 앱 세그먼트를 정의하는 데 쓰인 이름도 포함됩니다.
>
> 주의: 이 기능은 Quick Access 앱에 속합니다. 해석 경로가 Quick Access의 커넥터 그룹에 묶여 있으므로 그 그룹의 커넥터가 모두 내려가면 이름 확인도 함께 실패합니다 [판단: 문서의 경로 설명에서 추론].
>
> 출처: https://learn.microsoft.com/entra/global-secure-access/concept-private-name-resolution
>
> 출처: https://learn.microsoft.com/entra/global-secure-access/how-to-configure-quick-access
>
> 출처: https://learn.microsoft.com/entra/global-secure-access/troubleshoot-app-access
>
> 출처: https://learn.microsoft.com/azure/azure-monitor/reference/tables/networkaccesstraffic

#### L4 · 단일 레이블 · Kerberos · 점검 — 이름이 안 풀릴 때 확인할 것

1. [시작] 사용자가 접미사 없는 짧은 이름으로 접속 — 예: https://benefits
   - 주체: 사용자
   - 위치: 브라우저 주소창 → benefits
   - 데이터: 단일 레이블(SLD) 이름
   - 해설: 사내에서는 짧은 이름도 되지만 외부에서는 접미사를 붙일 곳이 없습니다
2. [처리] 클라이언트가 <appid>.globalsecureaccess.local 접미사를 붙여 질의
   - 주체: GSA 클라이언트
   - 위치: Windows 클라이언트 › NRPT의 globalsecureaccess.local. 규칙 (Private DNS 구성 시 생성)
   - 데이터: benefits.<appid>.globalsecureaccess.local. 질의가 DNS 프록시로 갑니다
   - 해설: 짧은 이름이 클라이언트가 만든 가상의 접미사로 보내집니다
3. [처리] DNS 프록시가 접미사를 떼고 커넥터가 로컬 검색 접미사로 해석
   - 주체: SSE 에지
   - 위치: DNS 프록시 → 커넥터 (커넥터 서버의 검색 접미사)
   - 데이터: 해석된 IP가 DNS 프록시를 거쳐 클라이언트에 전달됩니다
   - 해설: 검색 접미사 목록은 사용자 PC가 아니라 커넥터 서버의 설정을 따릅니다
4. [판단] 앱이 Kerberos 인증을 쓰는가?
   - 주체: 관리자
   - 위치: 대상 앱 · SPN (서비스 주체 이름)
   - 데이터: Kerberos는 정확한 SPN이 중요합니다
   - 해설: GSA의 synthetic 접미사가 Kerberos 흐름을 깰 수 있어 FQDN 사용이 권장됩니다
   - Kerberos 필요 → 5
   - Kerberos 불필요 → 6
5. [처리] Kerberos 앱은 FQDN으로 접속시키고 DC 세그먼트는 와일드카드 없이 게시
   - 주체: 관리자
   - 위치: Global Secure Access › Applications › Enterprise applications › New application (도메인 컨트롤러용) · Quick access › Private DNS 탭
   - 데이터: DC의 IP 또는 FQDN과 필요한 포트만 게시하고(Private Access 커넥터가 있는 AD 사이트의 DC만), 사용자는 Active Directory에서 동기화된 사용자를 앱에 할당합니다. Private DNS에는 최소한 사용자를 동기화하는 AD 포리스트의 최상위 접미사를 넣습니다
   - 해설: Kerberos SSO는 이름 확인(Private DNS)과 DC 앱 게시가 함께 갖춰져야 동작합니다
6. [처리] 이름 확인 점검 도구 — Resolve-DnsName · nslookup 차이
   - 주체: 관리자
   - 위치: 클라이언트 장치 PowerShell · Get-DnsClientNrptPolicy · wevtutil sl Microsoft-Windows-DNS-Client/Operational /enabled:true
   - 데이터: Resolve-DnsName은 NRPT를 따르지만 NSLOOKUP은 따르지 않으므로 nslookup fs.contoso.local 6.6.255.254 로 터널을 강제합니다. DNS Client 로그 공급자는 점검 후 끕니다
   - 해설: 같은 이름이 도구마다 다르게 풀리는 것은 NRPT 적용 여부 차이입니다
7. [처리] 클라이언트가 지원하지 않는 DNS 구성을 끔 — 보안 DNS · DNS over TCP
   - 주체: 관리자
   - 위치: 브라우저 설정(Edge · Chrome) · Windows 클라이언트 알려진 제한
   - 데이터: 보안 DNS(DoH · DoT · DNSSEC)는 미지원이라 Windows 클라이언트에서는 끄고, 53/TCP DNS는 미지원이라 브라우저 내장 DNS 클라이언트를 끕니다(BuiltInDnsClientEnabled = 0). macOS 클라이언트는 보안 DNS를 우회해 FQDN 터널링을 강제합니다
   - 해설: 브라우저가 자체 DNS로 이름을 풀면 클라이언트가 질의를 보지 못합니다
8. [판단] 장치에 그룹 정책(GPO)으로 NRPT 규칙이 설정돼 있는가?
   - 주체: 관리자
   - 위치: 장치의 HKLM\Software\Policies\Microsoft\Windows NT\DNSClient\DnsPolicyConfig 레지스트리 키 · 그룹 정책 편집기의 Name Resolution Policy Rules 대화 상자
   - 데이터: Windows 클라이언트는 GPO NRPT를 지원하지 않으며, GPO의 NRPT(빈 목록 포함)가 클라이언트가 만든 로컬 NRPT를 덮어써 Private DNS가 동작하지 않습니다
   - 해설: Private DNS가 안 되는 장치는 NRPT GPO 여부를 가장 먼저 의심합니다
   - GPO NRPT 있음 → [차단] 로컬 NRPT가 덮어써져 Private DNS가 동작하지 않음
   - GPO NRPT 없음 → 9
9. [끝] 이름 확인이 정상화되어 앱 세그먼트 규칙 평가로 이어짐
   - 주체: GSA 클라이언트
   - 위치: GSA 클라이언트 › Advanced diagnostics › Traffic (Action = Tunnel)
   - 데이터: 해석된 synthetic IP로 향하는 흐름이 Tunnel로 표시되면 이름 확인은 성공입니다. 이후 앱 세그먼트·할당 판정은 위 ② 시나리오와 같습니다
   - 해설: 이름이 풀리는 것과 앱에 접근이 허용되는 것은 별개의 두 단계입니다
- 시나리오: Kerberos 필요 ▸ GPO NRPT 있음 :: Kerberos 앱이지만 GPO NRPT가 덮어써 이름이 안 풀림
- 시나리오: Kerberos 필요 ▸ GPO NRPT 없음 :: FQDN·DC 앱 게시를 갖춰 이름 확인 후 SSO 진행
- 시나리오: Kerberos 불필요 ▸ GPO NRPT 있음 :: Kerberos 없이도 GPO NRPT 때문에 이름이 안 풀림
- 시나리오: Kerberos 불필요 ▸ GPO NRPT 없음 :: 단일 레이블 이름이 정상적으로 풀려 터널링

> 교육 포인트: 접미사가 없는 이름은 클라이언트가 globalsecureaccess.local 접미사를 붙여 커넥터가 풀게 합니다. 이름 확인 점검의 기본 순서는 NRPT 규칙 확인 → 도구 선택(Resolve-DnsName) → DNS Client 로그입니다.
>
> 주의: Windows 클라이언트는 NRPT GPO를 지원하지 않습니다. 과거 Windows 버전에서 NRPT를 만들었다 지운 흔적(registry.pol의 빈 DnsPolicyConfig)도 로컬 규칙을 덮어쓸 수 있으니 장치에서 확인합니다.

### L3 · C · 앱 할당 · 가시성 · 조건부 액세스 연결

#### L4 · 앱 속성과 할당 — 누가 토큰을 받고 누가 앱을 보는가

1. [시작] 관리자가 엔터프라이즈 앱을 연다 — 앱이 목록에 안 보이면 필터를 모두 지움
   - 주체: 관리자
   - 위치: Global Secure Access › Applications › Enterprise applications › 앱 검색 (Quick Access 앱은 Quick access › Edit application settings)
   - 데이터: Quick Access를 구성하면 엔터프라이즈 앱이 자동으로 만들어집니다
   - 해설: 사설 앱도 Entra ID에서는 엔터프라이즈 앱(서비스 주체) 객체로 관리됩니다
2. [판단] Enabled for users to sign in?이 Yes인가?
   - 주체: Entra ID
   - 위치: Enterprise applications › {앱} › Properties › Enabled for users to sign in?
   - 데이터: 서비스 주체 accountEnabled. No이면 Activation status가 Deactivated로 보이고 토큰이 발급되지 않습니다
   - 해설: 이 값이 No이면 할당이 있어도 아무도 접근하지 못합니다
   - Yes → 3
   - No → [차단] 토큰 미발급 — 할당돼도 로그인 불가(Deactivated)
3. [처리] 사용자·그룹 할당 — 앱 역할 User
   - 주체: 관리자
   - 위치: Enterprise applications › {앱} › Users and groups › Add user/group · Graph POST /beta/servicePrincipals/{id}/appRoleAssignments (principalId · principalType · appRoleId · resourceId)
   - 데이터: 사용자를 직접 또는 그룹으로 할당하며 중첩 그룹은 지원되지 않습니다. 할당은 새 엔터프라이즈 앱으로 자동 이전되지 않습니다
   - 해설: Quick Access에서 되던 사용자가 per-app으로 옮긴 뒤 막히는 가장 흔한 원인이 다시 지정하지 않은 할당입니다
4. [판단] 접속한 사용자가 앱에 직접 또는 그룹으로 할당되어 있는가?
   - 주체: Entra ID
   - 위치: 앱 역할 할당 (Entra ID에 저장된 값을 SSE 에지가 조회)
   - 데이터: 부모 엔터프라이즈 앱에 할당이 하나도 없으면 매칭된 세션이 모두 거부됩니다(운영 가이드)
   - 해설: 세그먼트를 추가하는 순간부터 정책이 클라이언트에 전달되므로 할당이 먼저 있어야 합니다
   - 할당됨 → 5
   - 미할당 → [차단] 앱 할당 없음 — Private Access 연결 거부
5. [처리] Visible to users · Assignment required · Homepage URL의 의미를 구분
   - 주체: 관리자
   - 위치: Enterprise applications › {앱} › Properties
   - 데이터: Visible to users = 할당된 사용자에게만 My Apps · Microsoft 365 앱 시작 관리자에 보임(홈페이지 URL이 없으면 My Apps에서 실행 불가). Assignment required = 토큰을 받을 수 있는 사용자·앱을 할당된 쪽으로 제한 [확인 필요: Private Access 앱에서 이 두 속성이 클라이언트 경로에 미치는 영향은 확인한 문서에 별도 설명이 없음]
   - 해설: 가시성은 "보이는가"의 문제이고 Private Access 접근은 GSA 클라이언트 경로와 앱 할당으로 정해집니다 [판단]
6. [처리] 변경 전파 대기 — 클라이언트 반영
   - 주체: GSA 클라이언트
   - 위치: GSA 클라이언트 › Advanced Diagnostics › Forwarding profile
   - 데이터: 할당 등 구성 변경은 클라이언트와 약 15분 걸려 동기화되고, 새 앱 정의는 약 5~10분 걸려 나타납니다
   - 해설: 할당 직후 실패는 설정 오류가 아니라 전파 지연일 수 있습니다
7. [끝] 접속 결과가 트래픽 로그에 앱 단위로 남음
   - 주체: 로그
   - 위치: Global Secure Access › Monitor › Traffic logs (Private access 필터)
   - 데이터: NetworkAccessTraffic: ApplicationObjectId · AppSegmentId · AccessType · Action(Allowed/Denied)
   - 해설: 같은 사용자가 어느 앱에서만 막히는지 앱 단위로 볼 수 있습니다
- 시나리오: Yes ▸ 할당됨 :: 로그인 허용에 할당도 있어 앱 접근이 진행됨
- 시나리오: Yes ▸ 미할당 :: 로그인은 허용이지만 할당이 없어 거부
- 시나리오: No :: 로그인 사용 안 함으로 토큰이 발급되지 않음

> 교육 포인트: 앱을 만들면 "연결할 대상(세그먼트)"과 "허용할 사람(할당)"이 별개로 있어야 합니다. 할당이 없는 앱은 세그먼트가 일치해도 모든 세션이 거부됩니다.
>
> 주의: Application discovery로 만든 앱은 생성 시 Quick Access의 할당을 상속하지만, 수동으로 만든 엔터프라이즈 앱은 자동으로 이전되지 않습니다. 앱별 로그인 허용 상태도 함께 확인합니다.

#### L4 · 앱별 조건부 액세스와 Graph 이름 — 어디에 걸리고 무엇이 미지원인가

1. [시작] 앱 단위 조건부 액세스 정책을 만든다 — 앱 화면에서 시작하면 대상 리소스가 자동 지정
   - 주체: 관리자
   - 위치: Global Secure Access › Applications › Enterprise applications › {앱} › Conditional Access › New policy (또는 Entra ID › Conditional Access › Policies › + Create new policy) — Conditional Access Administrator
   - 데이터: 앱 화면에서 시작하면 선택한 앱이 Target resources로 자동 지정됩니다
   - 해설: 정책은 Quick Access 앱 또는 Global Secure Access 앱 단위로만 걸립니다
2. [처리] 사용자와 부여 제어 설정 — 비상 계정 제외
   - 주체: 관리자
   - 위치: 정책 › Assignments › Users › Include All users · Exclude 비상 접근(break-glass) 계정 · Access controls › Grant
   - 데이터: Require multifactor authentication · Require device to be marked as compliant · Require Microsoft Entra hybrid joined device. 서비스 계정·서비스 주체는 사용자 대상 정책에 막히지 않으므로 워크로드 ID용 조건부 액세스를 따로 씁니다
   - 해설: 비상 계정을 빼 두어야 정책 실수로 관리자가 잠기는 일을 막습니다
3. [처리] Report-only로 먼저 검증한 뒤 On으로 전환
   - 주체: 관리자
   - 위치: 정책 › Enable policy › Report-only → On
   - 데이터: Report-only 모드에서 영향 분석 후 On 전환
   - 해설: 앱 접근이 끊기는 사고를 막으려면 보고 전용 단계가 필수입니다
4. [판단] 정책을 앱 단위로 거는가, Private Access 트래픽 전체에 거는가?
   - 주체: Entra ID
   - 위치: 정책 › Target resources (앱 지정 vs 트래픽 프로필)
   - 데이터: Private Access 트래픽 전체에 조건부 액세스를 적용하는 것은 현재 지원되지 않습니다. 모델링하려면 Quick Access와 Global Secure Access 앱 단위로 겁니다
   - 해설: 앱을 쪼갤수록 서로 다른 CA를 걸 수 있다는 점이 per-app 전환의 이유입니다
   - 앱 단위 → 5
   - 트래픽 전체 → [차단] 미지원 — 앱 단위 정책으로 대체
5. [판단] 조건이 디바이스·MFA 같은 일반 부여 제어인가, 규정 준수 네트워크 검사인가?
   - 주체: Entra ID
   - 위치: 정책 › Conditions · Grant
   - 데이터: Compliant network check는 현재 Private Access 앱에서 지원되지 않습니다. MFA · 규정 준수 디바이스 · 하이브리드 조인 디바이스는 사용할 수 있습니다
   - 해설: 네트워크 조건은 이 경로에서 못 쓰므로 디바이스·인증 강도로 설계합니다
   - 디바이스·MFA 조건 → 6
   - 준수 네트워크 조건 → [차단] 미지원 — Private Access 앱에서 사용 불가
6. [처리] 앱 여러 개를 한 정책으로 묶기 — 사용자 지정 특성 필터
   - 주체: 관리자
   - 위치: 정책 › Target resources › Filter for applications (사용자 지정 특성 기반 [확인 필요: 포털 세부 메뉴 이름])
   - 데이터: 앱 묶음에 같은 CA를 적용할 때 사용합니다
   - 해설: 앱이 많아지면 앱마다 정책을 만들기보다 특성으로 묶는 편이 관리에 유리합니다
7. [처리] 자동화에 쓰는 Graph 이름 — 앱 · 세그먼트 · 프로필
   - 주체: 관리자
   - 위치: Microsoft Graph beta (권한 Directory.ReadWrite.All · NetworkAccess.ReadWrite.All 위임) — Application Administrator + Global Secure Access Administrator
   - 데이터: 앱 유형 PATCH /beta/applications/{id} onPremisesPublishing.applicationType = quickaccessapp | nonwebapp · isAccessibleViaZTNAClient. 커넥터 그룹 PUT /beta/applications/{id}/connectorGroup/$ref. 세그먼트 …/onPremisesPublishing/segmentsConfiguration/microsoft.graph.ipSegmentConfiguration/applicationSegments (destinationHost · destinationType · ports · protocol). 라우팅 onPremisesPublishing.trafficRoutingMethod(random | 세션 지속). 프로필 /beta/networkAccess/forwardingProfiles. 할당 /beta/servicePrincipals/{id}/appRoleAssignments
   - 해설: 포털에서 만든 앱도 Graph로 그대로 읽고 바꿀 수 있어 점검·자동화에 쓰기 좋습니다 [확인 필요: 모두 beta 엔드포인트라 변경될 수 있음]
8. [끝] 평가 결과가 앱 단위로 기록됨
   - 주체: 로그
   - 위치: Global Secure Access › Monitor › Traffic logs (Private access 필터) · 진단 설정으로 내보낸 NetworkAccessTraffic
   - 데이터: ApplicationObjectId · AppSegmentId · Action(Allowed/Denied). 정책 평가 자체는 SSE 에지에서 Entra ID로 이뤄집니다
   - 해설: 앱별 정책이 어느 앱 접속을 거부했는지 로그에서 앱 기준으로 확인합니다
- 시나리오: 앱 단위 ▸ 디바이스·MFA 조건 :: 앱별 MFA·디바이스 조건으로 정책이 정상 적용됨
- 시나리오: 앱 단위 ▸ 준수 네트워크 조건 :: 앱 단위라도 준수 네트워크 검사는 미지원
- 시나리오: 트래픽 전체 :: Private Access 트래픽 전체 대상 CA는 미지원

> 교육 포인트: 앱별 조건부 액세스는 Private Access의 가장 큰 장점이지만 걸 수 있는 지점이 앱 단위로 제한됩니다. Graph 이름은 포털 설정과 1:1로 대응하므로 자동화할 때 함께 익힙니다.
>
> 주의: Graph 예제 대부분이 beta 엔드포인트입니다. 변경될 수 있으므로 운영 자동화 전에 최신 문서를 다시 확인합니다.
