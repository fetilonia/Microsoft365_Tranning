## L2 · 원격 네트워크 — 지점 연결(IPsec) · 클라이언트 없는 접속

- 설정(Control Plane): 원격 네트워크 · 디바이스 링크(IKEv2 IPsec/IKE 정책 · BGP 주소·ASN · 사전 공유 키 · 대역폭) | Microsoft 트래픽·Internet Access 전달 프로필 할당 → 기준선 보안 프로필
- 강제(Enforcement): 지점 CPE (IPsec 시작 · BGP 경로 광고) | Microsoft SSE 에지 게이트웨이 (연결된 전달 프로필에 맞지 않는 트래픽 폐기 · 기준선 프로필 판정)
- 증적(Evidence): 원격 네트워크 상태 로그 (모니터링 › 원격 네트워크 상태 로그) · GSA 트래픽 로그(Device category = remote network) | KQL: RemoteNetworkHealthLogs · NetworkAccessTraffic
- 메뉴(Admin Center): Global Secure Access > 연결 > 원격 네트워크 · 연결 > 트래픽 전달 · 모니터링 > 원격 네트워크 상태 로그 · 트래픽 로그
- 라이선스(License): 원격 네트워크(지점 연결)는 Microsoft 트래픽에는 Entra ID P1, 인터넷 트래픽에는 Entra Internet Access 라이선스 대상이며, 두 라이선스 합계 50개 이상이 있어야 구성할 수 있습니다. 합계 수에 따라 테넌트 대역폭이 정해집니다 [확인 필요: 인터넷 트래픽 라이선스 적용 시점(개요 문서는 "coming soon") · 고객 라이선스 수 · 미리 보기 범위]

### L3 · 0 · 기능 상태 전이 — 클라이언트 없는 지점 → 원격 네트워크 구성 → 에지 경유

#### L4 · ⓪ 비활성 — 지점의 클라이언트 없는 기기는 에지 통제 밖에 있다

1. [시작] 지점 사무실의 기기가 인터넷·Microsoft 365에 접속 — 직원 PC · 게스트 · 프린터 · 카메라
   - 주체: 사용자
   - 위치: 지점 LAN → 지점 라우터(CPE) → 로컬 인터넷 또는 본사 WAN
   - 데이터: 출발지 IP · 대상 FQDN · 포트
   - 해설: 지점에서는 사람의 PC뿐 아니라 클라이언트를 설치할 수 없는 장치도 같은 라우터로 인터넷에 나갑니다
2. [처리] 원격 네트워크가 없음 — 지점 라우터가 기존 경로로만 내보냄
   - 주체: 지점 CPE
   - 데이터: 원격 네트워크 0건 · 디바이스 링크 없음 · Microsoft 에지로 가는 IPsec 터널 없음. 지점은 보통 전용 WAN이나 VPN으로 본사에 연결해 트래픽을 되돌려 보내거나(backhaul) 로컬 ISP로 곧바로 나갑니다
   - 해설: Global Secure Access 입장에서 이 지점은 존재하지 않는 네트워크입니다
3. [판단] 기기에 Global Secure Access 클라이언트가 설치돼 있는가?
   - 주체: 디바이스
   - 데이터: 클라이언트 설치 여부 — 클라이언트는 Windows · macOS · Android · iOS용이 제공됩니다
   - 해설: 클라이언트가 있으면 지점 밖에서와 똑같이 기기 단위로 에지에 연결할 수 있습니다
   - 예 → 4
   - 아니오 → 5
4. [끝] 클라이언트가 있는 기기만 에지 경유 — 같은 지점의 다른 기기는 여전히 직접 나감
   - 주체: 디바이스
   - 위치: GSA 클라이언트 터널 → 가까운 Microsoft 에지
   - 데이터: 기기마다 클라이언트를 설치·관리해야 하며, 수천 대 규모 지점에서는 배포 부담이 큽니다
   - 해설: 클라이언트 방식은 설치한 기기까지만 통제하므로 지점 전체를 한 번에 덮지는 못합니다
5. [처리] 클라이언트를 설치할 수 없는 기기 — 정책을 걸 곳이 없음
   - 주체: 외부
   - 데이터: Linux · 메인프레임 · 카메라 · 프린터 · 클라이언트가 없는 게스트 기기
   - 해설: 이런 기기의 인터넷 트래픽은 모니터링도 보안 정책도 받지 못합니다
6. [끝] 지점 트래픽이 Entra에 기록되지 않음 — 위험이 그대로 남음
   - 주체: 로그
   - 위치: Global Secure Access › 모니터링(Monitor) › 트래픽 로그(Traffic logs)
   - 데이터: NetworkAccessTraffic 행 없음 · RemoteNetworkHealthLogs 행 없음 — 에지를 지나지 않은 트래픽은 로그 자체가 생기지 않습니다
   - 해설: 지점의 Linux 장비나 게스트 기기가 어디에 접속했는지 Entra에서 확인할 수 없습니다
- 시나리오: 예 :: 클라이언트 설치 기기만 통제되고 나머지는 직접 나감
- 시나리오: 아니오 :: 클라이언트 없는 기기는 통제도 기록도 없이 접속

> 교육 포인트: 원격 네트워크는 기기마다 클라이언트를 깔지 않고 지점의 CPE(고객 구내 장비, 보통 코어 라우터) 한 대와 에지 사이의 IPsec 터널로 지점 전체를 연결하는 방식입니다. 클라이언트로 풀 수 없는 기기와 게스트가 이 기능의 핵심 사용처입니다.
>
> 주의: 지점 사용자 기기에 클라이언트가 이미 있더라도 원격 네트워크와는 별개 경로입니다. 이 L2는 클라이언트 없이 지점 트래픽을 에지로 보내는 쪽만 다룹니다.

#### L4 · ① 구성 — 원격 네트워크 · 디바이스 링크 · 전달 프로필을 만들고 CPE를 맞춘다

1. [시작] 관리자가 Entra 관리 센터에 로그인 — 역할 · 라이선스 · CPE 요건 점검
   - 주체: 관리자
   - 위치: entra.microsoft.com — Global Secure Access Administrator 역할(원격 네트워크 생성·링크·프로필 할당 모두)
   - 데이터: Entra ID P1 + Internet Access 라이선스 합계 50개 이상. CPE 요건: IPsec · IKEv2 · BGP · IKE 2단계에 GCMAES128 / GCMAES192 / GCMAES256 · RouteBased VPN에 any-to-any(0.0.0.0/0) 트래픽 셀렉터 · Responder 모드이므로 CPE가 연결을 시작
   - 해설: 요건에 맞지 않는 CPE로는 터널 자체가 만들어지지 않으므로 먼저 장비 사양을 확인합니다
2. [처리] 기본(Basics) 입력 — Name · Region
   - 주체: 관리자
   - 위치: Global Secure Access › 연결(Connect) › 원격 네트워크(Remote networks) › Create remote network › Basics 탭 · Graph: POST /beta/networkAccess/connectivity/remoteNetworks
   - 데이터: name · region — 터널의 Microsoft 쪽 끝이 놓일 지역(예: koreaCentral, japanEast, eastUS, westEurope). 테넌트당 원격 네트워크 최대 200개, 원격 네트워크당 디바이스 링크 최대 25개(늘리려면 Microsoft 지원 문의)
   - 해설: Region은 지점에서 가장 가까운 지역을 고릅니다. 목록에 없는 지역은 쓸 수 없습니다
3. [처리] 연결(Connectivity) — + Add a link › General 탭
   - 주체: 관리자
   - 위치: Create remote network › Connectivity 탭 › + Add a link › General (생성 후에는 원격 네트워크 선택 › Links › + Add a link) · Graph: POST …/remoteNetworks/{remoteNetworkId}/deviceLinks
   - 데이터: Link name · Device type(예: ciscoMeraki · paloAltoNetworks · fortinet · checkPoint · versa 등 14종) · Device IP address(CPE 공인 IP) · Device BGP address · Device ASN(1~65534, 예약 ASN 제외) · Redundancy(No redundancy / Zone redundancy) · Bandwidth capacity(250 · 500 · 750 · 1,000 Mbps) · Local BGP address(지점 내부망과 겹치지 않는 주소, 예: 내부망 10.1.0.0/16이면 10.2.0.4)
   - 해설: Device BGP address와 Local BGP address는 CPE 쪽에서는 각각 local과 peer로 뒤집혀 입력됩니다. Azure 예약 ASN(12076 · 65517~65520 · 8076 · 8075) · IANA 예약 ASN · 65476과 0.0.0.0/32 · 127.0.0.0/8 · 224.0.0.0/4 · 255.255.255.255/32 주소는 쓸 수 없습니다
4. [판단] IPsec/IKE 정책을 기본값으로 둘 것인가?
   - 주체: 관리자
   - 위치: Add a link › Details 탭 › IKEv2(기본, 현재 IKEv2만 지원) · IPSec/IKE policy = Default 또는 Custom
   - 데이터: 어느 쪽이든 CPE에 입력하는 암호 정책은 디바이스 링크와 일치해야 합니다
   - 해설: 특별한 요구가 없으면 기본값을 쓰고, 보안 기준 때문에 조합을 고정해야 할 때만 사용자 지정으로 갑니다
   - 기본 정책 → 5
   - 사용자 지정 정책 → 6
5. [처리] 기본 정책 — CPE에 입력할 조합 확인
   - 주체: 관리자
   - 위치: 참고 문서 Valid remote network configurations › Default IPSec/IKE configurations
   - 데이터: 1단계(IKE) 8개 조합 중 하나(예: GCMAES256 + SHA384 + DHGroup24) + 2단계(IPsec) 3개 조합 중 하나(GCMAES256 / GCMAES192 / GCMAES128, PFS Group None). 1단계와 2단계를 둘 다 CPE에 지정해야 합니다
   - 해설: 기본 정책은 입력 칸이 없고 대신 위 조합 중 하나를 CPE에 맞춰 넣는 방식입니다
   - 다음 → 7
6. [처리] 사용자 지정 정책 — 1단계 · 2단계 직접 선택
   - 주체: 관리자
   - 위치: Details 탭 › IPSec/IKE policy = Custom › Encryption · IKEv2 integrity · DHGroup · IPsec encryption · IPsec integrity · PFS group · SA lifetime (seconds) · Graph: tunnelConfigurationIKEv2Custom
   - 데이터: 1단계는 암호·무결성·DH 그룹을 자유롭게 조합. 2단계는 GCMAES128/128 · GCMAES192/192 · GCMAES256/256 또는 None + SHA256 중에서만 선택, PFS group은 제한 없음, SA lifetime은 300초보다 커야 합니다
   - 해설: 허용된 조합에서 벗어나면 협상이 실패하므로 참고 문서 표에 있는 값만 고릅니다
7. [처리] 보안(Security) 탭 — 사전 공유 키 입력 후 Save
   - 주체: 관리자
   - 위치: Add a link › Security 탭 › Pre-shared key (Zone redundancy를 골랐다면 Zone Redundancy Pre-shared key도) › Save
   - 데이터: PSK — CPE에도 정확히 같은 값을 넣어야 합니다 (Graph에서는 tunnelConfiguration.preSharedKey)
   - 해설: PSK가 한 글자라도 다르면 IKE 인증 단계에서 터널이 올라오지 않습니다
8. [처리] 트래픽 프로필(Traffic profiles) 탭 — 전달 프로필 연결 후 Create remote network
   - 주체: 관리자
   - 위치: Create remote network › Traffic profiles 탭 › Microsoft traffic profile · Internet Access traffic profile 체크 › Review + create › Create remote network (나중에는 원격 네트워크 선택 › Traffic profiles › Save, 또는 연결 › 트래픽 전달(Traffic forwarding) › Add/edit assignments) · Graph: GET /beta/networkaccess/forwardingprofiles 후 PATCH …/branches/{id}/forwardingProfiles
   - 데이터: 연결된 프로필 = 에지가 터널에서 받아 주는 트래픽 종류. Private Access 프로필은 원격 네트워크에 할당할 수 없습니다
   - 해설: 라이선스가 허용하면 두 프로필을 모두 연결합니다. 하나만 연결하면 나머지 유형의 트래픽은 게이트웨이가 조용히 버립니다
9. [처리] CPE 연결 구성 보기 — Microsoft 쪽 값 확인
   - 주체: 관리자
   - 위치: Global Secure Access › 연결 › 원격 네트워크 › Connectivity details 열의 View configuration · Graph: GET /beta/networkaccess/connectivity/branches/{branchSiteId}/deviceLinks/{deviceLinkId}
   - 데이터: JSON의 endpoint(Microsoft 공인 IP) · asn · bgpAddress · region, 그리고 CPE 쪽 값을 담은 PeerConfiguration. 영역 이중화 링크는 두 번째 값 세트가 더 나옵니다
   - 해설: 링크를 지우고 다시 만들면 Microsoft 공인 IP가 바뀔 수 있으므로 그때마다 이 화면을 다시 확인합니다
10. [끝] CPE 관리 콘솔에서 터널·BGP 설정 — 이 단계는 Entra 관리 센터에 없음
   - 주체: 지점 CPE
   - 위치: 지점 라우터·방화벽 관리 콘솔(Entra 관리 센터 밖)
   - 데이터: RouteBased VPN · 트래픽 셀렉터 0.0.0.0/0 · Microsoft endpoint를 피어 IP로 · BGP local = Device BGP address, peer = Local BGP address · ASN은 Microsoft ASN(원격 네트워크 › Links › Link ASN 열) · Microsoft BGP 주소로 가는 정적 경로를 터널 인터페이스로 · UDP 500·4500, TCP 179 허용
   - 해설: 여기까지 끝나야 IPsec 터널이 양쪽에서 완성됩니다. 터널 시작은 CPE가 하며, 두 ASN은 서로 달라야 합니다
- 시나리오: 기본 정책 :: 기본 IKE 조합을 CPE에 맞춰 터널을 완성
- 시나리오: 사용자 지정 정책 :: 허용 범위 안에서 직접 고른 조합으로 터널 완성

> 교육 포인트: 구성은 Basics → Connectivity(디바이스 링크) → Traffic profiles → Review + create의 포털 4단계와, 그 뒤 CPE 쪽 설정으로 나뉩니다. Microsoft 쪽 값은 View configuration에서 읽어 CPE에 넣습니다. 디바이스 링크는 생성 후 언제든 추가·삭제할 수 있습니다.
>
> 주의: 관리 센터 한글 메뉴명은 영문 포털 경로(Connect › Remote networks)를 옮긴 것이라 실제 UI와 다를 수 있습니다. 공식 문서 안에도 같은 화면을 Devices › Remote Networks로 적은 곳이 있습니다 [확인 필요: 한글 메뉴명 · 현재 포털 경로]. Graph 원격 네트워크 API는 /beta라 변경될 수 있습니다.

#### L4 · ② 활성 — 지점 트래픽이 터널을 타고 에지에서 판정된다

1. [시작] 지점의 기기(클라이언트 없음)가 Microsoft 365 또는 인터넷에 접속
   - 주체: 사용자
   - 위치: 지점 LAN → 지점 CPE
   - 데이터: 출발지 IP · 대상 FQDN · 포트
   - 해설: 클라이언트가 없는 PC도, 프린터도, 게스트 기기도 같은 경로를 탑니다
2. [처리] CPE가 경로를 조회 — 터널 인터페이스로 보냄
   - 주체: 지점 CPE
   - 위치: CPE 라우팅 테이블 (BGP로 배운 Microsoft 경로 · 정적 경로)
   - 데이터: Microsoft BGP 주소를 향한 정적 경로가 터널 인터페이스에 있어야 BGP 경로를 학습합니다. 보안 우선이면 터널로 정적 라우팅만, 생산성 우선이면 기본 경로를 따로 둡니다
   - 해설: 어떤 트래픽이 터널을 타는지는 CPE의 라우팅이 정합니다
3. [처리] IPsec 터널로 에지에 전송 — ESP 암호화
   - 주체: 지점 CPE
   - 위치: IKEv2 IPsec 터널 (UDP 500 · UDP 4500) — 연결은 항상 CPE가 시작
   - 데이터: 트래픽 셀렉터 0.0.0.0/0 · 협상된 암호 정책 · 디바이스 링크의 대역폭(250 / 500 / 750 / 1,000 Mbps)
   - 해설: 지점의 모든 아웃바운드 트래픽이 가까운 Global Secure Access 에지로 암호화되어 들어갑니다
4. [처리] 에지 게이트웨이가 디바이스 링크로 터널을 식별
   - 주체: SSE 에지
   - 위치: Global Secure Access 게이트웨이 (Microsoft 쪽 터널 끝)
   - 데이터: 터널의 Source IP(CPE 공인 IP) · Destination IP(에지 공인 IP) 쌍 — 터널마다 유일하며 원격 네트워크 ID와 연결됩니다
   - 해설: 어느 지점의 터널인지가 이후 로그의 Remote network ID가 됩니다
5. [판단] 트래픽이 연결된 전달 프로필의 유형과 맞는가?
   - 주체: SSE 에지
   - 위치: 원격 네트워크에 연결된 Microsoft traffic profile · Internet Access traffic profile
   - 데이터: 활성·연결된 프로필과 일치하는 유형만 전달합니다. Microsoft 트래픽 대상은 Internet Access 프로필로 획득되지 않습니다
   - 해설: 프로필이 하나만 연결돼 있으면 나머지 유형은 이 단계에서 버려집니다
   - 프로필 일치 → 6
   - 프로필 불일치 → [차단] 게이트웨이가 폐기 — 연결되지 않은 프로필의 트래픽
6. [처리] 기준선 보안 프로필 적용 — 조건부 액세스 평가 없이
   - 주체: SSE 에지
   - 위치: Global Secure Access › 보안(Secure) › 보안 프로필(Security profiles) › Baseline profile (우선순위 65,000)
   - 데이터: 기준선 프로필에 연결된 정책(웹 콘텐츠 필터링 · 위협 인텔리전스 · TLS 검사 · 클라우드 방화벽)이 테넌트 전체 트래픽에 적용됩니다. 사용자별 보안 프로필과 조건부 액세스는 클라이언트가 있을 때만 적용됩니다
   - 해설: 지점 트래픽에는 사용자 신원이 없으므로 테넌트 단위 기준선이 유일한 보안 평가입니다
7. [판단] 기준선 프로필의 차단 규칙에 일치하는가?
   - 주체: SSE 에지
   - 데이터: 연결된 정책의 우선순위 순서 비교 · 정책 Action(Block / Allow)
   - 해설: 일치하는 Block이 있으면 거기서 멈추고, 연결된 정책이 없으면 별도 차단 없이 전달됩니다
   - 차단 규칙 일치 → [차단] 기준선 정책으로 차단 — Denied 기록
   - 일치 규칙 없음 → 8
8. [끝] 허용 후 목적지로 전달 — 두 가지 로그가 남음
   - 주체: 로그
   - 위치: Global Secure Access › 모니터링 › 트래픽 로그 / 원격 네트워크 상태 로그(Remote network health logs)
   - 데이터: NetworkAccessTraffic — Device category = remote network · Action · Sent/Received Bytes. RemoteNetworkHealthLogs — 터널이 살아 있으면 15분마다 Remote network alive(Source IP · Destination IP · Sent/Received Bytes · BGP Routes Advertised Count)
   - 해설: 사용자별 기록이 아니라 지점(원격 네트워크) 단위로 터널 상태와 트래픽이 남습니다
- 시나리오: 프로필 일치 ▸ 일치 규칙 없음 :: 프로필 일치에 차단 규칙도 없어 허용 후 전달
- 시나리오: 프로필 일치 ▸ 차단 규칙 일치 :: 기준선 정책에 걸려 차단되고 Denied 기록
- 시나리오: 프로필 불일치 :: 연결 안 된 프로필의 트래픽이라 게이트웨이가 폐기

> 교육 포인트: 원격 네트워크는 "누가"가 아니라 "어느 지점에서"를 기준으로 에지에 연결합니다. 사용자별 정책 · 조건부 액세스 · 컴플라이언트 네트워크 같은 신원 기반 통제는 클라이언트가 해 주고, 클라이언트 없는 지점 트래픽은 기준선 프로필이 대신 지킵니다.
>
> 주의: 인터넷 트래픽 전달에는 Internet Access 라이선스가 필요하고, 개요 문서는 이 부분을 "coming soon"으로 적고 있습니다 [확인 필요: 인터넷 프로필의 원격 네트워크 적용 시점 · 미리 보기 범위].

### L3 · A · 지점 → 에지 터널 수립과 BGP 라우팅

#### L4 · CPE가 IKEv2 터널을 열고 BGP로 경로를 교환하는 순서

1. [시작] CPE가 Microsoft 공인 IP(endpoint)로 IKE_SA_INIT 전송
   - 주체: 지점 CPE
   - 위치: CPE → Microsoft endpoint (View configuration에서 확인한 공인 IP), UDP 500
   - 데이터: Global Secure Access는 Responder 모드이므로 연결 시작은 항상 CPE가 합니다
   - 해설: 에지는 먼저 연결을 걸어 오지 않으므로 CPE가 먼저 말을 걸어야 터널이 시작됩니다
2. [판단] UDP 500 · 4500이 지점 방화벽과 ISP 라우터를 통과하는가?
   - 주체: 외부
   - 위치: 지점 방화벽 · ISP 라우터(NAT 장치일 수 있음)
   - 데이터: UDP 500 · UDP 4500(IPsec) · TCP 179(BGP)를 허용해야 합니다. ISP 라우터가 NAT면서 포트를 바꾸면 에지가 500번 포트의 협상을 알아보지 못해 1단계가 실패하므로 포트 포워딩이 필요합니다
   - 해설: 터널 장애의 첫 번째 흔한 원인은 CPE 설정이 아니라 중간 장비의 포트 처리입니다
   - UDP 허용 → 3
   - UDP 차단 → [차단] IKE 1단계 실패 — 포트 차단 · 터널 미수립
3. [판단] 에지가 본 공인 IP가 디바이스 링크의 Device IP address와 같은가?
   - 주체: SSE 에지
   - 위치: Global Secure Access › 연결 › 원격 네트워크 › Links › Device IP address
   - 데이터: CPE가 NAT 장치 뒤에 있으면 CPE의 사설 WAN IP가 아니라 상위 라우터의 공인 IP를 넣어야 합니다(NAT-T는 UDP 4500). 상위 라우터의 공인 IP가 바뀌면 링크를 지우고 새 IP로 다시 만듭니다
   - 해설: 에지는 들어오는 터널을 원본 IP로 식별하므로 이 값이 다르면 협상이 시작되지 않습니다
   - IP 일치 → 4
   - IP 불일치 → [차단] 디바이스 링크 식별 실패 — 터널 미수립
4. [판단] 1단계(암호·무결성·DH)와 PSK가 디바이스 링크와 일치하는가?
   - 주체: SSE 에지
   - 데이터: 기본 정책이면 8개 1단계 조합 중 하나(예: GCMAES256 / SHA384 / DHGroup24), 사용자 지정이면 설정한 조합. 사전 공유 키는 양쪽이 같아야 합니다
   - 해설: IKEv2로 서로를 인증하고 보안 연결(SA)의 키를 만드는 단계입니다
   - 협상 일치 → 5
   - 협상 불일치 → [차단] 1단계 실패 — 암호 정책 · PSK 불일치
5. [처리] 2단계(IPsec) 협상 — 자식 SA 수립, Tunnel connected 이벤트
   - 주체: SSE 에지
   - 데이터: IPsec 암호·무결성 GCMAES128 / 192 / 256(PFS 없음, 기본 정책 기준) · 트래픽 셀렉터 0.0.0.0/0 · Remote network health logs의 Status = Tunnel connected (BGP Routes Advertised Count 0)
   - 해설: 이 시점에 IPsec 터널이 올라오고 상태 로그에 첫 이벤트가 남습니다
6. [처리] CPE에 Microsoft BGP 주소로 가는 정적 경로 추가 — 터널 인터페이스로
   - 주체: 지점 CPE
   - 위치: CPE 라우팅 설정 (View configuration의 localConfigurations에서 확인한 BGP 주소)
   - 데이터: 이 경로가 있어야 CPE가 터널 안에서 BGP 이웃에 닿아 Microsoft가 광고하는 경로를 학습합니다. Microsoft 쪽 BGP 주소가 지점 내부 서브넷과 겹치면 터널 대신 물리 구간으로 ARP를 보내 BGP가 올라오지 않습니다
   - 해설: IPsec은 올라왔는데 BGP가 안 오는 사고의 대표적인 원인이 이 정적 경로 누락입니다
7. [판단] BGP 이웃이 성립하는가?
   - 주체: SSE 에지
   - 위치: BGP 피어링 — TCP 179, Microsoft ASN ↔ CPE ASN
   - 데이터: 두 ASN이 서로 달라야 하고 local/peer BGP 주소가 CPE와 Global Secure Access에서 서로 뒤집혀 있어야 합니다. Status = BGP connected / BGP disconnected
   - 해설: 터널이 up이어도 BGP가 down이면 경로 교환이 되지 않아 지점 트래픽이 에지로 가지 못합니다
   - BGP 성립 → 8
   - BGP 실패 → [차단] 경로 교환 실패 — 터널은 up, BGP는 down
8. [끝] 경로 교환 완료 — BGP connected, 15분마다 Remote network alive
   - 주체: 로그
   - 위치: Global Secure Access › 모니터링 › 원격 네트워크 상태 로그
   - 데이터: BGP connected 이벤트 · 이후 Remote network alive의 BGP Routes Advertised Count · Sent/Received Bytes(최근 15분 합계)
   - 해설: 광고 경로 수가 0이 아니고 바이트가 늘어나면 지점 트래픽이 실제로 흐르고 있다는 뜻입니다
- 시나리오: UDP 허용 ▸ IP 일치 ▸ 협상 일치 ▸ BGP 성립 :: 터널과 BGP가 모두 올라와 경로 교환 완료
- 시나리오: UDP 허용 ▸ IP 일치 ▸ 협상 일치 ▸ BGP 실패 :: 터널은 올라왔지만 BGP가 내려가 있음
- 시나리오: UDP 허용 ▸ IP 일치 ▸ 협상 불일치 :: 암호 정책 또는 PSK 불일치로 터널 미수립
- 시나리오: UDP 허용 ▸ IP 불일치 :: 공인 IP가 달라 에지가 링크를 식별하지 못함
- 시나리오: UDP 차단 :: 포트 차단으로 IKE 1단계부터 실패

> 교육 포인트: 터널(IPsec)과 경로 교환(BGP)은 별개 계층입니다. Tunnel connected와 BGP connected는 서로 다른 이벤트이고, BGP는 터널 위에서만 동작합니다. CPE는 BGP 이웃 주소를 터널 쪽으로 보내는 정적 경로를 반드시 가져야 합니다.
>
> 주의: NAT 뒤 CPE는 반드시 상위 라우터의 정적 공인 IP를 쓰고, NAT-T 키프얼라이브·DPD를 켜며, 상위 장치의 IPsec/VPN 패스스루 ALG는 끕니다. 라우팅 방식은 BGP가 기본이고 BGP를 지원하지 않는 장비는 적절한 메트릭의 정적 경로를 씁니다 [확인 필요: 정적 경로만 쓰는 구성의 지원 범위].

#### L4 · 암호 조합 · 영역 이중화 · 기본 경로 정책 — 어떻게 끊기지 않게 구성하는가

1. [시작] 디바이스 링크의 IPsec/IKE 정책 선택 지점
   - 주체: 관리자
   - 위치: Global Secure Access › 연결 › 원격 네트워크 › Links › + Add a link › Details 탭
   - 데이터: IKEv2(현재 유일) · IPSec/IKE policy = Default 또는 Custom
   - 해설: 정책 종류에 따라 CPE에 넣을 값이 정해집니다
2. [판단] 정책이 기본값인가 사용자 지정인가?
   - 주체: 관리자
   - 데이터: 기본값은 문서 표의 조합 중 하나를 CPE에 맞추고, 사용자 지정은 허용 범위 안에서 직접 고릅니다
   - 해설: 어느 쪽이든 CPE와 디바이스 링크의 정책이 일치해야 합니다
   - 기본값 → 3
   - 사용자 지정 → 4
3. [처리] 기본값 — 1단계 8조합 · 2단계 3조합 중 선택
   - 주체: 지점 CPE
   - 데이터: 1단계: GCMAES256 · GCMAES128 · AES256 · AES128 암호에 SHA384 · SHA256 무결성, DHGroup24 또는 DHGroup14. 2단계: GCMAES256 · GCMAES192 · GCMAES128 (PFS Group None)
   - 해설: 1단계와 2단계를 모두 지정해야 협상이 끝까지 진행됩니다
   - 다음 → 6
4. [판단] 선택한 2단계가 허용 조합인가?
   - 주체: 관리자
   - 데이터: 허용: GCMAES128/128 · GCMAES192/192 · GCMAES256/256, 또는 IPsec encryption None + SHA256. 1단계는 제한 없음 · PFS group 제한 없음 · SA lifetime 300초 초과
   - 해설: 목록 밖 조합을 고르면 협상이 실패합니다
   - 허용 조합 → 5
   - 허용 밖 → [차단] 협상 실패 — 지원하지 않는 2단계 조합
5. [처리] 사용자 지정 값 입력 — Encryption · IKEv2 integrity · DHGroup · IPsec · PFS · SA lifetime
   - 주체: 관리자
   - 위치: Details 탭 › Custom · Graph: tunnelConfigurationIKEv2Custom(saLifeTimeSeconds · ipSecEncryption · ipSecIntegrity · ikeEncryption · ikeIntegrity · dhGroup · pfsGroup)
   - 데이터: 같은 값을 CPE의 crypto profile에 넣습니다
   - 해설: 두 장비의 값이 정확히 같아야 하므로 CPE 콘솔에 옮겨 적은 뒤 한 번 더 대조합니다
6. [판단] 이중화를 구성하는가?
   - 주체: 관리자
   - 위치: General 탭 › Redundancy = No redundancy / Zone redundancy
   - 데이터: Zone redundancy는 같은 Azure 지역의 서로 다른 가용성 영역에 터널 2개를 만듭니다. 지역 단위 이중화는 다른 지역에 원격 네트워크를 하나 더 만들어 같은 CPE 구성을 재사용합니다
   - 해설: 위치마다 IPsec 터널을 2개 이상 두는 것이 권장 사항입니다
   - 영역 이중화 → 7
   - 단일 터널 → 8
7. [처리] 영역 이중화 — 두 번째 BGP 주소와 두 번째 PSK
   - 주체: 관리자
   - 위치: General 탭 › Zone redundancy local BGP address · Security 탭 › Zone Redundancy Pre-shared key
   - 데이터: 지점 내부망에 속하지 않고 Local BGP address와도 다른 주소. View configuration에는 두 번째 값 세트가 생성됩니다
   - 해설: 터널 하나가 영역 장애로 끊겨도 두 번째 터널이 살아 있습니다
8. [판단] CPE의 기본 경로 정책은 보안 우선인가 생산성 우선인가?
   - 주체: 관리자
   - 위치: CPE 라우팅·가중치 설정 (Equal split = active-active, Primary/secondary = active-standby)
   - 데이터: 보안 우선은 기본 경로 없이 터널로만 정적 라우팅해 에지를 거치지 않는 직행을 막습니다. 생산성 우선은 기본 경로를 두고 IP SLA Layer 7 헬스 프로브(http://m365.remote-network.edgediagnostic.globalsecureaccess.microsoft.com:6544/ping 또는 IP 198.18.1.101을 터널로 정적 라우팅)로 장애를 감지합니다
   - 해설: 에지 장애 때 직접 인터넷으로 나갈 것인지를 업무 우선순위에 맞춰 결정합니다
   - 보안 우선 → [끝] 기본 경로 없이 터널로만 — 에지 장애 시 접속 끊김 감수
   - 생산성 우선 → [끝] 기본 경로와 프로브 사용 — 에지 장애 시 직접 인터넷으로 폴백
- 시나리오: 기본값 ▸ 영역 이중화 ▸ 보안 우선 :: 기본 조합과 영역 이중화에 터널로만 라우팅
- 시나리오: 기본값 ▸ 영역 이중화 ▸ 생산성 우선 :: 기본 조합과 영역 이중화에 기본 경로 폴백
- 시나리오: 기본값 ▸ 단일 터널 ▸ 보안 우선 :: 기본 조합 단일 터널로 에지 장애 시 접속 끊김
- 시나리오: 기본값 ▸ 단일 터널 ▸ 생산성 우선 :: 기본 조합 단일 터널에 기본 경로 폴백
- 시나리오: 사용자 지정 ▸ 허용 조합 ▸ 영역 이중화 ▸ 보안 우선 :: 사용자 지정에 이중화와 터널 전용 라우팅
- 시나리오: 사용자 지정 ▸ 허용 조합 ▸ 영역 이중화 ▸ 생산성 우선 :: 사용자 지정에 이중화와 기본 경로 폴백
- 시나리오: 사용자 지정 ▸ 허용 조합 ▸ 단일 터널 ▸ 보안 우선 :: 사용자 지정 단일 터널에 터널 전용 라우팅
- 시나리오: 사용자 지정 ▸ 허용 조합 ▸ 단일 터널 ▸ 생산성 우선 :: 사용자 지정 단일 터널에 기본 경로 폴백
- 시나리오: 사용자 지정 ▸ 허용 밖 :: 허용되지 않는 2단계 조합이라 협상 실패

> 교육 포인트: 대역폭은 터널 단위로 250 · 500 · 750 · 1,000 Mbps 중에서 지정하고 테넌트 총량(라이선스 합계 50~99개 500 Mbps, 100~499개 1,000 Mbps 등) 안에서 나눠 씁니다. 부족하면 Remote Network Bandwidth SKU로 500 Mbps씩 추가할 수 있습니다.

### L3 · B · 원격 네트워크 트래픽 정책 적용

#### L4 · 연결된 전달 프로필만 통과 — 프로필이 지점 트래픽을 걸러 낸다

1. [시작] 지점 트래픽이 IPsec 터널로 에지 게이트웨이에 도착
   - 주체: SSE 에지
   - 위치: Global Secure Access 게이트웨이 (원격 네트워크의 디바이스 링크)
   - 데이터: 터널 Source IP · Destination IP · 원격 네트워크 ID
   - 해설: 도착한 트래픽은 먼저 어떤 전달 프로필에 속하는지부터 가려집니다
2. [판단] 트래픽 유형이 무엇인가?
   - 주체: SSE 에지
   - 데이터: Microsoft 365 등 Microsoft 대상인지, 일반 인터넷 대상인지. Microsoft traffic profile로 획득할 수 있는 트래픽은 Internet Access profile로는 획득되지 않습니다
   - 해설: 에지는 Microsoft 프로필, Private Access 프로필, Internet Access 프로필 순서로 유형을 평가합니다. Private Access는 원격 네트워크에 할당되지 않습니다
   - Microsoft 트래픽 → 3
   - 일반 인터넷 → 4
3. [판단] Microsoft traffic profile이 이 원격 네트워크에 연결·활성인가?
   - 주체: SSE 에지
   - 위치: 원격 네트워크 › Traffic profiles › Microsoft traffic profile, 또는 연결 › 트래픽 전달 › Microsoft traffic profile › Add/edit assignments
   - 데이터: 연결 여부 · 프로필 상태
   - 해설: 연결돼 있지 않으면 Microsoft 트래픽이 터널로 왔어도 처리되지 않습니다
   - MS 프로필 연결 → 5
   - MS 프로필 미연결 → [차단] 게이트웨이가 폐기 — Internet Access만 연결된 경우
4. [판단] Internet Access traffic profile이 이 원격 네트워크에 연결·활성인가?
   - 주체: SSE 에지
   - 위치: 원격 네트워크 › Traffic profiles › Internet Access traffic profile
   - 데이터: 연결 여부 · 프로필 상태 — Internet Access 라이선스 필요
   - 해설: 연결돼 있지 않으면 일반 인터넷 트래픽이 터널로 왔어도 에지가 받지 않습니다
   - 인터넷 프로필 연결 → 5
   - 인터넷 프로필 미연결 → [차단] 게이트웨이가 폐기 — Microsoft traffic profile만 연결된 경우
5. [처리] 해당 프로필이 획득한 트래픽으로 분류 — 보안 평가로 전달
   - 주체: SSE 에지
   - 데이터: 전달 프로필은 어떤 트래픽을 획득할지만 정하고 어떤 정책이 적용될지는 정하지 않습니다. 정책은 다음 단계의 보안 프로필이 정합니다
   - 해설: 프로필은 입구 필터이고, 보안 프로필이 그 안에서 허용·차단을 정합니다
6. [끝] 기준선 보안 프로필 평가로 이동
   - 주체: SSE 에지
   - 위치: Global Secure Access › 보안 › 보안 프로필 › Baseline profile
   - 데이터: 평가 결과는 트래픽 로그에 Device category = remote network로 남습니다
   - 해설: 두 프로필을 모두 연결하는 것이 라이선스가 허용하는 경우의 권장 구성입니다
- 시나리오: Microsoft 트래픽 ▸ MS 프로필 연결 :: Microsoft 프로필이 연결돼 있어 보안 평가로 이동
- 시나리오: Microsoft 트래픽 ▸ MS 프로필 미연결 :: Microsoft 프로필 미연결이라 게이트웨이가 폐기
- 시나리오: 일반 인터넷 ▸ 인터넷 프로필 연결 :: 인터넷 프로필이 연결돼 있어 보안 평가로 이동
- 시나리오: 일반 인터넷 ▸ 인터넷 프로필 미연결 :: 인터넷 프로필 미연결이라 게이트웨이가 폐기

> 교육 포인트: 연결된 프로필과 맞지 않는 유형의 트래픽은 오류 응답 없이 폐기되어 사용자에게는 "일부 사이트만 안 열리는" 증상으로 보입니다. 원인을 찾을 때는 먼저 이 원격 네트워크에 어떤 프로필이 연결돼 있는지부터 확인합니다.
>
> 주의: 프로필 하나만 연결할 때의 영향은 문서가 명시한 두 경우(Microsoft만 연결 → 비Microsoft 트래픽 폐기, Internet Access만 연결 → Microsoft 트래픽 폐기)입니다.

#### L4 · 클라이언트가 없어 달라지는 것 — 기준선 프로필 · CA 미적용 · Custom Bypass 미동작

1. [시작] 에지가 원격 네트워크의 트래픽을 획득
   - 주체: SSE 에지
   - 데이터: 출발지 = 원격 네트워크(지점), 사용자·기기 신원 없음
   - 해설: 클라이언트 경로와 가장 크게 다른 점은 요청에 사용자·기기 컨텍스트가 실리지 않는다는 것입니다
2. [처리] 조건부 액세스는 평가되지 않음 — 사용자별 보안 프로필도 적용 안 됨
   - 주체: Entra ID
   - 위치: Entra ID › 조건부 액세스 (대상 리소스 All internet resources with Global Secure Access)
   - 데이터: Microsoft·인터넷 트래픽에 대한 조건부 액세스는 클라이언트가 있는 사용자에게만 적용됩니다. Microsoft 트래픽은 원격 네트워크로 클라이언트 없이도 접근되지만 조건부 액세스는 강제되지 않습니다
   - 해설: MFA · 규정 준수 디바이스 · 로그인 위험 같은 신원 통제는 지점 트래픽에 걸리지 않습니다
3. [처리] 우회가 필요한 대상은 CPE에서 미리 처리 — Custom Bypass는 이 경로에서 동작하지 않음
   - 주체: 지점 CPE
   - 위치: CPE 라우팅 · 방화벽 정책 (Global Secure Access › 연결 › 트래픽 전달 › Internet Access policies의 Custom Bypass가 아님)
   - 데이터: 인터넷 프로필의 Custom Bypass는 원격 네트워크 연결에서 동작하지 않으므로 특정 URL은 CPE에서 직접 우회시켜야 합니다
   - 해설: 에지로 보내면 안 되는 대상은 터널에 태우기 전에 CPE 라우팅에서 빼야 합니다
4. [처리] 기준선 보안 프로필이 테넌트 전체 정책을 적용 — 우선순위 65,000
   - 주체: SSE 에지
   - 위치: Global Secure Access › 보안 › 보안 프로필 › Baseline profile › Edit profile › Link a policy › Existing policy › Add › Save · Graph: GET /beta/networkaccess/filteringProfiles
   - 데이터: 연결할 수 있는 정책 — 웹 콘텐츠 필터링 · 위협 인텔리전스 · TLS 검사 · 클라우드 방화벽. 조건부 액세스 연결 없이 지점 트래픽을 포함한 모든 트래픽에 자동 적용됩니다
   - 해설: 지점 트래픽에 정책을 걸려면 정책을 만든 뒤 기준선 프로필에 우선순위와 함께 연결해야 합니다
5. [판단] 규칙이 소스 유형(source traffic type)에 의존하는가?
   - 주체: SSE 에지
   - 데이터: 소스 유형 필터링은 클라이언트 연결에서만 지원되고 원격 네트워크는 소스 유형 규칙을 지원하지 않습니다. 범주 · URL · FQDN 규칙은 쓸 수 있습니다
   - 해설: 소스 유형은 클라이언트가 보내는 작업·프로세서 정보에 의존하기 때문에 지점 트래픽에는 없습니다
   - 소스 유형 규칙 → [끝] 소스 유형 규칙은 집행되지 않음 — 전달됨
   - 범주·URL·FQDN 규칙 → 6
6. [판단] 연결된 정책의 Block 규칙에 일치하는가?
   - 주체: SSE 에지
   - 위치: 정책 우선순위 순서 평가
   - 데이터: 정책 Action = Block / Allow. 평문 HTTP는 URL로, TLS 검사가 없는 HTTPS는 SNI로 판정합니다
   - 해설: 일치하는 Block이 있으면 차단하고, 없으면 허용합니다
   - 차단 규칙 일치 → [차단] 기준선 정책으로 차단 — Denied 기록
   - 일치 규칙 없음 → 7
7. [끝] 허용 후 전달 — 트래픽 로그에서 지점 트래픽 확인
   - 주체: 로그
   - 위치: Global Secure Access › 모니터링 › 트래픽 로그 › Add filter › Device category (client / remote network)
   - 데이터: Device category = remote network · Action(Allowed / Denied) · Web category · Sent/Received Bytes. 보기 최소 역할은 Reports Reader입니다
   - 해설: 정책이 지점 트래픽에 실제로 집행되는지는 Device category 필터로 확인합니다
- 시나리오: 소스 유형 규칙 :: 소스 유형 규칙은 지점에서 집행되지 않고 전달됨
- 시나리오: 범주·URL·FQDN 규칙 ▸ 차단 규칙 일치 :: 범주·URL 규칙이 Block에 일치해 차단되고 Denied 기록
- 시나리오: 범주·URL·FQDN 규칙 ▸ 일치 규칙 없음 :: 범주·URL 규칙에 걸리지 않아 허용 후 전달

> 교육 포인트: 클라이언트 경로는 "사용자 + 기기 + 조건부 액세스 + 사용자별 보안 프로필", 원격 네트워크 경로는 "지점 + 기준선 프로필"입니다. 같은 사이트 차단 규칙이라도 지점에서는 모든 사용자에게 똑같이 적용되고 예외를 사용자별로 둘 수 없습니다.
>
> 주의: 기준선 프로필은 "우선순위 65,000으로 가장 낮은" 프로필이어서 사용자별 프로필이 있는 클라이언트 트래픽에서는 그쪽이 먼저 적용됩니다. 원격 네트워크 트래픽은 CA 연결이 없으므로 기준선만 적용됩니다 [확인 필요: 소스 유형 규칙 외 클라이언트 전용 규칙 · 미리 보기 기능 범위].

### L3 · C · 상태 점검과 장애

#### L4 · 상태 로그와 알림으로 터널 · BGP 이상을 가려낸다

1. [시작] Entra Health 알림 또는 지점 사용자 신고로 점검 시작
   - 주체: 관리자
   - 위치: Entra ID › 모니터링 및 상태(Monitoring & health) › Health › Health Monitoring 탭 — 'Global Secure Access requiring remote network tunnel connectivity' · 'Global Secure Access requiring remote network BGP connectivity'
   - 데이터: 알림 시간대 · 영향받는 원격 네트워크. 신호 조회는 Reports Reader가 최소 역할이고, 알림 수정은 Helpdesk Administrator입니다
   - 해설: 터널 신호와 BGP 신호는 서로 다른 시나리오입니다
2. [처리] 원격 네트워크 상태 로그 열기 — Remote network ID로 필터
   - 주체: 관리자
   - 위치: Global Secure Access › 모니터링(Monitor) › Remote network health logs (Global Secure Access Administrator 또는 Security Administrator) · Graph: GET /beta/networkAccess/logs/remotenetworks
   - 데이터: Created date time · Source IP(CPE) · Destination IP(에지) · Status · Description · BGP Routes Advertised Count · Sent/Received Bytes · Remote network ID. 필터는 Description · Remote network ID · Source IP · Destination IP · BGP routes advertised count
   - 해설: Source IP와 Destination IP 쌍이 터널마다 유일하므로 어느 터널이 문제인지 이 쌍으로 짚습니다
3. [판단] 가장 최근 이벤트의 Status는 무엇인가?
   - 주체: 로그
   - 데이터: Tunnel connected · Tunnel disconnected · BGP connected · BGP disconnected · Remote network alive(활성 터널마다 15분 주기)
   - 해설: 어떤 계층의 이벤트인지에 따라 조사 방향이 갈립니다
   - Tunnel disconnected → 4
   - BGP disconnected → 6
   - Remote network alive → 8
4. [처리] 터널 끊김 조사 — CPE 상태 · 공인 IP · IPsec 값 · PSK 대조
   - 주체: 관리자
   - 위치: CPE 로그 · Global Secure Access › 모니터링 › Audit logs (원격 네트워크 · 디바이스 링크 · IPsec 구성 · 프로필 할당 변경 확인)
   - 데이터: CPE 정전·ISP 장애·구성 불일치(공인 IP · IPsec 파라미터 · 공유 비밀) 가운데 어느 것인지 가립니다. 감사 로그는 Reports Reader · Security Reader · Security Administrator가 볼 수 있고 기본 30일 보관됩니다
   - 해설: 알림 시작 시각 근처의 구성 변경이 가장 흔한 단서입니다
5. [끝] 복구 확인 — Tunnel connected 이벤트와 바이트 재개
   - 주체: 로그
   - 위치: Remote network health logs
   - 데이터: Tunnel connected 이후 Remote network alive의 Sent/Received Bytes가 다시 늘어나는지 확인
   - 해설: 이벤트 한 줄이 아니라 바이트가 실제로 늘어나는지까지 봐야 복구입니다
6. [처리] BGP 끊김 조사 — 터널은 Connected인지부터 확인
   - 주체: 관리자
   - 위치: Remote network health logs의 Tunnel connected · CPE의 BGP 이웃 설정
   - 데이터: CPE의 neighbor IP · ASN · 경로 광고 설정. Remote network alive의 BGP Routes Advertised Count로 광고된 경로 수를 비교합니다. IPsec 터널이 연결된 채로 BGP만 끊길 수 있습니다
   - 해설: BGP가 끊기면 터널이 살아 있어도 경로 교환이 안 되어 트래픽이 흐르지 않을 수 있습니다
7. [끝] BGP connected 이벤트와 광고 경로 수 복귀 확인
   - 주체: 로그
   - 위치: Remote network health logs
   - 데이터: BGP connected 이벤트 · 이후 Remote network alive의 BGP Routes Advertised Count가 평소 값으로 복귀
   - 해설: 광고 경로 수가 평소 값으로 돌아와야 정상 복구입니다
8. [끝] 정상 — 15분 주기 Remote network alive로 기준선 비교
   - 주체: 로그
   - 위치: Remote network health logs · Entra ID › 모니터링 및 상태 › 진단 설정(Diagnostic settings) › RemoteNetworkHealthLogs (Security Administrator)
   - 데이터: Log Analytics로 내보내면 BGP 끊김 같은 알림 규칙과 워크북을 쓸 수 있고, 로그가 대상에 나타나기까지 최대 3일이 걸릴 수 있습니다. 트래픽 로그와 상태 로그는 시스템에 30일 보관됩니다
   - 해설: 정상일 때 값을 기준선으로 남겨 두어야 이상 징후를 빨리 알아봅니다
- 시나리오: Tunnel disconnected :: 터널 끊김의 원인을 가려내 복구 후 바이트 재개 확인
- 시나리오: BGP disconnected :: 터널은 유지되나 BGP가 끊겨 BGP 설정을 점검
- 시나리오: Remote network alive :: 터널과 BGP가 모두 정상이며 기준선 비교

> 교육 포인트: 터널 신호와 BGP 신호는 서로 다른 계층입니다. 터널이 끊기면 BGP도 경로를 교환할 수 없지만, 터널이 살아 있어도 BGP만 끊길 수 있습니다. 상태 로그의 Remote network alive가 15분 주기로 오는지가 가장 단순한 생존 신호입니다.
>
> 주의: 이 로그는 터널·BGP의 상태이며 사용자별 접속 기록이 아닙니다. 사용자·정책 판정은 트래픽 로그의 Device category = remote network 행으로 봅니다. 운영 가이드 문서에는 원격 네트워크가 GRE 또는 IPsec이라고 적혀 있지만 개념 문서는 IPsec만 다룹니다 [확인 필요: GRE 터널 지원 여부 · 문서 불일치].

#### L4 · 지점 접속 장애를 단계별로 원인 분리한다

1. [시작] 지점 사용자가 접속 불가 또는 느림을 신고
   - 주체: 사용자
   - 위치: 지점 LAN
   - 데이터: 증상(전체 불통 · 일부 사이트만 불통 · 간헐 끊김 · 느림)과 시작 시각
   - 해설: 증상이 어느 계층인지부터 좁힙니다
2. [판단] IPsec 터널이 Connected인가?
   - 주체: 관리자
   - 위치: Global Secure Access › 연결 › 원격 네트워크(터널 상태) · Remote network health logs
   - 데이터: Tunnel connected / Tunnel disconnected
   - 해설: 터널이 내려가 있으면 아래 계층은 볼 필요가 없습니다
   - 터널 Down → 3
   - 터널 Up → 4
3. [끝] IKE · IPsec · PSK · 포트 · 공인 IP를 대조해 재구성
   - 주체: 관리자
   - 위치: CPE 로그 · 디바이스 링크 General/Details/Security 탭
   - 데이터: IKE 버전과 암호 정책 · PSK 일치, UDP 500/4500 허용, 디바이스 링크의 공인 IP(NAT 뒤라면 상위 라우터 공인 IP, NAT-T 키프얼라이브 · DPD 활성, VPN 패스스루 ALG 끔)와 링크를 지우고 다시 만든 뒤 달라진 Microsoft endpoint IP
   - 해설: 이 단계의 원인은 CPE와 디바이스 링크 값의 불일치인 경우가 대부분입니다
4. [판단] BGP 세션이 Connected인가?
   - 주체: 관리자
   - 위치: Remote network health logs의 BGP connected / BGP disconnected
   - 데이터: BGP Routes Advertised Count
   - 해설: 터널이 올라와 있어도 BGP가 내려가 있으면 지점 트래픽이 에지로 가지 못합니다
   - BGP Down → 5
   - BGP Up → 6
5. [끝] 정적 경로 · ASN · local/peer 주소를 점검
   - 주체: 관리자
   - 위치: CPE BGP 설정 · View configuration의 bgpAddress · asn
   - 데이터: Microsoft BGP 주소로 가는 정적 경로가 터널 인터페이스에 있는지, 두 ASN이 서로 다른지, local/peer 주소가 CPE와 Global Secure Access에서 서로 뒤집혀 있는지, Microsoft 쪽 BGP 주소가 지점 내부 서브넷과 겹치지 않는지
   - 해설: 터널이 up인데 BGP가 안 올라오는 장애는 대부분 이 네 가지 가운데 하나입니다
6. [판단] 증상은 어떤 유형인가?
   - 주체: 관리자
   - 데이터: 터널 Up · BGP Up인데도 남아 있는 증상 — 간헐 끊김 · 트래픽 미도달 · 속도 저하
   - 해설: 이 시점부터는 계층 문제가 아니라 패킷 크기 · 라우팅 · 용량 문제입니다
   - 간헐 끊김 → 7
   - 트래픽 안 흐름 → 8
   - 느림 → 9
7. [끝] MTU · MSS를 조정 — IPsec은 터널 MTU 1,380 권장
   - 주체: 지점 CPE
   - 위치: CPE 터널 인터페이스 설정
   - 데이터: 터널 MTU를 1,380바이트로 낮추고 TCP MSS clamping을 켭니다. 터널 플래핑이 같이 보이면 ISP 안정성도 확인합니다
   - 해설: ESP와 NAT-T 헤더 때문에 큰 패킷이 조각나거나 버려지면 일부 흐름만 간헐적으로 실패합니다
8. [끝] CPE 경로 · NAT · 프로필 연결을 확인
   - 주체: 지점 CPE
   - 위치: CPE 라우팅 테이블 · 원격 네트워크 › Traffic profiles
   - 데이터: 대상 트래픽이 터널로 가는 경로가 있는지, 소스 NAT/PAT 설정, 패킷 캡처. 프로필이 하나만 연결돼 있으면 다른 유형 트래픽은 게이트웨이가 폐기합니다. 다른 지점은 되는데 이 지점만 안 되면 프로필 할당을 다른 지점과 비교합니다
   - 해설: 터널과 BGP가 모두 정상이면 대개 라우팅이나 프로필 연결이 원인입니다
9. [끝] 대역폭 사용률을 확인 — 터널 추가 또는 대역폭 상향
   - 주체: 로그
   - 위치: Remote network health logs의 Sent/Received Bytes · Log Analytics의 RemoteNetworkHealthLogs
   - 데이터: 디바이스 링크 대역폭(250 · 500 · 750 · 1,000 Mbps) 대비 사용률. 운영 가이드는 70% 지속 시 경고, 85% 지속 시 심각으로 보고 두 번째 터널 추가나 대역폭 상향을 권장합니다
   - 해설: 용량이 찬 터널은 지연과 손실로 나타나므로 사용량 추세로 용량 계획을 세웁니다
- 시나리오: 터널 Down :: IKE · PSK · 포트 · 공인 IP 불일치로 터널이 내려감
- 시나리오: 터널 Up ▸ BGP Down :: 터널은 올라왔으나 BGP가 내려가 경로 교환 실패
- 시나리오: 터널 Up ▸ BGP Up ▸ 간헐 끊김 :: 터널과 BGP 정상이나 MTU로 일부 흐름이 끊김
- 시나리오: 터널 Up ▸ BGP Up ▸ 트래픽 안 흐름 :: 경로 · NAT · 프로필 연결 문제로 트래픽 미도달
- 시나리오: 터널 Up ▸ BGP Up ▸ 느림 :: 터널 대역폭 포화로 속도가 느려짐

> 교육 포인트: 장애는 "터널 → BGP → 패킷·경로·용량" 순서로 아래 계층부터 위로 좁히면 빠릅니다. 계층마다 확인할 곳이 다릅니다: 터널·BGP는 원격 네트워크 상태 로그, 트래픽 판정은 트래픽 로그, 변경 이력은 감사 로그입니다.
>
> 주의: 터널 MTU 값과 대역폭 임계값은 운영 가이드의 권장값이며 환경에 따라 달라질 수 있습니다. 장애 조치 시험은 예약된 유지보수 창에서만 하고, 대상 지점에 이중화 터널과 대체 경로가 있는지 먼저 확인합니다 [확인 필요: 고객 CPE 벤더별 값].
