## L2 · 네트워크 콘텐츠 · 클라우드 방화벽 — 콘텐츠 정책과 네트워크 계층 통제

- 설정(Control Plane): 콘텐츠 정책(Content policies: Allow · Block · Scan with Purview) | 클라우드 방화벽 정책(Cloud firewall policies: 5-tuple 규칙) | 보안 프로필에 링크(콘텐츠 정책 → 보안 프로필 + 조건부 액세스, 방화벽 정책 → Baseline profile · 클라이언트용은 보안 프로필[미리 보기]) | Scan with Purview 사용 시 Microsoft Purview DLP 정책(Inline web traffic)
- 강제(Enforcement): Microsoft SSE 에지 (콘텐츠 규칙·방화벽 규칙 판정, Purview에 검사 요청) | Global Secure Access 클라이언트 · 원격 네트워크 (트래픽 획득)
- 증적(Evidence): GSA 트래픽 로그 (Monitor › Traffic logs, Transactions · Connections) | KQL: NetworkAccessTraffic (Action · PolicyName · RuleName · FilteringProfileName · DeviceCategory) | Purview DLP Alerts · Activity explorer
- 메뉴(Admin Center): Global Secure Access > 보안(Secure) > Content policies · Cloud firewall policies · Security profiles(Baseline profile 포함) | Global Secure Access > 연결(Connect) > Traffic forwarding | Global Secure Access > Monitor > Traffic logs
- 라이선스(License): 두 기능 모두 Microsoft Entra Internet Access 라이선스가 필요하고, Scan with Purview는 Microsoft Purview 라이선스(DLP는 Microsoft 365 E5/A5 또는 Purview DLP 추가 구독)가 추가로 필요하며 기본 필터링(Allow·Block)은 Purview 없이 쓸 수 있습니다 [확인 필요: 고객 라이선스 · 콘텐츠 정책의 미리 보기 여부 — 문서 본문에 미리 보기 표기는 없으나 Purview Network Data Security는 일부 기능이 미리 보기 · 클라이언트용 클라우드 방화벽은 문서 제목에 (preview) 표기]

### L3 · 0 · 기능 상태 전이 — 본문·포트 무통제 → 콘텐츠 정책·방화벽 구성 → 에지 판정

#### L4 · ⓪ 비활성 — 파일 본문과 IP·포트를 에지가 판정하지 않는다

1. [시작] 사용자가 외부 앱에 파일 업로드 — 브라우저 HTTPS 요청 본문에 파일이 실립니다
   - 주체: 사용자
   - 위치: 브라우저 → 외부 SaaS 또는 생성형 AI 앱 (HTTPS 443)
   - 데이터: 요청 본문(unencoded 또는 multipart) · 파일 MIME 형식 · 대상 FQDN
   - 해설: 업무 PC 사용자가 민감한 PDF를 외부 앱에 올리려고 합니다
2. [처리] 콘텐츠 정책 없음 — 본문의 파일 형식·텍스트 유형을 감지하는 판정이 일어나지 않음
   - 주체: SSE 에지
   - 위치: Global Secure Access › Secure › Content policies (정책 0건)
   - 데이터: 콘텐츠 정책은 페이로드의 파일 MIME 형식과 텍스트 유형을 감지해 Allow · Block을 적용하는 기능입니다. 정책이 없으면 이 감지·판정 자체가 없고, Scan with Purview 위임도 일어나지 않습니다
   - 해설: 목적지가 허용된 앱이면 그 앱으로 무엇이 올라가는지는 에지가 보지 않습니다
3. [판단] 트래픽이 어떤 경로로 에지에 들어오는가?
   - 주체: SSE 에지
   - 데이터: 트래픽 출처 — Global Secure Access 클라이언트(DeviceCategory = Client) 또는 원격 네트워크(DeviceCategory = Branch)
   - 해설: 같은 비활성 상태라도 두 경로가 남기는 위험이 다릅니다
   - 클라이언트 → 4
   - 원격 네트워크 → 5
4. [처리] 클라이언트 경로 — 허용 목적지로 가는 민감 파일이 그대로 전송됨
   - 주체: GSA 클라이언트
   - 위치: 클라이언트 → Internet access profile 획득(기본 TCP 80·443) → 에지
   - 데이터: 콘텐츠 규칙 없음 · Purview DLP 연동 없음. Scan with Purview가 있어야 가능한 민감 정보 유형·민감도 레이블·사용자 위험 수준 기준 차단도 불가능합니다
   - 해설: 웹 필터링이 켜져 있어도 판정 기준은 목적지이므로 허용 앱 안의 파일 업로드는 막히지 않습니다
   - 다음 → 6
5. [처리] 원격 네트워크 경로 — 지점 트래픽에 에지의 5-tuple 통제가 없음
   - 주체: 지점 장비
   - 위치: Global Secure Access › Secure › Security profiles › Baseline profile (링크된 클라우드 방화벽 정책 없음)
   - 데이터: 소스 IP · 소스 포트 · 대상 IP · 대상 포트 · 프로토콜(TCP/UDP) 규칙이 에지에 없고, 이 L3 통제는 지점 장비 자체 규칙에만 의존합니다
   - 해설: 지점에서 나가는 트래픽을 중앙에서 한 번에 막거나 허용하는 기준이 없습니다
6. [끝] 허용된 채 기록 — 콘텐츠·방화벽 사유 없는 Allowed 행만 남음
   - 주체: 로그
   - 위치: Global Secure Access › Monitor › Traffic logs (Reports Reader 이상)
   - 데이터: NetworkAccessTraffic의 Action = Allowed. 콘텐츠 규칙·방화벽 규칙이 판정한 흔적(PolicyName · RuleName)은 없습니다 [확인 필요: 정책이 없을 때 해당 열의 실제 값]
   - 해설: 무엇이 업로드됐는지, 어떤 규칙이 허용했는지 Entra에서 설명할 수 없습니다
- 시나리오: 클라이언트 :: 민감 파일이 검사 없이 외부 앱에 업로드됨
- 시나리오: 원격 네트워크 :: 지점 트래픽에 에지 L3 통제가 없음

> 교육 포인트: 웹 콘텐츠 필터링은 목적지(FQDN·URL·웹 범주) 기준이고 콘텐츠 정책은 그 목적지로 오가는 본문의 파일·텍스트 기준이며, 클라우드 방화벽은 IP·포트·프로토콜(L3·L4) 기준입니다. 세 통제는 서로 대체하지 않습니다.
>
> 주의: 클라이언트 경로의 콘텐츠 정책은 인터넷 액세스 프로필로 획득된 HTTP/S 트래픽만 대상입니다(Network content filtering is supported with the Internet access profile only).

#### L4 · ① 구성 — 콘텐츠 정책 · Purview DLP · 방화벽 정책 · 보안 프로필 · CA를 만든다

1. [시작] 관리자가 Entra 관리 센터에 로그인 — 역할·라이선스 확인
   - 주체: 관리자
   - 위치: entra.microsoft.com — Global Secure Access Administrator(콘텐츠 정책·방화벽 정책·보안 프로필), Conditional Access Administrator(CA 정책), Purview 포털에서는 DLP Compliance Management 또는 Information Protection Admin 같은 역할
   - 데이터: Entra 역할 할당. 라이선스는 Entra Internet Access, Scan with Purview 사용 시 Purview 라이선스와 Microsoft 365 E5/A5 또는 Purview DLP 추가 구독입니다
   - 해설: 정책 작업, 조건부 액세스 작업, Purview 작업에 필요한 역할이 서로 다릅니다
2. [처리] 전제 구성 확인 — Internet access profile · TLS 검사 · 클라이언트 · QUIC
   - 주체: 관리자
   - 위치: Global Secure Access › Connect › Traffic forwarding › Internet access profile 켜기 · Secure › TLS inspection policies · 클라이언트 트레이 › Troubleshooting › Advanced Diagnostics › Run tool › Forwarding Profile 탭 › Rules에 Internet Access 규칙 확인
   - 데이터: 콘텐츠 정책은 Internet access profile과 TLS 검사 구성을 먼저 요구하고, 클라이언트(Windows·macOS)는 Entra joined 또는 Hybrid joined 기기여야 합니다. 프로필 반영은 클라이언트에 최대 15분 걸릴 수 있습니다. UDP(QUIC)는 콘텐츠 필터링에서 지원되지 않아 Windows 방화벽 규칙 New-NetFirewallRule -DisplayName "Block QUIC" -Direction Outbound -Action Block -Protocol UDP -RemotePort 443 으로 TCP 폴백을 유도하는 방법이 안내됩니다
   - 해설: 프로필·TLS 검사·클라이언트가 준비되지 않으면 정책을 만들어도 본문을 볼 수 없습니다 (TLS 검사 상세는 다른 기능에서 다룹니다)
3. [처리] 콘텐츠 정책과 규칙 만들기 — Basics · Rules
   - 주체: 관리자
   - 위치: Global Secure Access › Secure › Content policies › + Create Policy › Basics(Name · Description) › Rules › 규칙 추가 › Review › Create
   - 데이터: 규칙 필드 — Rule name · Description · Priority · Status · Action(Allow · Block · Scan with Purview) · Matching conditions의 Activities(예: Upload)와 Content types(파일 형식 예: PDF, 텍스트 형식은 선택) · 선택 Session type(Agent이면 AI 에이전트 트래픽, 미설정이면 전체, Agent가 아니면 User 취급) · + Add destination(URL · FQDN · 웹 범주). 웹 범주를 목적지로 쓰려면 웹 콘텐츠 필터링 정책이 먼저 있어야 합니다
   - 해설: 앱별 통제는 그 앱이 파일·텍스트 전송에 쓰는 정확한 URL과 FQDN을 목적지로 넣습니다. HTML·JSON 텍스트 유형을 Block하면 일반 웹·API 트래픽(GET · POST · PUT)까지 막을 수 있어 주의가 필요합니다
4. [판단] Action이 Scan with Purview인가?
   - 주체: 관리자
   - 위치: 규칙 편집 › Action 메뉴
   - 데이터: Allow · Block = 기본 콘텐츠 필터링(Purview 불필요) / Scan with Purview = Purview DLP 정책이 감사·차단을 결정
   - 해설: Scan with Purview를 고르면 짝이 되는 Purview DLP 정책이 반드시 있어야 합니다
   - Scan with Purview → 5
   - 기본 필터링 → 6
5. [처리] Purview DLP 정책 만들기 — Inline web traffic
   - 주체: 관리자
   - 위치: purview.microsoft.com › Data loss prevention › Policies › + Create policy › Inline web traffic › Categories = Custom · Regulations = Custom policy › Name · Description › + Add cloud apps(Adaptive app scopes 예: All unmanaged AI apps) › Choose where to enforce에서 Network and non-Microsoft secure browsers 켜기 › Create or customize advanced DLP rules
   - 데이터: 규칙 Conditions › Content contains(민감 정보 유형 또는 민감도 레이블) · Actions › Restrict browser and network activities에서 Text sent to or shared with cloud or AI apps · Text received from cloud or AI apps · File uploaded to or shared with cloud or AI apps · File downloaded from cloud or AI apps 각각을 Audit 또는 Block · Incident reports · 규칙 상태 On · Policy mode(Turn the policy on immediately 또는 시뮬레이션)
   - 해설: DLP 규칙의 동작은 GSA 콘텐츠 정책의 활동·콘텐츠 유형과 맞춰야 하며, 짝이 없으면 에지가 검사·차단 결정을 받지 못합니다
6. [처리] 콘텐츠 정책을 보안 프로필에 링크 — Link policies
   - 주체: 관리자
   - 위치: Global Secure Access › Secure › Security profiles › 프로필 선택 › Link policies › + Link a policy › Existing Content policy › Policy name 선택 › State 기본값 유지 › Add
   - 데이터: 보안 프로필은 정책을 묶어 조건부 액세스로 사용자에게 전달하는 객체이며, 프로필 안에서는 우선순위 숫자가 작을수록 먼저(100 최고 · 65,000 최저) 평가됩니다
   - 해설: 링크하지 않은 콘텐츠 정책은 어떤 트래픽에도 적용되지 않습니다
7. [처리] 클라우드 방화벽 정책 만들기 — 기본 동작 Allow
   - 주체: 관리자
   - 위치: Global Secure Access › Secure › Cloud firewall policies › Create firewall policy › Basics(Name · Description) › Policy settings › Review and create
   - 데이터: 정책 단위 Default Action = Allow 이며 변경할 수 없습니다. 규칙에 걸리지 않은 모든 트래픽에 이 기본 동작이 적용됩니다
   - 해설: 차단하려면 정책 기본값을 바꾸는 것이 아니라 명시적인 Block 규칙을 만듭니다
8. [처리] 방화벽 규칙 추가 — 5-tuple · 우선순위 · 상태 · Action
   - 주체: 관리자
   - 위치: 방화벽 정책 열기 › Rules › + Add rule
   - 데이터: Name · Description · Priority(100 이상, 정책 안에서 고유, 숫자가 낮을수록 높은 우선순위) · Status(Enable · Disable, 기본 Disable이며 적용 준비가 될 때까지 Disable 유지 권장) · 소스·대상 IP(IP · 범위 · CIDR) · 소스·대상 포트 · Protocol(TCP · UDP 또는 둘 다) · Action(Allow · Block). 소스 IP·소스 포트·대상 IP·대상 포트·프로토콜은 논리 AND이고 Not set은 무시됩니다. 대상 FQDN은 원격 네트워크 시나리오에서 지원되지 않아 Not set 유지를 권장합니다
   - 해설: 규칙은 비활성 상태로 만들고 검토한 뒤 켭니다. 한 정책 안의 규칙은 모두 함께 적용되도록 규칙을 먼저 완성하고 링크합니다
9. [처리] 방화벽 정책을 프로필에 링크 — Baseline profile 또는 보안 프로필
   - 주체: 관리자
   - 위치: 지점(원격 네트워크): Global Secure Access › Secure › Security profiles › Baseline profile › Edit profile › Link policies › + Link a policy · 클라이언트(미리 보기): Secure › Security profiles › 프로필 › Link a policy › 링크 상태 Enabled › 저장
   - 데이터: Baseline profile에는 클라우드 방화벽 정책을 하나만 링크할 수 있고 상태(State)는 연필 아이콘으로 enabled/disabled 전환합니다. 원격 네트워크 문서는 Baseline이 아닌 프로필에 링크하면 효과가 없다고 하나 클라이언트 문서는 보안 프로필 링크를 안내합니다 [확인 필요: 두 문서의 서술 차이 — 클라이언트 경로는 미리 보기]
   - 해설: 지점은 Baseline profile(우선순위 65,000)로 조건부 액세스 없이 적용되고, 클라이언트 트래픽은 사용자별 보안 프로필로 적용합니다
10. [끝] 조건부 액세스로 보안 프로필 연결 — 클라이언트 사용자 대상
   - 주체: 관리자
   - 위치: Entra ID › Protection › Conditional Access › Policies › + Create new policy › Users 지정 › Target resources = All internet resources with Global Secure Access › Session › Use Global Secure Access Security Profile 선택 › Create
   - 데이터: Network · Conditions · Grant는 필요에 따라 설정하고, 정책을 켜기 전에 소규모 시험 그룹으로 시작합니다. 보고 전용(Report-only) CA 정책은 방화벽 구성을 강제하지 않습니다. 방화벽 정책 변경은 적용에 15~20분이 걸릴 수 있습니다
   - 해설: 콘텐츠 정책·방화벽 정책 구성이 끝났고, 이후 적용 대상 트래픽부터 에지가 판정합니다
- 시나리오: Scan with Purview :: Purview DLP 정책까지 만들어 콘텐츠 규칙에 짝지음
- 시나리오: 기본 필터링 :: Purview 없이 Allow · Block으로 파일 형식만 통제

> 교육 포인트: 콘텐츠 정책 구성 순서는 정책 만들기 → 보안 프로필에 링크 → 조건부 액세스 연결이고, Scan with Purview 규칙에서는 Purview DLP 정책이 한 단계 더 필요합니다. 방화벽 정책은 지점이면 Baseline profile, 클라이언트(미리 보기)면 보안 프로필 + 조건부 액세스로 전달됩니다.
>
> 주의: Purview 검사에는 최대 콘텐츠 크기 3 MB 제한이 있고 OCR은 지원되지 않습니다. 클라우드 방화벽은 테넌트당 최대 1,000개 규칙, 규칙당 소스·대상 합계 500개까지입니다.

#### L4 · ② 활성 — 업로드 요청이 에지에서 판정되고 기록된다

1. [시작] 사용자가 파일 업로드 시도 — 관리 기기의 브라우저에서 HTTPS 요청
   - 주체: 사용자
   - 위치: 브라우저 → 대상 앱 (예: chatgpt.com 파일 업로드 엔드포인트)
   - 데이터: 요청 본문의 파일(PDF 등) · 대상 URL · FQDN · Entra 사용자 ID
   - 해설: 정책을 켠 뒤 같은 업로드를 다시 시도합니다
2. [처리] GSA 클라이언트가 획득해 에지로 전달 — Internet Access 규칙
   - 주체: GSA 클라이언트
   - 위치: 클라이언트 › Advanced Diagnostics › Forwarding Profile › Internet Access rules
   - 데이터: 기본 획득 범위 TCP 80·443. UDP(QUIC)는 지원되지 않아 TCP로 폴백합니다
   - 해설: 획득되지 않은 연결은 에지를 거치지 않으므로 콘텐츠 정책도 적용되지 않습니다
3. [처리] 에지가 적용 대상 보안 프로필을 선택 — 조건부 액세스 프로필이 먼저
   - 주체: SSE 에지
   - 위치: Conditional Access › Session › Use Global Secure Access Security Profile
   - 데이터: 일치하는 보안 프로필은 우선순위 순서로 처리되고 Baseline profile은 가장 낮은 우선순위(65,000)로 마지막에 적용됩니다
   - 해설: 사용자 인식은 클라이언트 트래픽에서만 가능하고 Baseline은 모든 트래픽의 마지막 안전망입니다
4. [처리] TLS 복호화 후 본문에서 형식 감지 — 파일 MIME 형식 · 텍스트 유형
   - 주체: SSE 에지
   - 위치: TLS inspection 정책(상세는 다른 기능) → 콘텐츠 정책 평가
   - 데이터: 감지 대상은 요청·응답 본문의 파일과 텍스트이며, WebSocket 트래픽은 파일 형식 필터링을 우회하고 텍스트 유형만 평가됩니다
   - 해설: 에지가 본문을 볼 수 있어야 콘텐츠 규칙을 판정할 수 있습니다
5. [판단] 콘텐츠 규칙의 조건과 대상이 일치하는가?
   - 주체: SSE 에지
   - 데이터: Activities · Content types · (선택) Session type · Destination(URL · FQDN · 웹 범주). 목적지 와일드카드는 *.contoso.com은 되지만 *.com · contoso.*는 안 됩니다
   - 해설: 일치하지 않으면 이 규칙은 아무 동작도 하지 않습니다
   - 일치 → 6
   - 불일치 → 10
6. [판단] 규칙의 Action은 무엇인가?
   - 주체: SSE 에지
   - 데이터: Action = Block · Allow · Scan with Purview
   - 해설: 동작은 규칙의 Action 값 하나로 결정됩니다
   - Block → 7
   - Allow → 10
   - Scan with Purview → 8
7. [차단] 콘텐츠 규칙 Block — 업로드를 에지가 거부
   - 주체: SSE 에지
   - 위치: 에지 → 사용자 (대상 앱은 전송 실패 오류를 표시할 수 있음)
   - 데이터: Action = Denied로 기록 (Traffic logs)
   - 해설: 사용자는 앱 화면에서 업로드가 실패한 것으로 보게 됩니다 [확인 필요: 사용자에게 보이는 별도 차단 페이지 여부 — 문서 미확인]
8. [판단] Purview DLP 판정은 무엇인가?
   - 주체: Purview
   - 데이터: 에지가 해당 업로드를 Purview로 보내 DLP 규칙(민감 정보 유형 · 민감도 레이블 · 사용자 위험 수준)과 대조하고 판정을 돌려받아 집행합니다. 3 MB 초과 · 내부 오류 등 검사 불가면 허용(fail-open)이고 Entra 사용자 ID에 매핑되지 않는 트래픽은 Purview로 보내지 않습니다
   - 해설: 에지는 Purview의 결정을 그대로 집행합니다
   - DLP Block → 9
   - DLP Audit → 10
   - 검사 못 함 → 10
9. [차단] Purview DLP Block — 민감 콘텐츠 전송 차단
   - 주체: SSE 에지
   - 위치: Purview DLP 규칙 Action = Block
   - 데이터: Traffic logs의 차단 기록과 Purview Alerts · Activity explorer의 Network DLP activities
   - 해설: 차단 원인은 GSA 로그와 Purview 양쪽에서 확인합니다
10. [끝] 허용되고 기록 — 일치 규칙 · 프로필 · 정책 정보와 함께 로그 행 생성
   - 주체: 로그
   - 위치: Global Secure Access › Monitor › Traffic logs · KQL: NetworkAccessTraffic
   - 데이터: Action · FilteringProfileName · PolicyName · RuleName · HttpRequestContentType · DestinationFqdn · DestinationUrl. 기본 필터링만 쓴 경우 Purview 알림은 없고 Traffic logs로만 확인합니다
   - 해설: 허용·감사·검사 생략 건도 같은 로그에 남습니다
- 시나리오: 불일치 :: 규칙에 걸리지 않아 다른 정책 평가로 넘어감
- 시나리오: 일치 ▸ Allow :: 허용 규칙이 일치해 업로드가 통과함
- 시나리오: 일치 ▸ Block :: 규칙 Block으로 에지가 업로드를 거부함
- 시나리오: 일치 ▸ Scan with Purview ▸ DLP Block :: Purview가 민감 콘텐츠로 판정해 차단함
- 시나리오: 일치 ▸ Scan with Purview ▸ DLP Audit :: Purview 감사만 하고 업로드는 통과함
- 시나리오: 일치 ▸ Scan with Purview ▸ 검사 못 함 :: 검사 불가라 fail-open으로 통과함

> 교육 포인트: 콘텐츠 정책은 네 단계(획득 → 프로필 선택 → 복호화·형식 감지 → 규칙 판정)를 거치고, Scan with Purview일 때만 다섯 번째로 Purview가 개입합니다.
>
> 주의: 요청이 API 사용량 기반 속도 제한을 넘으면 트래픽이 자동으로 차단됩니다(fail-closed). 반대로 Purview 검사가 끝나지 못하면 허용(fail-open)되므로 두 실패 방향이 다릅니다.

### L3 · A · 정책 규칙 평가 — 콘텐츠 규칙과 방화벽 규칙은 어떤 순서·조건으로 판정되는가

#### L4 · 콘텐츠 규칙 — 감지 가능 여부 · 조건 일치 · Action

1. [시작] 에지가 복호화된 HTTP/S 요청·응답을 받는다 — 콘텐츠 정책 평가 시작
   - 주체: SSE 에지
   - 위치: Internet access profile로 획득된 HTTP/S 트래픽 (콘텐츠 필터링은 Internet access profile만 지원)
   - 데이터: 요청·응답 본문 · 대상 URL · FQDN
   - 해설: 평가는 본문을 읽을 수 있는 트래픽에서만 시작됩니다
2. [판단] 본문에서 파일·텍스트를 감지할 수 있는 전송 방식인가?
   - 주체: SSE 에지
   - 데이터: 감지 가능 = 인코딩 없이 요청·응답 본문으로 전송되거나 multipart 인코딩. 감지 불가 = 앱이 파일을 JSON 안에 인코딩하거나 여러 암호화된 요청으로 쪼개는 방식
   - 해설: 일부 파일 전송 방식은 검사를 막을 수 있다고 문서가 명시합니다
   - 검사 가능 → 3
   - 검사 불가 → 8
3. [처리] 파일 MIME 형식과 텍스트 유형 감지 — Basic content policy
   - 주체: SSE 에지
   - 데이터: 감지된 MIME 형식(예: PDF) · 텍스트 유형(HTML · JSON 등). WebSocket 트래픽은 파일 형식 필터링을 우회하지만 텍스트 유형은 평가됩니다
   - 해설: 이 감지는 Purview 없이 에지가 수행하고, Purview는 Scan with Purview일 때만 관여합니다
4. [판단] 규칙의 활동·콘텐츠 유형·대상이 일치하는가?
   - 주체: SSE 에지
   - 데이터: Activities(예: Upload) · Content types · 선택 Session type(Agent · User) · Destination. 조건 결합 방식과 규칙 Priority의 방향은 문서에서 확인하지 못했습니다 [확인 필요]
   - 해설: Session type을 설정하지 않으면 규칙이 모든 트래픽에 적용됩니다
   - 일치 → 5
   - 불일치 → 9
5. [판단] 일치한 규칙의 Action은?
   - 주체: SSE 에지
   - 데이터: Action = Allow · Block · Scan with Purview
   - 해설: 같은 정책 안의 규칙은 Action이 서로 다를 수 있고, 판정은 일치한 규칙의 Action을 따릅니다
   - Block → 6
   - Allow → 7
   - Scan with Purview → 10
6. [차단] Block — 해당 업로드·다운로드를 거부
   - 주체: SSE 에지
   - 데이터: Action = Denied · 정책·규칙 정보가 Traffic logs에 기록. HTML·JSON 텍스트 유형 Block은 일반 웹·API 트래픽(GET · POST · PUT)까지 막을 수 있습니다
   - 해설: 텍스트 유형 Block은 의도한 범위를 먼저 좁혀야 합니다
7. [끝] Allow — 통과시키고 기록
   - 주체: 로그
   - 위치: Traffic logs
   - 데이터: Action = Allowed · 일치한 규칙 정보
   - 해설: 허용 규칙은 같은 프로필의 다른 정책보다 앞선 우선순위에서 예외를 만들 때 씁니다 [확인 필요: 콘텐츠 정책 간 평가 순서는 문서에서 확인하지 못함]
8. [끝] 감지 불가 — 파일 형식 규칙이 적용되지 않은 채 통과
   - 주체: SSE 에지
   - 데이터: JSON 내부 인코딩 · 여러 암호화 요청으로 분할 전송된 파일은 파일 형식으로 감지되지 않을 수 있습니다
   - 해설: 이것은 정책 오류가 아니라 문서에 명시된 알려진 제한입니다
9. [끝] 불일치 — 이 규칙은 건너뜀
   - 주체: SSE 에지
   - 데이터: 조건 일치 없음 → 해당 규칙의 Action은 실행되지 않음
   - 해설: 다른 규칙·정책 또는 Baseline profile이 이어서 판정합니다
10. [끝] Scan with Purview — 검사를 Purview DLP 정책에 위임
   - 주체: SSE 에지
   - 위치: 에지 → Microsoft Purview (Inline web traffic DLP 정책)
   - 데이터: 선택한 파일·텍스트 콘텐츠를 보내 DLP 규칙(민감 정보 유형 · 민감도 레이블 · 사용자 위험 수준)과 대조. Purview 결과는 DLP 규칙의 Audit 또는 Block 동작
   - 해설: 판정의 결과는 ② 활성의 Purview 판정 단계와 같고, 이 위임은 Entra 사용자 ID로 매핑되는 트래픽에만 일어납니다
- 시나리오: 검사 가능 ▸ 일치 ▸ Allow :: 허용 규칙이 일치해 통과
- 시나리오: 검사 가능 ▸ 일치 ▸ Block :: 규칙 Block으로 거부
- 시나리오: 검사 가능 ▸ 일치 ▸ Scan with Purview :: 판정을 Purview DLP에 위임
- 시나리오: 검사 가능 ▸ 불일치 :: 규칙 조건이 맞지 않아 건너뜀
- 시나리오: 검사 불가 :: 파일을 감지하지 못해 규칙이 적용되지 않음

> 교육 포인트: 콘텐츠 규칙이 무엇을 못 보는지(분할·인코딩 전송, WebSocket 파일)를 알아야 정책의 한계를 설명할 수 있습니다.
>
> 주의: 와일드카드는 *.contoso.com 형식만 가능하고 TLD(*.com)·SLD(contoso.*) 와일드카드는 지원되지 않습니다.

#### L4 · 방화벽 규칙 — 5-tuple · 우선순위 · 기본 Allow

1. [시작] 에지가 획득된 연결의 5-tuple을 확인한다 — 방화벽 평가 시작
   - 주체: SSE 에지
   - 위치: 원격 네트워크 트래픽 또는 클라이언트 트래픽(미리 보기)
   - 데이터: 소스 IP · 소스 포트 · 대상 IP · 대상 포트 · 프로토콜(TCP/UDP)
   - 해설: 클라우드 방화벽은 Layer 3(네트워크) 통제이며 먼저 트래픽이 획득돼야 평가됩니다
2. [처리] 선택된 방화벽 정책의 규칙을 우선순위 순으로 정렬 — 비활성 규칙 제외
   - 주체: SSE 에지
   - 데이터: Priority는 100 이상이며 정책 안에서 고유, 숫자가 낮을수록 높은 우선순위. Status = Disabled인 규칙은 강제되지 않습니다
   - 해설: 새 규칙은 기본 Disabled이므로 만든 직후에는 아무 영향이 없습니다
3. [처리] 연결의 대상 이름 확보 여부 확인 — FQDN 조건 사용 가능성
   - 주체: SSE 에지
   - 데이터: 원격 네트워크: 대상 FQDN 조건 미지원(Not set 권장). 클라이언트(미리 보기): 평가 시점에 대상 FQDN이 있으면 FQDN 규칙이 일치할 수 있고, 직접 IP 연결처럼 FQDN이 없으면 FQDN 규칙은 일치하지 않으며 이후 TLS SNI로 이름을 알게 돼도 이전 판정은 다시 평가되지 않습니다
   - 해설: FQDN Block 규칙만으로는 직접 IP 접속을 막지 못하므로 IP 규칙도 함께 둡니다
4. [판단] 우선순위가 가장 높은 일치 규칙이 있는가?
   - 주체: SSE 에지
   - 데이터: 규칙의 소스 IP · 소스 포트 · 대상 IP · 대상 포트 · Protocol이 모두 일치해야 하고(논리 AND) Not set 값은 무시됩니다
   - 해설: 일치하는 규칙이 하나라도 정해지면 그 규칙의 Action이 판정을 끝냅니다
   - 일치 규칙 없음 → 8
   - 일치 규칙 있음 → 5
5. [판단] 일치 규칙의 Action은?
   - 주체: SSE 에지
   - 데이터: Action = Allow 또는 Block
   - 해설: 낮은 번호의 Allow 규칙이 있으면 높은 번호의 Block 규칙을 켜도 이 연결에는 효과가 없습니다
   - Block → 6
   - Allow → 7
6. [차단] Block — 연결 차단
   - 주체: SSE 에지
   - 데이터: Action = Denied · 정책 · 규칙 정보
   - 해설: UDP는 타임아웃만으로 차단을 단정하지 말고 Block 판정 로그와 대조합니다
7. [끝] Allow — 연결 허용
   - 주체: 로그
   - 위치: Traffic logs › Connections
   - 데이터: Action = Allowed · 연결 기록
   - 해설: 명시적 Allow 규칙이 있어도 로그에는 허용으로 남습니다
8. [끝] 일치 규칙 없음 — 정책 기본 동작 Allow
   - 주체: SSE 에지
   - 데이터: 정책의 Default Action = Allow(변경 불가). 고른 프로필의 방화벽 정책 기본 동작은 그 평가를 종료시킵니다
   - 해설: Block을 원하는 대상은 반드시 명시적 Block 규칙으로 만들어야 합니다
- 시나리오: 일치 규칙 없음 :: 일치 규칙이 없어 기본 Allow가 적용됨
- 시나리오: 일치 규칙 있음 ▸ Allow :: 일치한 Allow 규칙으로 연결 허용
- 시나리오: 일치 규칙 있음 ▸ Block :: 일치한 Block 규칙으로 연결 차단

> 교육 포인트: 방화벽 정책은 "기본 Allow + 명시적 Block"입니다. block-all 규칙을 만든 뒤 예외 Allow 규칙을 추가하면 그 사이에 지점 트래픽이 모두 막힐 수 있으니 규칙을 모두 만든 뒤 링크합니다.
>
> 주의: 이 클라우드 방화벽 문서의 기능은 DNS 트래픽을 필터링하지 않으며(미리 보기에서 DNS 미획득), 예시는 IPv4만 다룹니다 [미리 보기 확인 필요].

### L3 · B · 보안 프로필에 연결되는 과정 — 콘텐츠 정책 링크 · 방화벽 정책 선택

1. [시작] 콘텐츠 정책 완성 — 규칙 · 대상 · Action 확인

   - 위치: Global Secure Access › Secure › Content policies
   - 데이터: Scan with Purview 규칙이 있으면 Purview DLP 정책도 준비되어야 합니다

4. [처리] 조건부 액세스 정책 만들기 — 보안 프로필을 세션 제어로 지정
   - 주체: 관리자

   - 데이터: 여러 CA 정책이 일치하면 일치한 보안 프로필들이 우선순위 순으로 처리되며, Baseline profile은 CA 일치 여부와 관계없이 가장 낮은 우선순위로 항상 실행됩니다

5. [판단] CA 정책 상태는 무엇인가?

   - 위치: Conditional Access › 정책 › 상태(Enable policy)

   - 해설: 시험 그룹에서 켜짐으로 검증한 뒤 대상 범위를 넓힙니다
   - 켜짐 → 6
   - 보고 전용 → 7
6. [끝] 켜짐 — 대상 사용자 트래픽에 콘텐츠 정책 적용
   - 주체: 사용자
   - 위치: GSA 클라이언트(Windows · macOS) → 에지
   - 데이터: 프로필·정책 변경은 클라이언트에 수 분~ 수십 분 뒤 반영될 수 있습니다 [확인 필요: 콘텐츠 정책의 정확한 반영 시간 — 문서에는 방화벽 15~20분, 클라이언트 프로필 15분 안내]
   - 해설: 사용자는 새 연결부터 정책 영향을 받습니다
7. [끝] 보고 전용 — 정책이 강제되지 않음
   - 주체: Entra ID
   - 데이터: CA 결과만 평가되고 프로필의 정책은 적용되지 않음 [확인 필요]
   - 해설: 운영 투입 전 영향 평가에는 쓸 수 있으나 차단·허용은 일어나지 않습니다
- 시나리오: 켜짐 :: CA 켜짐으로 대상 사용자에게 정책 적용
- 시나리오: 보고 전용 :: 보고 전용이라 평가만 하고 강제되지 않음

> 교육 포인트: 콘텐츠 정책은 정책 → 보안 프로필 → 조건부 액세스 세 연결 고리가 모두 있어야 사용자에게 도달합니다. 어느 하나라도 빠지면 정책은 존재하지만 어떤 트래픽에도 작동하지 않습니다.

#### L4 · 클라우드 방화벽 — Baseline 연결과 프로필 선택

1. [시작] 방화벽 정책의 규칙을 먼저 모두 만든다 — 링크는 마지막
   - 주체: 관리자
   - 위치: Global Secure Access › Secure › Cloud firewall policies › 정책 › Rules
   - 데이터: 규칙은 Disable로 만들고 검토 후 Enable. 정책을 링크한 뒤 block-all을 먼저 만들면 모든 지점 트래픽을 스스로 차단할 위험이 있습니다
   - 해설: 변경이 한 덩어리로 적용되도록 규칙을 먼저 완성합니다
2. [판단] 어떤 트래픽에 적용하는가?
   - 주체: 관리자
   - 데이터: 원격 네트워크(지점) 인터넷 트래픽 / Global Secure Access 클라이언트 트래픽(미리 보기)
   - 해설: 두 경로는 적용 단위가 다릅니다 — 지점은 Baseline, 클라이언트는 보안 프로필입니다
   - 원격 네트워크 → 3
   - 클라이언트 → 5
3. [처리] Baseline profile에 방화벽 정책 링크
   - 주체: 관리자
   - 위치: Global Secure Access › Secure › Security Profiles › Baseline Profile › Edit profile › Link policies › + Link a policy
   - 데이터: Baseline profile 하나에 클라우드 방화벽 정책은 하나만 링크할 수 있고, 링크한 정책의 State는 enabled/disabled 전환이 가능하며 삭제 후 다른 정책을 링크할 수 있습니다. Graph(beta): GET /networkaccess/filteringProfiles로 Baseline ID 조회, filteringPolicyLink로 링크
   - 해설: 정책이 프로필에 링크돼야 비로소 효력이 생깁니다
4. [처리] Baseline 우선순위 65,000 — CA 없이 모든 원격 네트워크 트래픽에 적용
   - 주체: SSE 에지
   - 데이터: Baseline profile은 가장 낮은 우선순위이며 클라이언트 트래픽과 원격 네트워크 트래픽 모두의 catch-all입니다. 원격 네트워크의 비클라이언트 트래픽은 Baseline만 통과하고 사용자 인식은 클라이언트에서만 가능합니다
   - 해설: 사용자별 예외는 클라이언트 프로필로만 만들 수 있습니다
   - 다음 → 8
5. [처리] 클라이언트용 — 방화벽 정책을 보안 프로필에 링크하고 CA로 전달
   - 주체: 관리자
   - 위치: Secure › Security profiles › 프로필 › Link a policy › 링크 Enabled › 저장 · Conditional Access › Session › Use Global Secure Access security profile
   - 데이터: 클라이언트 방화벽 정책은 미리 보기이며 Internet Access 프로필이 해당 트래픽(예: TCP 8080 · UDP 3478)을 획득하도록 Custom Acquire를 따로 구성해야 합니다. 방화벽 규칙을 만든다고 획득이 자동 설정되지는 않습니다
   - 해설: 트래픽 획득과 방화벽 강제는 서로 다른 두 계층입니다
6. [판단] 사용자에게 적용되는 프로필에 방화벽 정책이 있는가?
   - 주체: SSE 에지
   - 데이터: 에지는 여러 일치 프로필의 방화벽 정책을 합치지 않고, 우선순위 번호가 가장 낮은 적용 프로필 하나의 방화벽 정책만 평가합니다
   - 해설: 높은 우선순위 프로필의 방화벽 정책 기본 동작이 그 평가를 끝냅니다
   - 정책 있음 → 7
   - 정책 없음 → 4
7. [처리] 선택된 프로필의 방화벽 정책 하나만 평가
   - 주체: SSE 에지
   - 데이터: 해당 정책의 규칙 평가 후 일치 규칙이 없으면 정책 기본 동작 Allow로 종료. Private Access로 라우팅되는 트래픽은 Internet Access 방화벽 규칙으로 평가되지 않습니다
   - 해설: 가장 높은 우선순위의 프로필이 최종 결과를 정합니다
8. [끝] 반영 확인 — 새 연결로 시험하고 Connections 로그 확인
   - 주체: 로그
   - 위치: Global Secure Access › Monitor › Traffic logs › Connections (원격 네트워크는 DeviceCategory 필터)
   - 데이터: 방화벽 정책 변경은 적용에 15~20분이 걸릴 수 있습니다. 기록된 판정과 연결된 보안 프로필 · 정책 · 규칙 정보(FilteringProfileName · PolicyName · RuleName)를 확인합니다
   - 해설: 새 연결로 시험해 기대한 Action과 로그가 일치하는지 대조합니다
- 시나리오: 원격 네트워크 :: Baseline profile에 링크해 지점 전체에 적용
- 시나리오: 클라이언트 ▸ 정책 있음 :: 우선순위 높은 프로필의 정책 하나만 평가
- 시나리오: 클라이언트 ▸ 정책 없음 :: 방화벽 정책이 없어 Baseline로 대체됨

> 교육 포인트: 클라이언트 트래픽에서는 보안 프로필 중 우선순위가 가장 높은 것 하나의 방화벽 정책만 평가되고, 그 프로필에 방화벽 정책이 없으면 Baseline profile로 되돌아갑니다.

> 주의: 원격 네트워크 문서에는 클라우드 방화벽이 Global Secure Access 클라이언트에서 지원되지 않는다고 적혀 있으나 별도 클라이언트 문서(preview)가 있어 문서 간 서술이 다릅니다 — 최신 문서와 포털 화면을 확인합니다 [확인 필요].

### L3 · C · 오탐 · 예외 · 로그 분석 — 차단 원인을 좁히고 범위를 조정한다

#### L4 · 오탐 · 예외 — 어느 정책이 막았는지 구분하고 범위를 줄인다

1. [시작] 사용자가 업로드·접속 차단을 신고한다

   - Purview DLP → 5
   - 클라우드 방화벽 → 6

   - 해설: 예외는 규칙을 삭제하기보다 범위를 좁히거나 비활성으로 두는 순서로 시도합니다

   - 주체: 관리자
   - 위치: purview.microsoft.com › Data loss prevention › Policies › 정책 › 규칙 · Policy mode
   - 데이터: DLP 규칙 Action을 Block에서 Audit로 바꾸거나 시뮬레이션 모드로 테스트, 조건(민감 정보 유형 · 민감도 레이블)과 Cloud apps 범위 조정. 최대 콘텐츠 크기 3 MB 초과나 OCR 미지원 때문에 검사되지 않은 경우는 오탐이 아니라 미검사입니다
   - 해설: Purview 판정은 GSA 콘텐츠 정책이 아니라 DLP 정책에서 고칩니다
   - 다음 → 7
6. [처리] 방화벽 규칙 점검 — 우선순위 · 상태 · 소스 조건을 확인한다
   - 주체: 관리자
   - 위치: Secure › Cloud firewall policies › 정책 › Rules
   - 데이터: 점검 — 겹치는 규칙의 Priority · 규칙 Status · Not set 처리 · 프로필에 링크된 정책 State · FQDN 규칙과 직접 IP 접속의 차이. 조정 — 규칙 Disable 또는 링크 State disabled, 삭제 대신 비활성 권장
   - 해설: 낮은 번호의 Allow가 있으면 높은 번호의 Block은 이 연결에 영향이 없습니다
7. [끝] 새 연결로 재시험하고 로그로 확인 — 변경 반영 대기
   - 주체: 관리자
   - 위치: Traffic logs · 방화벽은 변경 후 15~20분
   - 데이터: Action 변화와 일치한 규칙 · 범위 밖 대상이 영향받지 않았는지 대조 시험
   - 해설: 예외를 넣은 뒤에는 의도하지 않은 대상까지 허용되지 않았는지 함께 확인합니다
- 시나리오: 콘텐츠 규칙 :: 콘텐츠 규칙의 대상과 형식 범위를 좁힘
- 시나리오: Purview DLP :: DLP 조건 · 동작을 조정하고 시뮬레이션으로 검증
- 시나리오: 클라우드 방화벽 :: 우선순위와 상태를 조정해 규칙 충돌 해소

> 교육 포인트: 같은 "차단"이라도 콘텐츠 규칙(기본 필터링), Purview DLP, 클라우드 방화벽은 수정 위치와 증적이 모두 다릅니다. 로그의 정책·규칙 이름으로 계층을 먼저 가리고 가장 좁은 범위만 조정합니다.
>
> 주의: 에지가 API 속도 제한을 넘기면 트래픽이 자동 차단되며(fail-closed), 이것은 규칙 오탐이 아니라 사용량 문제입니다.

#### L4 · 로그 — Traffic logs · KQL · Purview 조사

1. [시작] 점검 목적을 정한다 — 차단 사유 · 검사 누락 · 지점/클라이언트 비교
   - 주체: 관리자
   - 위치: Global Secure Access › Monitor › Traffic logs
   - 데이터: 점검 질문 — 누가 어디로 무엇을 보냈고 어떤 정책이 판정했는가
   - 해설: 질문이 정해져야 필터와 열을 고를 수 있습니다
2. [처리] Traffic logs에서 필터와 열 선택 — Transactions · Connections
   - 주체: 관리자
   - 위치: Traffic logs › Columns · Add filter · Transactions 탭 · Connections 탭(미리 보기)
   - 데이터: Connection ID · Transaction ID · User principal name · DeviceCategory 필터. Sent Bytes · Received Bytes · Web category 열. Connections 탭은 같은 흐름 상관 ID의 최근 24시간 트랜잭션을 요약해 차단된 건수를 보여 줍니다
   - 해설: 연결 로그로 차단 여부를 먼저 보고 트랜잭션 로그로 세부를 봅니다
3. [처리] 핵심 필드 읽기 — Action · 정책 · 규칙 · 프로필 · 형식
   - 주체: 로그
   - 위치: 로그 상세 · KQL: NetworkAccessTraffic
   - 데이터: Action(Allowed · Denied · Redirect) · FilteringProfileName/Id · PolicyName/Id · PolicyRuleId · RuleName · HttpRequestContentType · HttpResponseContentType · SourceIp · SourcePort · DestinationIp · DestinationPort · DestinationFqdn · DestinationUrl · TransportProtocol · RemoteNetworkId · DeviceCategory
   - 해설: 5-tuple 열로 방화벽 판정을, 콘텐츠 유형 열로 파일 전송을 추적합니다
4. [판단] 해당 규칙이 Scan with Purview를 쓰는가?
   - 주체: 관리자
   - 데이터: Scan with Purview 규칙이면 Purview에도 조사 데이터가 있고, 기본 Allow · Block 규칙이나 방화벽이면 GSA 트래픽 로그가 유일한 증적입니다
   - 해설: 증적이 있는 곳이 규칙 종류에 따라 다릅니다
   - Scan with Purview → 5
   - 기본 필터링·방화벽 → 6
5. [처리] Purview 쪽 조사 — DLP Alerts와 Activity explorer
   - 주체: 관리자
   - 위치: purview.microsoft.com › Data loss prevention › Alerts · Activity explorer(Network DLP activities 필터)
   - 데이터: DLP 경고와 이벤트 · 정책 · 사용자 · 앱 기준 필터. Purview 검사를 건너뛴 트랜잭션은 Traffic logs의 PurviewStatus 필드로 식별한다고 안내됩니다 [확인 필요: NetworkAccessTraffic 열 목록에서 PurviewStatus를 확인하지 못함]
   - 해설: 차단은 에지에서, 판정 근거는 Purview에서 확인합니다
   - 다음 → 7
6. [처리] KQL로 보관·분석 — 진단 설정으로 내보내기
   - 주체: 관리자
   - 위치: Entra ID › Monitoring & health › Diagnostic settings › Add Diagnostic setting › NetworkAccessTrafficLogs › Log Analytics workspace · Storage · Event hub · 파트너 솔루션 (Security Administrator 이상)
   - 데이터: 예시(열 이름은 문서 기준): NetworkAccessTraffic | where Action == "Denied" | summarize count() by PolicyName, RuleName, DeviceCategory. 값 형식은 환경에서 확인합니다 [확인 필요]
   - 해설: 로그를 장기 보관하고 규칙별 차단 건수로 오탐 후보를 찾습니다
7. [끝] 결과를 정책 조정에 환류 — 규칙 · DLP · 방화벽 수정 후보 기록
   - 주체: 관리자
   - 위치: Content policies · Purview DLP · Cloud firewall policies
   - 데이터: 규칙별 차단 건수 · 미검사 건 · 오탐 후보
   - 해설: 로그 점검 결과가 다음 정책 변경의 근거가 됩니다
- 시나리오: Scan with Purview :: Traffic logs와 Purview 증적을 함께 조사
- 시나리오: 기본 필터링·방화벽 :: Traffic logs와 KQL만으로 조사

> 교육 포인트: 기본 필터링(Allow · Block) 규칙은 Purview 경고가 없으므로 Traffic logs가 유일한 증적이고, Scan with Purview 규칙은 GSA 로그와 Purview 조사 데이터를 짝지어 봅니다.
>
> 주의: 문서의 PolicyType 열 설명에 열거된 값(mcpFirewall · promptProtection · threatIntelligence · webContentFiltering)에 콘텐츠 정책·클라우드 방화벽은 보이지 않습니다. 해당 규칙이 어떤 값으로 기록되는지는 실제 로그에서 확인합니다 [확인 필요].
