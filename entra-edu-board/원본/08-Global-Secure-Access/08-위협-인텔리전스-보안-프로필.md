## L2 · 위협 인텔리전스 · 보안 프로필 — 악성 대상 차단과 정책 묶음

- 설정(Control Plane): 위협 인텔리전스 정책(기본 동작 Allow · 허용 규칙 · 규칙 우선순위·상태) | 보안 프로필(정책 연결·우선순위) · 기준선 프로필 → 조건부 액세스 세션 제어로 사용자에게 연결
- 강제(Enforcement): Global Secure Access 클라이언트 (트래픽 획득) | Microsoft SSE 에지 (프로필 안의 정책 평가·위협 판정)
- 증적(Evidence): GSA 트래픽 로그 (모니터링 › 트래픽 로그, Threat Type 열) | KQL: NetworkAccessTraffic(ThreatType · PolicyType · PolicyName · PolicyRuleId · RuleName · FilteringProfileName · Action) · NetworkAccessAlerts
- 메뉴(Admin Center): Global Secure Access > 보안 > 위협 인텔리전스 정책 · 보안 > 보안 프로필 · 모니터링 > 트래픽 로그
- 라이선스(License): 위협 인텔리전스는 Entra Internet Access 라이선스 대상(Entra Suite 포함)이고 사용자당 Entra ID P1/P2가 필요하며, Entra ID P1/P2만으로 쓰는 Microsoft 트래픽 프로필 열에는 포함되지 않습니다. 정책 관리는 Global Secure Access Administrator, 조건부 액세스 연결은 Conditional Access Administrator, 로그 조회는 Reports Reader 이상입니다 [확인 필요: 고객 라이선스 · 트래픽 로그와 Microsoft Graph 베타 API의 미리 보기 표기 · 한글 메뉴명]

### L3 · 0 · 기능 상태 전이 — 위협 판정 없음 → 정책·프로필·조건부 액세스 구성 → 에지가 악성 대상을 차단

#### L4 · ⓪ 비활성 — 악성 대상을 판정하는 층이 없어 침해된 사이트가 통과한다

1. [시작] 사용자가 침해된 웹 사이트에 접속 — 겉보기엔 평범한 사이트
   - 주체: 사용자
   - 위치: 브라우저 → 대상 FQDN·URL (HTTPS 443)
   - 데이터: 대상 FQDN · URL · TLS SNI(서버 이름)
   - 해설: 평소 정상 범주로 분류되던 사이트가 악성코드 유포나 피싱에 쓰이게 된 상황입니다
2. [처리] 위협 인텔리전스 정책이 없음 — 악성 대상 판정 단계가 비어 있음
   - 주체: SSE 에지
   - 위치: Global Secure Access › 보안(Secure) › 위협 인텔리전스 정책(Threat Intelligence Policies) 목록이 비어 있음
   - 데이터: 보안 프로필·기준선 프로필에 연결된 위협 인텔리전스 정책 0건. 인터넷 액세스 프로필을 켜서 트래픽이 에지에 와도 이 판정은 일어나지 않습니다
   - 해설: Microsoft와 외부 위협 인텔리전스 피드의 고위험 도메인·URL 지표를 대조하는 단계가 이 사용자 트래픽에는 없습니다
3. [판단] 웹 필터링 범주 규칙이 이 사이트를 차단하는가?
   - 주체: SSE 에지
   - 데이터: 웹 필터링은 범주(예: 도박·성인) 기준이라 침해된 뉴스 사이트 같은 정상 범주의 악성 사이트는 막지 못합니다. 위협 인텔리전스는 범주와 무관하게 알려진 악성 대상을 막는 별개 제어입니다
   - 해설: 웹 필터링 규칙이 우연히 같은 범주를 막고 있을 때만 차단되고, 그 이유는 위협 때문이 아닙니다
   - 범주 규칙 차단 → [차단] 범주 정책이 차단 — 위협 판정이 아니라 범주 규칙에 따른 차단
   - 범주 규칙 없음 → 4
4. [처리] 에지가 요청을 통과시킴 — 위협 판정 없이 대상 사이트로 전달
   - 주체: SSE 에지
   - 데이터: 적용되는 보안 제어에 위협 지표 대조가 없어 Action = Allowed로 전달됨
   - 해설: 에지는 이 대상이 알려진 악성 대상이라는 사실을 알지 못한 채 전달합니다
5. [처리] 엔드포인트 보호만 남음 — 마지막 방어선
   - 주체: 디바이스
   - 데이터: Microsoft Defender · SmartScreen 경고. 문서는 위협 인텔리전스 다음 계층으로 엔드포인트 보호(Microsoft Defender for Endpoint)를 마지막 방어선으로 둡니다
   - 해설: 네트워크 단계 차단이 없으면 엔드포인트의 경고에만 의존하게 되고, 사용자가 경고를 넘기면 접속됩니다
6. [끝] 악성 접속이 네트워크 증적 없이 남음 — ThreatType이 비어 있음
   - 주체: 로그
   - 위치: Global Secure Access › 모니터링(Monitor) › 트래픽 로그(Traffic logs) (Reports Reader 이상으로 조회)
   - 데이터: NetworkAccessTraffic: Action = Allowed, ThreatType 열 비어 있음 — ThreatType은 위협 인텔리전스가 대상과 일치할 때만 채워집니다
   - 해설: 어떤 사용자가 알려진 악성 대상에 접속했는지 Entra의 위협 증적으로는 알 수 없습니다
- 시나리오: 범주 규칙 차단 :: 범주 규칙 때문에 차단되지만 위협 판정은 없음
- 시나리오: 범주 규칙 없음 :: 범주에 안 걸려 위협 판정 없이 접속 허용

> 교육 포인트: 웹 필터링은 범주로, 위협 인텔리전스는 알려진 악성 대상으로 막습니다. 침해된 정상 사이트는 위협 인텔리전스만 막을 수 있고, 두 제어는 서로를 대신하지 못합니다.
>
> 주의: 위협 인텔리전스는 이미 발견된 위협만 압니다. 새로 만들어지는 악성코드·피싱 사이트는 놓칠 수 있어 웹 필터링·콘텐츠 정책·엔드포인트 보호와 함께 겹겹이 쓰라고 문서가 안내합니다.

#### L4 · ① 구성 — 위협 인텔리전스 정책 · 보안 프로필 · 조건부 액세스를 만든다

1. [시작] 관리자가 Entra 관리 센터에 로그인 — 역할 세 가지가 갈린다
   - 주체: 관리자
   - 위치: entra.microsoft.com — Global Secure Access Administrator(정책·보안 프로필), Conditional Access Administrator(조건부 액세스 정책), Reports Reader 이상(트래픽 로그 조회), Security Administrator(진단 설정)
   - 데이터: Entra 역할 할당(roleAssignments). Graph로 위협 인텔리전스 규칙을 만들 때도 Global Secure Access Administrator 또는 Security Administrator 역할이 필요하며, Graph API는 현재 beta입니다 [미리 보기 확인 필요]
   - 해설: 정책 작업과 조건부 액세스 작업에 필요한 역할이 서로 다르므로 한 사람이 둘 다 갖지 않았다면 작업을 나눕니다
2. [처리] 사전 조건 확인 — 인터넷 트래픽이 에지로 들어와야 판정이 가능
   - 주체: 관리자
   - 위치: Global Secure Access › 연결(Connect) › 트래픽 전달(Traffic forwarding) › Internet access profile 켜짐 + 클라이언트 설치 기기 (인터넷 프로필 켜기 자체는 Internet Access L2 참고)
   - 데이터: 문서 사전 조건 — Secure DNS(DoH) 끄기 · Chrome/Edge 내장 DNS 클라이언트 끄기 · IPv4 우선(IPv6는 획득되지 않음) · QUIC(UDP 443)은 지원되지 않아 차단 규칙 권장
   - 해설: 트래픽이 클라이언트에 잡히지 않으면 아래에서 만드는 정책은 그 트래픽에 평가되지 않습니다
3. [처리] (선택) TLS 검사 구성 — HTTPS의 URL 지표를 보려면 필요
   - 주체: 관리자
   - 위치: Global Secure Access › 보안(Secure) › TLS inspection policies [확인 필요: 한글 메뉴명 · 세부 단계는 TLS 검사 문서]
   - 데이터: TLS 검사를 켜지 않으면 위협 인텔리전스는 HTTPS 트래픽에서 악성 URL 지표를 평가하지 못하고, 나머지 탐지 유형은 계속 탐지·차단됩니다
   - 해설: 선택 사항이지만 HTTPS 비중이 큰 환경에서는 URL 수준 보호의 전제 조건입니다
4. [처리] 위협 인텔리전스 정책 만들기 — 이름·설명·기본 동작
   - 주체: 관리자
   - 위치: Global Secure Access › Secure › Threat Intelligence Policies › Create policy › 이름·설명 입력 › Next › Default Action 확인(Allow) › Next › Review › Create
   - 데이터: 정책 이름 · 설명 · 기본 동작(settings.defaultAction = allow). 규칙에 일치하지 않는 트래픽은 정책 엔진이 허용하고 다음 보안 제어로 넘깁니다
   - 해설: 기본 동작이 Allow인 이유는 이 정책이 알려진 위협에 일치할 때만 막는 정책이기 때문입니다
5. [처리] 생성된 기본 차단 규칙 확인 — 높은 심각도 위협 차단
   - 주체: 관리자
   - 위치: 정책 선택 › Rules (정책 생성 시 높은 심각도 위협 차단 규칙이 함께 만들어짐)
   - 데이터: 문서 설명 — 정책은 높은 심각도 위협이 탐지된 대상 접근을 차단하는 규칙과 함께 만들어집니다. Graph 예시 응답에는 "Default threat intel rule"(action = block · severity = high · priority = 65000)이 나옵니다 [확인 필요: 포털에서의 규칙 이름·표시]
   - 해설: 높은 심각도 위협은 활성 악성코드 유포·피싱 캠페인·C2 인프라 등으로 Microsoft와 외부 피드가 높은 신뢰도로 식별한 도메인·URL입니다
6. [처리] (선택) 허용 목록 규칙 추가 — 업무상 꼭 필요한 대상·오탐
   - 주체: 관리자
   - 위치: Threat Intelligence Policies › 정책 선택 › Rules › Add rule › 이름 · 설명 · 우선순위 · 상태 입력 › Destination FQDNs 편집 › Add
   - 데이터: Destination FQDNs는 쉼표로 구분한 도메인 목록입니다. Graph 규칙에는 priority · action(allow/block) · settings.status(enabled/disabled/reportOnly) · matchingConditions.severity · destinations(threatIntelligenceFqdnDestination)가 있습니다. IP·URL·범주를 대상으로 쓰는 방법은 문서에서 확인하지 못했습니다 [확인 필요]
   - 해설: 예외는 보안 위험이 따르므로 꼭 필요한 FQDN만, 기본 차단 규칙(65000)보다 작은 우선순위 번호로 넣습니다
7. [처리] 보안 프로필 만들기 — 위협 인텔리전스 정책 연결
   - 주체: 관리자
   - 위치: Global Secure Access › Secure › Security profiles › Create profile › 이름·설명 입력 › Next › Link a policy › Existing threat intelligence policy › 정책 선택 › Add › Next › Create profile › Refresh
   - 데이터: 보안 프로필은 웹 필터링·위협 인텔리전스 같은 보안 제어의 묶음이고, 한 프로필에는 같은 유형 정책을 하나만 연결합니다(위협 인텔리전스 정책도 프로필당 하나). 연결한 정책의 우선순위와 상태(Enabled/Disabled)를 정합니다
   - 해설: 정책만 만들어서는 어떤 사용자에게도 적용되지 않고, 프로필에 연결해야 전달 대상이 됩니다
8. [판단] 누구에게 적용하는가? — 전체 기준선 또는 특정 사용자
   - 주체: 관리자
   - 위치: 기준선: Security profiles › Baseline profile › Edit profile › Link policies › Link a policy › Existing policy · 사용자 지정: 7번에서 만든 프로필
   - 데이터: 위협 인텔리전스는 기본 보안 태세에 핵심이라 기준선 프로필(우선순위 65000)에 연결해 테넌트 전체 사용자의 트래픽에 적용하는 방법이 문서에 안내되어 있습니다. 기준선은 조건부 액세스 연결이 필요 없습니다
   - 해설: 전원에게 같은 보호를 주려면 기준선, 부서·조건별로 다르게 주려면 사용자 지정 프로필과 조건부 액세스를 씁니다
   - 기준선 → 10
   - 사용자 지정 → 9
9. [처리] 조건부 액세스 정책으로 프로필을 사용자에게 연결 — 세션 제어
   - 주체: 관리자
   - 위치: Identity › Protection › Conditional Access › 새 정책 만들기 › 대상 사용자·그룹 지정 › Target resources › All internet resources with Global Secure Access › Session › Use Global Secure Access security profile › 프로필 선택 › Select › Enable policy = On › Create
   - 데이터: 조건부 액세스 정책 상태(On) · 사용자·그룹 할당 · 보안 프로필 ID. 조건부 액세스는 인터넷 액세스 정책에 사용자·컨텍스트 인식을 주는 전달 수단입니다
   - 해설: 새 보안 프로필이 적용되려면 프로필 클레임이 든 새 액세스 토큰이 필요해 최대 60~90분이 걸립니다
10. [끝] 적용 확인 — 클라이언트 규칙 확인 후 테스트 사이트 접속
    - 주체: 디바이스
    - 위치: 작업 표시줄 클라이언트 아이콘 우클릭 › Advanced Diagnostics › Forwarding profile 에서 Internet access 획득 규칙 확인 · 테스트용 사용자 세션 철회(Revoke sessions)로 새 토큰 유도
    - 데이터: 테스트 사이트 entratestthreat.com · smartscreentestratings2.net (문서가 안전한 테스트 용도로 안내). 차단 시 Threat Type 필드가 비어 있지 않아야 하며 트래픽 로그는 최대 5분 뒤 나타납니다
    - 해설: 테스트 전에 브라우저 캐시를 지우고, 실제 악성 사이트 테스트는 샌드박스·테스트 환경에서만 합니다
- 시나리오: 기준선 :: 기준선 프로필에 연결해 전체 사용자에게 바로 적용
- 시나리오: 사용자 지정 :: 사용자 지정 프로필을 조건부 액세스로 연결해 대상 한정

> 교육 포인트: 구성 순서는 인터넷 트래픽 전달 → 위협 인텔리전스 정책 → (허용 목록) → 보안 프로필 또는 기준선 → 조건부 액세스입니다. 조건부 액세스 연결을 빼먹으면 사용자 지정 프로필은 아무에게도 적용되지 않습니다.
>
> 주의: 새 프로필 연결이 반영되려면 새 토큰이 필요합니다. 기존 프로필 안의 정책 변경은 훨씬 빨리 반영되고, 허용 규칙은 문서 기준 2분 안에 효과가 보입니다. 테스트를 서두르려면 사용자 세션을 철회합니다. 보고 전용(report-only) 조건부 액세스 정책은 보안 프로필을 강제하지 않습니다.

#### L4 · ② 활성 — 요청이 프로필 안에서 순서대로 판정되고 위협 대상이 차단된다

1. [시작] 사용자가 접속 — ⓪과 같은 침해된 사이트 요청
   - 주체: 사용자
   - 위치: 브라우저 → 대상 FQDN·URL (HTTPS 443)
   - 데이터: 대상 FQDN · URL · TLS SNI
   - 해설: 구성 전과 똑같은 요청이 이번에는 에지에서 위협 지표와 대조됩니다
2. [처리] 클라이언트가 트래픽을 획득해 에지로 전송
   - 주체: GSA 클라이언트
   - 위치: GSA 클라이언트 터널 → 가까운 Microsoft SSE 에지 (인터넷 트래픽 획득 규칙 기준)
   - 데이터: 인터넷 액세스 획득 규칙에 일치한 트래픽(기본 TCP 80·443)과 Entra 토큰. IPv6와 UDP(QUIC)는 획득되지 않고 직접 전송됩니다
   - 해설: 획득되지 않은 트래픽은 에지 정책을 지나지 않으므로 아래 판정도 일어나지 않습니다
3. [처리] 조건부 액세스가 보안 프로필을 정함 — 토큰의 프로필 ID 클레임
   - 주체: Entra ID
   - 위치: Entra ID 토큰 발급 시점의 조건부 액세스 평가 (대상 리소스 All internet resources with Global Secure Access)
   - 데이터: 일치한 조건부 액세스 정책의 세션 제어 → 액세스 토큰의 보안 프로필 ID 클레임. 기준선 프로필은 조건부 액세스와 무관하게 항상 적용됩니다
   - 해설: 에지는 토큰을 검증한 뒤 이 토큰 안의 프로필과 기준선 프로필을 적용합니다
4. [처리] TLS 검사 단계 — 복호화 여부 결정
   - 주체: SSE 에지
   - 위치: 에지의 TLS 검사 정책 (보안 제어 평가 순서에서 가장 먼저 오는 제어)
   - 데이터: TLS 검사 대상이면 HTTPS의 URL까지 볼 수 있고, 아니면 도메인(SNI) 수준만 평가됩니다
   - 해설: 이 단계는 이후 제어가 볼 수 있는 정보의 깊이를 정합니다
5. [판단] 웹 필터링 정책이 먼저 차단하는가?
   - 주체: SSE 에지
   - 데이터: 평가 순서 2번 웹 필터링 — 범주·URL·FQDN 규칙에서 Block에 일치하면 그 자리에서 판정(PolicyType = webContentFiltering)
   - 해설: 웹 필터링은 위협 인텔리전스보다 앞서 평가되므로 범주 차단이 먼저 적용됩니다
   - 웹 필터 차단 → [차단] 웹 필터링 규칙이 차단 — 위협 인텔리전스까지 가지 않음
   - 웹 필터 통과 → 6
6. [판단] 위협 인텔리전스 허용 규칙에 일치하는가?
   - 주체: SSE 에지
   - 데이터: 정책의 규칙을 우선순위 번호가 작은 것부터 비교. 허용 규칙의 Destination FQDNs와 일치하면 허용
   - 해설: 허용 목록은 기본 차단 규칙(65000)보다 작은 번호를 가져 먼저 평가됩니다
   - 허용 규칙 일치 → 8
   - 불일치 → 7
7. [판단] 높은 심각도 위협 지표에 일치하는가?
   - 주체: SSE 에지
   - 데이터: Microsoft Defender Threat Intelligence · Microsoft 보안 연구 · 외부 피드 · 커뮤니티 인텔리전스의 도메인·URL 지표 대조(Threat Type: Phishing · C2 · MaliciousUrl · Malware 등). 일치하면 Action = Denied, 사용자에게는 차단 화면이 보이고 More info에서 Threat Type을 확인할 수 있습니다
   - 해설: 일치한 거래에는 Microsoft가 위협 유형을 붙여 로그에 남깁니다
   - 위협 탐지 → [차단] 차단 — 위협 유형 표시, Denied 기록
   - 탐지 없음 → 8
8. [처리] 위협 인텔리전스는 통과 — 다음 보안 제어로 전달
   - 주체: SSE 에지
   - 데이터: 규칙에 일치하는 위협이 없으면 기본 동작 Allow로 다음 보안 제어(파일 형식·데이터 손실 방지·타사)로 넘어갑니다. 위협 인텔리전스가 허용해도 다른 정책 유형이 뒤에서 차단할 수 있습니다
   - 해설: 위협 인텔리전스의 Allow는 최종 허용이 아니라 '이 제어는 이의 없음'입니다
9. [끝] 허용 후 대상 사이트로 전달 — 로그 기록
   - 주체: 로그
   - 위치: Global Secure Access › 모니터링(Monitor) › 트래픽 로그(Traffic logs) (Reports Reader 이상)
   - 데이터: NetworkAccessTraffic: Action(Allowed/Denied/Redirect) · PolicyType(threatIntelligence 등) · PolicyName · PolicyRuleId · RuleName · FilteringProfileName · ThreatType. 위협에 일치한 거래만 ThreatType이 채워집니다
   - 해설: 허용도 차단도 어느 프로필·정책·규칙이 판정했는지 트래픽 로그에 남습니다
- 시나리오: 웹 필터 차단 :: 웹 필터링 규칙이 먼저 차단해 위협 판정까지 못 감
- 시나리오: 웹 필터 통과 ▸ 허용 규칙 일치 :: 허용 목록에 일치해 위협 판정 없이 통과
- 시나리오: 웹 필터 통과 ▸ 불일치 ▸ 위협 탐지 :: 위협 지표에 일치해 차단 화면과 위협 유형 기록
- 시나리오: 웹 필터 통과 ▸ 불일치 ▸ 탐지 없음 :: 위협이 없어 다음 보안 제어로 넘어가 통과

> 교육 포인트: 위협 인텔리전스는 기본 동작이 Allow인 차단 목록 방식입니다. 이 정책이 막는 것은 높은 심각도 위협에 일치한 대상뿐이고, 나머지 트래픽은 다음 제어가 판정합니다.
>
> 주의: 제어 평가 순서와 위협 인텔리전스 Allow가 이후 제어를 건너뛰게 하는지는 문서가 서로 다르게 읽힐 수 있어 B 탭에서 따로 다룹니다 [확인 필요].

### L3 · A · 위협 인텔리전스 규칙과 동작 — 규칙 우선순위 · 동작 값 · HTTPS 판정

#### L4 · 정책 안에서 규칙이 우선순위로 평가되는 길

1. [시작] 요청이 위협 인텔리전스 정책에 도달
   - 주체: SSE 에지
   - 위치: 에지의 위협 인텔리전스 정책 (보안 프로필에 연결된 정책 하나)
   - 데이터: 대상 도메인·URL · 정책의 기본 동작(defaultAction = allow) · 정책 안의 규칙 목록(허용 규칙 + 기본 차단 규칙)
   - 해설: 정책 하나에는 여러 규칙이 들어 있고 규칙마다 이름·설명·우선순위·상태가 있습니다
2. [처리] 규칙을 우선순위 번호 순으로 정렬 — 사용 중인 규칙만
   - 주체: SSE 에지
   - 데이터: priority 값이 작을수록 우선(Graph: Lower values indicate higher priority). 상태 enabled=적용, disabled=비활성, reportOnly=평가는 하되 기록만 하고 동작은 적용하지 않음. 문서 예의 기본 차단 규칙 priority = 65000
   - 해설: 허용 목록처럼 예외를 두려면 기본 차단 규칙보다 작은 번호를 줍니다
3. [판단] 허용 규칙(Destination FQDNs)에 일치하는가?
   - 주체: SSE 에지
   - 데이터: 허용 규칙의 FQDN 목록(쉼표 구분, Graph 예시에는 *.example.com 형태의 와일드카드도 나옴)과 대상 비교
   - 해설: 우선순위가 높은 허용 규칙이 먼저 맞으면 뒤의 기본 차단 규칙은 평가되지 않습니다
   - 허용 규칙 일치 → 8
   - 불일치 → 4
4. [처리] 위협 인텔리전스 지표와 대상 대조 — 도메인·URL 지표
   - 주체: SSE 에지
   - 데이터: Microsoft와 외부 위협 인텔리전스 제공자의 도메인·URL 지표 목록(수시 갱신). 대상 유형은 범주가 아니라 도메인·URL 지표입니다
   - 해설: 웹 필터링처럼 범주를 고르는 방식이 아니라 알려진 악성 대상 목록과 대조합니다
5. [판단] 높은 심각도 위협 지표에 일치하는가?
   - 주체: SSE 에지
   - 데이터: 일치 조건 severity = high(Graph에는 low · medium · high 값이 정의되어 있으나 포털 문서는 높은 심각도 차단만 설명합니다 [확인 필요])
   - 해설: 일치하지 않으면 이 정책은 아무 동작도 하지 않습니다
   - 위협 일치 → 6
   - 일치 없음 → 8
6. [판단] 일치한 차단 규칙의 상태는?
   - 주체: SSE 에지
   - 데이터: settings.status = enabled 이면 차단 · reportOnly 이면 로그만 남김. 기본 차단 규칙의 상태를 포털에서 바꿀 수 있는지는 문서에서 확인하지 못했습니다 [확인 필요]
   - 해설: 보고 전용은 새 규칙이 얼마나 많은 트래픽에 영향을 주는지 보려는 시험 상태입니다
   - 적용 → [차단] 차단 — 차단 화면과 Threat Type, Action = Denied 기록
   - 보고 전용 → 7
7. [처리] 보고 전용 — 동작은 적용하지 않고 기록만
   - 주체: 로그
   - 데이터: 규칙이 평가한 사실만 로그에 남고 트래픽은 그대로 다음 단계로 진행
   - 해설: 차단하지 않은 채 일치 건수를 먼저 관찰할 수 있습니다
8. [끝] 위협 인텔리전스 판정 종료 — 다음 보안 제어로
   - 주체: 로그
   - 위치: Global Secure Access › 모니터링 › 트래픽 로그
   - 데이터: PolicyType = threatIntelligence · PolicyName · RuleName · PolicyRuleId · ThreatType. 일치 없음 · 허용 규칙 일치 · 보고 전용은 모두 다음 보안 제어로 넘어갑니다
   - 해설: 이 정책이 허용하더라도 최종 허용은 모든 제어를 통과한 뒤에 결정됩니다
- 시나리오: 허용 규칙 일치 :: 허용 규칙이 먼저 일치해 위협 대조 없이 통과
- 시나리오: 불일치 ▸ 위협 일치 ▸ 적용 :: 위협 일치에 규칙이 적용 상태라 차단
- 시나리오: 불일치 ▸ 위협 일치 ▸ 보고 전용 :: 위협 일치지만 보고 전용이라 기록만 하고 통과
- 시나리오: 불일치 ▸ 일치 없음 :: 위협 지표에 안 걸려 기본 동작 Allow로 통과

> 교육 포인트: 규칙 동작 값은 allow와 block 두 가지이고, 정책 기본 동작도 allow 또는 block 값입니다. 포털 흐름의 기본값은 Allow입니다.
>
> 주의: 문서는 허용 규칙의 대상을 Destination FQDNs로만 설명하고 규칙 우선순위의 허용 범위(숫자 한도)는 밝히지 않습니다 [확인 필요]. 규칙이 Graph 베타 API로 노출된다는 점도 변경 가능성이 있습니다 [미리 보기 확인 필요].

#### L4 · HTTPS 요청에서 TLS 검사 유무에 따라 지표 적용이 갈리는 길

1. [시작] HTTPS 요청이 위협 인텔리전스 단계에 도착
   - 주체: SSE 에지
   - 데이터: TLS 핸드셰이크의 SNI(서버 이름) · 필요하면 복호화된 URL 경로
   - 해설: 같은 정책이라도 TLS 검사가 되었는지에 따라 볼 수 있는 정보가 달라집니다
2. [판단] 이 트래픽에 TLS 검사가 적용되는가?
   - 주체: SSE 에지
   - 위치: Global Secure Access › 보안 › TLS 검사 정책 (선택 사항, 위협 인텔리전스 문서의 사전 조건에 '선택'으로 표기)
   - 데이터: TLS 검사 정책 일치 여부 · 검사 제외(bypass) 규칙 여부
   - 해설: 문서는 URL 지표가 HTTPS 트래픽에 평가되려면 TLS 검사가 필요하다고 설명합니다
   - 검사함 → 5
   - 검사 안 함 → 3
3. [처리] 검사 없음 — 도메인 수준 지표만 대조
   - 주체: SSE 에지
   - 데이터: 도메인(SNI) 기반 지표만 평가 가능하고, 악성 URL 지표는 HTTPS에 평가되지 않아 이 유형의 위협은 보호되지 않습니다. 나머지 탐지 유형은 계속 탐지·차단됩니다
   - 해설: TLS 검사를 켜지 않은 환경에서는 같은 정책이라도 악성 URL 보호 범위가 좁아집니다
4. [판단] 도메인 지표에 일치하는가?
   - 주체: SSE 에지
   - 데이터: 도메인 지표 일치 여부. 차단 화면의 형태는 TLS 검사 없는 HTTPS에 대해 문서에서 확인하지 못했습니다 [확인 필요]
   - 해설: 일치하면 위협 유형과 함께 차단되고 로그에 ThreatType이 채워집니다
   - 도메인 일치 → [차단] 차단 — 도메인 수준 위협 일치, Denied 기록
   - 도메인 불일치 → 7
5. [처리] 검사함 — 복호화된 URL까지 지표 대조
   - 주체: SSE 에지
   - 데이터: 복호화된 HTTPS의 URL 경로까지 보이므로 도메인 지표와 URL 지표를 함께 대조. 사용자에게는 일반 HTTP·TLS 검사 트래픽처럼 평문 브라우저 오류(차단 화면)가 표시됩니다
   - 해설: URL 단위로 악성 경로만 골라 막을 수 있어 같은 도메인의 정상 경로는 통과합니다
6. [판단] 도메인·URL 지표에 일치하는가?
   - 주체: SSE 에지
   - 데이터: Settings › Session management › Custom Block Page에서 사용자 지정 차단 메시지(최대 1,024자)를 켜면 TLS 검사된 트래픽에서만 표시됩니다
   - 해설: 차단 화면의 More info에서 Threat Type(예: MaliciousUrl)을 볼 수 있습니다
   - URL 일치 → [차단] 차단 — 차단 화면과 위협 유형 표시, Denied 기록
   - URL 불일치 → 7
7. [끝] 위협 판정을 통과 — 다음 보안 제어로 전달
   - 주체: 로그
   - 위치: Global Secure Access › 모니터링 › 트래픽 로그
   - 데이터: ThreatType 열 비어 있음 · Action = Allowed(최종 허용은 이후 제어 결과에 따름)
   - 해설: 일치하는 위협이 없으면 기본 동작 Allow로 다음 제어가 이어서 판정합니다
- 시나리오: 검사함 ▸ URL 일치 :: URL까지 보여 악성 경로가 차단 화면과 함께 막힘
- 시나리오: 검사함 ▸ URL 불일치 :: 도메인·URL 모두 위협 없음으로 통과
- 시나리오: 검사 안 함 ▸ 도메인 일치 :: 검사 없어도 도메인 지표에 일치해 차단
- 시나리오: 검사 안 함 ▸ 도메인 불일치 :: 도메인 지표에 없어 악성 URL 보호 없이 통과

> 교육 포인트: TLS 검사는 위협 인텔리전스의 필수 조건은 아니지만 HTTPS의 악성 URL 보호 범위를 결정합니다. 검사를 안 한다고 정책이 꺼지는 것은 아니고 도메인 수준 보호는 유지됩니다.
>
> 주의: 사용자 지정 차단 페이지는 TLS 검사된 트래픽에만 나타납니다. TLS 검사를 하지 않은 환경에서는 사용자 문의가 차단 이유를 알려 주지 못할 수 있으니 안내 문서를 따로 준비합니다.

### L3 · B · 한 프로필 안의 정책 평가 순서 — 제어 유형 순서 · 우선순위 · 여러 프로필

#### L4 · 한 프로필 안에서 보안 제어가 유형 순서대로 판정되는 길

1. [시작] 사용자에게 적용된 프로필의 연결 정책 목록
   - 주체: SSE 에지
   - 위치: Global Secure Access › 보안 › 보안 프로필 › 프로필 선택 › Link policies
   - 데이터: 예: "Security Profile for Sales" — TLS 검사 정책 · 웹 필터링 정책 · 위협 인텔리전스 정책. 한 프로필에는 같은 유형 정책을 하나만 연결합니다(위협 인텔리전스 정책은 프로필당 하나, V2 웹 필터링 정책은 정확히 하나)
   - 해설: 프로필은 서로 다른 보안 제어를 한 묶음으로 사용자에게 전달하는 그릇입니다
2. [처리] 연결된 정책의 우선순위와 상태 확인
   - 주체: 관리자
   - 위치: Security profiles › 프로필 › Link policies 목록의 Priority · State 열
   - 데이터: 프로필 안 정책 우선순위는 100(가장 높음)~65000(가장 낮음)의 고유 번호이고, 앞으로 끼워 넣을 수 있게 약 100 간격을 두길 권장합니다. 정책 링크 상태는 enabled/disabled입니다
   - 해설: 숫자가 작은 정책이 먼저이며 방화벽 규칙과 같은 방식입니다
3. [처리] 보안 제어 유형 순서를 적용 — 문서의 고정 순서
   - 주체: SSE 에지
   - 데이터: 문서의 제어 순서: (1) TLS 검사 > (2) 웹 필터링 > (3) 위협 인텔리전스 > (4) 파일 형식 > (5) 데이터 손실 방지 > (6) 타사. 각 제어 안의 예외는 그 제어의 규칙 우선순위가 처리합니다. 정책 우선순위 번호가 서로 다른 유형 간 순서에도 영향을 주는지는 문서에 명시가 없습니다 [확인 필요]
   - 해설: 제어 유형 사이의 순서는 정해져 있고, 같은 유형 안에서는 규칙(또는 V1 정책) 우선순위로 정합니다
4. [처리] 1단계 TLS 검사 — 복호화해서 이후 제어가 볼 수 있게 함
   - 주체: SSE 에지
   - 데이터: 검사 대상이면 URL·HTTP 메서드까지 노출. 허용·차단 판정이 아니라 가시성을 결정하는 단계입니다
   - 해설: 이 단계 결과에 따라 아래 웹 필터링·위협 인텔리전스가 보는 정보가 달라집니다
5. [판단] 2단계 웹 필터링이 차단하는가?
   - 주체: SSE 에지
   - 데이터: 웹 필터링 정책의 규칙을 우선순위 순으로 평가해 Block에 일치하면 차단. 예: 우선순위 100 Allow m365.cloud.microsoft, 우선순위 200 Block Artificial Intelligence. 웹 필터링 Allow가 일치한 뒤 위협 인텔리전스가 계속 평가되는지는 문서에 명시가 없어 테스트가 필요합니다 [확인 필요]
   - 해설: 웹 필터링의 Allow·Block이 멈추게 하는 것은 웹 필터링 평가이고, Continue 같은 기본 동작도 다른 정책 유형으로 평가를 넘기지 않는다고 문서가 설명합니다
   - 웹 필터 차단 → [차단] 웹 필터링 차단 — PolicyType = webContentFiltering
   - 웹 필터 통과 → 6
6. [판단] 3단계 위협 인텔리전스가 차단하는가?
   - 주체: SSE 에지
   - 데이터: 규칙 우선순위 순으로 허용 규칙 → 위협 지표 일치 → 일치 시 Block. 일치하는 규칙이 없으면 기본 동작 Allow로 다음 제어에 넘깁니다
   - 해설: 웹 필터링을 통과한 침해된 사이트도 여기서 걸러집니다
   - 위협 차단 → [차단] 위협 인텔리전스 차단 — PolicyType = threatIntelligence
   - 위협 통과 → 7
7. [처리] 4~6단계 이후 제어로 이동 — 파일 형식 · 데이터 손실 방지 · 타사
   - 주체: SSE 에지
   - 데이터: 파일 형식 필터링 · 데이터 손실 방지 · 타사(예: Netskope) 제어. 각 제어의 구성은 해당 L2·문서가 다루며 제공 상태는 제어마다 다릅니다 [확인 필요: 미리 보기 범위]
   - 해설: 위협 인텔리전스를 통과한 요청도 뒤쪽 제어가 판정할 수 있습니다
8. [끝] 모든 제어를 통과해 허용 — 정책별 판정이 각각 기록
   - 주체: 로그
   - 위치: Global Secure Access › 모니터링 › 트래픽 로그
   - 데이터: Action = Allowed · FilteringProfileName · PolicyType으로 판정한 제어가 구분됨. PolicyType 값은 mcpFirewall · promptProtection · threatIntelligence · webContentFiltering
   - 해설: 차단된 경우 로그의 PolicyType을 보면 어느 제어가 막았는지 바로 알 수 있습니다
- 시나리오: 웹 필터 차단 :: 웹 필터링이 먼저 차단해 위협 인텔리전스는 평가 안 됨
- 시나리오: 웹 필터 통과 ▸ 위협 차단 :: 웹 필터링은 통과했지만 위협 인텔리전스가 차단
- 시나리오: 웹 필터 통과 ▸ 위협 통과 :: 두 제어 모두 통과해 뒤쪽 제어로 넘어가 허용

> 교육 포인트: 프로필 안에서는 제어 유형 순서가 고정이고 같은 유형 안의 예외는 규칙 우선순위로 처리합니다. '위협 때문인지 범주 때문인지'는 로그의 PolicyType으로 구분합니다.
>
> 주의: 문서는 프로필 안 정책의 우선순위 번호(100~65000)와 제어 유형 고정 순서를 서로 다른 문서에서 설명합니다. 유형이 다른 정책끼리 번호가 순서에 영향을 주는지는 문서에 없으므로 테스트로 확인합니다 [확인 필요].

#### L4 · 사용자 지정 프로필과 기준선 프로필이 겹칠 때

1. [시작] 사용자 토큰의 프로필 ID 클레임으로 적용 프로필 결정
   - 주체: SSE 에지
   - 위치: 액세스 토큰의 보안 프로필 ID 클레임 · 기준선 프로필(우선순위 65000)
   - 데이터: 조건부 액세스 정책의 세션 제어로 연결된 프로필 · 테넌트 기준선 프로필. 원격 네트워크의 클라이언트 없는 트래픽은 사용자 인식이 불가능해 기준선만 거칩니다
   - 해설: 사용자마다 일치하는 조건부 액세스 정책이 달라 적용되는 프로필 수가 달라집니다
2. [판단] 일치하는 조건부 액세스 정책(보안 프로필)이 몇 개인가?
   - 주체: Entra ID
   - 데이터: 조건부 액세스 정책 일치 수 · 정책 상태 On
   - 해설: 여러 정책이 일치하면 일치한 프로필들이 프로필 우선순위 순으로 모두 처리됩니다
   - 일치 없음 → 6
   - 하나 → 3
   - 여러 개 → 4
3. [처리] 일치한 프로필 하나의 정책을 평가
   - 주체: SSE 에지
   - 데이터: 프로필 안에서 제어 유형 순서대로 정책 평가(앞 L4 참고)
   - 해설: 프로필이 하나면 그 프로필의 정책이 곧 사용자 지정 판정입니다
   - 다음 → 5
4. [처리] 일치한 프로필들을 프로필 우선순위 순으로 처리
   - 주체: SSE 에지
   - 데이터: 우선순위 번호가 작은 프로필부터 처리. 클라우드 방화벽은 여러 프로필의 방화벽 정책을 합치지 않고 선택된 프로필 하나만 평가하는 등 제어별로 다를 수 있습니다
   - 해설: 위협 인텔리전스처럼 제어마다 여러 프로필에 걸치는 방식이 다를 수 있어 필요한 제어는 개별로 확인합니다 [확인 필요: 위협 인텔리전스의 다중 프로필 처리]
5. [판단] 프로필 안에서 일치한 규칙이 판정을 확정했는가?
   - 주체: SSE 에지
   - 데이터: 정책이 일치해 동작(차단·허용)을 낸 경우 평가가 멈춘다고 문서가 설명합니다. 위협 인텔리전스 기본 동작 Allow가 이 '확정'에 해당하는지는 문서에 명시가 없습니다 [확인 필요]
   - 해설: 사용자 지정 프로필의 명시적 규칙이 기준선의 일반 규칙보다 먼저 이깁니다
   - 확정 → 7
   - 미확정 → 6
6. [처리] 기준선 프로필(65000)을 평가 — 마지막 안전망
   - 주체: SSE 에지
   - 위치: Global Secure Access › Secure › Security profiles › Baseline profile
   - 데이터: 기준선은 조건부 액세스 연결 없이 모든 인터넷 액세스 트래픽에 적용되고 가장 낮은 우선순위로 평가됩니다. 다른 프로필이 조건부 액세스로 일치해도 기준선은 계속 실행됩니다. 우선순위가 높은 프로필과 규칙이 충돌하면 높은 프로필이 이깁니다
   - 해설: 위협 인텔리전스를 기준선에 연결하면 조건부 액세스에 빠진 사용자와 클라이언트 없는 원격 네트워크 트래픽도 보호됩니다
7. [끝] 판정 확정 — 어느 프로필이 판정했는지 로그에 기록
   - 주체: 로그
   - 위치: Global Secure Access › 모니터링 › 트래픽 로그
   - 데이터: FilteringProfileId · FilteringProfileName · PolicyName · RuleName · Action. 기준선이 판정하면 FilteringProfileName에 기준선 프로필 이름이 보입니다 [확인 필요: 기준선 프로필 이름 표시]
   - 해설: 사용자가 기대한 프로필과 실제 판정 프로필이 다르면 이 열로 원인을 찾습니다
- 시나리오: 일치 없음 :: 일치하는 프로필이 없어 기준선이 판정
- 시나리오: 하나 ▸ 확정 :: 프로필 하나가 판정을 확정해 종료
- 시나리오: 하나 ▸ 미확정 :: 프로필이 확정하지 못해 기준선이 마지막 판정
- 시나리오: 여러 개 ▸ 확정 :: 우선순위 높은 프로필이 판정을 확정해 종료
- 시나리오: 여러 개 ▸ 미확정 :: 모든 프로필이 미확정이라 기준선이 마지막 판정

> 교육 포인트: 일반 사용자는 조건부 액세스로 받은 프로필을 먼저, 기준선을 마지막에 거칩니다. 전사 공통 위협 차단은 기준선에, 부서별 예외는 사용자 지정 프로필에 두는 설계가 문서의 의도입니다.
>
> 주의: 사용자 인식은 GSA 클라이언트를 통해서만 가능합니다. 클라이언트 없이 원격 네트워크로 오는 트래픽은 조건부 액세스 프로필을 받지 못하고 기준선만 거칩니다. 새 프로필 연결은 새 토큰이 필요해 60~90분까지 걸립니다.

### L3 · C · 오탐 대응과 예외 — 차단 확인 · 허용 규칙 · 지속 점검

#### L4 · 업무 사이트 차단 신고를 확인하고 예외를 만드는 길

1. [시작] 사용자가 업무 사이트가 차단되었다고 신고
   - 주체: 사용자
   - 위치: 차단 화면 More info의 Threat Type 확인
   - 데이터: 대상 URL·FQDN · 차단 시각 · 차단 화면의 Threat Type(예: MaliciousUrl · Phishing)
   - 해설: 사용자가 알려 준 대상이 정말 위협 때문에 막혔는지부터 확인합니다
2. [처리] 트래픽 로그에서 차단 거래 찾기
   - 주체: 관리자
   - 위치: Global Secure Access › 모니터링(Monitor) › 트래픽 로그 › Add filter (User principal name · Action = Denied) · Columns에서 Threat Type · Policy name · Rule name · Filtering profile name 표시
   - 데이터: NetworkAccessTraffic 거래: Action · PolicyType · PolicyName · RuleName · FilteringProfileName · ThreatType. 로그는 최대 5분 뒤에 나타나고 조회는 Reports Reader 이상입니다
   - 해설: 로그의 정책·규칙 이름으로 어느 제어가 어떤 규칙으로 막았는지 알 수 있습니다
3. [판단] 로그의 ThreatType이 채워져 있는가?
   - 주체: 관리자
   - 데이터: ThreatType은 위협 인텔리전스가 대상과 일치할 때만 채워지고 대부분의 거래에서는 비어 있습니다. 채워져 있으면 위협 유형(Botnet · C2 · Malware · Phishing · PUA 등)이 보입니다
   - 해설: 비어 있으면 위협 인텔리전스가 아니라 다른 정책이 막은 것이니 PolicyType으로 정책을 구분합니다
   - 채워짐 → 4
   - 비어 있음 → [끝] 위협 인텔리전스가 아닌 정책이 차단 — PolicyType·PolicyName으로 해당 정책 점검
4. [판단] 대상이 안전하다고 확인했는가?
   - 주체: 관리자
   - 데이터: 위협 유형 · 대상 소유 조직 확인 · 보안팀 판단. 문서 경고: 도메인을 위협 인텔리전스에서 우회하는 것은 위험하므로 안전이 확실할 때만 합니다
   - 해설: 인터넷 위협 지형은 계속 바뀌어 한 번 안전했던 대상도 다시 악성이 될 수 있습니다
   - 안전 확인 → 5
   - 확인 불가 → [차단] 차단 유지 — 예외를 만들지 않고 보안팀이 조사
5. [처리] 허용 규칙 만들기 — 필요한 FQDN만
   - 주체: 관리자
   - 위치: Global Secure Access › Secure › Threat Intelligence Policies › 정책 선택 › Rules › Add rule › 이름 · 설명 · 우선순위 · 상태 입력 › Destination FQDNs 입력 › Add
   - 데이터: Destination FQDNs는 쉼표로 구분한 도메인 목록. 우선순위는 기본 차단 규칙(65000)보다 작은 번호여야 먼저 평가되고, 규칙 이름·설명에 예외 사유를 남깁니다
   - 해설: 와일드카드를 넓게 쓰지 말고 필요한 FQDN만 넣어 예외 범위를 최소화합니다
6. [처리] Microsoft에 오탐 제보 — 규칙 추가와 별도로 메일
   - 주체: 외부
   - 위치: 문서에 안내된 메일 주소(GSAThreatIntel@microsoft.com)와 제목 형식 [Customer Dispute] <Destination> is a false positive
   - 데이터: 본문 항목 — Dispute Type: Threat intelligence false positive · URL OR FQDN OR IP · Threat Type · Justification
   - 해설: 허용 규칙은 내 테넌트의 예외일 뿐이고 근본 오탐은 Microsoft 제보로 지표 자체를 바로잡습니다
7. [끝] 반영 확인 — 허용 규칙은 약 2분 안에 효과
   - 주체: 디바이스
   - 위치: 브라우저 캐시 삭제 후 대상 재접속 · 트래픽 로그에서 Action = Allowed 확인
   - 데이터: 문서 기준 허용 규칙을 만들면 2분 안에 접속할 수 있습니다. 허용 규칙에 일치한 거래가 로그에 어떤 PolicyName·RuleName·ThreatType으로 남는지는 문서에서 확인하지 못했습니다 [확인 필요]
   - 해설: 접속이 안 되면 브라우저 캐시를 지우고, 그래도 안 되면 규칙 우선순위·프로필 연결·조건부 액세스 상태를 점검합니다
- 시나리오: 채워짐 ▸ 안전 확인 :: 위협 때문에 막혔고 안전을 확인해 허용 규칙과 제보
- 시나리오: 채워짐 ▸ 확인 불가 :: 위협 유형이 맞고 안전 불명이라 차단을 유지
- 시나리오: 비어 있음 :: 위협 인텔리전스가 아니라 다른 정책의 차단

> 교육 포인트: 오탐 대응은 로그 확인 → 안전 확인 → 최소 범위 허용 규칙 → Microsoft 제보 순서입니다. 허용 규칙만으로 끝내지 않고 제보까지 하는 것이 문서의 안내입니다.
>
> 주의: 허용 규칙은 보호를 줄이는 예외입니다. 규칙에 사유를 적고 정기적으로 다시 검토합니다. 위협 인텔리전스가 아닌 정책이 막은 경우 이 규칙으로는 풀리지 않습니다.

#### L4 · 위협 탐지 현황과 예외를 정기적으로 점검하는 흐름

1. [시작] 정기 점검 시작 — 정책이 실제로 동작하는지부터
   - 주체: 관리자
   - 위치: Global Secure Access › 보안 › 위협 인텔리전스 정책 · 보안 프로필 · 모니터링 › 트래픽 로그
   - 데이터: 정책 상태 · 프로필 연결 상태 · 조건부 액세스 정책 상태(On)
   - 해설: 정책을 만들고 끝내지 않고 주기적으로 동작과 예외를 확인합니다
2. [처리] 테스트 사이트로 차단 동작 확인
   - 주체: 디바이스
   - 위치: 클라이언트 기기 브라우저에서 entratestthreat.com 또는 smartscreentestratings2.net 접속 (문서가 안전한 테스트 용도로 안내)
   - 데이터: 차단 화면의 Threat Type = MaliciousUrl · 트래픽 로그의 Threat Type 열. Defender나 SmartScreen이 먼저 막으면 More information › Continue to the unsafe site (not recommended)로 넘겨 Global Secure Access 차단 메시지를 확인할 수 있으나 실습 환경에서만 합니다
   - 해설: 테스트 사이트는 위협 인텔리전스가 살아 있는지 확인하는 신호로 씁니다
3. [처리] KQL로 위협 인텔리전스 차단 현황 조회
   - 주체: 관리자
   - 위치: Log Analytics · Microsoft Sentinel — 진단 설정(Entra ID › Monitoring & health › Diagnostic settings, NetworkAccessTrafficLogs 선택)으로 내보낸 로그
   - 데이터: NetworkAccessTraffic | where TrafficType == "internet" | where isnotempty(ThreatType) | project UserPrincipalName, ThreatType, DestinationFqdn, DestinationUrl, DestinationIp, Action
   - 해설: ThreatType은 일치한 경우에만 채워지므로 이 조건으로 위협 일치 건만 모읍니다
4. [판단] 위협 일치 건이 있는가?
   - 주체: 관리자
   - 데이터: 쿼리 결과 행 수 · 사용자·대상별 분포. 실습·저위험 테넌트에서 30일간 0건이어도 탐지가 고장난 것은 아닙니다
   - 해설: 있으면 해당 사용자·기기를 조사하고, 없으면 예외 점검으로 넘어갑니다
   - 일치 있음 → 5
   - 일치 없음 → 6
5. [처리] 일치 건 대응 — 페이로드 다운로드 여부 확인
   - 주체: 관리자
   - 위치: NetworkAccessAlerts · NetworkAccessTraffic ('Malware or phishing URL detected' 경보, 심각도 High)
   - 데이터: ThreatType 채워진 거래 · 사용자 · 기기. 문서 권고 — 페이로드 다운로드 여부 확인, 엔드포인트 보호와 협의해 기기 검사, 확인된 침해면 인시던트 대응 절차로 인계. Microsoft Sentinel은 Global Secure Access Content hub 솔루션 템플릿을 제공합니다
   - 해설: 차단했다고 끝이 아니라 차단 전에 이미 받은 것이 없는지 확인합니다
6. [처리] 허용 규칙을 정기 검토 — 오래된 예외 정리
   - 주체: 관리자
   - 위치: Threat Intelligence Policies › 정책 › Rules 목록의 이름 · 우선순위 · 상태 열
   - 데이터: 규칙별 Destination FQDNs · 사유 · 마지막 검토. 필요 없어진 예외는 상태를 Disabled로 바꿔 시험하거나 삭제합니다 [확인 필요: 포털의 규칙 상태 선택지 표기]
   - 해설: 예외는 시간이 지나면 위험만 남기므로 주기적으로 줄입니다
7. [끝] 점검 결과 기록 — 정책 변경 이력은 감사 로그로 추적
   - 주체: 로그
   - 위치: Entra ID › Monitoring & health › Audit logs
   - 데이터: AuditLogs — 웹 필터링 정책 변경을 승인되지 않은 신원이 수정했는지 점검하는 규칙이 보안 운영 가이드에 있습니다. 위협 인텔리전스 정책·규칙 변경이 같은 로그에 남는지는 문서에서 확인하지 못했습니다 [확인 필요]
   - 해설: 누가 허용 규칙을 추가했는지 추적할 수 있어야 예외를 통제할 수 있습니다
- 시나리오: 일치 있음 :: 위협 일치 건이 있어 사용자·기기 조사 후 예외 점검
- 시나리오: 일치 없음 :: 일치 건이 없어도 이상 없음으로 보고 예외만 점검

> 교육 포인트: 점검은 테스트 사이트(동작 확인) → KQL(현황) → 일치 건 대응 → 허용 규칙 정리 순서입니다. ThreatType이 비어 있는 것이 정상 상태라는 점이 핵심입니다.
>
> 주의: 문서는 일부 KQL 임계값과 허용 목록을 환경에 맞게 검증한 뒤 분석 규칙으로 쓰라고 안내합니다. 트래픽 로그와 연결 로그 일부 기능은 미리 보기 표기가 있습니다 [미리 보기 확인 필요].
