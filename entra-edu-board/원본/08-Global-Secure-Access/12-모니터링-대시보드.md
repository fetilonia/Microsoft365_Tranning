## L2 · 모니터링 · 대시보드 — 대시보드 · 보강된 로그 · 통합 문서 · 상태

- 설정(Control Plane): Microsoft Entra 진단 설정(Diagnostic settings)의 로그 범주 선택(NetworkAccessTrafficLogs · RemoteNetworkHealthLogs · NetworkAccessAlerts 등)과 내보낼 대상(Log Analytics · Storage · Event Hub · 파트너 솔루션) | Microsoft traffic profile 켜기(보강된 Microsoft 365 로그의 전제) | Microsoft Sentinel 콘텐츠 허브 Global Secure Access 솔루션(통합 문서 3개 · 분석 규칙 7개)
- 강제(Enforcement): 이 기능은 트래픽을 허용·차단하지 않는 관찰 계층입니다 — Microsoft SSE 에지(로그·경고 생성) | Log Analytics · Microsoft Sentinel(분석 규칙으로 탐지)
- 증적(Evidence): 대시보드 위젯 · 모니터(Monitor) 로그(트래픽 · 원격 네트워크 상태 · 감사) · 경고(Alerts) | KQL: NetworkAccessTraffic · OfficeActivity(UniqueTokenId 조인) · NetworkAccessAlerts · RemoteNetworkHealthLogs · SigninLogs(IsThroughGlobalSecureAccess)
- 메뉴(Admin Center): Global Secure Access > 대시보드 · 모니터(Monitor) > 트래픽 로그 · 경고 · 원격 네트워크 상태 로그 · 감사 로그 · 통합 문서(Workbooks) | Entra ID > 모니터링 및 상태 > 진단 설정
- 라이선스(License): 대시보드는 Global Secure Access Administrator 역할과 Microsoft Entra ID P1이 필요하고, 보강된 Microsoft 365 로그는 Microsoft traffic profile 라이선스가 전제입니다. Log Analytics · Sentinel · Storage · Event Hub는 Azure 구독 비용이 별도입니다 [확인 필요: 고객 라이선스 · 미리 보기 범위 · 로그 수집 비용]

### L3 · 0 · 기능 상태 전이 — 보기만 하는 상태 → 내보내기 · 통합 문서 구성 → 로그 · 경고가 흐르는 상태

#### L4 · ⓪ 비활성 — 진단 설정이 없으면 포털 기본 보관 기간 안에서만 보인다

1. [시작] 관리자가 Global Secure Access 대시보드를 연다 — 트래픽이 정상인지 확인하려 함
   - 주체: 관리자
   - 위치: Global Secure Access › 대시보드(Dashboard) — Global Secure Access Administrator 역할 필요
   - 데이터: 위젯(Global Secure Access snapshot · Alerts and notifications · Device status 등). 대시보드 조회는 Global Secure Access Administrator 역할과 Entra ID P1 라이선스가 전제입니다
   - 해설: 관리자는 먼저 대시보드의 위젯으로 전체 상태를 훑어봅니다
2. [판단] 에지가 획득한 트래픽이 있는가?
   - 주체: SSE 에지
   - 데이터: 전달 프로필(Internet · Microsoft · Private) 구성과 클라이언트·원격 네트워크 연결 여부
   - 해설: 구성을 하지 않았으면 대시보드에 보여 줄 데이터 자체가 생기지 않습니다
   - 예 → 4
   - 아니오 → 3
3. [끝] 위젯이 No data available — 온보딩과 전달 프로필 구성부터 필요
   - 주체: 관리자
   - 위치: 위젯 메시지 No data available → 문서의 Get started 안내(테넌트 온보딩)
   - 데이터: 표시할 트래픽 없음 — 구성하지 않은 기능은 대시보드에도 로그에도 남지 않습니다
   - 해설: 안 켠 상태에서는 모니터링할 대상도 없습니다
4. [처리] 포털 로그는 기본 보관 기간만 — 지나면 조사할 수 없다
   - 주체: 로그
   - 위치: Global Secure Access › Monitor › Traffic logs · Remote network health logs · Audit logs
   - 데이터: 트래픽 로그·원격 네트워크 상태 로그 30일, 감사 로그 Free 7일 · P1/P2 30일, Office 로그 최대 24시간
   - 해설: 내보내지 않으면 보관 기간이 지난 사건은 되돌아볼 수 없습니다
5. [처리] 진단 설정이 없어 KQL · 경고 규칙 · 통합 문서를 쓸 수 없다
   - 주체: 관리자
   - 위치: Entra ID › 모니터링 및 상태(Monitoring & health) › 진단 설정(Diagnostic settings) — 설정 없음
   - 데이터: Log Analytics 테이블 없음(Sentinel은 수집이 없으면 테이블이 만들어지지 않습니다). 통합 문서는 로그 데이터가 수집되기 전에는 목록에 보이지 않습니다
   - 해설: 포털 화면에서 눈으로 보는 것 말고는 분석 수단이 없습니다
6. [처리] 보강된 Microsoft 365 로그도 만들 수 없다
   - 주체: 로그
   - 데이터: NetworkAccessTraffic과 OfficeActivity가 같은 워크스페이스에 없어 UniqueTokenId 조인 불가. Office 로그는 최대 24시간만 보관
   - 해설: Microsoft 365 활동이 어느 기기·원래 IP에서 나왔는지 연결할 근거가 없습니다
7. [끝] 이상 징후를 늦게 알고 사후 조사도 어렵다
   - 주체: 관리자
   - 데이터: 경고는 포털 Alerts 화면에서만 확인 — 알림 규칙·SIEM 연동 없음
   - 해설: 보고 있지 않은 동안 생긴 사건은 눈에 띄지 않거나 보관 기간 뒤에 사라집니다
- 시나리오: 예 :: 포털 보관 기간 안에서만 보이고 내보내기는 없음
- 시나리오: 아니오 :: 획득 트래픽이 없어 위젯에 데이터가 비어 있음

> 교육 포인트: 모니터링은 "켜는" 스위치 하나가 아니라, 먼저 트래픽이 에지로 들어와야 하고(전달 프로필), 오래 보려면 진단 설정으로 내보내야 합니다.
>
> 주의: 보관 기간은 문서의 기본값이며(트래픽 로그 30일 · 감사 로그 7/30일 · Office 로그 24시간) 내보내면 대상 서비스의 보존 정책을 따릅니다.

#### L4 · ① 구성 — 진단 설정 · Sentinel 솔루션 · 통합 문서를 준비한다

1. [시작] 관리자가 Entra 관리 센터에 로그인 — 작업마다 필요한 역할이 다르다
   - 주체: 관리자
   - 위치: entra.microsoft.com — Global Secure Access Administrator(대시보드 · 경고 · 원격 네트워크 상태 로그), Reports Reader 이상(트래픽 로그·감사 로그 보기), Security Administrator(진단 설정 · 통합 문서 만들기·편집·사용), Sentinel 솔루션 설치는 Microsoft Sentinel Contributor
   - 데이터: Entra 역할 할당. 트래픽 로그 문서는 Global Secure Access Administrator · Global Secure Access Log Reader 역할도 전제로 안내하고, 감사 로그는 Reports Reader · Security Reader · Security Administrator로 볼 수 있습니다
   - 해설: 보는 사람과 내보내는 사람의 역할이 다르므로 담당을 나눠 미리 할당합니다
2. [처리] Microsoft traffic profile 켜기 — 보강된 Microsoft 365 로그의 전제
   - 주체: 관리자
   - 위치: Global Secure Access › 연결(Connect) › 트래픽 전달(Traffic forwarding) › Microsoft traffic profile
   - 데이터: 프로필 상태 = 켜짐. 이 프로필이 있어야 Microsoft 365 서비스로 가는 트래픽이 에지를 거쳐 기록에 디바이스 ID · 운영 체제 · 원래 IP 주소가 붙습니다
   - 해설: 인터넷·Private 프로필도 같은 방식으로 트래픽을 획득해야 대시보드와 로그에 데이터가 생깁니다
3. [처리] 내보낼 대상 준비 — Log Analytics · Storage · Event Hub
   - 주체: 관리자
   - 위치: Azure 포털 — Log Analytics workspace(Sentinel 권장) · Storage account(ListKeys 권한 필요) · Event Hubs namespace와 event hub
   - 데이터: 진단 설정을 만들기 전에 대상이 먼저 있어야 합니다. 보강된 로그를 쓸 계획이면 Sentinel을 켠 Log Analytics 워크스페이스가 권장됩니다
   - 해설: 대상 서비스를 먼저 만들어야 진단 설정에서 고를 수 있습니다
4. [처리] 진단 설정 추가 — 이름 입력
   - 주체: 관리자
   - 위치: Entra ID › 모니터링 및 상태(Monitoring & health) › 진단 설정(Diagnostic settings) › 진단 설정 추가(Add diagnostic setting)
   - 데이터: 진단 설정 이름 (Security Administrator 이상으로 로그인)
   - 해설: Global Secure Access 로그도 다른 Entra 로그와 같은 진단 설정 화면에서 내보냅니다
5. [처리] 로그 범주 선택 — 트래픽 · 연결 · 원격 네트워크 상태 · 경고
   - 주체: 관리자
   - 위치: 진단 설정 › 로그(Logs) › 범주(Categories)
   - 데이터: NetworkAccessTrafficLogs(→ NetworkAccessTraffic) · NetworkAccessConnectionEvents · RemoteNetworkHealthLogs · NetworkAccessAlerts · AuditLogs · NetworkAccessGenerativeAIInsights(미리 보기). 통합 문서 문서에는 EnrichedOffice365AuditLogs(미리 보기) 범주도 표에 있으나 보강된 로그 문서는 OfficeActivity와 NetworkAccessTraffic을 조인하는 방식으로 설명합니다 [확인 필요: 범주 이름·존재 여부]
   - 해설: 보고 싶은 로그 범주를 골라야 해당 테이블이 만들어집니다
6. [처리] 대상 선택 후 저장 — Retention days · 지연
   - 주체: 관리자
   - 위치: 진단 설정 › 대상 정보(Destination details) › Send to Log Analytics workspace · Archive to a storage account · Stream to an event hub · Send to partner solution › 저장(Save)
   - 데이터: Storage에는 Retention days를 지정. 원격 네트워크 상태 로그는 대상에 나타나기까지 최대 3일이 걸릴 수 있습니다
   - 해설: 하나 이상의 대상을 고르며, 저장 직후 바로 데이터가 보이지 않을 수 있습니다
7. [처리] Microsoft 365 감사 로그(OfficeActivity) 수집 — 같은 워크스페이스로
   - 주체: 관리자
   - 위치: Microsoft Defender 포털 › Microsoft Sentinel › Configuration › Data connectors › Microsoft 365(Office 365) › Open connector page › 워크로드(Exchange · SharePoint · Teams) 선택 › Apply Changes
   - 데이터: OfficeActivity 테이블은 Entra 진단 범주가 아니라 Sentinel Microsoft 365 커넥터가 채웁니다. 통합 감사 로깅(unified audit logging)이 켜져 있어야 하며, NetworkAccessTraffic과 같은 워크스페이스여야 상관 분석이 됩니다. 현재 보강은 SharePoint Online만 지원합니다
   - 해설: 두 로그가 한 워크스페이스에 모여야 UniqueTokenId로 이어 붙일 수 있습니다
8. [처리] Global Secure Access 솔루션 설치 — 통합 문서 3개 · 분석 규칙 7개
   - 주체: 관리자
   - 위치: Microsoft Defender 포털 › Microsoft Sentinel › Content management › Content hub › 검색 Global Secure Access › Install (Microsoft Sentinel Contributor 필요)
   - 데이터: 통합 문서 Network Traffic Insights · Enriched Microsoft 365 logs · MCP Servers Dashboard(미리 보기), 분석 규칙 7개(TI Domain/IP/URL Entity Match · Abnormal Deny Rate for Source-to-Destination IP · Protocol Changes for Destination Ports · Source IP Scanning Multiple Open Ports · Connections Outside Operational Hours)
   - 해설: 설치 뒤에 분석 규칙을 직접 켜고 임계값을 조정합니다
9. [처리] Entra 관리 센터의 내장 통합 문서 확인
   - 주체: 관리자
   - 위치: Global Secure Access › 모니터(Monitor) › 통합 문서(Workbooks)
   - 데이터: Network Traffic Insights · Remote Network Health · Clients Activity and Status · Discovered Application Segments · Enriched Microsoft 365 Logs 워크북. 로그 데이터가 수집되기 전에는 보이지 않으며, 만들고 편집하고 쓰려면 Security Administrator가 필요합니다
   - 해설: 통합 문서는 Log Analytics의 로그를 읽어 그리므로 6단계의 내보내기가 먼저입니다
10. [끝] 데이터 수집 확인 — 테이블이 보이는지 본다
   - 주체: 관리자
   - 위치: Microsoft Defender 포털 › Microsoft Sentinel › Configuration › Tables
   - 데이터: NetworkAccessTraffic · NetworkAccessConnectionEvents · RemoteNetworkHealthLogs · NetworkAccessAlerts · (선택) OfficeActivity · NetworkAccessGenerativeAIInsights(미리 보기)가 보이는지 확인
   - 해설: 테이블이 없으면 수집이 안 된 것이므로 범주·대상·트래픽 획득을 다시 점검합니다

> 교육 포인트: 구성은 ① 트래픽을 에지로 보내고(프로필) ② 진단 설정으로 내보내고 ③ 그 로그 위에 통합 문서·분석 규칙을 올리는 세 겹입니다. 보강된 Microsoft 365 로그는 거기에 Microsoft 365 감사 로그 수집이 하나 더 필요합니다.
>
> 주의: 보강된 Microsoft 365 로그 문서는 별도 포털 메뉴 없이 "두 테이블을 조인하거나 통합 문서를 쓰는" 방식을 설명하고, 운영 가이드 문서는 Monitor › Enriched Microsoft 365 logs 메뉴를 언급합니다. 화면 이름이 다를 수 있습니다 [확인 필요: 메뉴 · 미리 보기]
>

#### L4 · ② 활성 — 트래픽이 로그 · 대시보드 · 경고로 바뀌어 흐른다

1. [시작] 사용자·원격 네트워크의 트래픽이 에지로 들어온다
   - 주체: GSA 클라이언트
   - 위치: GSA 클라이언트 또는 원격 네트워크(IPsec 터널) → Microsoft SSE 에지
   - 데이터: 전달 프로필 규칙으로 획득된 Internet · Microsoft 365 · Private 트래픽
   - 해설: 획득된 트래픽만 로그와 대시보드의 재료가 됩니다
2. [처리] 에지가 정책을 판정하고 로그를 만든다 — 트랜잭션 · 연결
   - 주체: SSE 에지
   - 위치: Global Secure Access › Monitor › Traffic logs
   - 데이터: 트랜잭션 로그(NetworkAccessTraffic): 사용자 · 기기 · 대상 · Action · 보낸·받은 바이트. 연결 로그(NetworkAccessConnectionEvents, 미리 보기)는 연결의 시작·종료와 Active/Closed 상태
   - 해설: 한 번의 접속이 세션 → 연결 → 트랜잭션 구조로 쪼개져 기록됩니다
3. [처리] Entra 로그인 로그에 경유 여부가 남는다
   - 주체: Entra ID
   - 위치: Entra ID › 사용자 › 로그인 로그(Sign-in logs) — 상세의 Through Global Secure Access
   - 데이터: SigninLogs.IsThroughGlobalSecureAccess(true/false), 원본 IP 복원을 켜면 사용자의 실제 공용 IP가 로그인 로그에 보입니다
   - 해설: 로그인 로그와 트래픽 로그를 짝지어 GSA 경유 여부를 가릴 수 있습니다
4. [처리] 대시보드 위젯이 24시간·7일 단위로 집계한다
   - 주체: 로그
   - 위치: Global Secure Access › 대시보드
   - 데이터: Users(UPN) · Devices(device ID) · Destinations(FQDN·IP) · Agents의 최근 24시간 고유 개수. Active devices는 24시간, Inactive devices는 최근 7일에는 보였으나 24시간에는 안 보인 기기
   - 해설: 대시보드는 로그의 요약 보기이며 자세한 근거는 로그로 내려가서 봅니다
5. [처리] 경고 엔진이 이상 징후를 평가한다
   - 주체: SSE 에지
   - 위치: Global Secure Access › Monitor › Alerts
   - 데이터: Token/Device Inconsistency(같은 토큰이 둘 이상의 기기에서 사용) · Increased External Tenant Activity(14일 슬라이딩 윈도우) · Unhealthy Remote Network(매시간 BGPDisconnect · TunnelDisconnect 확인). Netskope 경고는 Netskope ATP·DLP 모듈이 있을 때만 나타납니다
   - 해설: 경고는 심각도 · 유형 · 날짜로 걸러 보며, 대시보드 Alerts 위젯에는 요약이 표시됩니다
6. [처리] 진단 설정대로 로그를 내보낸다
   - 주체: 로그
   - 위치: Entra ID › 진단 설정에 지정한 대상
   - 데이터: Log Analytics 테이블(NetworkAccessTraffic · NetworkAccessConnectionEvents · RemoteNetworkHealthLogs · NetworkAccessAlerts) · Storage 보관 · Event Hub로 SIEM 전달. 원격 네트워크 상태 로그는 도착까지 최대 3일 걸릴 수 있습니다
   - 해설: 내보낸 로그는 포털 보관 기간을 넘겨 오래 둘 수 있습니다
7. [판단] 경고나 분석 규칙이 발생했는가?
   - 주체: 관리자
   - 위치: Monitor › Alerts · Sentinel › Incidents(분석 규칙 사용 시)
   - 데이터: 경고 심각도 · 유형 · 관련 개체(사용자 · 기기 · 앱) · Sentinel 인시던트
   - 해설: 경고가 있으면 확인해서 대응하고, 없으면 기준선과 추세만 지켜봅니다
   - 경고 발생 → 8
   - 이상 없음 → 9
8. [끝] 경고 확인 · 대응 — Alerts에서 필터 후 관련 로그로 이동
   - 주체: 관리자
   - 위치: Global Secure Access › Monitor › Alerts › 경고 선택 → 관련 로그
   - 데이터: 경고 상세 · 연결된 트래픽 로그/원격 네트워크 상태 로그/로그인 로그
   - 해설: 경고는 시작점일 뿐이며 근거는 관련 로그에서 확인합니다
9. [끝] 이상 없음 — 로그와 통계가 쌓여 기준선이 된다
   - 주체: 로그
   - 위치: 대시보드 · 통합 문서(Network Traffic Insights)
   - 데이터: 평상시 트래픽 볼륨 · 차단 비율 · 사용자 수 추세
   - 해설: 평상시 값을 알아야 나중에 이상 값을 구별할 수 있습니다
- 시나리오: 경고 발생 :: 경고가 발생해 Alerts와 관련 로그에서 대응
- 시나리오: 이상 없음 :: 경고가 없어 로그가 쌓이며 평상시 기준선이 됨

> 교육 포인트: 대시보드 · 로그 · 경고 · 통합 문서는 모두 같은 에지 로그를 서로 다른 시야로 보는 화면입니다. 요약은 대시보드, 근거는 로그, 알림은 Alerts, 장기 분석은 통합 문서와 Sentinel입니다.
>
> 주의: 연결 로그(Connections)와 일부 위젯(Usage profiling · Network activity by location)은 미리 보기로 안내되어 화면이 바뀔 수 있습니다 [확인 필요: 미리 보기]

### L3 · A · 대시보드 — 위젯을 따라 이상 징후를 좁혀 들어간다

#### L4 · 스냅샷 → 경고 → 사용 패턴 → 로그로 드릴다운

1. [시작] 대시보드를 열고 Global Secure Access snapshot을 확인한다
   - 주체: 관리자
   - 위치: Global Secure Access › 대시보드 (Global Secure Access Administrator 필요)
   - 데이터: Users · Devices · Destinations · Agents — 최근 24시간 고유 개수. 필터로 All · Internet Access · Private Access · Microsoft 트래픽을 바꿔 볼 수 있습니다
   - 해설: 평소와 비교해 사용자·기기 수가 갑자기 달라졌는지부터 봅니다
2. [판단] Alerts and notifications 위젯에 경고가 있는가?
   - 주체: 관리자
   - 위치: 대시보드 › Alerts and notifications
   - 데이터: Unhealthy remote network · Increased external tenants activity · Token and device inconsistency · Web content blocked
   - 해설: 경고가 있으면 가장 먼저 원인을 따라갑니다
   - 경고 있음 → 3
   - 경고 없음 → 4
3. [처리] 경고 링크로 관련 화면에 이동한다
   - 주체: 관리자
   - 위치: 경고 이름 옆 링크 → 관련 페이지(Monitor › Alerts, 원격 네트워크 상태 로그, 트래픽 로그 등)
   - 데이터: 경고 유형 · 심각도. 대시보드 Alerts 위젯은 유형·심각도별 건수 차트를 보여 줍니다
   - 해설: 대시보드는 알려 주기만 하고 상세는 연결된 화면에서 확인합니다
4. [처리] Device status로 기기 활동 변화를 본다
   - 주체: 관리자
   - 위치: 대시보드 › Device status
   - 데이터: Active devices(24시간 내 고유 device ID · 변화율), Inactive devices(최근 7일에는 보였으나 24시간에는 없음 · 변화율)
   - 해설: 비활성 기기가 늘면 클라이언트 연결 문제나 사용 중단을 의심합니다
5. [처리] Usage profiling으로 사용량 패턴을 비교한다 [미리 보기 확인 필요]
   - 주체: 관리자
   - 위치: 대시보드 › Usage profiling (preview) › Display by · View details
   - 데이터: Display by = Transactions · Users · Devices · Bytes sent · Bytes received. 기간은 기본이 지난 달이며 최근 24시간·지난 주로 바꿀 수 있습니다
   - 해설: 평소 패턴을 벗어난 날짜를 찾아 그 날짜의 트래픽 로그로 내려갑니다
6. [처리] Top used destinations · Cloud applications로 쏠림을 본다
   - 주체: 관리자
   - 위치: 대시보드 › Top used destinations · Top used cloud applications · Cloud applications status
   - 데이터: 대상 목록은 트랜잭션 수순이며 Transactions · Users · Devices · Bytes sent · Bytes received 기준으로 바꿉니다. 클라우드 앱은 All 또는 Generative AI 탭, 상태 위젯은 전체 · 생성형 AI · 고위험 앱 수를 보여 줍니다
   - 해설: 전체 바이트가 한 대상에 쏠리거나 알 수 없는 AI 앱이 늘면 점검 대상입니다
7. [처리] Cross-tenant access 위젯으로 외부 테넌트 접근을 본다
   - 주체: 관리자
   - 위치: 대시보드 › Cross-tenant access › Configure tenant restrictions(세션 관리로 이동)
   - 데이터: Sign-ins · Total distinct tenants · Unseen tenants(24시간 내 보였으나 이전 7일에는 없던 테넌트) · Users · Devices
   - 해설: Unseen tenants가 늘면 Increased External Tenant Activity 경고와 함께 확인합니다
8. [처리] Web category filtering 위젯으로 차단·허용 범주를 본다
   - 주체: 관리자
   - 위치: 대시보드 › Web category filtering › View all web categories
   - 데이터: Blocked / Allowed 필터, Transactions · Users · Devices 정렬. 규칙을 만드는 방법은 Entra Internet Access 기능에서 다룹니다
   - 해설: 허용되는 상위 범주를 보고 차단할 범주를 정하는 근거로 씁니다
9. [처리] Network activity by location으로 지역 이상을 본다 [미리 보기 확인 필요]
   - 주체: 관리자
   - 위치: 대시보드 › Network activity by location (preview) › Map view · Simplified view
   - 데이터: 사용자 · 기기 · 연결 · 트랜잭션 · 원격 네트워크 활동을 원본 IP 위치별로 표시. Simplified view의 국가를 선택하면 해당 국가로 필터된 연결 로그가 열립니다
   - 해설: 평소와 다른 지역 활동은 보안 점검 단서이고 ISP 문제 진단에도 쓰입니다
10. [끝] 의심 지표를 트래픽 로그로 드릴다운한다
   - 주체: 관리자
   - 위치: Usage profiling 날짜 선택 · View all destinations · 국가 선택 → Global Secure Access › Monitor › Traffic logs
   - 데이터: 날짜 · 대상 · 국가 조건이 걸린 로그 목록 (Reports Reader 이상으로 조회)
   - 해설: 대시보드는 어디를 볼지 알려 주고, 정확한 사용자·규칙은 로그에서 확인합니다
- 시나리오: 경고 있음 :: 경고 링크를 따라가 위젯과 로그까지 좁혀 들어감
- 시나리오: 경고 없음 :: 경고가 없어도 위젯 추세로 이상을 찾아 로그로 내려감

> 교육 포인트: 위젯 대부분이 "최근 24시간 고유 개수"이므로 어제와 비교해 변화량을 보는 용도입니다. 정확한 원인은 로그의 필터(사용자 · 대상 · 범주)로 내려가서 찾습니다.
>
> 주의: 대시보드는 Global Secure Access Administrator 역할이 있어야 보이며, 사용량·위치 위젯은 미리 보기입니다. 트래픽 획득 구성이 없으면 No data available이 표시됩니다 [확인 필요: 미리 보기]

### L3 · B · 보강된 Microsoft 365 로그 — 사용자 행위를 기기와 원래 IP까지 추적한다

#### L4 · SharePoint 활동 → 트래픽 로그 조인 → 증거 보존

1. [시작] "이 SharePoint 파일을 누가 어느 기기·IP에서 내려받았나" 조사를 시작한다
   - 주체: 관리자
   - 위치: Microsoft Sentinel(Log Analytics) 워크스페이스 · Defender 포털 › Advanced hunting
   - 데이터: 단서: 파일 이름 · 사용자 · 시각. 보강된 로그의 SharePoint는 파일 다운로드·업로드·삭제·수정·휴지통 이동과 삭제·휴지통 처리된 목록 항목을 보여 줍니다
   - 해설: 일반 감사 로그만으로는 기기와 원래 IP가 없어 연결이 어렵습니다
2. [판단] 두 로그가 같은 워크스페이스에 들어오고 있는가?
   - 주체: 관리자
   - 위치: Sentinel › Configuration › Tables — NetworkAccessTraffic · OfficeActivity 확인
   - 데이터: Microsoft traffic profile 켜짐 · 진단 설정으로 NetworkAccessTrafficLogs 전송 · Microsoft 365 커넥터로 OfficeActivity 수집
   - 해설: 한 워크스페이스에 없는 두 테이블은 서로 조인할 수 없습니다
   - 준비됨 → 3
   - 미준비 → [차단] 조인 불가 — 프로필·진단 설정·Microsoft 365 커넥터 중 하나가 없습니다
3. [처리] 두 테이블의 역할과 키를 확인한다
   - 주체: 로그
   - 데이터: OfficeActivity(Exchange · SharePoint · Teams 통합 감사 이벤트, 현재 보강은 SharePoint만 지원)와 NetworkAccessTraffic(디바이스 ID · 운영 체제 · 원래 IP). 조인 키는 UniqueTokenId입니다
   - 해설: 별도의 새 로그 스트림이 아니라 기존 두 테이블을 토큰 ID로 합치는 방식입니다
4. [판단] 통합 문서로 볼 것인가, 직접 쿼리를 쓸 것인가?
   - 주체: 관리자
   - 데이터: Enriched Microsoft 365 logs 워크북(이미 쿼리가 들어 있음) 또는 직접 만든 조인 쿼리
   - 해설: 정해진 질문은 통합 문서로, 변형 질문은 직접 쿼리로 합니다
   - 통합 문서 → 5
   - 직접 쿼리 → 6
5. [처리] Enriched Microsoft 365 logs 통합 문서를 연다
   - 주체: 관리자
   - 위치: Global Secure Access › 모니터(Monitor) › 통합 문서 › Enriched Microsoft 365 Logs, 또는 Defender 포털 › Microsoft Sentinel › Content hub › Global Secure Access › Enriched Microsoft 365 logs › View Template
   - 데이터: 상관 키 UniqueTokenId. 누가 어떤 리소스에 어느 기기에서 접근했는지와 원래 소스 IP를 함께 보여 줍니다
   - 해설: 통합 문서는 필요한 조인 쿼리를 이미 적용해 둔 보기입니다
   - 다음 → 7
6. [처리] OfficeActivity와 NetworkAccessTraffic을 직접 조인한다
   - 주체: 관리자
   - 위치: Sentinel › Logs (KQL) — join 연산자
   - 데이터: UniqueTokenId 기준 조인 후 사용자 · 파일 · 디바이스 · 원래 IP 열을 선택. 열 이름은 테이블 스키마(NetworkAccessTraffic · OfficeActivity) 문서를 확인합니다 [확인 필요: 열 이름]
   - 해설: 조인 뒤에야 파일 이벤트 한 줄에 기기와 IP가 함께 붙습니다
7. [처리] 보강된 필드로 행위를 해석한다 — 기기 · 운영 체제 · 원래 IP
   - 주체: 로그
   - 데이터: 보강 속성: 디바이스 ID · 운영 체제 · 원래 IP 주소. SharePoint 로그는 다운로드·업로드·삭제·수정·휴지통 이벤트를 포함합니다
   - 해설: 회사 기기에서 평소 IP로 온 접근인지, 낯선 기기·IP인지 구분합니다
8. [처리] 로그인 로그로 경유 여부를 교차 확인한다
   - 주체: Entra ID
   - 위치: Entra ID › 사용자 › 로그인 로그 — 상세 Through Global Secure Access, 또는 KQL SigninLogs
   - 데이터: IsThroughGlobalSecureAccess(true/false), 원본 IP 복원이 켜져 있으면 사용자의 실제 공용 IP. 로그인 로그가 나타나기까지 시간이 걸릴 수 있습니다
   - 해설: Microsoft 365 접근이 GSA를 우회했는지 로그인 로그로 확인합니다
9. [처리] 증거를 장기 보관하도록 내보낸다
   - 주체: 관리자
   - 위치: Entra ID › 모니터링 및 상태 › 진단 설정 — Storage 보관 · Event Hub 전송 · Sentinel 워크스페이스 보존
   - 데이터: 트래픽 로그 30일, Office 로그는 최대 24시간만 보관되므로 내보내지 않으면 사라집니다. Storage는 Retention days 지정
   - 해설: 조사 중인 사건의 로그는 보관 기간이 끝나기 전에 별도로 남깁니다
10. [끝] 사용자 행위 타임라인을 정리한다
   - 주체: 관리자
   - 데이터: 누가 · 언제 · 어떤 파일을 · 어느 기기와 원래 IP에서 · GSA 경유 여부로 정리한 타임라인
   - 해설: 일반 감사 로그에 네트워크 맥락을 더해 사건의 근거를 완성합니다
- 시나리오: 준비됨 ▸ 통합 문서 :: 통합 문서로 파일 이벤트에 기기와 원래 IP를 붙임
- 시나리오: 준비됨 ▸ 직접 쿼리 :: 직접 조인 쿼리로 파일 이벤트에 기기와 IP를 붙임
- 시나리오: 미준비 :: 두 로그가 한 워크스페이스에 없어 조인 불가

> 교육 포인트: 보강은 "새 로그"가 아니라 OfficeActivity와 NetworkAccessTraffic을 UniqueTokenId로 합치는 일입니다. 그래서 같은 워크스페이스에 두 로그가 함께 들어오는지가 첫 점검입니다.
>
> 주의: 현재 SharePoint Online 로그만 보강됩니다. 이 기능은 미리 보기로 표기되어 있고 운영 가이드와 화면 이름이 다를 수 있습니다 [확인 필요: 미리 보기 · 메뉴 이름 · EnrichedOffice365AuditLogs 범주]

### L3 · C · 상태 점검과 경고 대응 — 원격 네트워크 · 경고 · 정기 점검

#### L4 · Unhealthy Remote Network 경고를 터널과 BGP로 나누어 원인을 찾는다

1. [시작] Unhealthy Remote Network 경고가 올라온다
   - 주체: SSE 에지
   - 위치: Global Secure Access › 대시보드 › Alerts and notifications · Monitor › Alerts
   - 데이터: 원격 네트워크 가용성 결함 경고. 매시간 BGPDisconnect · TunnelDisconnect 같은 상태 이벤트를 확인해 만들어집니다
   - 해설: 원격 네트워크(지사)의 IPsec 터널이나 BGP 경로 광고에 문제가 생겼다는 뜻입니다
2. [처리] 경고를 열어 시간과 영향 범위를 확인한다
   - 주체: 관리자
   - 위치: Global Secure Access › Monitor › Alerts (심각도 · 날짜 · 유형으로 필터)
   - 데이터: 경고 시간대 · 영향 원격 네트워크. 보다 넓은 신호는 Entra ID › 모니터링 및 상태 › Health › Health Monitoring 탭의 Global Secure Access requiring remote network tunnel/BGP connectivity 시나리오에서 확인합니다
   - 해설: 먼저 한 곳만 문제인지 여러 곳이 함께 문제인지 범위를 잡습니다
3. [판단] 터널 문제인가, BGP 문제인가?
   - 주체: 관리자
   - 위치: Global Secure Access › Monitor › Remote network health logs
   - 데이터: Status — Tunnel connected · Tunnel disconnected · BGP connected · BGP disconnected · Remote network alive(활성 터널마다 15분 주기)
   - 해설: BGP는 IPsec 터널이 먼저 수립되어야 동작하므로 터널부터 확인합니다
   - 터널 → 4
   - BGP → 5
4. [처리] Tunnel disconnected 이벤트로 CPE와 게이트웨이를 확인한다
   - 주체: 관리자
   - 위치: Remote network health logs › 필터(Remote network ID · Source IP · Destination IP)
   - 데이터: Source IP = CPE의 IP, Destination IP = Microsoft Entra 게이트웨이 IP(이 쌍은 터널마다 고유). Graph: GET /beta/networkAccess/logs/remotenetworks (NetworkAccess-Reports.Read.All 등 권한)
   - 해설: 어느 터널이 언제 끊겼는지를 이벤트 한 줄로 확인합니다
   - 다음 → 6
5. [처리] BGP disconnected와 광고 경로 수 변화를 확인한다
   - 주체: 관리자
   - 위치: Remote network health logs › BGP disconnected 이벤트와 Remote network alive 이벤트의 BGP Routes Advertised Count
   - 데이터: BGP Routes Advertised Count — Tunnel/BGP 연결·끊김 이벤트에서는 0이고 alive 이벤트에서 광고 경로 수가 나옵니다
   - 해설: 경로 수가 평소보다 크게 줄었는지 비교해 BGP 구성 변경이나 장애를 구분합니다
6. [처리] Remote network alive의 송수신 바이트로 영향도를 비교한다
   - 주체: 로그
   - 위치: Remote network health logs › Sent Bytes · Received Bytes(최근 15분)
   - 데이터: 경고 전·중 송수신 바이트 비교. 터널 연결·끊김·BGP 이벤트에서는 0입니다
   - 해설: 트래픽이 실제로 줄었는지 보면 사용자 영향의 크기를 알 수 있습니다
7. [판단] 영향이 한 사이트인가, 여러 사이트인가?
   - 주체: 관리자
   - 데이터: Remote network ID별 이벤트 · Entra Health 시나리오의 영향 원격 네트워크 목록
   - 해설: 한 곳이면 지사 장비(CPE)·회선, 여러 곳이면 서비스 쪽 문제를 의심합니다
   - 단일 사이트 → 8
   - 여러 사이트 → 9
8. [처리] CPE를 점검한다 — 장비 안정성 · 인증 정보 · 회선
   - 주체: 관리자
   - 위치: 지사 CPE(라우터·방화벽) 로그 · ISP 상태
   - 데이터: CPE 안정성 · PSK 또는 인증서 유효성 · ISP·라우팅 변경. 운영 가이드는 터널 flapping(15분 내 상태 변화 3회 초과 같은 시작값)과 1시간 내 반복 끊김(5회 초과)을 점검 신호로 제시합니다 [확인 필요: 임계값은 환경별 기준선으로 대체]
   - 해설: 끊김이 반복되면 장비·인증 정보·회선 순으로 원인을 좁힙니다
   - 다음 → 10
9. [처리] 서비스 쪽 영향으로 보고 Microsoft Entra Health · Service Health를 확인한다
   - 주체: 관리자
   - 위치: Entra ID › 모니터링 및 상태 › Health · Azure Service Health 알림(Global Secure Access 서비스)
   - 데이터: Entra Health 시나리오 알림과 Azure Service Health의 인시던트·계획된 유지 관리 공지
   - 해설: 여러 사이트가 동시에 떨어졌다면 서비스 장애나 공통 회선 문제를 먼저 의심합니다
10. [끝] 복구를 확인한다 — Tunnel connected · BGP connected · 경고 해소
   - 주체: 로그
   - 위치: Remote network health logs · 통합 문서 Remote Network Health
   - 데이터: Tunnel connected / BGP connected 이벤트와 정상 Remote network alive(15분 주기) 확인, 경고 목록에서 해소
   - 해설: 복구 이벤트와 정상 통계가 돌아와야 조치가 끝난 것입니다
- 시나리오: 터널 ▸ 단일 사이트 :: 터널 끊김이 한 사이트라 CPE 장비·인증·회선 점검
- 시나리오: 터널 ▸ 여러 사이트 :: 터널 끊김이 여러 사이트라 Entra Health·서비스 상태 확인
- 시나리오: BGP ▸ 단일 사이트 :: BGP 문제가 한 사이트라 CPE BGP 설정과 경로 수 점검
- 시나리오: BGP ▸ 여러 사이트 :: BGP 문제가 여러 사이트라 서비스 쪽 영향과 공지 확인

> 교육 포인트: 터널과 BGP는 별도 건강 시나리오이지만 BGP는 터널 위에서 동작하므로 터널을 먼저 확인합니다. Source IP/Destination IP 쌍이 터널을 식별하는 열쇠입니다.
>
> 주의: 원격 네트워크 상태 로그가 진단 설정 대상에 나타나기까지 최대 3일이 걸릴 수 있습니다. 임계값(3회·5회 등)은 시작값이며 30일 기준선으로 바꿔야 합니다.

#### L4 · 기준선을 만들고 경고 · 분석 규칙을 정기적으로 점검한다

1. [시작] 운영 주기를 시작한다 — 30일 기준선부터
   - 주체: 관리자
   - 위치: Sentinel › Logs — NetworkAccessTraffic · SigninLogs 쿼리
   - 데이터: 문서는 임계값을 정하기 전에 30일 기준선을 만들고 시작값은 환경 값으로 바꾸라고 안내합니다
   - 해설: 평상시 값을 모르면 경고 임계값이 너무 시끄럽거나 너무 둔해집니다
2. [처리] 공통 기준선 쿼리를 돌려 지표를 기록한다
   - 주체: 관리자
   - 위치: Sentinel › Logs — NetworkAccessTraffic 최근 30일 요약
   - 데이터: 일별 세션 수 · 차단 세션 비율 · 고유 사용자 · 송수신 바이트 · TLS 검사 실패율 · 위협 인텔리전스 일치 수(TrafficType별)
   - 해설: 서비스 업데이트나 큰 정책 변경 뒤에는 기준선을 다시 만들고, 최소 분기마다 다시 돌립니다
3. [처리] 내장 신호를 먼저 본다 — Alerts · Deployment logs · Entra Health
   - 주체: 관리자
   - 위치: Global Secure Access › Monitor › Alerts · Deployment logs · Entra ID › 모니터링 및 상태 › Health
   - 데이터: 내장 경고와 구성 배포 상태. 운영 가이드는 사용자 지정 Sentinel 규칙을 켜기 전에 이 내장 신호를 먼저 보라고 안내합니다
   - 해설: 사용자 지정 규칙은 내장 신호를 보완하는 용도입니다
4. [처리] Sentinel 분석 규칙을 켜고 시작값을 조정한다
   - 주체: 관리자
   - 위치: Sentinel › Analytics — Global Secure Access 솔루션의 분석 규칙 7개
   - 데이터: TI Domain/IP/URL Entity Match(Medium) · Abnormal Deny Rate(5일 기준선 학습) · Protocol Changes for Destination Ports · Source IP Scanning Multiple Open Ports(30초에 포트 100개 이상) · Connections Outside Operational Hours(오전 8시 이전·오후 6시 이후, High)
   - 해설: 영업시간 같은 조건은 조직 환경에 맞게 바꿔야 오탐이 줄어듭니다
5. [판단] 어떤 경고 유형인가 — Token/Device Inconsistency인가?
   - 주체: 관리자
   - 위치: NetworkAccessAlerts · Monitor › Alerts
   - 데이터: AlertType · 심각도. Token/Device Inconsistency는 기준선이 0이며 발생 즉시 Critical로 다루라고 안내됩니다
   - 해설: 토큰 도용을 시사하는 경고는 일반 경고보다 먼저 처리합니다
   - Token/Device 불일치 → 6
   - 그 밖의 경고 → 7
6. [처리] Critical로 처리 — 로그인 로그와 ID 보호로 교차 확인
   - 주체: 관리자
   - 위치: SigninLogs(TokenIssuerType) · Microsoft Entra ID Protection · IR 플레이북
   - 데이터: 같은 토큰이 둘 이상의 기기에서 사용됨. 문서는 MITRE T1528 / T1550을 연결해 안내합니다
   - 해설: 토큰 도용 여부를 로그인 로그와 위험 신호로 확인하고 사고 대응 절차로 넘깁니다
   - 다음 → 8
7. [처리] 기준선과 비교해 판단한다 — External Tenant · 컴플라이언트 네트워크 우회
   - 주체: 관리자
   - 위치: NetworkAccessAlerts · SigninLogs(IsThroughGlobalSecureAccess == "false")
   - 데이터: Increased External Tenant Activity(14일 슬라이딩 윈도우, High)는 SigninLogs 교차 테넌트 이벤트와 B2B·교차 테넌트 접근 설정으로 확인. 성공 로그인인데 IsThroughGlobalSecureAccess가 false면 컴플라이언트 네트워크 우회(High)로 봅니다
   - 해설: 기준선보다 증가했는지, 정말 GSA를 우회했는지 로그인 로그로 확인합니다
8. [처리] 트래픽 하트비트로 로그가 끊겼는지 감시한다
   - 주체: 관리자
   - 위치: Sentinel › Analytics — Global Secure Access - Traffic heartbeat (anti-tamper)
   - 데이터: 15분마다 최근 1시간 볼륨을 7일 롤링 기준선과 비교해 Critical/High/Medium 심각도로 구분. 프로필 비활성화·삭제, 진단 설정 제거, 플랫폼 장애, 테넌트 오프보딩의 결과를 잡습니다
   - 해설: 오프보딩은 감사 로그에 남지 않으므로 "트래픽이 갑자기 줄었는가"로 감시합니다
9. [처리] 튜닝 주기를 지킨다 — 주간 · 월간 · 분기
   - 주체: 관리자
   - 위치: 운영 점검 일정(SOC 분석가 · 네트워크 보안 엔지니어)
   - 데이터: 오탐률 검토 주 1회, 임계값 조정 월 1회, 용량 기준선 재실행 분기 1회(또는 서비스 업데이트 후), 변경 승인자 허용 목록은 역할 변경 때마다 갱신
   - 해설: 정기 점검이 없으면 기준선이 낡아 오탐이 늘어납니다
10. [끝] 정기 보고로 마무리한다
   - 주체: 관리자
   - 위치: 대시보드 · 통합 문서 · Sentinel 인시던트 요약
   - 데이터: 운영팀 주간(경고 요약 · 상태 점검) · 서비스 소유자 월간(가용성·보안 효과) · 보안 리더십 분기 보고
   - 해설: 대시보드 수치와 경고 이력을 대상별 주기로 보고합니다
- 시나리오: Token/Device 불일치 :: 토큰 불일치는 Critical로 로그인 로그와 ID 보호 확인
- 시나리오: 그 밖의 경고 :: 기준선과 비교해 증가 여부와 GSA 우회를 확인

> 교육 포인트: 기준선 → 내장 신호 → 사용자 지정 규칙 → 튜닝 순서입니다. 문서의 임계값은 모두 "시작값"이므로 내 환경의 30일 기준선으로 바꿔야 합니다.
>
> 주의: 분석 규칙의 영업시간(오전 8시·오후 6시) 등은 예시 값이며, 일부 기능(Gen AI 로그 · 연결 로그)은 미리 보기입니다 [확인 필요: 미리 보기 · 조직별 값]
