### L3 · C · 매칭 · 오류 — Source Anchor · 소프트 매치 · 중복 속성

#### L4 · 내보낸 개체를 기존 Entra 개체와 맞추고 충돌을 처리한다

1. [시작] 새 개체가 sourceAnchor와 함께 Entra로 도착
   - 주체: Entra ID
   - 데이터: sourceAnchor = ms-DS-ConsistencyGuid 또는 objectGUID의 Base64 → 클라우드 immutableId
   - 해설: Entra는 이 값을 이미 있는 개체의 식별자와 비교합니다. 사용자가 아닌 개체는 objectGUID를 씁니다.
2. [판단] sourceAnchor가 기존 개체의 immutableId와 같은가?
   - 주체: Entra ID
   - 위치: GET /v1.0/users/{id}?$select=onPremisesImmutableId
   - 데이터: user.onPremisesImmutableId (하드 매치)
   - 해설: 공식 문서의 평가 순서는 sourceAnchor(ImmutableId) 일치를 먼저 보고, 없으면 UPN·기본 SMTP로 소프트 매치를 시도하며, 둘 다 없을 때 신규 개체를 만듭니다. 하드 매치는 클라우드 개체의 ImmutableId와 AD의 ms-DS-ConsistencyGuid를 미리 맞춰 둔 경우에만 일치하는 의도적인 방법이라, 이 보드의 기본 시나리오는 소프트 매치로 보여 주고 하드 매치는 필요할 때 쓰는 두 번째 시나리오로 둡니다. 두 방식 모두 기존 클라우드 계정을 인수할 때만 필요하므로 평소에는 차단해 두는 것이 권장됩니다.
   - 예 → 3
   - 아니오 → 4
3. [처리] 하드 매치 — 기존 개체를 AD 개체와 연결
   - 주체: Entra ID
   - 위치: 하드 매치 차단 옵션은 Graph PowerShell — Update-MgDirectoryOnPremiseSynchronization (Features.BlockCloudObjectTakeoverThroughHardMatchEnabled, 권한 OnPremDirectorySynchronization.ReadWrite.All)
   - 데이터: 동기화 소유로 전환 · onPremisesSyncEnabled = true · AD에 값이 있는 클라우드 속성은 AD 값으로 덮어씀 · 2026년 7월 1일부터 대상 클라우드 계정이 이미 onPremisesObjectIdentifier를 갖고 있거나 권한 있는 Entra 역할을 할당·적격으로 가지면 하드 매치가 차단될 수 있음(InvalidHardMatch 오류)
   - 해설: 서버를 새로 만들어도 같은 anchor면 기존 개체가 그대로 이어집니다. 하드 매치를 일반적인 복구 수단으로 쓰면 잘못된 온프레미스 개체에 소유권이 넘어갈 수 있고, 클라우드 계정을 가로채는 경로가 되지 않도록 매칭이 끝나면 차단 옵션을 다시 켭니다.
   - 다음 → 7
4. [판단] UPN 또는 기본 SMTP가 기존 개체와 같은가?
   - 주체: Entra ID
   - 위치: Graph PowerShell — Update-MgDirectoryOnPremiseSynchronization (Features.BlockSoftMatchEnabled)
   - 데이터: userPrincipalName · proxyAddresses 중 "SMTP:" 기본 주소 (소프트 매치)
   - 해설: 새 개체에 대해서만 소프트 매치를 평가하며 기존 개체를 고쳐서는 맞추지 않습니다. 클라우드 계정을 AD 계정으로 인수할 일이 없다면 소프트 매치 차단을 켜 두는 것이 권장됩니다.
   - 예 → 5
   - 아니오 → 6
5. [처리] 소프트 매치 — 기존 클라우드 사용자에 연결
   - 주체: Entra ID
   - 데이터: 기존 클라우드 user에 anchor 기록 (관리자 계정과의 소프트 매치는 권장하지 않음) · AD 값이 클라우드 값을 덮어쓰고 PHS를 쓰면 클라우드 암호 해시도 AD 해시로 덮임
   - 해설: 클라우드에서 먼저 만든 같은 사람 계정이 AD 계정과 합쳐집니다. Microsoft 365에서만 관리하던 이메일 같은 값은 AD에 없으면 사라지므로 합치기 전에 AD 값을 채웁니다. 소프트 매치로 붙은 뒤에는 anchor가 기록되어 이후에는 하드 매치로 이어집니다.
   - 다음 → 7
6. [처리] 신규 개체 생성
   - 주체: Entra ID
   - 데이터: 새 user · onPremisesImmutableId 기록
   - 해설: 어디에도 일치하지 않으면 새 사용자로 만들어집니다.
7. [판단] UPN · ProxyAddress 고유성을 지키는가?
   - 주체: Entra ID
   - 데이터: UPN · SMTP ProxyAddress는 테넌트의 사용자·그룹·연락처 전체에서 고유해야 함(UPN은 사용자만 해당) · 중복 속성 복원력은 모든 테넌트에서 기본으로 켜져 있고 끌 수 없음
   - 해설: 중복이면 속성을 격리해 개체 생성이 막히지 않게 합니다. 필수 속성인 UPN은 대신 임시 값을 부여하고 ProxyAddress는 충돌 값만 격리합니다.
   - 예 → 8
   - 아니오 → [차단] 중복 속성 격리 — UPN은 임시 onmicrosoft.com 값으로 대체
8. [끝] 오류 확인 — onPremisesProvisioningErrors
   - 주체: 로그
   - 위치: GET /v1.0/users/{id}?$select=onPremisesProvisioningErrors,onPremisesImmutableId · Entra PowerShell Get-EntraDirectoryObjectOnPremisesProvisioningError (Connect-Entra 후) · Connect: 동기화 서비스 관리자 · Cloud Sync: 구성 › 로그
   - 데이터: onPremisesProvisioningErrors · DirSyncProvisioningErrors · AttributeValueMustBeUnique 등 (AttributeConflictName = OnPremiseSecurityIdentifier 또는 ProxyAddresses)
   - 해설: 충돌 원인은 개체의 오류 속성과 동기화 도구 로그에서 확인합니다. 같은 사람을 다시 프로비전하는 충돌이면 AD 사용자의 ms-DS-ConsistencyGuid를 기존 클라우드 사용자의 ImmutableId와 같게 맞춰 하드 매치되게 합니다.
- 시나리오: 아니오 ▸ 예 ▸ 예 :: 소프트 매치 후 충돌 없이 연결
- 시나리오: 예 ▸ 예 :: 하드 매치 후 충돌 없이 연결
- 시나리오: 아니오 ▸ 아니오 ▸ 예 :: 신규 개체를 만들고 충돌 없이 완료
- 시나리오: 아니오 ▸ 예 ▸ 아니오 :: 소프트 매치 후 중복 속성 격리로 차단
- 시나리오: 예 ▸ 아니오 :: 하드 매치 후 중복 속성 격리로 동기화 차단
- 시나리오: 아니오 ▸ 아니오 ▸ 아니오 :: 신규 개체 생성 후 중복 속성 격리로 차단

> 교육 포인트: sourceAnchor는 개체 수명 동안 바뀌면 안 되는 값입니다. 서버를 재구축해도 같은 값을 쓰면 기존 개체와 다시 연결됩니다.
>
> 주의: 이미 내보낸 개체의 sourceAnchor를 바꾸면 Connect Sync가 그 개체의 추가 변경을 막습니다. 격리된 중복 속성은 충돌이 해소되면 자동으로 격리가 풀리며, Entra는 1시간 주기의 백그라운드 작업으로 이를 확인합니다.
