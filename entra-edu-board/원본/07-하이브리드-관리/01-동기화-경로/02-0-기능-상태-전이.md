### L3 · 0 · 기능 상태 전이 — 온프레미스 전용 → 동기화 구성 → 개체 반영

#### L4 · ⓪ 비활성 — AD 개체가 Entra에 없다

1. [시작] 온프레미스 AD에서 사용자 생성
   - 주체: 관리자
   - 위치: Active Directory 사용자 및 컴퓨터 · New-ADUser
   - 데이터: AD user (objectGUID · userPrincipalName · sAMAccountName · mail · proxyAddresses)
   - 해설: AD에 사용자를 만듭니다. UPN 접미사가 라우팅되지 않는 도메인이면 Entra에서 확인할 수 없어 나중에 Alternate login ID 같은 별도 구성이 필요합니다.
2. [처리] 동기화 도구가 없어 Entra로 가는 경로 없음
   - 주체: 온프레미스
   - 위치: Entra ID › Entra Connect › Connect Sync · Cloud Sync (구성이 비어 있음)
   - 데이터: AD 변경이 Entra로 전달되지 않음 · onPremisesSyncEnabled = true인 개체가 없음
   - 해설: 동기화가 없으니 클라우드 쪽은 AD의 변화를 알지 못합니다.
3. [판단] 같은 사람의 클라우드 전용 계정이 이미 있는가?
   - 주체: 관리자
   - 위치: ID › 사용자 › 모든 사용자 (UPN 검색)
   - 데이터: 클라우드 user의 userPrincipalName · mail · proxyAddresses 중 기본 SMTP 주소
   - 해설: 나중에 동기화를 켜면 UPN이나 기본 SMTP가 같은 계정이 소프트 매치로 AD 계정에 합쳐지고, 이때 AD에 값이 있는 클라우드 속성은 AD 값으로 덮어써집니다. 기존 관리자 계정과의 매칭은 특히 권장되지 않습니다.
   - 예 → [차단] 계정 이원화 — 같은 사람의 계정이 두 개로 나뉨
   - 아니오 → 4
4. [처리] Entra 사용자 목록에 개체가 없음
   - 주체: Entra ID
   - 위치: ID › 사용자 › 모든 사용자 (검색 결과 없음)
   - 데이터: GET /v1.0/users/{upn} → 404
   - 해설: 라이선스, 그룹, CA 대상으로 지정할 개체가 없습니다.
5. [끝] 클라우드 로그인 · 라이선스 할당 불가
   - 주체: 로그
   - 데이터: SigninLogs에 해당 사용자 없음
   - 해설: Microsoft 365 같은 클라우드 서비스를 쓸 수 없고 Entra 쪽에 개체가 없어 사용자·그룹 기반 정책의 대상도 될 수 없습니다.
- 시나리오: 예 :: 같은 사람의 클라우드 계정이 있어 계정 이원화
- 시나리오: 아니오 :: 클라우드 계정도 없어 로그인·라이선스 불가

#### L4 · ① 구성 — Connect Sync 또는 Cloud Sync를 구성한다

1. [시작] 동기화 도구를 선택
   - 주체: 관리자
   - 위치: 하이브리드 관리 › Microsoft Entra Connect › Connect Sync 또는 Cloud Sync (Entra ID › Entra Connect)
   - 데이터: 요구 비교 — 분리된(연결되지 않은) 여러 포리스트 · 다중 활성 에이전트 · 온디맨드 프로비전 · AD로의 그룹 프로비저닝은 Cloud Sync만 지원 / 고급 동기화 규칙 · 속성 기반 필터링 · 포리스트 간 참조 · 여러 도메인 속성 병합 · PTA·AD FS 구성은 Connect Sync만 지원 / 규모: Cloud Sync는 도메인당 150,000개 개체 · 그룹 멤버 50,000명, Connect Sync는 그룹 멤버 250,000명
   - 해설: 환경과 요구에 맞는 도구를 고릅니다. Microsoft는 새 기능이 Cloud Sync 중심으로 개발된다고 안내하며 대부분의 조직에 권장되는 방향이지만, 요구가 위 목록에 걸리면 Connect Sync를 유지합니다.
2. [판단] 어느 도구를 쓰는가?
   - 주체: 관리자
   - 위치: 하이브리드 관리 › Microsoft Entra Connect › Connect Sync · Cloud Sync
   - 데이터: 지원 토폴로지 · 필요한 사용자 지정 수준 · 두 도구 모두 Seamless SSO · PHS · 암호 쓰기 저장 · 디바이스 동기화(하이브리드 조인용)를 지원
   - 해설: 두 도구는 구성 위치와 방식이 완전히 다릅니다. Connect Sync는 사내 서버에, Cloud Sync는 구성을 클라우드에 두고 사내에는 경량 에이전트만 둡니다.
   - Connect Sync → 3
   - Cloud Sync → 6
3. [처리] Connect Sync 설치 + Source Anchor 선택
   - 주체: 관리자
   - 위치: Microsoft Entra Connect 설치 마법사 › 사용자 지정 설치 › Identifying users 페이지 › Let Azure manage the source anchor 또는 Choose a specific attribute
   - 데이터: sourceAnchor — 사용자는 ms-DS-ConsistencyGuid(1.1.524.0 이상, 비어 있으면 objectGUID 값을 AD에 기록하므로 연결 계정에 쓰기 권한 필요), 그 밖의 개체는 objectGUID · 설치 후 변경 불가, 바꾸려면 재설치 · 60자 미만, @ 등 특수문자 불가(그래서 UPN·mail 선택 불가), 대소문자 구분
   - 해설: 개체를 평생 식별할 특성을 설치 때 정하며 나중에 바꿀 수 없습니다. 서버를 추가하거나 재구축할 때는 반드시 같은 sourceAnchor를 선택해야 하고, 설치에는 Hybrid Identity Administrator가 필요합니다.
4. [처리] 동기화 범위 필터링 — 도메인 · OU · 그룹
   - 주체: 관리자
   - 위치: 설치 마법사 › Domain and OU filtering · Sync filtering based on groups (파일럿용) · 설치 후에는 시작 메뉴 › Synchronization Rules Editor (범위 지정 필터)
   - 데이터: 포함할 OU 목록 · 범위 필터 규칙 · 기본은 모든 도메인·OU 동기화 · OU 필터가 그룹 필터보다 먼저 평가됨 · 그룹 필터는 직접 멤버만 인식하고 중첩 그룹은 풀지 않음
   - 해설: 어떤 개체를 Entra로 보낼지 범위를 정합니다. 그룹 기반 필터는 파일럿 전용이며 운영 배포에는 OU·도메인 또는 속성 기반 필터를 씁니다. 필터를 바꾼 뒤에는 전체 가져오기가 필요합니다.
5. [처리] 로그인 방식 선택 — "인증 경로" 참조
   - 주체: 관리자
   - 위치: 설치 마법사 › 사용자 로그인 (암호 해시 동기화 · 통과 인증 · 페더레이션)
   - 데이터: 로그인 방식 선택값 — Password hash synchronization · Pass-through authentication · Federation with AD FS · Federation with PingFederate · Do not configure · Enable single sign-on(PHS 또는 PTA 선택 시에만)
   - 해설: 암호를 어디서 검증할지는 다음 기능에서 자세히 다룹니다. 이 선택은 동기화 도구와 별개의 결정입니다.
   - 다음 → 9
6. [처리] Cloud Sync 프로비전 에이전트 설치
   - 주체: 관리자
   - 위치: Entra ID › Entra Connect › Cloud sync › Agents › Download on-premises agent › Accept terms & download → AADConnectProvisioningAgentSetup.exe 실행 (Hybrid Identity Administrator, 게스트 불가)
   - 데이터: 에이전트 서버 — 도메인에 가입된 Windows Server 2016 이상(2022·2025 권장, Server Core 불가) · RAM 4GB 이상 · .NET 4.7.1+ · TLS 1.2 · 도메인 컨트롤러 설치도 지원하지만 Tier 0 서버로 취급 · 서비스 계정은 gMSA(기본 provAgentgMSA$, 생성 시 도메인 관리자 자격 필요) · DC와 TCP 389·3268 통신 · 아웃바운드 443(선택 8080)만 필요 · AD 스키마에 msDS-ExternalDirectoryObjectId(Windows Server 2016 이상) 필요
   - 해설: 사내에는 경량 에이전트만 두고 구성은 클라우드에 둡니다. 가용성을 위해 에이전트를 여러 대 설치할 수 있습니다.
7. [처리] 새 구성 만들기 — AD에서 Microsoft Entra ID로 동기화
   - 주체: 관리자
   - 위치: Cloud sync › 새 구성 (New configuration) › AD to Microsoft Entra ID sync › 도메인 선택 · 암호 해시 동기화 사용 여부 › 만들기 (Create)
   - 데이터: 동기화 구성 (도메인 · PHS 사용 여부) · 구성 화면은 Add scoping filters · Map attributes · Test · View default properties · Enable your configuration 다섯 단계
   - 해설: 구성은 Entra에 저장되어 어디서든 관리할 수 있습니다. 구성을 삭제할 때는 확인 창이 없으므로 주의합니다.
8. [처리] 범위 필터 · 속성 매핑 · 테스트
   - 주체: 관리자
   - 위치: 구성 › Scoping filters (All users · Selected security groups · Selected organizational units, 그룹·OU는 DN 입력 후 Add) · Attribute mapping · Test (On-demand provisioning)
   - 데이터: 범위 필터 · 속성 매핑 · 단일 사용자(또는 그룹) 시험 결과 · 보안 그룹 범위는 중첩 그룹을 포함하지 않고 대형 그룹에는 한계가 있어 파일럿에만 권장 · 기본 범위에서 IsCriticalSystemObject = TRUE인 개체는 제외
   - 해설: 단일 사용자로 시험한 뒤에 전체에 켭니다. 범위를 바꾼 뒤에는 Restart sync로 즉시 반영합니다.
9. [끝] 초기 동기화 — 범위 안 개체가 처음 생성
   - 주체: Entra ID
   - 위치: Connect: 구성 완료 후 초기 동기화 · Cloud Sync: 구성 › 구성 사용 (Enable configuration)
   - 데이터: Entra ID에 user · group 개체 생성 (onPremisesSyncEnabled = true)
   - 해설: 범위 안의 AD 개체가 Entra에 처음 만들어집니다. Connect Sync는 스테이징 모드 서버라면 가져오기와 동기화만 하고 내보내기는 하지 않습니다.
- 시나리오: Connect Sync :: Connect Sync로 구성해 초기 동기화
- 시나리오: Cloud Sync :: Cloud Sync로 구성해 초기 동기화

#### L4 · ② 활성 — AD 변경이 Entra에 반영된다

1. [시작] AD 개체 변경 — 생성 · 수정 · 삭제
   - 주체: 온프레미스
   - 위치: Active Directory 사용자 및 컴퓨터
   - 데이터: AD 개체의 속성 변경 · 범위 필터 안에 있는 개체만 동기화 대상
   - 해설: AD에서 변경이 일어납니다.
2. [판단] 어느 도구가 동기화하는가?
   - 주체: Entra ID
   - 위치: Entra ID › Entra Connect › Connect Sync · Cloud Sync
   - 데이터: 구성된 동기화 도구
   - 해설: 도구마다 변경을 가져가는 방식이 다릅니다. Connect Sync는 사내 서버가 주기적으로 끌어오고 Cloud Sync는 클라우드 서비스가 에이전트에 요청합니다.
   - Connect Sync → 3
   - Cloud Sync → 4
3. [처리] Connect Sync — 주기마다 가져오기 · 동기화 · 내보내기
   - 주체: 온프레미스
   - 위치: Connect 서버 PowerShell — Get-ADSyncScheduler · Start-ADSyncSyncCycle -PolicyType Delta (즉시 실행)
   - 데이터: 기본 30분 주기 (세부는 L3 A) · 델타 주기 = 델타 가져오기 → 델타 동기화 → 내보내기
   - 해설: 사내 동기화 서버가 변경을 가져와 규칙을 거쳐 내보냅니다. AD 변경이 Entra에 보이기까지 최대 한 주기(기본 30분 안팎)가 걸립니다.
   - 다음 → 5
4. [처리] Cloud Sync — 서비스가 약 2분 주기로 에이전트에 요청
   - 주체: Entra ID
   - 위치: Entra ID › Entra Connect › Cloud sync › {구성} (Restart sync로 즉시 실행 가능)
   - 데이터: SCIM 요청 · 워터마크 이후 변경 (세부는 L3 B)
   - 해설: 클라우드 서비스가 에이전트에게 변경분을 요청해 가져옵니다.
5. [처리] 범위 필터와 속성 규칙 적용
   - 주체: Entra ID
   - 위치: Connect: Synchronization Rules Editor · Cloud Sync: 구성 › Scoping filters · Attribute mapping
   - 데이터: 범위 밖 개체 제외 · 속성 변환 규칙 · Cloud Sync 프로비전 로그에는 범위 밖 개체가 Status = Skipped로 남음
   - 해설: 범위 밖 개체는 제외되고 속성은 규칙대로 변환됩니다.
6. [처리] Source Anchor로 Entra 개체와 매칭
   - 주체: Entra ID
   - 데이터: sourceAnchor ↔ user.onPremisesImmutableId (세부는 L3 C) · 매칭은 새로 들어오는 개체에 대해서만 평가
   - 해설: 같은 개체로 매칭되면 갱신하고 없으면 새로 만듭니다.
7. [판단] Entra가 변경을 수락하는가?
   - 주체: Entra ID
   - 데이터: UPN · ProxyAddress 고유성 · 속성 검증
   - 해설: 충돌이나 검증 실패는 해당 개체만 오류로 기록됩니다. UPN과 SMTP ProxyAddress 중복은 중복 속성 복원력 기능 덕분에 개체 생성을 막지 않고 충돌 속성만 격리합니다.
   - 예 → 8
   - 아니오 → [차단] 오류 기록 — 충돌·검증 실패, 해당 개체만 보류
8. [끝] 동기화 결과 기록
   - 주체: 로그
   - 위치: GET /v1.0/users/{id}?$select=onPremisesLastSyncDateTime,onPremisesProvisioningErrors · Connect: 동기화 서비스 관리자 › 작업 · Cloud Sync: 구성 › 로그
   - 데이터: user.onPremisesLastSyncDateTime · onPremisesProvisioningErrors
   - 해설: 마지막 동기화 시각과 오류가 개체에 남습니다.
- 시나리오: Connect Sync ▸ 예 :: Connect Sync가 변경을 수락해 결과 기록
- 시나리오: Connect Sync ▸ 아니오 :: Connect Sync에서 Entra가 거부해 오류
- 시나리오: Cloud Sync ▸ 예 :: Cloud Sync가 변경을 수락해 결과 기록
- 시나리오: Cloud Sync ▸ 아니오 :: Cloud Sync에서 Entra가 거부해 오류

> 교육 포인트: 인증 방식(PHS·PTA·페더레이션)의 선택은 동기화 도구와 별개입니다. "인증 경로"에서 이어서 다룹니다.
>
> 주의: Cloud Sync는 도메인당 약 15만 개체, 그룹 멤버 5만 명까지 지원하고 PTA·AD FS 구성이나 고급 동기화 규칙은 지원하지 않습니다. 분리된 여러 포리스트는 Cloud Sync만 지원하며 이 비교는 변경될 수 있어 도입 시점에 최신 문서를 확인합니다.
