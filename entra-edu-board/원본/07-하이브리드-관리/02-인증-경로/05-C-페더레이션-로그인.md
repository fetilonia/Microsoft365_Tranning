### L3 · C · 페더레이션 로그인 — AD FS 위임 · SSO · 클레임

#### L4 · 구성 요소와 구역 — Entra 신뢰, AD FS 팜, 프런트엔드(WAP · 어플라이언스) 선택, DC

1. [시작] 도메인이 페더레이션으로 확인된 테넌트
   - 주체: Entra ID
   - 위치: 구역 ① 클라우드 — Entra ID 도메인 페더레이션 설정 (Entra 관리 센터 › 도메인 이름 · Graph: GET /v1.0/domains/{도메인}/federationConfiguration)
   - 데이터: 페더레이션 설정 속성 — passiveSignInUri(AuthURL) · issuerUri · signingCertificate · nextSigningCertificate · federatedIdpMfaBehavior · preferredAuthenticationProtocol
   - 해설: 도메인을 페더레이션으로 두면 Entra는 그 도메인 사용자의 암호를 직접 받지 않고 신뢰하는 AD FS(IdP)에 인증을 위임하며, AD FS가 서명한 토큰만 믿습니다
2. [처리] Entra ID 쪽 신뢰 대상 — AD FS의 신뢰 당사자 트러스트
   - 주체: AD FS
   - 위치: 구역 ④ AD FS 팜 — AD FS 관리 › 신뢰 당사자 트러스트 › Microsoft Office 365 Identity Platform
   - 데이터: Entra Connect가 관리하는 트러스트 설정 — 토큰 서명 인증서와 알고리즘(SHA-256 권장) · 트러스트 식별자 · Entra 엔드포인트 · 발급 변환 규칙 · 대체 ID · 자동 메타데이터 업데이트 · 다른 신뢰 당사자 트러스트는 Connect가 바꾸지 않음
   - 해설: AD FS 입장에서 Entra는 하나의 신뢰 당사자입니다. 이 트러스트에 어떤 규칙과 인증서가 있는지가 로그인 성공을 좌우하므로 Connect가 이를 관리하게 두는 것이 권장됩니다
3. [처리] AD FS 앞단에 둘 수 있는 프런트엔드가 놓이는 구역 (선택 구성)
   - 주체: WAP (DMZ)
   - 위치: 구역 ② DMZ(경계) — AD FS 로그인 URL의 요청을 받아 AD FS로 중계하는 프런트엔드가 놓이는 자리
   - 데이터: 프런트엔드를 두면 클라이언트 ↔ 프런트엔드와 프런트엔드 ↔ AD FS 사이 방화벽에 TCP 443 인바운드(사용자 인증서 로그인이 443이 아니면 49443) · 프런트엔드는 AD FS 팜(내부망)과만 통신하고 DC에는 직접 가지 않음 · 프런트엔드가 AD FS 서비스 이름을 AD FS 로드 밸런서로 해석할 수 있어야 함(DMZ 전용 DNS 또는 HOSTS) · 프런트엔드는 요청을 중계하면서 x-ms-proxy 정보를 AD FS에 전달
   - 해설: 프런트엔드는 AD FS의 필수 구성 요소가 아니라 접근 경로 설계에 따라 두는 선택 요소입니다. 프록시는 토큰 서명 개인 키를 갖지 않아 경계망에 적합하며, 인터넷에서 오는 요청으로부터 AD FS 엔드포인트와 키를 격리합니다
4. [판단] 요청이 프런트엔드(WAP · 어플라이언스)를 거쳐 AD FS에 도달하게 설계했는가?
   - 주체: 관리자
   - 위치: 접근 경로 설계 — 외부(extranet) 접근에는 프런트엔드 배포가 필수 · 내부 DNS가 AD FS 서비스 이름을 AD FS 서버(또는 로드 밸런서)로 해석하면 내부 클라이언트는 직접 접속
   - 데이터: 경유 = 외부·내부 모두 프런트엔드를 지나고 AD FS는 모든 요청을 프록시를 거친 엑스트라넷 요청으로 취급 · 직접 = 회사망 클라이언트만 AD FS 팜에 직접 접속하고 AD FS가 프록시 기능을 겸함(외부 사용자는 로그인 불가)
   - 해설: 공식 문서는 외부 접근에는 프런트엔드를 요구하지만 내부 사용자까지 거치게 할지는 요구하지 않습니다. 이 선택이 이후 인증 방법(엑스트라넷·인트라넷 정책)과 보호 기능을 가릅니다
   - 프런트엔드 경유 → 5
   - 직접 접속 → 8
5. [판단] 프런트엔드를 무엇으로 구성했는가?
   - 주체: 관리자
   - 위치: 구역 ② DMZ — Windows Server Remote Access 역할(Web Application Proxy) 또는 서드파티 네트워크 어플라이언스
   - 데이터: WAP 서버 = Windows Server의 Web Application Proxy(AD FS 프록시 겸 리버스 프록시) · 어플라이언스 = 서드파티 프록시가 AD FS 앞에 놓이려면 WAP 대신 쓸 수 있도록 MS-ADFSPIP 프로토콜을 지원해야 함 (문서가 알려진 예로 F5 Access Policy Manager · Citrix ADC 제시)
   - 해설: 프런트엔드는 WAP 서버일 수도 있고 별도의 네트워크 어플라이언스일 수도 있습니다. 어느 쪽이든 AD FS와의 관계와 로그인 흐름의 구조는 같습니다
   - WAP 서버 → 6
   - 어플라이언스 → 7
6. [처리] WAP 서버가 프런트엔드를 호스팅
   - 주체: WAP (DMZ)
   - 위치: Web Application Proxy 서버 (Windows Server 원격 액세스 역할) — AD FS 팜에 프록시로 등록(신뢰 인증서 사용)
   - 데이터: WAP는 AD FS 인증 요청을 안전하게 AD FS로 프록시하고, 소프트 엑스트라넷 계정 잠금 같은 기능은 WAP 사용이 필요 · WAP도 이중화(여러 대 + 로드 밸런서)
   - 해설: Microsoft가 제공하는 기본 프런트엔드입니다. AD FS 프록시 용도만이면 WAP 서버는 도메인 멤버이거나 워크그룹이어도 됩니다. 도메인 가입이 필요한 경우는 Kerberos 제한 위임(KCD)으로 Windows 통합 인증 앱을 게시할 때입니다(AD FS 프록시 기능이 아니라 앱 게시 기능)
   - 다음 → 9
7. [처리] 네트워크 어플라이언스가 프런트엔드를 호스팅
   - 주체: WAP (DMZ)
   - 위치: 서드파티 리버스 프록시 · ADC (예: F5 APM, Citrix ADC) — AD FS 프록시 역할(MS-ADFSPIP) 지원
   - 데이터: MS-ADFSPIP를 지원하지 않는 프록시는 WAP 대신 쓸 수 없음 · 어플라이언스가 WAP를 대체하는 경우(MS-ADFSPIP 구현)와 WAP 앞단에 놓이는 방화벽·로드 밸런서·WAF는 다름 · WAP 앞단에서 SSL을 종단하는 장비는 비권장(X-MS-Forwarded-Client-IP에 클라이언트가 아닌 앞단 장비 IP가 들어가 IP 기반 보호가 왜곡됨)
   - 해설: WAP를 대체하는 어플라이언스는 WAP와 같은 자리(DMZ)에서 같은 일을 합니다. 지원 여부와 구성은 제조사 문서를 따르고, 단순 L7 장비를 WAP 앞에 두는 구성은 SSL 종단 없이 통과시키는 방식만 지원됩니다
   - 다음 → 9
8. [처리] 프런트엔드 없이 AD FS 팜에 직접 접속 (내부망 전용)
   - 주체: AD FS
   - 위치: 구역 ④ 내부망 — 내부 DNS가 AD FS 서비스 이름을 AD FS 서버(또는 로드 밸런서)로 해석
   - 데이터: AD FS가 직접 받은 요청은 x-ms-proxy 값이 없고 insidecorporatenetwork = True로 내부 요청으로 구분 · 인트라넷 인증 정책(예: Windows 통합 인증) 적용 · 이 설계만으로는 회사망 밖 사용자의 로그인이 불가(외부 접근에는 프런트엔드 필요)
   - 해설: 회사망 클라이언트는 federation server에 직접 통신할 수 있고, 이때 AD FS가 프록시 기능도 겸합니다. 외부 접근이 필요 없는 환경에서 쓰는 단순한 구성입니다
9. [끝] 접근 경로가 정해져 요청을 받을 준비 완료
   - 주체: AD FS
   - 데이터: 이후 단계 — 인증 · SSO 쿠키 · 토큰 발급 · Entra 검증 (다음 시나리오)
   - 해설: 구역은 클라우드(Entra) · DMZ(프런트엔드, 선택) · 내부망(AD FS, DC)입니다. 로그인 한 번에 브라우저가 Entra → (프런트엔드) → AD FS → Entra 순으로 이동합니다
- 시나리오: 프런트엔드 경유 ▸ WAP 서버 :: WAP 서버가 AD FS 앞단 프런트엔드를 호스팅
- 시나리오: 프런트엔드 경유 ▸ 어플라이언스 :: MS-ADFSPIP 지원 어플라이언스가 프런트엔드 호스팅
- 시나리오: 직접 접속 :: 프런트엔드 없이 내부망에서 AD FS에 직접 접속

> 교육 포인트: 프런트엔드(WAP 또는 MS-ADFSPIP 어플라이언스)는 외부 접근에는 필수이지만 내부 사용자까지 거치게 할지는 설계 선택입니다. 선택에 따라 AD FS가 요청을 엑스트라넷 또는 인트라넷으로 구분하고 인증 정책이 달라집니다.
>
> 주의: 프런트엔드는 DC로 가는 경로를 열지 않고 AD FS 팜과만 통신합니다. 프런트엔드를 쓰는 환경에서 프런트엔드가 중단되면 AD FS가 살아 있어도 해당 경로의 로그인이 실패하므로 이중화합니다.

#### L4 · 전체 흐름 — Entra가 인증을 AD FS에 넘기고 토큰을 받는다

1. [시작] 사용자가 UPN 입력
   - 주체: 사용자
   - 위치: Entra 로그인 페이지 (login.microsoftonline.com) › 사용자 이름 입력
   - 데이터: UPN의 접미사(도메인)
   - 해설: 입력한 UPN의 접미사로 이 계정이 어느 도메인에 속하는지 알아냅니다
2. [처리] Entra가 도메인을 조회해 페더레이션으로 판별 (홈 영역 검색)
   - 주체: Entra ID
   - 위치: 구역 ① 클라우드 — Entra 도메인 설정
   - 데이터: 도메인 인증 유형 = 페더레이션 · 관리형(PHS·PTA)이면 이 단계에서 Entra가 직접 암호를 받음
   - 해설: 접미사가 페더레이션 도메인이면 Entra는 암호 입력란을 열지 않고 위임합니다
3. [처리] WS-Federation 로그인 요청을 만들어 브라우저를 AD FS로 리디렉션
   - 주체: Entra ID
   - 위치: 페더레이션 설정의 AuthURL(passiveSignInUri)로 브라우저 이동 · 프로토콜 기본 WS-Federation (필요 시 preferredAuthenticationProtocol 설정)
   - 데이터: 요청 파라미터 — 어느 신뢰 당사자(Entra)인지 · 로그인 힌트 · 반환 주소 · 기존 인증 유지 여부
   - 해설: 브라우저가 중개자가 되어 Entra의 요청을 AD FS에 전달합니다. Entra와 AD FS는 직접 통신하지 않습니다
4. [처리] AD FS가 접근 경로에 맞는 인증 정책으로 사용자를 인증
   - 주체: AD FS
   - 위치: 구역 ④ AD FS 팜 — 프런트엔드(WAP · 어플라이언스, 선택)를 거친 요청은 엑스트라넷 정책, 직접 도착한 요청은 인트라넷 정책 적용
   - 데이터: 양식 · 사용자 인증서 · (직접 도착 시) Windows 통합 인증 · AD FS와 DC 사이는 DC에서 자격 증명·속성 조회 · 상세는 다음 시나리오
   - 해설: 인증 방법·SSO 쿠키·추가 인증은 AD FS 쪽 구성에 따라 달라집니다
5. [처리] AD FS가 발급 변환 규칙을 실행해 클레임을 만들고 토큰에 서명
   - 주체: AD FS
   - 위치: 신뢰 당사자 트러스트 › 발급 변환 규칙 · 토큰 서명 인증서(Token-signing) 사용
   - 데이터: Entra가 요구하는 클레임 — WS-Fed: UPN · ImmutableID / SAML 2.0 IdP: IDPEmail · NameID · 보조 클레임(nameidentifier · issuerid · authnmethodsreferences · insidecorporatenetwork 등)
   - 해설: 이 클레임으로 Entra가 어느 사용자인지 매칭하고, 서명 인증서로 토큰이 진짜 AD FS가 만든 것임을 확인합니다
6. [처리] 브라우저가 AD FS 토큰을 Entra로 POST
   - 주체: 사용자
   - 위치: Entra 로그인 엔드포인트 (login.microsoftonline.com) — 브라우저가 AD FS가 돌려준 토큰을 그대로 제출
   - 데이터: 서명된 WS-Fed(또는 SAML) 토큰
   - 해설: 토큰은 클라이언트가 직접 전달하는 값입니다. 공격자가 훔치지 못하도록 전송은 HTTPS여야 합니다
7. [판단] 토큰의 서명 인증서가 Entra에 등록된 값과 같은가?
   - 주체: Entra ID
   - 위치: GET /v1.0/domains/{도메인}/federationConfiguration (signingCertificate · nextSigningCertificate · signingCertificateUpdateStatus) · AD FS: Get-AdfsProperties
   - 데이터: AD FS 기본 토큰 서명 인증서 ↔ 도메인 페더레이션 설정의 인증서 · AutoCertificateRollover(기본 켜짐)은 인증서를 보통 1년 주기로 갱신 · Entra는 만료 35일 전부터 페더레이션 메타데이터를 폴링해 새 인증서를 확인
   - 해설: 인증서가 자동 롤오버되었는데 Entra가 모르면 토큰을 신뢰하지 않습니다. 메타데이터를 가져올 수 없거나 자동 롤오버를 쓰지 않으면 알림 메일이 오고, 이때는 Update-MgDomainFederationConfiguration으로 도메인마다 직접 갱신합니다
   - 예 → 8
   - 아니오 → [차단] 토큰 불신 — 서명 인증서 갱신 후 Entra 업데이트 필요
8. [판단] 토큰의 UPN · ImmutableID가 Entra의 동기화된 사용자와 일치하는가?
   - 주체: Entra ID
   - 위치: Get-MgUser -UserId <사용자> 로 UserPrincipalName · OnPremisesImmutableId 확인
   - 데이터: WS-Fed UPN = 사용자 UPN · ImmutableID = onPremisesImmutableId(sourceAnchor) · SAML 2.0 IdP는 IDPEmail = UPN, NameID = ImmutableID
   - 해설: 일치하지 않으면 토큰이 유효해도 사용자를 찾지 못합니다. UPN을 AD에서 바꾸고 클라우드 값을 안 바꿨거나, 메일을 UPN·사번을 sourceAnchor로 동기화하는데 AD FS 규칙이 그대로면 발생합니다
   - 예 → 9
   - 아니오 → [차단] 사용자 불일치 — 클레임 규칙과 Entra 속성을 맞춰야 함
9. [끝] Entra가 토큰을 검증하고 CA 평가 후 자체 토큰 발급
   - 주체: 로그
   - 위치: ID › 모니터링 및 상태 › 로그인 로그 (Sign-in logs)
   - 데이터: 조건부 액세스 평가 → Entra 토큰 + SigninLogs
   - 해설: Entra가 AD FS 토큰을 검증하고 MFA·CA를 평가한 뒤 자체 토큰을 발급합니다. 이후 앱은 AD FS가 아니라 Entra 토큰을 씁니다
- 시나리오: 예 ▸ 예 :: 인증서와 클레임이 맞아 Entra 토큰 발급
- 시나리오: 예 ▸ 아니오 :: 인증서는 맞지만 사용자 불일치로 차단
- 시나리오: 아니오 :: 서명 인증서가 달라 토큰 불신

> 교육 포인트: 페더레이션 로그인에서 Entra는 "누구인지(클레임)"와 "진짜인지(서명 인증서)" 두 가지를 모두 검증합니다. 둘 중 하나만 틀려도 로그인은 실패합니다.

> 주의: Windows 기기의 PRT 발급에는 AD FS의 WS-Trust 엔드포인트가 필요합니다. windowstransport 엔드포인트는 인트라넷 전용이고 WAP로 외부에 노출하지 않으며 PRT 갱신에는 usernamemixed가 필요합니다.

#### L4 · AD FS 인증 — 접근 경로(프런트엔드 경유 · 직접) · SSO 쿠키 · 추가 인증

1. [시작] 브라우저가 AD FS 로그인 URL로 인증을 요청
   - 주체: 사용자
   - 위치: AD FS 로그인 URL (Entra가 보낸 WS-Federation 요청의 passiveSignInUri)
   - 데이터: Entra가 보낸 WS-Federation 요청 · 브라우저 ↔ 받는 서버는 HTTPS(443)
   - 해설: 이 URL이 어디로 해석되는지(프런트엔드 또는 AD FS 팜)에 따라 이후 처리가 갈립니다
2. [판단] 요청이 프런트엔드(WAP · 어플라이언스)를 거쳐 왔는가?
   - 주체: AD FS
   - 위치: AD FS가 요청 헤더에서 만든 x-ms-proxy · insidecorporatenetwork 클레임으로 판별
   - 데이터: 경유 = 프록시가 x-ms-proxy(프록시 DNS 이름)를 채워 전달 · 직접 = 이 값이 없고 insidecorporatenetwork = True(회사망 내부에서 federation service로 직접)
   - 해설: AD FS는 프록시 경유 여부로 엑스트라넷과 인트라넷 요청을 구분해 서로 다른 인증 정책을 적용합니다
   - 프런트엔드 경유 → 3
   - 직접 도착 → 4
3. [처리] 프런트엔드가 요청을 AD FS 팜으로 중계 (엑스트라넷 요청)
   - 주체: WAP (DMZ)
   - 위치: 구역 ② DMZ → 구역 ④ 내부망 AD FS 팜 — 프런트엔드가 AD FS와 맺은 프록시 신뢰
   - 데이터: 프런트엔드가 x-ms-proxy 정보를 채워 전달 · 인증은 위임 · 엑스트라넷 인증 정책과 엑스트라넷 잠금이 적용됨 · Extranet Smart Lockout은 WAP(또는 MS-ADFSPIP 프록시)가 필요
   - 해설: 프런트엔드는 인증을 직접 하지 않고 AD FS에 위임합니다. 프록시를 거친 요청은 요청자가 회사망 안에 있어도 AD FS에게는 엑스트라넷 요청입니다
   - 다음 → 5
4. [처리] 클라이언트가 AD FS 팜에 직접 도착 (인트라넷 요청)
   - 주체: AD FS
   - 위치: 구역 ④ 내부망 — 내부 DNS가 AD FS 서비스 이름을 AD FS 서버(또는 로드 밸런서)로 해석
   - 데이터: x-ms-proxy 값 없음 · 인트라넷 인증 정책 적용(Windows 통합 인증 가능) · 인트라넷 요청에는 엑스트라넷 잠금 정책이 적용되지 않음 [확인 필요: 인트라넷 요청의 잠금 동작]
   - 해설: 회사망 클라이언트가 federation service에 직접 통신하는 구성이며 AD FS가 프록시 기능도 겸합니다
5. [판단] AD FS에 유효한 SSO 쿠키가 있는가?
   - 주체: AD FS
   - 위치: AD FS가 이전 인증 때 브라우저에 기록한 SSO 쿠키 (세션 SSO · 영구 SSO)
   - 데이터: 있으면 자격 증명을 다시 묻지 않음 · 없거나 만료되면 인증 필요
   - 해설: 인증 요청이 오면 AD FS는 먼저 SSO 컨텍스트가 있는지, 그다음 MFA가 필요한지 순서로 판단합니다
   - 예 → 8
   - 아니오 → 6
6. [처리] 1차 인증 — 접근 경로에 맞는 인증 정책으로 자격 증명 수집
   - 주체: AD FS
   - 위치: AD FS 관리 › 서비스 › 인증 방법 › 기본 인증 (Primary Authentication) — 엑스트라넷 · 인트라넷 설정을 따로 가짐
   - 데이터: 엑스트라넷(프런트엔드 경유) 기본 = 양식(Forms) · 사용자 인증서(certauth) 가능 · 인트라넷(직접) = Windows 통합 인증(IWA)을 설정할 수 있음 · 프런트엔드 경유 요청의 IWA 지원 여부는 확인 필요 [확인 필요: 프런트엔드 경유 IWA 지원 여부]
   - 해설: 같은 사용자라도 어느 경로로 들어왔는지에 따라 적용되는 인증 방법이 다릅니다
7. [판단] AD FS가 DC에 검증한 결과가 성공인가?
   - 주체: DC (AD)
   - 위치: 구역 ④ 내부망 — AD FS 팜 → DC · Windows 로그온 API(PTA 에이전트와 같은 LogonUser) · 인증서 로그인은 인증서 검증 후 DC 매핑
   - 데이터: 성공 · 암호 오류 · 계정 잠김 · 암호 만료 · 로그온 시간 외
   - 해설: 암호는 클라우드가 아니라 AD FS가 DC와 직접 검증합니다. AD 계정 상태가 그대로 반영됩니다
   - 성공 → 8
   - 실패 → [차단] 인증 실패 — AD FS가 오류 페이지를 표시하고 토큰을 발급하지 않음
8. [판단] 추가 인증(MFA)이 필요하고 SSO 컨텍스트에 아직 없는가?
   - 주체: AD FS
   - 위치: AD FS 관리 › 서비스 › 인증 방법 › 추가 인증 방법 · 인증 정책 · 신뢰 당사자별 액세스 제어
   - 데이터: 이전 로그인이 기본 자격 증명뿐이었는데 지금 MFA가 필요하면 SSO 설정과 무관하게 MFA를 다시 요구 · 이미 MFA가 컨텍스트에 있으면 건너뜀
   - 해설: SSO가 길어도 더 강한 인증이 요구되는 요청에서는 MFA만 추가로 묻습니다
   - 예 → 9
   - 아니오 → 10
9. [처리] AD FS가 추가 인증을 수행
   - 주체: 사용자
   - 위치: AD FS 인증 공급자(서드파티 MFA 등)
   - 데이터: 추가 요소 통과 여부 · 서드파티 MFA 공급자를 쓸 때는 기기가 Entra에 조인될 수 있도록 WS-Trust 지원 필요
   - 해설: 통과하면 인증 방법 정보가 컨텍스트에 기록되어 이후 authnmethodsreferences 클레임으로 나갑니다
10. [끝] 인증 완료 — SSO 쿠키를 기록하거나 갱신하고 토큰 발급 단계로
   - 주체: AD FS
   - 데이터: 세션 SSO 또는 영구 SSO 쿠키 기록(다음 시나리오) · 이후 발급 변환 규칙 실행
   - 해설: 인증은 여기서 끝나고 클레임을 만드는 단계가 이어집니다
- 시나리오: 프런트엔드 경유 ▸ 아니오 ▸ 성공 ▸ 아니오 :: 프런트엔드 경유, 쿠키 없이 DC 인증만 완료
- 시나리오: 프런트엔드 경유 ▸ 아니오 ▸ 성공 ▸ 예 :: 프런트엔드 경유, DC 인증 후 MFA 수행
- 시나리오: 프런트엔드 경유 ▸ 예 ▸ 아니오 :: 프런트엔드 경유, SSO 쿠키로 바로 토큰 단계
- 시나리오: 프런트엔드 경유 ▸ 예 ▸ 예 :: 프런트엔드 경유, SSO 쿠키가 있어도 MFA 수행
- 시나리오: 프런트엔드 경유 ▸ 아니오 ▸ 실패 :: 프런트엔드 경유, DC가 인증을 거부
- 시나리오: 직접 도착 ▸ 아니오 ▸ 성공 ▸ 아니오 :: 직접 도착, 쿠키 없이 DC 인증만 완료
- 시나리오: 직접 도착 ▸ 아니오 ▸ 성공 ▸ 예 :: 직접 도착, DC 인증 후 MFA 수행
- 시나리오: 직접 도착 ▸ 예 ▸ 아니오 :: 직접 도착, SSO 쿠키로 바로 토큰 단계
- 시나리오: 직접 도착 ▸ 예 ▸ 예 :: 직접 도착, SSO 쿠키가 있어도 MFA 수행
- 시나리오: 직접 도착 ▸ 아니오 ▸ 실패 :: 직접 도착, DC가 인증을 거부

> 교육 포인트: AD FS는 요청이 프런트엔드를 거쳤는지로 엑스트라넷과 인트라넷을 구분하고, 그 뒤 SSO 컨텍스트, DC 인증, MFA 필요 여부를 차례로 판단합니다. SSO 쿠키가 있다고 해서 모든 추가 인증을 건너뛰는 것은 아닙니다.

#### L4 · SSO 정의 — 세션 SSO · 영구 SSO · KMSI와 쿠키 수명

1. [시작] 같은 사용자가 다른 앱으로 이동해 AD FS에 다시 인증을 요청
   - 주체: 사용자
   - 위치: 같은 브라우저에서 두 번째 앱(신뢰 당사자) 접근
   - 데이터: 직전 인증에서 AD FS가 기록한 SSO 쿠키 존재 여부
   - 해설: SSO는 한 번 인증하고 여러 리소스에 추가 자격 증명 요구 없이 접근하게 하는 것입니다
2. [판단] 사용자의 기기가 등록(Workplace Join · Entra 등록)되어 있는가?
   - 주체: AD FS
   - 위치: 기기 등록 상태 — AD FS 장치 등록 서비스
   - 데이터: 등록 기기 = 영구 SSO 대상 · 미등록 기기 = 세션 SSO가 기본
   - 해설: 등록된 기기는 PSSO가 꺼져 있지 않은 한 항상 영구 SSO를 받습니다
   - 예 → 3
   - 아니오 → 4
3. [처리] 영구 SSO(PSSO) 쿠키 기록
   - 주체: AD FS
   - 위치: Set-AdfsProperties -EnablePersistentSso (기본 켜짐 · 끄면 PSSO 쿠키가 만들어지지 않음)
   - 데이터: AD FS 2016 — 최대 90일(PersistentSsoLifetimeMins), 단 기기를 14일(DeviceUsageWindowInDays) 안에 AD FS 리소스 접근에 사용해야 유지 · 15일 뒤에는 자격 증명을 다시 요구 · AD FS 2012 R2는 기본 7일
   - 해설: 브라우저를 닫아도 유지되는 쿠키이고 OAuth 앱에서는 새로 고침 토큰의 수명 기준이 됩니다
   - 다음 → 6
4. [판단] KMSI(로그인 상태 유지)를 켰고 사용자가 선택했는가?
   - 주체: AD FS
   - 위치: Set-AdfsProperties -EnableKmsi $true (기본 꺼짐 · 켜면 AD FS 로그인 페이지에 선택지 표시)
   - 데이터: 미등록 기기에서 영구 SSO를 얻는 방법
   - 해설: KMSI를 쓰지 않으면 세션 SSO만 적용됩니다
   - 예 → 5
   - 아니오 → 7
5. [처리] KMSI 영구 SSO 쿠키 기록
   - 주체: AD FS
   - 위치: Set-AdfsProperties -KmsiLifetimeMins
   - 데이터: 기본 1440분(24시간) · 최대 7일
   - 해설: 등록되지 않은 기기도 이 기간에는 다시 로그인하지 않습니다
   - 다음 → 6
6. [판단] SSO 컨텍스트에 이번 요청에 필요한 MFA가 이미 들어 있는가?
   - 주체: AD FS
   - 위치: AD FS 인증 정책(MFA 필요 조건)
   - 데이터: 쿠키는 있지만 이전 로그인이 MFA 없이 기본 자격 증명뿐이었고 지금 MFA가 필요하면 SSO 설정과 무관하게 MFA를 다시 요구
   - 해설: AD FS는 먼저 SSO 컨텍스트가 있는지, 그다음 MFA가 필요한지 평가합니다
   - 예 → 8
   - 아니오 → 9
7. [처리] 세션 SSO 쿠키 기록
   - 주체: AD FS
   - 위치: Set-AdfsProperties -SsoLifetime
   - 데이터: 기본 480분(8시간) · 브라우저 세션이 끝나면 쿠키 삭제 · 미등록 기기에서 AD FS가 기본으로 기록
   - 해설: 같은 세션 안에서 앱을 바꿀 때만 프롬프트가 사라집니다
   - 다음 → 6
8. [끝] 프롬프트 없이 AD FS가 토큰 발급 단계로 진행
   - 주체: AD FS
   - 데이터: 자격 증명 · MFA 재요구 없음
   - 해설: SSO가 길게 유지되는 대신 쿠키 수명과 MFA 컨텍스트를 함께 관리해야 합니다
9. [끝] MFA만 다시 요구 — 기본 자격 증명은 SSO로 인정
   - 주체: AD FS
   - 데이터: 추가 요소만 재요청 · 통과하면 컨텍스트에 MFA 기록
   - 해설: SSO와 MFA 요구는 독립적으로 평가됩니다
- 시나리오: 예 ▸ 예 :: 등록 기기의 영구 SSO와 MFA 컨텍스트로 프롬프트 없음
- 시나리오: 예 ▸ 아니오 :: 등록 기기의 영구 SSO지만 MFA만 다시 요구
- 시나리오: 아니오 ▸ 예 ▸ 예 :: 미등록 기기의 KMSI 영구 SSO로 프롬프트 없음
- 시나리오: 아니오 ▸ 예 ▸ 아니오 :: 미등록 기기의 KMSI 영구 SSO지만 MFA만 요구
- 시나리오: 아니오 ▸ 아니오 ▸ 예 :: 미등록 기기의 세션 SSO로 프롬프트 없음
- 시나리오: 아니오 ▸ 아니오 ▸ 아니오 :: 미등록 기기의 세션 SSO지만 MFA만 다시 요구

> 교육 포인트: AD FS의 SSO는 세 가지입니다. 세션 SSO(브라우저 세션, 기본 8시간), 영구 SSO(등록 기기, 최대 90일·14일 사용 창), KMSI(미등록 기기, 기본 24시간). OAuth에서는 새로 고침 토큰 수명이 쿠키 수명을 따릅니다.
>
> 주의: Entra 쪽의 Seamless SSO(Kerberos 티켓)와는 다른 개념입니다. 페더레이션에서는 AD FS 쿠키가 SSO를 만들고 Entra 세션은 Entra 토큰과 CA 세션 컨트롤이 별도로 정합니다.

#### L4 · 토큰 발급 — 발급 변환 규칙과 클레임 (자동 관리 vs 수동 작성)

1. [시작] 인증이 끝난 사용자에 대해 AD FS가 클레임 파이프라인을 시작
   - 주체: AD FS
   - 위치: 신뢰 당사자 트러스트(Microsoft Office 365 Identity Platform) › 발급 변환 규칙 · 클레임 발급 정책
   - 데이터: 입력 = 인증 결과(Windows 계정 이름 클레임 등) · 규칙 순서대로 실행 · 앞 규칙의 출력이 뒤 규칙의 입력(중간 클레임)
   - 해설: 규칙의 순서가 결과를 바꿉니다
2. [처리] 속성 저장소(Active Directory)에서 사용자 속성을 조회
   - 주체: AD FS
   - 위치: 클레임 규칙 언어 — 속성 저장소 = Active Directory
   - 데이터: 조회 대상 예) userPrincipalName · objectGuid · ms-ds-consistencyguid · mail · 사번
   - 해설: AD FS는 빈 값인 클레임을 만들지 않고 버립니다
3. [판단] 발급 변환 규칙을 Entra Connect가 관리하는가?
   - 주체: 관리자
   - 위치: Entra Connect › 추가 작업 › 사용자 로그인 변경 · AD FS 트러스트 복구(Repair)
   - 데이터: Connect 관리 = 동기화 설정에 맞춰 권장 규칙 세트를 자동 유지 · 직접 관리 = 관리자가 규칙을 직접 작성·유지
   - 해설: Microsoft는 Connect로 Entra 트러스트를 관리하기를 권장합니다. 관리자가 규칙을 직접 고치면 Connect 작업 때 의도와 달라질 수 있어, Connect는 변경 전에 %ProgramData%\AADConnect\ADFS 에 백업을 남깁니다
   - 자동 → 4
   - 수동 → 5
4. [처리] Connect가 관리하는 권장 클레임 규칙 세트
   - 주체: AD FS
   - 위치: 발급 변환 규칙 — Issue UPN · Issue msdsconsistencyguid as Immutable ID if it exists · Issue objectGuidRule if msdsConsistencyGuid rule doesn't exist · Issue nameidentifier · Issue accounttype · Issue issuerid
   - 데이터: Pass through primary SID · insideCorporateNetwork · Psso · Issue Password Expiry Claims · authnmethodsreferences · multifactorauthenticationinstant · AlternateLoginID
   - 해설: UPN과 ImmutableID는 Connect의 동기화 설정(UPN 속성 · sourceAnchor)과 항상 짝이 맞게 만들어집니다. 도메인을 추가하면 issuerid 규칙의 정규식이 자동으로 갱신됩니다(Connect 1.1.553.0 이상)
   - 다음 → 6
5. [처리] 직접 작성하는 클레임 규칙 — UPN · ImmutableID · issuerid
   - 주체: 관리자
   - 위치: AD FS 관리 › 신뢰 당사자 트러스트 › 클레임 발급 정책 편집 › 규칙 추가 (사용자 지정 규칙)
   - 데이터: ImmutableID 클레임 유형 http://schemas.microsoft.com/LiveID/Federation/2008/05/ImmutableID · 소스 앵커로 ms-ds-consistencyguid를 쓰면 값이 있을 때 그 값을, 없으면 objectGuid를 발급하는 조건부 규칙 필요(다음 시나리오) · 서브도메인·다중 도메인 UPN은 issuerid 규칙 필요
   - 해설: Connect를 쓰지 않거나 소스 앵커·UPN 속성을 기본값과 다르게 썼다면 AD FS 규칙을 같은 값이 나가도록 직접 맞춰야 합니다. 맞추지 않으면 Entra가 사용자를 찾지 못합니다
   - 다음 → 6
6. [판단] 발급된 UPN · ImmutableID가 Entra의 사용자 속성과 같은가?
   - 주체: 관리자
   - 위치: 비교 — Entra Connect › 현재 구성 보기에서 SOURCE ANCHOR · USER PRINCIPAL NAME 확인, AD FS 규칙의 조회 속성과 대조 · Get-MgUser로 Entra 값 확인
   - 데이터: WS-Fed: UPN · ImmutableID / SAML 2.0 IdP: IDPEmail · NameID · 값이 다르면 토큰은 유효해도 사용자 매칭 실패
   - 해설: 어긋난 경우 Connect가 관리하면 트러스트를 복구하고, 직접 관리하면 규칙이 올바른 속성을 쓰도록 고칩니다
   - 예 → 7
   - 아니오 → [차단] 클레임 불일치 — 규칙을 Connect 설정과 같은 속성으로 수정
7. [처리] MFA 인증 클레임 전달 — authnmethodsreferences · multipleauthn
   - 주체: AD FS
   - 위치: 규칙 템플릿 ‘들어오는 클레임을 통과 또는 필터링’ — 인증 방법 참조(Authentication Methods References) 모든 값 통과
   - 데이터: AD FS에서 MFA를 했다면 multipleauthn 클레임이 Entra로 전달돼야 Entra가 그 MFA를 인정할 수 있음
   - 해설: Entra가 이 클레임으로 AD FS에서 MFA가 수행됐는지 판단합니다. 규칙이 없으면 AD FS에서 MFA를 했어도 Entra가 다시 MFA를 요구할 수 있습니다
8. [끝] AD FS가 토큰을 서명해 브라우저로 반환
   - 주체: AD FS
   - 위치: 토큰 서명 인증서(Token-signing) · 서명 알고리즘 SHA-256 권장
   - 데이터: 클레임이 담긴 WS-Fed(SAML 1.1) 토큰에 AD FS의 개인 키로 서명 → 브라우저 POST
   - 해설: Entra는 등록된 공개 인증서로 이 서명을 검증합니다
- 시나리오: 자동 ▸ 예 :: Connect 관리 규칙으로 클레임이 맞아 토큰 반환
- 시나리오: 수동 ▸ 예 :: 직접 작성한 규칙이 Entra 속성과 맞아 토큰 반환
- 시나리오: 자동 ▸ 아니오 :: Connect 관리지만 속성이 어긋나 클레임 불일치
- 시나리오: 수동 ▸ 아니오 :: 직접 작성한 규칙이 어긋나 클레임 불일치

> 교육 포인트: 클레임 규칙은 Entra에 "이 사람이 누구인지"를 알려 주는 번역표입니다. 기본 설정에서는 Connect가 맞춰 주지만 소스 앵커나 UPN 속성을 바꾸면 AD FS 규칙도 같이 바뀌어야 합니다.
>
> 주의: 사용자 지정(수동) 규칙은 업그레이드·트러스트 복구·도메인 추가 때 Connect가 덮어쓸 수 있습니다. 직접 규칙을 쓰는 경우 변경 전후 백업과 규칙 순서를 반드시 기록합니다.

#### L4 · 클레임 규칙 수동 작성 — ImmutableID 조건부 발급과 issuerid

1. [시작] ms-ds-consistencyguid를 소스 앵커로 쓰는데 AD FS 규칙은 직접 작성해야 함
   - 주체: 관리자
   - 위치: AD FS 관리 › 신뢰 당사자 트러스트 › Microsoft Office 365 Identity Platform › 클레임 발급 정책 편집
   - 데이터: 소스 앵커 속성 = ms-ds-consistencyguid(비어 있는 사용자는 objectGuid) · 클레임 유형은 환경에 맞게 정의
   - 해설: 값이 비어 있는 사용자가 섞여 있으면 단일 규칙으로는 ImmutableID를 만들 수 없어 여러 규칙을 차례로 써야 합니다
2. [처리] 규칙 1 — AD에서 objectGuid · ms-ds-consistencyguid를 조회해 중간 클레임으로 추가
   - 주체: 관리자
   - 위치: 사용자 지정 규칙 (add 사용, issue 사용 금지)
   - 데이터: c:[Type == windowsaccountname] => add(store = "Active Directory", types = (objectguid, msdsconsistencyguid), query = "; objectGuid,ms-ds-consistencyguid;{0}", param = c.Value)
   - 해설: add를 쓰면 클레임이 토큰으로 나가지 않고 파이프라인 안의 임시 값으로만 남습니다. 값이 비어 있는 속성은 AD FS가 바로 버리므로 msdsconsistencyguid 클레임은 값이 있는 사용자에게만 생깁니다
3. [처리] 규칙 2 — msdsconsistencyguid가 없으면 임시 플래그(idflag = useguid) 설정
   - 주체: 관리자
   - 위치: 사용자 지정 규칙
   - 데이터: NOT EXISTS([Type == msdsconsistencyguid]) => add(Type = "idflag", Value = "useguid")
   - 해설: 모든 객체에는 objectGuid가 있으므로 규칙 1 이후 objectGuid 클레임은 항상 있습니다
4. [판단] msdsconsistencyguid 값이 사용자에게 있는가?
   - 주체: AD FS
   - 데이터: 있음 = 규칙 3이 이 값을 ImmutableID로 발급 · 없음 = 규칙 4가 objectGuid를 ImmutableID로 발급
   - 해설: 이 분기는 규칙으로 구현되어 AD FS가 자동으로 한쪽만 실행합니다
   - 있음 → 5
   - 없음 → 6
5. [처리] 규칙 3 — msdsconsistencyguid를 ImmutableID로 발급
   - 주체: 관리자
   - 위치: 사용자 지정 규칙
   - 데이터: c:[Type == msdsconsistencyguid] => issue(Type = "http://schemas.microsoft.com/LiveID/Federation/2008/05/ImmutableID", Value = c.Value)
   - 해설: 클레임이 존재하는 것이 암묵적 존재 검사입니다
   - 다음 → 7
6. [처리] 규칙 4 — idflag = useguid이면 objectGuid를 ImmutableID로 발급
   - 주체: 관리자
   - 위치: 사용자 지정 규칙
   - 데이터: c1:[Type == idflag, Value == useguid] && c2:[Type == objectguid] => issue(Type = ImmutableID, Value = c2.Value)
   - 해설: 임시 플래그 값으로 어느 규칙이 발급할지 정합니다
   - 다음 → 7
7. [판단] 여러 도메인(서브도메인 UPN 포함)을 페더레이션했는가?
   - 주체: 관리자
   - 위치: Entra 관리 센터 › 도메인 이름 · Connect 추가 작업 › 페더레이션 도메인 추가
   - 데이터: 여러 도메인이면 issuerid 클레임 규칙이 모든 페더레이션 도메인을 포함해야 서브도메인 UPN으로 SSO 가능 · Connect 1.1.553.0 이상은 issuerid 규칙을 자동 생성
   - 해설: Connect로 도메인을 추가하지 않고 직접 추가했다면 issuerid 규칙도 직접 맞춰야 합니다
   - 예 → 8
   - 아니오 → 9
8. [처리] issuerid 규칙을 모든 페더레이션 도메인에 맞게 작성
   - 주체: 관리자
   - 위치: 사용자 지정 규칙 · 정규식에 페더레이션 도메인 반영
   - 데이터: issuerid 값은 UPN 접미사에서 도메인을 뽑는 정규식으로 만들고 페더레이션한 모든 도메인을 반영
   - 해설: 빠뜨린 도메인의 사용자는 SSO 로그인에서 실패합니다
   - 다음 → 10
9. [처리] 단일 도메인 — 기본 issuerid 규칙 사용
   - 주체: 관리자
   - 위치: 사용자 지정 규칙
   - 데이터: 단일 도메인 UPN 접미사 기준
   - 해설: 도메인이 하나뿐이면 별도 정규식 작업이 필요 없습니다
   - 다음 → 10
10. [판단] 규칙 순서가 올바른가?
   - 주체: 관리자
   - 위치: 클레임 발급 정책 › 규칙 목록 순서
   - 데이터: 문서의 주의 — 규칙의 순서가 중요(조회 → 플래그 → 발급 순서 유지)
   - 해설: 순서가 어긋나면 플래그가 만들어지기 전에 발급 규칙이 실행되어 ImmutableID가 발급되지 않거나 두 번 발급될 수 있습니다
   - 예 → 11
   - 아니오 → [차단] ImmutableID 누락 — Entra가 사용자를 찾지 못함
11. [끝] 토큰 클레임 확인 — 발급 값과 Entra 값 대조
   - 주체: 로그
   - 위치: Dump Token 앱으로 토큰 확인 · Get-MgUser 로 UserPrincipalName · OnPremisesImmutableId 확인
   - 데이터: 토큰의 ImmutableID와 UPN이 Entra의 사용자 속성과 같은지
   - 해설: 이 대조가 규칙 작성의 최종 확인입니다
- 시나리오: 있음 ▸ 아니오 ▸ 예 :: 소스 앵커 값이 있고 단일 도메인이라 정상 발급
- 시나리오: 있음 ▸ 예 ▸ 예 :: 소스 앵커 값이 있고 다중 도메인 규칙도 맞아 정상
- 시나리오: 없음 ▸ 아니오 ▸ 예 :: 값이 없어 objectGuid로 발급, 단일 도메인 정상
- 시나리오: 없음 ▸ 예 ▸ 예 :: 값이 없어 objectGuid로 발급, 다중 도메인도 정상
- 시나리오: 있음 ▸ 아니오 ▸ 아니오 :: 소스 앵커 값은 있으나 규칙 순서 오류로 누락
- 시나리오: 있음 ▸ 예 ▸ 아니오 :: 다중 도메인이지만 규칙 순서 오류로 누락
- 시나리오: 없음 ▸ 아니오 ▸ 아니오 :: objectGuid로 발급하려 했으나 순서 오류로 누락
- 시나리오: 없음 ▸ 예 ▸ 아니오 :: 값이 없고 다중 도메인이나 순서 오류로 누락

> 교육 포인트: ImmutableID 규칙은 "값이 있으면 그 값, 없으면 objectGuid"라는 조건을 AD FS 규칙 순서로 구현합니다. 규칙이 하나라도 빠지거나 순서가 바뀌면 Entra가 사용자를 찾지 못합니다.
>
> 주의: add와 issue의 차이를 구분합니다. add는 임시 값, issue는 토큰으로 나가는 값입니다. 이 규칙들은 Connect가 관리하는 트러스트를 직접 편집하면 이후 Connect 작업에서 덮어써질 수 있습니다.

#### L4 · Entra의 토큰 검증과 MFA 동작 — federatedIdpMfaBehavior

1. [시작] 브라우저가 AD FS 토큰을 Entra에 제출
   - 주체: 사용자
   - 위치: Entra 로그인 엔드포인트 (login.microsoftonline.com)
   - 데이터: 서명된 토큰 + authnmethodsreferences(multipleauthn) 등 클레임
   - 해설: Entra가 토큰을 검증하는 단계의 시작입니다
2. [판단] 서명 인증서가 Entra에 등록된 값과 같은가?
   - 주체: Entra ID
   - 위치: federationConfiguration의 signingCertificate · nextSigningCertificate
   - 데이터: AD FS 자동 롤오버 인증서를 Entra가 메타데이터 폴링으로 알고 있는지 · 알림 메일이 오면 직접 갱신
