### L3 · 0 · 기능 상태 전이 — 방법 미선택 → 방식 구성 → 방식별 검증 경로

#### L4 · ⓪ 비활성 — 암호를 검증할 경로가 정해지지 않았다

1. [시작] 동기화된 사용자가 클라우드 로그인 요청
   - 주체: 사용자
   - 위치: login.microsoftonline.com › UPN 입력
   - 데이터: 동기화된 user (암호 없이 프로비전된 상태)
   - 해설: 온프레미스에서 동기화된 사용자가 로그인합니다. UPN 접미사는 Entra에서 확인된 도메인이어야 하고, 확인할 수 없는 라우팅 불가 도메인이면 Alternate login ID 같은 별도 구성이 필요합니다.
2. [처리] 사용자 영역(Realm) 조회
   - 주체: Entra ID
   - 위치: GET /v1.0/domains/{도메인} (authenticationType)
   - 데이터: 도메인의 인증 유형 (관리형 · 페더레이션)
   - 해설: Entra가 이 사용자의 암호를 어디서 확인해야 하는지 찾습니다.
3. [처리] 암호 검증 수단이 없음 — 해시 · 에이전트 · 페더레이션 모두 없음
   - 주체: Entra ID
   - 데이터: 최초 객체 동기화에는 암호가 포함되지 않음 · 암호 해시 동기화를 켜지 않으면 클라우드 계정에 암호가 없는 상태
   - 해설: 로그인 방식을 고르기 전에는 클라우드가 암호를 검증할 근거가 없습니다.
4. [판단] 암호 없는 로그인 방법(패스키 등)이 등록되어 있는가?
   - 주체: Entra ID
   - 데이터: 사용자의 인증 방법 등록 상태 [확인 필요: 동기화 사용자 적용 범위]
   - 해설: 암호 대신 쓸 방법이 있으면 일부 로그인은 가능할 수 있습니다.
   - 예 → 5
   - 아니오 → [차단] 로그인 실패 — 검증할 암호가 없음
5. [끝] 암호 기반 로그인은 불가 — 방식 선택 필요
   - 주체: 로그
   - 위치: ID › 모니터링 및 상태 › 로그인 로그 (Sign-in logs)
   - 데이터: SigninLogs 실패 결과 코드 · 사용자에게는 "Your account or password is incorrect" 오류가 보임(계정에 암호가 없을 때)
   - 해설: 대부분의 사용자는 로그인 방식을 정할 때까지 클라우드 서비스를 쓰기 어렵습니다. 클라우드 관리자가 암호를 직접 설정하는 방법도 있지만 동기화 구성 후에는 온프레미스 암호가 이를 덮어씁니다.
- 시나리오: 예 :: 패스키 등은 있으나 암호 기반 로그인은 불가
- 시나리오: 아니오 :: 등록된 방법이 없어 로그인 실패

#### L4 · ① 구성 — PHS · PTA · 페더레이션 중 하나를 고른다

1. [시작] 사용자 로그인 방식 선택 시작
   - 주체: 관리자
   - 위치: Microsoft Entra Connect 마법사 › 사용자 로그인 (암호 해시 동기화 · 통과 인증 · AD FS와 페더레이션 · 페더레이션 안 함) · 설치 후에는 Additional tasks › Change user sign-in
   - 데이터: 도메인 인증 유형 (관리형 · 페더레이션) · 마법사에서 선택할 수 있는 항목은 Password hash synchronization · Pass-through authentication · Federation with AD FS · Federation with PingFederate · Do not configure
   - 해설: 인증 경로를 정하는 출발점입니다. 인증 방식 선택은 동기화 도구(Connect Sync · Cloud Sync) 선택과 독립입니다.
2. [판단] 어떤 방식을 고르는가?
   - 주체: 관리자
   - 위치: 하이브리드 관리 › Microsoft Entra Connect › 사용자 로그인
   - 데이터: 요구 사항 — 인프라 부담 · 온프레미스 계정 상태 즉시 반영 · 서드파티 MFA · PHS는 추가 인프라 없음 · PTA는 에이전트 3대 권장 · 페더레이션은 AD FS 팜 운영 필요
   - 해설: 인프라, 보안 요구, 가용성에 따라 방식이 갈립니다. 서드파티 MFA나 sAMAccountName 로그인처럼 Entra가 기본 지원하지 않는 요구가 있을 때 페더레이션을 고려합니다.
   - PHS → 3
   - PTA → 4
   - 페더레이션 → 5
3. [처리] PHS — 암호 해시 동기화 켜기
   - 주체: 관리자
   - 위치: Microsoft Entra Connect 마법사 › 사용자 로그인 › 암호 해시 동기화 · PTA·페더레이션과 함께 켤 때는 Optional features 페이지 [확인 필요: 한글 메뉴명]
   - 데이터: 2분 주기 해시 동기화 (주기 변경 불가) · 처음 켜면 범위 안 전체 사용자 암호를 초기 동기화 · 동기화되는 개체는 Active Directory user 유형(iNetOrgPerson 제외)
   - 해설: 추가 인프라 없이 클라우드에서 검증하는 가장 단순한 방식입니다. PTA나 페더레이션을 쓰더라도 PHS를 함께 켜 두면 장애 시 대체 수단이 됩니다.
   - 다음 → 6
4. [처리] PTA — 인증 에이전트 설치 · 고가용성 구성
   - 주체: 관리자
   - 위치: Entra ID › Entra Connect › Connect Sync › 통과 인증 (Pass-through authentication) › 다운로드 (추가 서버에 설치, 총 3대 권장) · 처음 설치하면 Connect 마법사에서 PTA를 고르는 것만으로 Connect 서버에 에이전트가 설치되고 테넌트 기능이 켜짐
   - 데이터: 에이전트 서버 — Windows Server 2016 이상 · TLS 1.2 · Server Core 불가 · 아웃바운드 443(CRL용 80, 선택 8080) · 방화벽 허용 대상 *.msappproxy.net · *.servicebus.windows.net · 테넌트당 에이전트 최대 40개 · PTA는 테넌트 수준 기능이라 모든 관리형 도메인에 적용됨
   - 해설: 에이전트를 여러 대 두어야 에이전트 한 대가 멈춰도 로그인이 유지됩니다. 에이전트 서버는 도메인 컨트롤러처럼 Tier 0로 보호하고 경계 네트워크(DMZ)에는 두지 않습니다.
   - 다음 → 6
5. [처리] 페더레이션 — AD FS 팜 구성 · 도메인 연동
   - 주체: 관리자
   - 위치: Microsoft Entra Connect 마법사 › AD FS와 페더레이션 · AD FS 관리 콘솔
   - 데이터: AD FS 팜 · 토큰 서명 인증서 · 도메인 authenticationType = Federated · 도메인 연동 설정은 GET /v1.0/domains/{도메인}/federationConfiguration (issuerUri · passiveSignInUri · signingCertificate)
   - 해설: Entra가 로그인 처리를 AD FS에 넘기도록 도메인을 연동합니다. 외부 접속이 필요하면 Web Application Proxy 서버도 함께 구성합니다.
6. [처리] Seamless SSO 켜기 — PHS·PTA와 함께 선택
   - 주체: 관리자
   - 위치: Microsoft Entra Connect 마법사 › 로그인 페이지 › 단일 로그인 사용 (Enable single sign on, 포리스트별 도메인 관리자 자격) · 확인은 Entra ID › Entra Connect › Connect sync › Seamless single sign-on = Enabled [확인 필요: 한글 메뉴명]
   - 데이터: AD에 AZUREADSSOACC 컴퓨터 계정 생성 · Kerberos 복호화 키를 Entra와 공유 · Connect 1.1.880.0 이상은 Change user sign-in에서 기본 선택 · PowerShell 대안: Enable-AzureADSSOForest · 현대 인증(modern authentication) 사용 필요 · 페더레이션(AD FS)과는 함께 쓸 수 없음
   - 해설: 사내 도메인 PC에서 로그인 프롬프트 없이 들어가게 합니다. 도메인 관리자 자격은 기능을 켤 때만 쓰이고 Connect나 Entra에 저장되지 않습니다.
7. [처리] 브라우저 인트라넷 영역에 Entra 주소 배포
   - 주체: 관리자
   - 위치: 그룹 정책 › 사용자 구성 › 정책 › 관리 템플릿 › Windows 구성 요소 › Internet Explorer › 인터넷 제어판 › 보안 페이지 › 사이트와 영역 할당 목록 (Site to Zone Assignment List) · 같은 보안 페이지의 인트라넷 영역 › 스크립트를 통한 상태 표시줄 업데이트 허용 (Allow updates to status bar via script)을 사용으로 설정
   - 데이터: https://autologon.microsoftazuread-sso.com = 1 (인트라넷 영역) · 특정 사용자만 막으려면 값을 4(제한된 영역)로 지정 · 그룹 정책 기본 설정 방식은 레지스트리 ZoneMap\Domains\microsoftazuread-sso.com\autologon에 https = 1 (REG_DWORD)
   - 해설: 브라우저가 이 주소로 Kerberos 티켓을 보낼 수 있게 허용합니다. Edge·Chrome에서 AuthServerAllowlist 정책을 덮어썼다면 이 주소도 추가하고, Firefox는 SPNEGO 정책에 추가합니다.
8. [처리] 단계적 롤아웃으로 소수 사용자에게 먼저 적용
   - 주체: 관리자
   - 위치: Entra ID › Entra Connect › Connect sync › 관리형 사용자 로그인에 대한 단계적 롤아웃 사용 (Enable staged rollout for managed user sign-in) › 기능별 켜기 › 그룹 추가 (Hybrid Identity Administrator 필요)
   - 데이터: 감사 로그 "Create rollout policy for feature" · "Add a group to feature rollout" · "Add user to feature rollout" · 기능당 그룹 최대 10개 · 새 그룹은 처음 200명까지 · 중첩·동적 그룹 미지원 · 연락처 개체가 있는 그룹은 추가 불가 · 그룹 구성 변경은 반영까지 최대 24시간 · PHS+PTA+Seamless SSO 동시 선택은 미지원
   - 해설: 페더레이션에서 클라우드 인증으로 옮기기 전에 일부 사용자로 시험합니다. 단계적 롤아웃은 임시 시험용이어서 페더레이션 IdP를 폴백으로 유지해야 하고, Connect로 동기화된 사용자와 브라우저·현대 인증 클라이언트 로그인에만 적용됩니다.
9. [끝] 저장 — 다음 로그인부터 선택한 경로 적용
   - 주체: 관리자
   - 위치: 마법사 › 구성 · 단계적 롤아웃 › 저장
   - 데이터: 단계적 롤아웃은 도메인을 페더레이션에서 관리형으로 바꾸지 않음 — 최종 전환은 Microsoft Entra Connect 또는 PowerShell로 따로 수행 · AD FS에서 PTA로 옮길 때는 Exchange ActiveSync 로그인 유지를 위해 최소 12시간 뒤에 AD FS를 종료
   - 해설: 저장 뒤 다음 로그인부터 새 경로를 탑니다. 단계적 롤아웃에 새로 추가된 사용자는 기존 페더레이션으로 한 번 더 로그인해야 관리형 인증으로 바뀔 수 있습니다.
- 시나리오: PHS :: PHS를 골라 SSO·단계적 롤아웃 후 저장
- 시나리오: PTA :: PTA를 골라 SSO·단계적 롤아웃 후 저장
- 시나리오: 페더레이션 :: 페더레이션을 골라 SSO·단계적 롤아웃 후 저장

#### L4 · ② 활성 — 선택한 방식에 따라 검증 위치가 달라진다

1. [시작] 사용자가 로그인 요청
   - 주체: 사용자
   - 위치: Entra 로그인 페이지 › UPN 입력
   - 데이터: 로그인 요청 (UPN)
   - 해설: 사용자가 로그인을 시작합니다.
2. [처리] 사용자 영역(Realm) 조회 — 관리형인가 페더레이션인가
   - 주체: Entra ID
   - 데이터: 영역 정보 JSON (페더레이션이면 AuthURL) · 단계적 롤아웃 그룹 멤버십
   - 해설: 도메인 유형과 단계적 롤아웃 대상 여부로 경로를 결정합니다. 앱이 domain_hint를 보내는 흐름은 단계적 롤아웃 사용자도 계속 페더레이션을 탑니다.
3. [판단] 구성된 로그인 방식은?
   - 주체: Entra ID
   - 위치: Entra ID › Entra Connect › Connect sync (Password Hash Sync · Pass-through authentication · Seamless single sign-on 상태)
   - 데이터: 테넌트에 설정된 방식
   - 해설: 방식별로 암호를 검증하는 위치가 다릅니다. PHS와 PTA는 클라우드 인증(관리형), 페더레이션은 외부 IdP 인증입니다.
   - PHS → 4
   - PTA → 5
   - 페더레이션 → 6
4. [처리] PHS — 동기화된 해시와 비교해 Entra에서 검증
   - 주체: Entra ID
   - 데이터: 입력 암호를 같은 가공(salt · PBKDF2)으로 해시 후 저장 해시와 비교 (세부는 L3 A)
   - 해설: 검증이 클라우드 안에서 끝납니다.
   - 다음 → 7
5. [처리] PTA — 에이전트가 큐에서 받아 DC에 검증 요청
   - 주체: PTA 에이전트
   - 데이터: 암호화된 사용자 이름·암호 → 인증 에이전트 → DC (세부는 L3 B)
   - 해설: 에이전트가 큐에서 받은 요청을 복호화해 도메인 컨트롤러에 검증하고 결과만 Entra에 돌려줍니다.
   - 다음 → 7
6. [처리] 페더레이션 — AD FS로 리디렉션하고 토큰 수신
   - 주체: AD FS
   - 데이터: AuthURL 리디렉션 → AD FS 토큰 (세부는 L3 C)
   - 해설: AD FS가 인증하고 토큰을 돌려줍니다. 외부 접속은 DMZ의 WAP를 거칩니다.
7. [처리] 조건부 액세스 · MFA 평가
   - 주체: Entra ID
   - 데이터: 1차 인증 결과 + 정책 조건
   - 해설: 어떤 방식이든 1차 인증이 끝나면 같은 CA 평가를 거칩니다. PHS·PTA에서는 Entra MFA 또는 CA 사용자 지정 컨트롤을 쓰며, 서드파티·온프레미스 MFA는 페더레이션이 필요합니다.
8. [끝] 토큰 발급 + 로그인 로그 기록
   - 주체: 로그
   - 위치: ID › 모니터링 및 상태 › 로그인 로그 (Sign-in logs)
   - 데이터: SigninLogs (결과 코드 · 인증 세부 정보 · CA 결과)
   - 해설: 발급 결과가 로그인 로그에 남습니다. PTA 실패는 로그인 오류 코드 800xx(예: 80001 에이전트 없음)로 구분할 수 있습니다.
- 시나리오: PHS :: PHS 검증 후 CA · MFA 평가, 토큰 발급
- 시나리오: PTA :: PTA 검증 후 CA · MFA 평가, 토큰 발급
- 시나리오: 페더레이션 :: 페더레이션 검증 후 CA · MFA 평가, 토큰 발급

> 교육 포인트: 방식에 따라 장애 지점이 다릅니다. PHS는 클라우드만, PTA는 에이전트와 DC, 페더레이션은 AD FS 가용성에 의존합니다.

> 주의: 인증 방식 선택은 동기화 도구(Connect Sync · Cloud Sync) 선택과 독립입니다. Windows 기기 로그온의 PRT 발급은 "디바이스 ID"에서 다룹니다.
