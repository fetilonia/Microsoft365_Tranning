## L2 · 역할 · 관리 단위 — 최소 권한 · 범위 위임

- 설정(Control Plane): 역할 할당 (역할 정의 + 보안 주체 + 범위) | 관리 단위(AU) · 사용자 지정 역할
- 강제(Enforcement): Entra 관리 작업 권한 검사 | 역할 + 범위(AU)
- 증적(Evidence): 감사 로그 RoleManagement · AdministrativeUnit | GET /v1.0/roleManagement/directory/roleAssignments
- 메뉴(Admin Center): ID > 역할 및 관리자 · 관리 단위
- 라이선스(License): 기본 제공 역할 사용 · AU 생성은 Free · AU 관리자(AU 범위 역할을 받는 사람)는 사용자당 P1 이상, AU 멤버는 Free · 동적 멤버십 AU는 멤버 사용자마다 P1 · 사용자 지정 역할과 역할 할당 가능 그룹은 P1 · PIM 적격 할당은 P2 [확인 필요: 고객 라이선스]

### L3 · 0 · 기능 상태 전이 — 광범위 관리자 → 최소 권한·범위 → 범위 안에서만 작업

#### L4 · ⓪ 비활성 — 넓은 역할을 여러 명에게 부여한다

1. [시작] 헬프데스크가 사용자 암호 재설정을 요청
   - 주체: 관리자
   - 위치: 포털 › 사용자 › {사용자} › 암호 재설정 (Graph 호출로도 수행 가능)
   - 데이터: 요청자 계정 · 대상 사용자 · 이 작업에 필요한 최소 역할은 Helpdesk Administrator(비관리자 대상 암호 재설정)처럼 범위가 좁은 기본 제공 역할
   - 해설: 일상적인 사용자 관리 작업이 시작됩니다. 기본 제공 역할은 사용하는 데 별도 라이선스가 필요 없습니다.
2. [처리] 필요한 최소 역할을 모르고 전역 관리자를 부여
   - 주체: 관리자
   - 위치: ID › 역할 및 관리자 (Roles & admins) › Global Administrator › 할당 추가 (Add assignments) — 이 할당은 Privileged Role Administrator 이상이 수행
   - 데이터: roleAssignment (directoryScopeId = "/" 테넌트 전체) · PIM을 쓰지 않으면 상시(permanent) 할당
   - 해설: 작업보다 훨씬 큰 권한이 상시 할당됩니다. 테넌트 범위의 기본 제공 역할 할당에는 개수 제한이 없어 막는 장치도 없습니다.
3. [처리] 전역 관리자가 테넌트 어디서나 작업 가능
   - 주체: Entra ID
   - 데이터: 모든 사용자 · 그룹 · 앱 · 정책에 대한 권한 (제한된 관리 AU에 속한 개체만 예외)
   - 해설: 범위를 제한하는 장치가 없어 어떤 대상에도 작업이 허용됩니다. 제한된 관리 AU는 ① 구성 단계에서 다룹니다.
4. [처리] 작업 이력은 감사 로그에 남지만 막지는 못함
   - 주체: 로그
   - 위치: 모니터링 및 상태 (Monitoring & health) › 감사 로그 (Audit logs)
   - 데이터: 감사 로그 Category = UserManagement · Activity 예) "Reset password" · "Update user" (사후 조회만 가능)
   - 해설: 사고가 나야 발견되는 사후 기록입니다. 로그는 작업이 끝난 뒤 남을 뿐 실행 전에 막지 않습니다.
5. [끝] 오남용 · 실수의 영향이 테넌트 전체
   - 주체: 관리자
   - 데이터: 계정 하나 탈취 = 전체 테넌트 영향
   - 해설: 한 계정의 침해나 실수가 조직 전체로 번집니다. 최소 권한 역할과 AU 범위로 줄이면 영향이 AU 멤버로 한정됩니다.

#### L4 · ① 구성 — 최소 권한 역할과 관리 단위를 만든다

1. [시작] Privileged Role Administrator로 로그인
   - 주체: 관리자
   - 위치: entra.microsoft.com (AU 생성 · AU 멤버 추가 · 역할 할당 · 사용자 지정 역할 생성은 모두 Privileged Role Administrator 이상)
   - 데이터: roleAssignments · PowerShell 사용 시 Connect-MgGraph -Scopes "RoleManagement.ReadWrite.Directory"(역할 할당·정의) 또는 "AdministrativeUnit.ReadWrite.All"(AU)
   - 해설: 위임 구조를 설계하는 사람 자신이 높은 권한 역할이 필요합니다. 역할을 받는 AU 관리자에게는 사용자당 Entra ID P1이 필요합니다.
2. [처리] 작업에 필요한 최소 기본 제공 역할 선택
   - 주체: 관리자
   - 위치: ID › 역할 및 관리자 (Roles & admins) › 역할 이름 선택(체크박스가 아니라 이름을 눌러 열기) › 설명 [확인 필요: 탭 이름]
   - 데이터: roleDefinition.rolePermissions (allowedResourceActions) · 기본 제공 역할은 수정할 수 없고 역할별 권한 목록은 "Microsoft Entra built-in roles" 문서에 있음
   - 해설: 작업에 필요한 가장 작은 권한의 역할을 고릅니다 (예: 헬프데스크 관리자). AU 범위로 쓸 수 있는 기본 제공 역할은 Authentication · Groups · Helpdesk · License · Password · User Administrator 등으로 한정됩니다.
3. [처리] 관리 단위 만들기 — 이름 · 설명 · 제한된 관리 여부
   - 주체: 관리자
   - 위치: ID › 역할 및 관리자 › 관리 단위 (Admin units) › 추가 (Add) › Name · Description · Restricted management administrative unit 토글 › (선택) Assign roles 탭 › Review + create › Create
   - 데이터: administrativeUnit (displayName · description · isMemberManagementRestricted) · POST /v1.0/directory/administrativeUnits · PowerShell New-MgDirectoryAdministrativeUnit · 제한된 관리 여부는 생성할 때만 정하고 나중에 바꿀 수 없음
   - 해설: 부서나 지역처럼 위임 단위가 될 사용자·그룹·디바이스 묶음을 만듭니다. AU는 중첩할 수 없고 Entra ID Governance 기능에서는 현재 쓸 수 없습니다.
4. [처리] AU에 사용자 · 그룹 · 디바이스 추가
   - 주체: 관리자
   - 위치: 관리 단위 › {AU} › 사용자 · 그룹 · 디바이스 › 멤버 추가 (사용자는 Bulk operations › Bulk add members로 CSV 일괄 추가) · 개체 쪽에서는 해당 개체 › Administrative units › Assign to administrative unit · 동적 규칙은 AU › 속성 (Properties) › 멤버십 유형 (Membership type)
   - 데이터: AU members — 그룹을 넣으면 그룹 개체만 포함되고 멤버 사용자는 별도 추가 · POST /v1.0/directory/administrativeUnits/{id}/members/$ref { "@odata.id": ".../users/{id}" } · New-MgDirectoryAdministrativeUnitMemberByRef · 한 개체는 최대 30개 AU에 소속 가능
   - 해설: AU에는 사용자, 그룹, 디바이스만 담을 수 있고 중첩은 안 됩니다. AU 멤버 사용자는 Free 라이선스면 충분합니다.
5. [처리] AU 범위로 역할 할당
   - 주체: 관리자
   - 위치: 관리 단위 › {AU} › 역할 및 관리자 (Roles and administrators) › {역할} › 할당 추가 (Add assignments)
   - 데이터: POST /v1.0/roleManagement/directory/roleAssignments { principalId · roleDefinitionId · directoryScopeId = "/administrativeUnits/{id}" } · 대안 POST /directory/administrativeUnits/{id}/scopedRoleMembers · 지원하지 않는 역할은 400 Bad Request · 비테넌트 범위 기본 제공 역할 할당은 보안 주체당 최대 100건
   - 해설: 역할의 영향이 AU 멤버로 제한됩니다. 이 범위는 AU 멤버를 관리한다는 뜻이며 AU 자체나 테넌트 설정(예: 그룹 만료 정책)은 관리하지 못합니다.
6. [처리] 보안 주체 선택 — 사용자 · 역할 할당 가능 그룹 · 서비스 주체
   - 주체: 관리자
   - 위치: 할당 추가 창 (역할 할당 가능 그룹만 목록에 표시) · 그룹 만들 때 "Microsoft Entra roles can be assigned to the group" = Yes
   - 데이터: group.isAssignableToRole = true — 생성할 때만 지정할 수 있고 변경 불가 · 테넌트당 최대 500개 · 멤버십 유형은 Assigned만(동적 그룹 불가) · 그룹 중첩 불가 · 그룹 멤버 변경에는 Graph 권한 RoleManagement.ReadWrite.Directory 필요(Group.ReadWrite.All로는 불가)
   - 해설: 그룹에 역할을 주려면 처음부터 역할 할당 가능 그룹으로 만들어야 합니다. 온프레미스 그룹에는 Entra 역할을 할당할 수 없습니다.
7. [처리] 상시 할당 대신 PIM 적격 할당 검토
   - 주체: 관리자
   - 위치: ID 거버넌스 (ID Governance) › Privileged Identity Management › Microsoft Entra 역할 (Microsoft Entra roles) › 할당 추가 › Membership settings › Assignment type: Eligible 또는 Active
   - 데이터: 적격(eligible) 할당 · 시작·종료 시간 (Entra ID P2) · 활성화할 때 MFA · 사유 · 승인을 요구할 수 있음
   - 해설: 역할은 할당해 두되 사용자가 필요할 때만 활성화해서 쓰도록(적격) 하고 시간을 제한합니다. 활성(Active)으로 두면 활성화 없이 바로 쓰게 됩니다. 역할 할당 가능 그룹을 적격으로 쓴다면 적격 멤버 추가에 승인 절차를 두는 것이 권장됩니다.
8. [끝] 할당 저장 — 감사 로그에 범위 할당 기록
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 감사 로그 (카테고리 RoleManagement · AdministrativeUnit)
   - 데이터: 감사 로그 RoleManagement "Add scoped member to role" (AU 범위) · "Add member to role" (테넌트 범위) · AdministrativeUnit "Add administrative unit" · "Add member to administrative unit"
   - 해설: 누가 어느 범위에 어떤 권한을 받았는지 기록됩니다. 역할 할당이나 회수가 실제로 적용되기까지 최대 15분이 걸리거나 다시 로그인해야 할 수 있습니다.

#### L4 · ② 활성 — 범위 안에서만 작업이 허용된다

1. [시작] 위임 관리자가 관리 작업 호출
   - 주체: 관리자
   - 위치: 포털 또는 PATCH /v1.0/users/{id} 같은 Graph 호출
   - 데이터: 액세스 토큰 + 대상 개체 ID · 서비스 주체와 게스트는 AU 범위 할당만으로는 개체를 읽지 못해 테넌트 범위 Directory Readers가 추가로 필요
   - 해설: 포털의 관리 작업도 내부적으로 Graph 호출입니다. 호출자는 사용자 또는 서비스 주체일 수 있습니다.
2. [처리] Graph가 토큰으로 호출자를 식별
   - 주체: Entra ID
   - 데이터: 액세스 토큰의 wids 클레임 (역할 템플릿 ID 목록)
   - 해설: 상황에 따라 토큰의 wids 클레임으로 역할 멤버십을 보거나 디렉터리의 할당 정보를 조회합니다. 역할 변경이 토큰에 반영되기까지 지연이 있을 수 있습니다.
3. [처리] 대상 리소스에 적용되는 역할 할당 조회
   - 주체: Entra ID
   - 데이터: roleAssignments (직접 + 그룹 경유 · principalId · roleDefinitionId · directoryScopeId)
   - 해설: 호출자에게 걸린 모든 할당을 모읍니다. 직접 받은 할당과 역할 할당 가능 그룹을 거쳐 받은 할당을 모두 포함합니다.
4. [판단] 요청한 작업이 역할 정의에 포함되는가?
   - 주체: Entra ID
   - 데이터: roleDefinition.rolePermissions.allowedResourceActions (예: microsoft.directory/applications/credentials/update 같은 작업 문자열)
   - 해설: 역할이 허용하지 않는 작업은 범위와 상관없이 거부됩니다. 요청한 범위에 해당 작업을 가진 역할이 없으면 접근이 허용되지 않습니다.
   - 예 → 5
   - 아니오 → [차단] 거부 — 역할에 해당 작업 권한 없음
5. [판단] 대상이 할당 범위 안인가?
   - 주체: Entra ID
   - 데이터: 범위 — 테넌트("/") · AU 멤버("/administrativeUnits/{id}") · 리소스("/{개체 ID}") · 제한된 관리 AU 소속 개체는 그 AU 범위로 명시 할당된 관리자만 수정 가능
   - 해설: AU 범위 할당은 그 AU의 멤버에게만 적용됩니다. 제한된 관리 AU에 속한 개체는 테넌트 범위의 Global Administrator나 Privileged Role Administrator도 수정할 수 없습니다.
   - 예 → 6
   - 아니오 → [차단] 거부 — 범위 밖 대상
6. [판단] AU 범위 역할이면 대상이 비관리자인가?
   - 주체: Entra ID
   - 데이터: 대상 사용자의 관리자 역할 보유 여부 · 제한되는 작업: 인증 방법 읽기·변경 · 암호 재설정 · 전화번호·대체 이메일·OAuth 비밀 키 같은 민감 속성 수정 · 사용자 삭제·복원
   - 해설: AU 범위 헬프데스크도 관리자 계정의 암호·인증 방법은 바꿀 수 없습니다. 예외로 AU 범위 Privileged Authentication Administrator는 관리자·비관리자 모두의 인증 방법을 관리할 수 있습니다.
   - 예 → 7
   - 아니오 → [차단] 거부 — 관리자 대상 암호 재설정·인증 방법 변경 제한
7. [처리] 작업 수행 — 범위 안 대상에만 반영
   - 주체: Entra ID
   - 데이터: 대상 개체 속성 변경 · AU에 그룹만 넣은 경우 그룹 이름·멤버십만 변경되고 멤버 사용자의 속성·암호는 변경되지 않음
   - 해설: 허용된 대상에게만 변경이 적용됩니다. 제한된 관리 AU 개체여도 라이선스 할당, Exchange 메일 설정, Intune 정책 적용은 막히지 않습니다.
8. [끝] 감사 기록 — 수행자 · 대상 · 활동
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 감사 로그 (Audit logs)
   - 데이터: 감사 로그 Category = UserManagement · Activity 예) "Reset password" · "Update user" (수행자 · 대상 · 활동)
   - 해설: 누가 어느 대상에게 무엇을 했는지 남습니다. 작업별 활동 이름은 "Microsoft Entra audit log categories and activities" 참조 문서에서 확인합니다.
- 시나리오: 예 ▸ 예 ▸ 예 :: 역할·범위·AU 조건을 모두 충족해 수행 후 감사 기록
- 시나리오: 예 ▸ 예 ▸ 아니오 :: AU 범위 역할인데 대상이 관리자라 거부
- 시나리오: 예 ▸ 아니오 :: 대상이 할당 범위 밖이라 거부
- 시나리오: 아니오 :: 역할 정의에 없는 작업이라 거부

> 교육 포인트: 역할만 보지 말고 "역할 + 범위"를 함께 봅니다. 같은 역할이라도 범위가 AU면 영향이 AU 멤버로 한정됩니다.

### L3 · A · 역할 할당 평가 — 역할 + 범위 해석

#### L4 · 역할 할당 한 건이 범위에 따라 다르게 적용된다

1. [시작] 역할 할당 한 건 — 보안 주체 · 역할 정의 · 범위
   - 주체: 관리자
   - 위치: ID › 역할 및 관리자 › {역할} › 할당 (Assignments)
   - 데이터: unifiedRoleAssignment (principalId · roleDefinitionId · directoryScopeId) · 보안 주체는 사용자 · 역할 할당 가능 그룹 · 서비스 주체
   - 해설: 세 요소가 모여야 권한이 생기고 할당을 지우면 권한도 사라집니다. 할당은 관리 센터, Microsoft Graph PowerShell, Graph API로 만들 수 있고 Azure CLI는 지원하지 않습니다.
2. [판단] 범위 종류는 무엇인가?
   - 주체: Entra ID
   - 데이터: directoryScopeId 값 — "/" · "/administrativeUnits/{id}" · "/{개체 ID}"
   - 해설: 범위 값에 따라 권한이 미치는 대상이 달라집니다. 기본 제공 역할과 사용자 지정 역할 모두 범위를 좁힐 수 있지만 단일 리소스 범위를 지원하지 않는 기본 제공 역할은 400 오류로 거부됩니다.
   - 테넌트 → 3
   - 관리 단위 → 4
   - 리소스 → 5
3. [처리] 테넌트 범위 — "/"
   - 주체: Entra ID
   - 위치: ID › 역할 및 관리자 › {역할} › 할당 추가 · PowerShell: $directoryScope = '/' 후 New-MgRoleManagementDirectoryRoleAssignment
   - 데이터: directoryScopeId = "/" · 테넌트 범위 기본 제공 역할 할당은 개수 제한이 없음
   - 해설: 역할의 권한이 테넌트 전체 개체에 적용됩니다. 컨테이너 범위이므로 개체에는 권한을 주지만 테넌트라는 컨테이너 자체를 뜻하지는 않습니다.
   - 다음 → 6
4. [처리] AU 범위 — "/administrativeUnits/{id}"
   - 주체: Entra ID
   - 위치: ID › 역할 및 관리자 › 관리 단위 › {AU} › 역할 및 관리자 › {역할} › 할당 추가
   - 데이터: directoryScopeId = "/administrativeUnits/{id}" · AU 관리자는 사용자당 P1 · 서비스 주체와 게스트는 테넌트 범위 Directory Readers가 추가로 필요(디렉터리 읽기 권한은 AU 범위로 줄 수 없음)
   - 해설: AU 멤버를 관리할 수 있지만 AU 자체나 테넌트 설정(그룹 만료·이름 지정 정책 등)은 관리할 수 없습니다. AU 안에 그룹만 넣었다면 그 멤버 사용자까지 관리되지는 않습니다.
   - 다음 → 6
5. [처리] 리소스 범위 — "/{개체 ID}"
   - 주체: Entra ID
   - 위치: ID › 앱 등록 (App registrations) › {앱} › 역할 및 관리자 › 역할 선택 › 할당 추가 (엔터프라이즈 앱 · 그룹도 같은 방식)
   - 데이터: 앱 등록 · 엔터프라이즈 앱 · 그룹 개체 (directoryScopeId = "/{id}") · 목록에는 해당 개체 관리와 관련된 역할만 표시
   - 해설: 그 리소스 자체만 관리하며 그룹일 때도 멤버에게는 미치지 않습니다. 앱 하나의 자격 증명만 관리하게 하려는 경우처럼 두 번째 사용자 지정 역할을 만들지 않고도 범위를 좁힐 수 있습니다.
6. [처리] 간접 할당 확장 — 그룹 멤버십으로 받은 역할
   - 주체: Entra ID
   - 위치: ID › 그룹 › 새 그룹 › "Microsoft Entra roles can be assigned to the group" = Yes (생성 시에만 설정)
   - 데이터: 역할 할당 가능 그룹 (isAssignableToRole) 멤버십 · 불변 속성 · 테넌트당 최대 500개 · 멤버십 유형은 Assigned만 · 그룹 중첩 불가 · 그룹 구성원·소유자의 자격 증명·MFA 초기화·민감 속성 변경에는 Privileged Authentication Administrator 이상 필요
   - 해설: 사용자는 직접 할당과 그룹 경유 할당을 모두 가집니다. 동적 멤버십으로 자동 채워진 그룹에 역할을 주면 권한이 의도치 않게 상승할 수 있어 허용되지 않습니다.
7. [처리] 요청 작업을 허용하는 할당이 하나라도 있는지 판정
   - 주체: Entra ID
   - 데이터: 요청 범위에서 allowedResourceActions에 작업이 있는 역할 존재 여부 · 사용자 지정 역할 할당은 보안 주체당 최대 150건
   - 해설: 요청 범위에 해당 작업을 허용하는 역할이 없으면 접근이 거부됩니다. 할당을 추가하거나 회수한 뒤 효력이 나타나기까지 최대 15분이 걸리거나 다시 로그인해야 할 수 있습니다.
8. [끝] 할당 목록 확인
   - 주체: 관리자
   - 위치: ID › 역할 및 관리자 › {역할} › 할당 (CSV 내려받기 가능) · GET /v1.0/roleManagement/directory/roleAssignments?$filter=principalId eq '{id}'
   - 데이터: roleAssignments (principalId · roleDefinitionId · directoryScopeId) · 최소 권한 Graph 권한 RoleManagement.Read.Directory · 호출자 역할은 Directory Readers · Global Reader · Privileged Role Administrator 중 하나 · $filter · $expand · $select 지원
   - 해설: 포털과 Graph 모두에서 현재 할당을 감사할 수 있습니다. 감사 로그로는 할당이 언제 바뀌었는지 함께 추적합니다.
- 시나리오: 테넌트 :: 테넌트 범위 할당을 확장해 평가하고 목록 확인
- 시나리오: 관리 단위 :: 관리 단위(AU) 범위 할당을 확장해 평가하고 목록 확인
- 시나리오: 리소스 :: 리소스 범위 할당을 확장해 평가하고 목록 확인

> 교육 포인트: 컨테이너 범위(테넌트·AU)는 안의 개체에 권한을 주고 컨테이너 자체는 포함하지 않습니다. 리소스 범위는 리소스 자체를 관리합니다.
>
> 주의: PIM 적격 할당은 할당된 역할을 활성화해야 사용할 수 있고, 활성 할당은 할당 즉시 활성화 없이 사용합니다. 상세는 PIM 기능에서 다룹니다.

### L3 · B · 관리 단위 위임 — AU 설계 · 멤버 · 제한된 관리

#### L4 · 부서·지역 단위 위임을 AU로 구성한다

1. [시작] 지역·부서별 위임 요구 발생
   - 주체: 관리자
   - 데이터: 예) 서울 헬프데스크는 서울 사용자만 관리 · 예) 대학의 학부 IT 팀은 자기 학부만 관리 · 예) 임원 계정은 지정한 소수만 관리
   - 해설: 같은 역할을 조직 단위로 나눠 줘야 하는 요구입니다. AU는 독립적으로 운영되는 부서나 지역이 있는 조직에서 특히 유용합니다.
2. [처리] AU 구조 설계 — 중첩 불가 · 다중 소속 가능
   - 주체: 관리자
   - 위치: ID › 역할 및 관리자 › 관리 단위
   - 데이터: AU는 사용자 · 그룹 · 디바이스만 포함 · 한 사용자가 여러 AU에 소속 가능(개체당 최대 30개) · AU 개수 자체의 제한은 없음 · 제한된 관리 AU는 테넌트당 최대 100개
   - 해설: AU는 중첩할 수 없으므로 처음부터 평평한 기준(지역 · 부서)으로 나눕니다. Microsoft 365 전반에서 쓰이므로 다른 서비스에서의 활용도 함께 보고 설계합니다.
3. [처리] AU 멤버 구성 — 수동 또는 동적 규칙
   - 주체: 관리자
   - 위치: 관리 단위 › {AU} › 속성 (Properties) › 멤버십 유형 (Membership type): Assigned · Dynamic User · Dynamic Device › 동적 쿼리 추가 (Add dynamic query) [확인 필요: 한글 메뉴명]
   - 데이터: 동적 규칙은 사용자 또는 디바이스 한 종류만 가능하고 그룹용 동적 AU는 미지원 · 동적 AU의 멤버 사용자(고유 사용자 수)마다 P1 필요(사용자에게 라이선스를 할당할 필요는 없고 테넌트 보유 수량이 충족돼야 함) · 디바이스는 라이선스 불필요 · 글로벌 클라우드에서만 사용 가능 · 동적 AU와 동적 그룹 합계 최대 15,000개
   - 해설: 규칙으로 멤버를 채우면 인사 이동이 자동으로 따라옵니다. 멤버십 유형을 바꾸면 기존 멤버가 규칙 결과에 맞춰 바뀔 수 있다는 확인 창이 나타납니다.
4. [판단] 그룹을 AU에 추가했는가?
   - 주체: 관리자
   - 데이터: AU members에 group 개체 포함 여부 · 그룹 개체와 그 멤버 사용자는 별개 개체
   - 해설: 그룹을 넣어도 그 안의 사용자가 AU 멤버가 되는 것은 아닙니다. AU 범위 User Administrator가 그룹 이름과 멤버십은 관리하지만 멤버 사용자의 속성·인증 방법·암호는 관리하지 못합니다.
   - 예 → 5
   - 아니오 → 6
5. [처리] 그룹 개체만 범위 — 멤버 사용자는 별도로 추가
   - 주체: 관리자
   - 위치: 관리 단위 › {AU} › 그룹 › 추가
   - 데이터: 그룹 이름 · 멤버십 관리는 가능, 멤버의 속성 · 암호 재설정 · 인증 방법 관리는 불가
   - 해설: 멤버 사용자까지 관리하려면 사용자를 AU 멤버로 직접 추가해야 합니다. 그룹 안의 멤버 변화가 AU 멤버십에 자동 반영되지 않으므로 사용자 대상 위임이 목적이면 동적 규칙이 더 알맞습니다.
   - 다음 → 7
6. [처리] 사용자를 AU 멤버로 직접 추가
   - 주체: 관리자
   - 위치: 관리 단위 › {AU} › 사용자 › 멤버 추가 · 일괄 추가는 사용자 › Bulk operations › Bulk add members (CSV 템플릿 업로드)
   - 데이터: AU members (user) · New-MgDirectoryAdministrativeUnitMemberByRef 또는 POST /v1.0/directory/administrativeUnits/{id}/members/$ref
   - 해설: AU 멤버가 된 사용자는 AU 범위 관리자가 관리할 수 있습니다. 같은 사용자가 여러 AU에 소속될 수 있으므로 지역과 부서 기준을 겹쳐 쓸 수 있습니다.
7. [처리] 제한된 관리 AU 선택 — 테넌트 관리자도 접근 불가
   - 주체: 관리자
   - 위치: 관리 단위 › 추가 › Restricted management administrative unit = Yes (AU 생성 시에만 선택 가능, 이후 변경 불가) [확인 필요: 한글 메뉴명]
   - 데이터: isMemberManagementRestricted = true · 감사 로그 "Add member to restricted management administrative unit" · 멤버로 넣을 수 있는 개체는 사용자 · 디바이스 · 보안 그룹뿐(Microsoft 365 · 메일 사용 보안 · 배포 그룹은 불가) · 삭제 뒤 보호가 완전히 풀리기까지 최대 30분
   - 해설: 임원 계정처럼 테넌트 수준 관리자에게도 맡기고 싶지 않은 대상을 보호합니다. 테넌트 범위 Global Administrator와 Privileged Role Administrator는 개체를 못 고치지만 AU 자체를 관리하고 자신에게 AU 범위 역할을 줄 수 있으며 이 행위는 감사 로그에 남습니다. 기존 워크플로가 깨질 수 있고 PIM · 권한 관리 · 수명 주기 워크플로 · 액세스 검토로는 이 개체들을 관리할 수 없습니다.
8. [끝] AU 범위로 역할 할당 — 헬프데스크 · 사용자 · 그룹 · 라이선스 관리자 등
   - 주체: 관리자
   - 위치: 관리 단위 › {AU} › 역할 및 관리자 › {역할} › 할당 추가
   - 데이터: 감사 로그 RoleManagement "Add scoped member to role" (제한된 관리 AU는 "Add member to role scoped over Restricted Management Administrative Unit") · 서비스 주체와 게스트는 테넌트 범위 Directory Readers 필요 · 애플리케이션은 Graph 애플리케이션 권한이 아니라 AU 범위 Entra 역할을 받아야 제한된 관리 AU 개체를 수정 가능
   - 해설: AU에서 선택할 수 있는 역할은 사용자·그룹·디바이스 권한이 있는 역할만 표시됩니다. 예를 들어 Teams Administrator와 SharePoint Administrator는 AU 범위에서 Microsoft 365 그룹 관리에 한정되고 각 관리 센터 자체는 쓸 수 없습니다.
- 시나리오: 예 :: 그룹을 AU에 추가해 그룹 개체만 위임
- 시나리오: 아니오 :: 사용자를 AU 멤버로 직접 추가해 위임

> 교육 포인트: AU 범위 역할은 테넌트 전체 설정(그룹 만료 정책 등)을 관리하지 못합니다. 그래서 "역할 + AU 범위"가 최소 권한에 맞습니다.
>
> 주의: 제한된 관리 AU에서 공개(Public) 멤버십 그룹은 사용자가 스스로 가입할 수 있어 권장되지 않습니다. 제한된 관리 AU에 있는 Global Administrator의 암호는 AU 범위로 줄 수 있는 역할로는 재설정할 수 없어 AU에서 먼저 빼야 합니다.

### L3 · C · 사용자 지정 역할 — 필요한 권한만 골라 정의

#### L4 · 기본 제공 역할이 넓을 때 권한 단위로 역할을 만든다

1. [시작] 기본 제공 역할로는 과하거나 부족한 위임 요구
   - 주체: 관리자
   - 데이터: 예) 앱 등록의 자격 증명만 관리 · 사용자 지정 역할은 할당받은 사용자마다 Entra ID P1 필요 · 테넌트당 최대 100개
   - 해설: 필요한 권한만 담은 역할이 필요한 경우입니다. 사용자 지정 역할은 역할 정의를 만든 뒤 역할 할당으로 부여하는 두 단계입니다.
2. [처리] 사용 가능한 권한 범주 확인
   - 주체: 관리자
   - 위치: Microsoft Learn › 사용자 지정 역할에 쓸 수 있는 권한 문서 (앱 등록 · 엔터프라이즈 앱 · 동의 · 디바이스 · 사용자 · 그룹 범주별 문서)
   - 데이터: 사용자 지정 사용이 가능한 범주 — 앱 등록 · 엔터프라이즈 앱 · 동의 · 디바이스 · 사용자 · 그룹
   - 해설: 모든 권한이 아니라 사용자 지정 허용 권한만 고를 수 있습니다. 기본 제공 역할에 쓰이는 권한 목록에서 미리 필요한 작업을 골라 두면 편합니다.
3. [처리] 새 사용자 지정 역할 — 기본 사항 입력
   - 주체: 관리자
   - 위치: ID › 역할 및 관리자 › 새 사용자 지정 역할 (New custom role) › 기본 사항 (Basics)
   - 데이터: 이름 · 설명 · 기존 사용자 지정 역할 복제(기본 제공 역할은 복제 불가) · 생성자는 Privileged Role Administrator 이상, 라이선스는 P1 또는 P2
   - 해설: 이름과 설명을 정하고 필요하면 기존 사용자 지정 역할에서 시작합니다.
4. [처리] 권한 선택
   - 주체: 관리자
   - 위치: 새 사용자 지정 역할 › 권한 (Permissions) (검색: credentials · basic)
   - 데이터: microsoft.directory/applications/credentials/update · microsoft.directory/applications/basic/update
   - 해설: 작업 이름(권한)을 하나씩 골라 역할에 담습니다. 이 예에서는 앱 등록의 기본 속성과 자격 증명만 바꿀 수 있는 역할이 됩니다.
5. [처리] 검토 후 만들기 — 역할 정의 생성
   - 주체: 관리자
   - 위치: 새 사용자 지정 역할 › 검토 + 만들기 (Review + create) › 만들기 · POST /v1.0/roleManagement/directory/roleDefinitions · PowerShell New-MgRoleManagementDirectoryRoleDefinition (Connect-MgGraph -Scopes "RoleManagement.ReadWrite.Directory")
   - 데이터: roleDefinition { displayName · description · isEnabled · templateId(선택, (New-Guid).Guid로 생성) · rolePermissions[].allowedResourceActions } · 수정은 Update-MgRoleManagementDirectoryRoleDefinition, 삭제는 Remove-MgRoleManagementDirectoryRoleDefinition
   - 해설: 만들어지면 할당 가능한 역할 목록에 나타납니다. 같은 공통 속성의 역할을 여러 개 만들 때는 templateId를 미리 정해 두는 편이 좋습니다.
6. [처리] 역할 할당 — 디렉터리 또는 앱 등록 범위
   - 주체: 관리자
   - 위치: ID › 역할 및 관리자 › {사용자 지정 역할} › 할당 추가 · 앱 범위는 ID › 앱 등록 › {앱} › 역할 및 관리자 › 할당 추가 · POST /v1.0/roleManagement/directory/roleAssignments
   - 데이터: directoryScopeId = "/" 또는 "/{앱 등록 ID}" · 사용자·그룹·디바이스 권한을 포함하면 AU 범위로도 할당 가능 · 사용자 지정 역할 할당은 보안 주체당 최대 150건
   - 해설: 사용자 지정 역할은 디렉터리 수준 또는 개체(앱 등록) 범위로 할당하고, 사용자·그룹·디바이스를 다루는 역할이면 AU 범위로도 할당합니다.
7. [판단] 역할 권한에 사용자·그룹·디바이스 관련 권한이 있는가?
   - 주체: Entra ID
   - 데이터: allowedResourceActions의 대상 개체 종류 · AU 범위 할당 시도에서 지원하지 않는 역할이면 400 Bad Request
   - 해설: AU 범위 할당은 이 종류의 권한이 하나라도 있어야 가능합니다.
   - 예 → 8
   - 아니오 → [차단] AU 범위 할당 불가 — 관련 권한 없음
8. [끝] 감사 기록 — 역할 정의 생성 · 할당
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 감사 로그 (카테고리 RoleManagement)
   - 데이터: 감사 로그 RoleManagement "Add role definition" · "Update role definition" · "Delete role definition" · "Add scoped member to role"
   - 해설: 역할 정의 변경과 할당이 모두 감사 로그에 남습니다. 새로 만든 할당이 적용되기까지 최대 15분이 걸리거나 다시 로그인해야 할 수 있습니다.
- 시나리오: 예 :: 권한에 사용자·그룹·디바이스 관련 있어 할당 후 감사 기록
- 시나리오: 아니오 :: 관련 권한이 없어 AU 범위 할당 불가

> 교육 포인트: 사용자 지정 역할은 역할 정의를 한 번 만들고 서로 다른 범위로 여러 번 할당할 수 있습니다.
