## L2 · 디바이스 ID — Join · 등록 · 디바이스 설정

- 설정(Control Plane): 디바이스 설정(Join·등록 허용 범위 · MFA 요구 · 기기 한도) | 하이브리드 조인 구성 (SCP · 동기화)
- 강제(Enforcement): Entra 디바이스 등록 서비스(DRS) | PRT 발급 (기기 ID 클레임)
- 증적(Evidence): 디바이스 목록 Join 유형(trustType) | 감사 로그 Device · KeyManagement | SigninLogs DeviceDetail
- 메뉴(Admin Center): ID > 디바이스
- 라이선스(License): 디바이스 등록 · Join · 디바이스 목록은 Entra ID Free 포함 [확인 필요: 고객 라이선스]

### L3 · 0 · 기능 상태 전이 — 미등록 → Join·등록 구성 → 기기 ID가 PRT·토큰에 반영

#### L4 · ⓪ 비활성 — 기기가 Entra에 알려져 있지 않다

1. [시작] 사용자가 미등록 기기에서 로그인
   - 주체: 사용자
   - 위치: 브라우저 · 앱 → login.microsoftonline.com
   - 데이터: 요청에 기기 인증서 · PRT 없음. 개인 기기의 브라우저처럼 Entra 신원이 없는 기기는 키 쌍만 가진 비등록 PRT를 쓸 수 있습니다
   - 해설: Entra가 모르는 기기에서 로그인이 시작됩니다
2. [처리] Entra가 기기 신호를 찾지만 디바이스 개체 없음
   - 주체: Entra ID
   - 위치: 모니터링 및 상태 › 로그인 로그 › 해당 로그인 상세의 디바이스 정보
   - 데이터: SigninLogs.DeviceDetail.deviceId 비어 있음 (deviceId·displayName·browser는 Entra에 등록된 기기에서만 채워짐)
   - 해설: 기기 정보가 없어 기기 상태 조건을 평가할 수 없습니다
3. [판단] 조건부 액세스가 기기 상태를 요구하는가?
   - 주체: Entra ID
   - 위치: 보호 › 조건부 액세스 › 정책 › 액세스 제어 › 권한 부여 (Grant)
   - 데이터: Grant 컨트롤 "준수 디바이스 요구" · "하이브리드 조인 디바이스 요구". PRT는 등록된 기기에 발급된 것일 때만 기기 정책을 충족하며, 비등록 기기용 PRT는 충족하지 못합니다
   - 해설: 기기 조건을 요구하는 정책은 기기 ID가 없으면 충족되지 않습니다
   - 예 → [차단] 차단 — 기기 ID가 없어 Grant 충족 불가
   - 아니오 → 4
4. [처리] 사용자 ID만으로 토큰 발급 — 기기 신뢰 신호 없음
   - 주체: Entra ID
   - 위치: Entra 토큰 발급 서비스
   - 데이터: 토큰에 기기 ID 클레임 없음
   - 해설: 기기 정보 없이 사용자 인증만으로 토큰이 발급됩니다
5. [끝] 회사 기기와 개인 기기를 구분할 수 없다
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 로그인 로그 · ID › 디바이스 › 모든 디바이스 (해당 기기가 목록에 없음)
   - 데이터: 로그인 로그에 기기 식별 정보 없음 · isCompliant · isManaged · trustType도 비어 있어 기기 기준 필터링이 불가
   - 해설: 기기 기반 통제를 걸고 싶어도 구분 기준이 없습니다
- 시나리오: 예 :: 기기 상태 요구 정책이 있어 미등록 기기 차단
- 시나리오: 아니오 :: 요구 정책이 없어 ID만으로 발급, 기기 구분 불가

#### L4 · ① 구성 — 허용 범위를 정하고 Join 방식을 준비한다

1. [시작] 관리자가 디바이스 설정을 연다
   - 주체: 관리자
   - 위치: ID › 디바이스 › 모든 디바이스 › 디바이스 설정 (Cloud Device Administrator 읽기·수정, Intune Administrator·Windows 365 Administrator 읽기 전용)
   - 데이터: 디바이스 등록 정책 (deviceRegistrationPolicy) — GET /v1.0/policies/deviceRegistrationPolicy (위임 권한 Policy.Read.DeviceConfiguration, 호출자는 Global Reader · Cloud Device Administrator · Intune Administrator · Windows 365 Administrator · Directory Reviewer 중 하나)
   - 해설: 디바이스 등록 정책을 보거나 바꾸려면 지정된 역할이 필요합니다
2. [처리] Join 허용 사용자 지정 — 기본값 모두
   - 주체: 관리자
   - 위치: 디바이스 설정 › 사용자가 Microsoft Entra ID에 디바이스를 조인할 수 있음 (모두 · 선택 · 없음) [확인 필요: 한글 메뉴명]
   - 데이터: deviceRegistrationPolicy.azureADJoin (allowedToJoin) · 기본값 모두 · Windows 10 이상·macOS·Linux의 Entra join에만 적용
   - 해설: 누가 Entra join을 할 수 있는지 정합니다. 하이브리드 조인, Azure의 Entra 조인 VM, Windows Autopilot 셀프 배포 모드(사용자 없는 방식)에는 적용되지 않습니다
3. [처리] 디바이스 등록 허용 지정
   - 주체: 관리자
   - 위치: 디바이스 설정 › 사용자가 디바이스를 Microsoft Entra ID에 등록할 수 있음 (모두 · 없음) [확인 필요: 한글 메뉴명]
   - 데이터: Windows 10 이상 개인 · iOS · Android · macOS 등록 허용 여부 (Intune 구성 시 모두로 고정) · deviceRegistrationPolicy.azureADRegistration
   - 해설: Intune 등록은 Entra 등록을 전제로 하므로 없음을 선택할 수 없습니다. 없음이면 이 방식의 등록이 모두 거부됩니다
4. [처리] 등록·Join 시 MFA 요구 방식 선택
   - 주체: 관리자
   - 위치: 디바이스 설정 › 등록 또는 조인 시 MFA 요구 = 아니요 + 보호 › 조건부 액세스 › 정책 › 새 정책 만들기 › 사용자 작업 › 디바이스 등록 또는 조인 (Conditional Access Administrator 이상)
   - 데이터: CA 사용자 작업 (urn:user:registerdevice) · 설정 토글은 기본값 아니요 (multiFactorAuthConfiguration = notRequired) · CA 권한 부여는 기본 제공 인증 강도 Multifactor authentication
   - 해설: 권장 방식은 토글 대신 조건부 액세스 사용자 작업으로 MFA를 요구하는 것입니다. CA 정책을 쓸 때는 토글을 반드시 아니요로 두어야 정책이 제대로 적용되며, 토글은 하이브리드 조인·Azure의 Entra 조인 VM·Autopilot 셀프 배포에는 적용되지 않고 서드파티 ID 공급자에서는 동작하지 않을 수 있습니다
5. [처리] 사용자당 기기 한도와 로컬 관리자 지정
   - 주체: 관리자
   - 위치: 디바이스 설정 › 최대 디바이스 수 · 추가 로컬 관리자 관리 · 등록 사용자를 로컬 관리자로 추가 [확인 필요: 한글 메뉴명]
   - 데이터: 한도 기본 50 · 최대 100 (100 초과 입력은 100으로 조정, 무제한 선택 가능) · userDeviceQuota · Microsoft Entra Joined Device Local Administrator 역할 (테넌트 전체 Entra join 기기에 적용) · 로컬 관리자 암호 솔루션(LAPS)은 미리 보기
   - 해설: 한도는 Entra join과 등록 기기에만 적용되고 하이브리드 조인은 제외됩니다. 한도에 도달하면 기존 기기를 지우기 전에는 추가할 수 없습니다. Graph로 정책을 갱신할 때 userDeviceQuota를 빼면 0(조인 불가)으로 초기화되므로 값을 항상 함께 보냅니다
6. [처리] 하이브리드 조인 준비 — SCP 구성
   - 주체: 관리자
   - 위치: Microsoft Entra Connect 마법사 › 추가 작업 › 디바이스 옵션 구성 › 하이브리드 조인 구성 › SCP 구성 (포리스트 · 인증 서비스 · 엔터프라이즈 관리자 자격)
   - 데이터: AD 구성 파티션의 서비스 연결 지점 (Device Registration Configuration 컨테이너 · keywords 값) · Connect 1.1.819.0 이상 · Entra 쪽 Hybrid Identity Administrator 자격 · 포리스트별 엔터프라이즈 관리자 자격 · 페더레이션이면 인증 서비스에서 AD FS 서버를 선택
   - 해설: 도메인 PC가 어느 등록 서비스로 갈지 AD의 SCP가 알려 줍니다. 대부분의 조직은 PHS·PTA와 원활한 SSO를 쓰는 관리형 도메인으로 배포합니다
7. [처리] 컴퓨터 개체를 동기화 범위에 포함
   - 주체: 관리자
   - 위치: Connect Sync › OU 기반 필터링 — 조인할 PC의 OU 포함, 기본 디바이스 속성 제외 금지
   - 데이터: AD computer 개체 (userCertificate · objectGUID · SID)
   - 해설: 컴퓨터 개체가 동기화되어야 Entra에 디바이스 개체가 생깁니다 (자세한 동기화는 "동기화 경로" 참조)
8. [처리] 기기의 Microsoft 연결 요건 확인
   - 주체: 관리자
   - 위치: 프록시 · 방화벽 — enterpriseregistration.windows.net · login.microsoftonline.com · device.login.microsoftonline.com 허용 (원활한 SSO를 쓰면 autologon.microsoftazuread-sso.com, 페더레이션이면 사내 STS도 접근 가능해야 함)
   - 데이터: device.login · enterpriseregistration 주소는 TLS 검사 제외 · 인증 프록시는 컴퓨터(머신) 컨텍스트에서 인증되도록 구성 (등록이 머신 컨텍스트로 실행됨) · WPAD 또는 GPO의 WinHTTP 프록시 설정 · 시스템 계정 연결 점검용 Test Device Registration Connectivity 스크립트
   - 해설: TLS를 가로채면 기기 인증서 인증이 깨져 등록과 기기 기반 CA가 실패합니다
9. [끝] 저장 — 이후 Join·등록부터 적용
   - 주체: 관리자
   - 위치: 디바이스 설정 › 저장
   - 데이터: 감사 로그 Policy "Set device registration policies"
   - 해설: 이미 등록된 기기가 아니라 앞으로의 등록에 적용됩니다

#### L4 · ② 활성 — 기기 ID가 로그인 판정에 쓰인다

1. [시작] 기기가 Join 또는 등록을 마친 상태
   - 주체: 디바이스
   - 위치: dsregcmd /status (DeviceId · AzureAdJoined · DomainJoined) · ID › 디바이스 › 모든 디바이스 (Join 유형·등록됨 열)
   - 데이터: devices 개체 (deviceId · trustType · registrationDateTime) · trustType: AzureAd = Entra join, ServerAd = 하이브리드 조인, Workplace = 등록
   - 해설: 디바이스 개체와 기기 인증서가 있어야 기기 ID로 인증할 수 있습니다
2. [처리] 사용자가 Windows에 로그인
   - 주체: 사용자
   - 위치: Windows 로그인 화면 (CloudAP 플러그인)
   - 데이터: 조직 자격 증명 — 암호 또는 Windows Hello for Business (지원되는 자격 증명 모두 PRT 발급 대상, 서드파티 자격 증명 공급자는 미지원)
   - 해설: Entra join·하이브리드 조인 기기는 Windows 로그인 시점에 PRT를 받습니다. CloudAP는 PRT를 캐시해 인터넷이 없어도 캐시 로그인이 되게 합니다
3. [처리] 기기 키로 서명해 Entra에 인증 요청
   - 주체: 디바이스
   - 위치: 기기의 보안 저장소 (TPM이 정상이면 개인 키가 TPM에 바인딩됨)
   - 데이터: 디바이스 키(dkpriv)로 서명 · 전송 키(tkpub)로 세션 키 보호 · 공개 키는 등록 때 Entra에 전달되어 PRT 요청 시 기기 상태 검증에 쓰임
   - 해설: 요청이 등록된 그 기기에서 왔다는 것을 키로 증명합니다
4. [처리] Entra가 PRT 발급 — 사용자와 기기를 묶은 토큰
   - 주체: Entra ID
   - 위치: Entra 토큰 서비스 (CloudAP가 PRT의 1차 권한자)
   - 데이터: PRT는 불투명 blob · 90일 유효 · 사용 중 계속 갱신 (CloudAP가 로그인 시 4시간마다 갱신) · 발급·갱신 시 CA는 평가되지 않음 · Windows Hello for Business 로그인이면 PRT에 MFA 클레임이 붙음 · 서드파티 IdP 페더레이션은 WS-Trust 지원이 있어야 PRT 발급 가능
   - 해설: PRT가 앱 로그인에 쓰이는 SSO의 뿌리입니다. 로그인 빈도(sign-in frequency) 세션 제어로 재인증을 강제할 수 있습니다
5. [처리] 앱이 토큰을 요청하면 WAM이 PRT로 무음 인증
   - 주체: 앱
   - 위치: Windows WAM(Web Account Manager) 브로커 · Entra WAM 플러그인
   - 데이터: 앱별 액세스 토큰 요청 + PRT 헤더 · 브라우저 SSO는 Edge(기본), Chrome(Microsoft Single Sign On 확장), Firefox v91 이상(Windows SSO 설정)에서 지원
   - 해설: 사용자는 다시 로그인하지 않고도 Microsoft 365 앱에 들어갑니다. 같은 테넌트의 두 번째 계정도 브라우저에서 첫 계정의 PRT 기기 인증을 받아 기기 기반 정책을 충족합니다
6. [판단] 조건부 액세스의 기기 조건을 만족하는가?
   - 주체: Entra ID
   - 위치: 보호 › 조건부 액세스 › 정책 › 권한 부여 (Require device to be marked as compliant · Require Microsoft Entra hybrid joined device)
   - 데이터: PRT의 기기 클레임 — 조인 유형 · 준수 여부 (준수는 Intune 연동) · 등록된 기기에서 발급된 PRT만 기기 정책을 충족함
   - 해설: 정책이 요구하는 기기 상태와 PRT가 전달한 기기 정보를 비교합니다
   - 예 → 7
   - 아니오 → [차단] 차단 — 비준수·미조인 기기
7. [처리] 토큰 발급 — 기기 정보 반영
   - 주체: Entra ID
   - 위치: Entra 토큰 서비스
   - 데이터: 액세스 토큰 (사용자 + 기기 컨텍스트)
   - 해설: 조건을 통과하면 앱이 쓸 토큰이 발급됩니다
8. [끝] 로그인 로그에 기기 정보 기록
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 로그인 로그 (SigninLogs.DeviceDetail)
   - 데이터: SigninLogs.DeviceDetail (deviceId · displayName · browser · operatingSystem · isCompliant · isManaged · trustType). deviceId·displayName·browser는 Entra에 등록된 기기에서만 채워짐
   - 해설: 어떤 기기에서 어떤 상태로 로그인했는지 추적할 수 있습니다
- 시나리오: 예 :: 기기 조건을 만족해 토큰 발급 후 기기 정보 기록
- 시나리오: 아니오 :: 기기 조건을 만족하지 못해 로그인 차단

> 교육 포인트: 기기 준수 여부(Intune)를 CA에서 쓰려면 먼저 이 기기 ID가 있어야 합니다. L1 02 "CA 연동"과 이어집니다.
>
> 주의: 디바이스를 사용 안 함으로 바꾸면 PRT와 기기의 갱신 토큰이 폐기됩니다. 삭제는 복구할 수 없습니다.

### L3 · A · Microsoft Entra join — 클라우드 전용 Windows 기기

#### L4 · OOBE 로그인에서 디바이스 개체 생성까지

1. [시작] OOBE에서 회사·학교 계정으로 로그인
   - 주체: 사용자
   - 위치: Windows 초기 설정(OOBE) › Cloud Experience Host(CXH)의 Entra join 웹 앱
   - 데이터: 사용자 UPN
   - 해설: 가장 흔한 Entra join은 OOBE 중 CXH 앱에서 시작됩니다. Join 허용 설정은 Windows 10 이상·macOS·Linux의 Entra join에 적용됩니다
2. [처리] OpenID 구성 조회 — 인증 엔드포인트 발견
   - 주체: 디바이스
   - 위치: Entra OpenID configuration 엔드포인트 (GET)
   - 데이터: 인증 엔드포인트가 담긴 JSON
   - 해설: 앱이 로그인 요청을 보낼 주소를 알아냅니다. 이어 앱이 인증 엔드포인트로 가는 로그인 요청을 만들고 자격 증명을 받을 준비를 합니다
3. [처리] 영역(Realm) 조회 — 관리형인지 페더레이션인지 판별
   - 주체: Entra ID
   - 위치: Entra 영역 조회 엔드포인트 (UPN 입력 직후 GET)
   - 데이터: 영역 정보 JSON (페더레이션이면 AuthURL 포함)
   - 해설: 관리형이면 자격 증명을 Entra에 POST하고 OOBE 중에는 인증 버퍼를 임시 캐시했다가 OOBE 끝에 자동 로그인에 씁니다. 페더레이션이면 AuthURL의 사내 STS 로그인 페이지로 리디렉션해 자격 증명을 받고(추가 인증 요구 가능), 받은 토큰을 Entra에 POST합니다 (방식별 흐름은 "인증 경로" 참조)
4. [처리] 자격 증명 검증 — ID 토큰 수신
   - 주체: Entra ID
   - 위치: Entra 인증 엔드포인트
   - 데이터: ID 토큰 클레임 (mdm_tou_url이 있으면 MDM 약관 표시) · 클레임이 없거나 비어 있으면 약관 단계는 생략
   - 해설: 인증이 끝나면 등록 요청에 쓸 ID 토큰을 받습니다. 약관이 있으면 사용자가 동의할 때까지 기다린 뒤 DRS에 등록 탐색 요청을 보내 테넌트별 등록 URI를 받습니다
5. [판단] 이 사용자가 Join할 수 있는가?
   - 주체: Entra ID
   - 위치: 디바이스 설정 › Join 허용 사용자 · 최대 디바이스 수 [확인 필요: 평가 시점]
   - 데이터: 허용 대상 여부 · 사용자당 기기 수 (기본 50 · 최대 100 · 하이브리드 조인은 제외) · 등록·Join 시 MFA 요구 설정
   - 해설: 허용 대상이 아니거나 한도를 넘으면 Join이 거부됩니다
   - 예 → 6
   - 아니오 → [차단] 차단 — Join 허용 대상 아님 · 한도 초과
6. [처리] 키 쌍 생성 — 디바이스 키와 전송 키
   - 주체: 디바이스
   - 위치: 기기의 TPM (없거나 비정상이면 TPM 바인딩이 되지 않음)
   - 데이터: TPM 바인딩(권장) RSA 2048 디바이스 키(dkpub/dkpriv) + 저장소 루트 키 기반 전송 키(tkpub/tkpriv). 인증서 요청은 dkpub로 만들고 dkpriv로 서명
   - 해설: 이후 PRT 요청을 서명하고 보호할 키를 만듭니다
7. [처리] 등록 요청 — DRS가 디바이스 ID와 인증서 발급
   - 주체: Entra ID
   - 위치: Azure Device Registration Service (DRS)
   - 데이터: ID 토큰 + 인증서 요청 + tkpub + 증명 → 디바이스 개체(trustType = AzureAd)
   - 해설: DRS가 ID 토큰을 검증하고 디바이스 ID를 만든 뒤 인증서 요청으로 인증서를 만들어 디바이스 개체를 쓰고(감사 로그 Device "Register device"), 기기 ID와 인증서를 돌려줍니다
8. [끝] 인증서 설치 후 MDM 등록으로 이어짐
   - 주체: 디바이스
   - 위치: 컴퓨터 개인 저장소 · dsregcmd /status
   - 데이터: 디바이스 ID 저장 · AzureAdJoined = YES · 기기 인증서는 컴퓨터의 개인(Personal) 저장소에 설치
   - 해설: 등록이 끝나면 Intune 같은 MDM 등록이 이어집니다
- 시나리오: 예 :: Join 가능한 사용자라 등록 후 MDM 등록으로 연결
- 시나리오: 아니오 :: Join 권한이 없는 사용자라 차단

> 교육 포인트: 등록 서비스 호출 결과로 만들어진 디바이스 개체는 ID › 디바이스 › 모든 디바이스에서 trustType으로 구분됩니다 (AzureAd = Entra join).

### L3 · B · 하이브리드 조인 — 도메인 가입 PC

#### L4 · 자동 디바이스 조인 작업이 관리형·페더레이션 환경에서 등록한다

1. [시작] 도메인 가입 PC에서 자동 디바이스 조인 작업 시작
   - 주체: 디바이스
   - 위치: 도메인 조인 시 · 사용자 로그온 시 · 1시간 주기 재시도
   - 데이터: 작업 트리거 (로그온에만 의존하지 않음) · 도메인 자격 증명(사용자 이름·암호 또는 스마트 카드)으로 로그온한 Windows 10 이상 PC
   - 해설: 도메인 조인 직후와 로그온마다 등록을 시도하고 실패하면 다시 시도합니다
2. [처리] LDAP로 SCP 조회 — 등록 서비스 결정
   - 주체: 디바이스
   - 위치: AD 구성 파티션 CN=Device Registration Configuration의 SCP (CN=62a0ff2e-97b9-4513-943f-0d221bd30080,CN=Device Registration Configuration,CN=Services,CN=Configuration,DC=…)
   - 데이터: keywords 값 → Azure DRS 또는 온프레미스 엔터프라이즈 등록 서비스
   - 해설: SCP가 PC를 올바른 등록 서비스로 안내합니다
3. [판단] 도메인이 관리형인가 페더레이션인가?
   - 주체: 디바이스
   - 위치: 도메인 인증 방식 (PHS·PTA + 원활한 SSO는 관리형, AD FS 등은 페더레이션)
   - 데이터: 영역 정보 (managed / federated)
   - 해설: 환경에 따라 기기가 자신을 증명하는 방법이 달라집니다. 대부분의 조직은 관리형 도메인으로 하이브리드 조인을 배포합니다
   - 관리형 → 4
   - 페더레이션 → 7
4. [처리] 관리형: 자체 서명 인증서를 컴퓨터 개체에 기록
   - 주체: 디바이스
   - 위치: AD computer 개체 › userCertificate 특성 (LDAP)
   - 데이터: 초기 인증용 자체 서명 인증서
   - 해설: 이 인증서가 Entra에 기기를 알리는 임시 신분증이 됩니다
5. [처리] 동기화가 userCertificate·GUID·SID를 DRS에 전달
   - 주체: 온프레미스
   - 위치: Connect Sync 다음 동기화 주기 (동기화 경로 참조)
   - 데이터: userCertificate · objectGUID · 컴퓨터 SID → 디바이스 개체 (포털 등록됨 열: 보류 중) · 기본 디바이스 속성을 동기화에서 제외하지 않고 컴퓨터 OU가 범위에 있어야 함
   - 해설: DRS가 컴퓨터 정보를 받아 Entra에 디바이스 개체를 먼저 만듭니다. 이 개체가 생기기 전에는 컴퓨터가 Azure DRS에 인증할 수 없습니다
6. [처리] 관리형: 인증서 개인 키로 Entra 인증 — ID 토큰 수신
   - 주체: 디바이스
   - 위치: 자동 디바이스 조인 작업 (로그온마다 또는 1시간마다 실행)
   - 데이터: userCertificate의 공개 키에 대응하는 개인 키 서명 → ID 토큰
   - 해설: 디바이스 개체가 생긴 뒤에야 기기가 Entra에 인증할 수 있습니다
   - 다음 → 8
7. [처리] 페더레이션: 통합 Windows 인증으로 등록 → 토큰 제출
   - 주체: 온프레미스
   - 위치: AD FS WS-Trust 엔드포인트 (windowstransport는 인트라넷 전용)
   - 데이터: 토큰 클레임 objectGUID · 컴퓨터 SID · 도메인 조인 상태 → Entra에 제출해 ID 토큰 수신 · AD FS에서 usernamemixed · certificatemixed · windowstransport(2005·13) 엔드포인트가 필요하며 windowstransport는 Web Application Proxy로 외부에 노출 금지 · 온프레미스 페더레이션 앱 SSO용 엔터프라이즈 PRT를 AD FS에 따로 요청 · 서드파티 IdP는 WS-Trust를 지원해야 함
   - 해설: 사내 STS가 기기의 도메인 조인 사실을 보증하는 토큰을 만듭니다. Windows 10 1803 이상에서는 즉시 조인이 실패하면 Entra Connect가 동기화한 컴퓨터 개체로 등록을 마무리합니다
8. [처리] 키 생성 후 등록 요청 — DRS가 디바이스 ID·인증서 발급
   - 주체: Entra ID
   - 위치: Azure Device Registration Service (DRS)
   - 데이터: 디바이스 키 · 전송 키 · ID 토큰 + 증명 → 관리형은 5단계에서 만든 디바이스 개체를 갱신, 페더레이션은 디바이스 개체를 새로 기록 · 인증서 발급
   - 해설: 관리형에서는 이미 있던 디바이스 개체가 갱신되고 페더레이션에서는 개체가 새로 만들어지며, 어느 쪽이든 기기에 인증서가 내려갑니다
9. [끝] 디바이스 ID·인증서 저장 — 하이브리드 조인 완료
   - 주체: 디바이스
   - 위치: dsregcmd /status (AzureAdJoined = YES · DomainJoined = YES)
   - 데이터: 디바이스 개체 trustType = ServerAd (하이브리드 조인) · 등록됨 열 = 보류 중 → 등록됨 · 디바이스 ID와 인증서는 컴퓨터 개인 저장소에 저장
   - 해설: 이후 Windows 로그온 때 PRT가 발급됩니다. 하이브리드 조인 기기는 Intune에서 기본 사용자를 지정하지 않으면 소유자가 없어 디바이스 ID로 검색해야 합니다
- 시나리오: 관리형 :: 관리형 도메인 — 인증서 개인 키로 인증해 등록
- 시나리오: 페더레이션 :: 페더레이션 도메인 — 통합 Windows 인증으로 등록

> 교육 포인트: 하이브리드 조인은 AD와 Entra 두 디렉터리에 기기가 모두 있는 상태입니다. 동기화가 늦으면 포털에서 등록됨 열이 보류 중으로 보입니다.
>

### L3 · C · 등록(Registered) · PRT — 개인 기기와 보조 계정

#### L4 · 등록 기기에서 업무 계정 추가부터 PRT 폐기까지

1. [시작] 사용자가 업무 계정을 개인 기기에 추가
   - 주체: 사용자
   - 위치: 앱 로그인 후 "내 조직이 내 디바이스를 관리하도록 허용" 또는 설정 › 계정 › 회사 또는 학교 액세스 › 연결
   - 데이터: 업무 계정 UPN
   - 해설: 개인 Windows 기기에서는 보조 계정을 추가하는 방식으로 등록됩니다. 이 방식은 Windows 10 이상 개인·iOS·Android·macOS 기기에 쓰입니다
2. [판단] 디바이스 등록이 허용되는가?
   - 주체: Entra ID
   - 위치: 디바이스 설정 › 사용자가 디바이스를 등록할 수 있음
   - 데이터: 등록 허용 범위 (모두 · 없음) · Intune·Microsoft 365 모바일 기기 관리를 쓰면 모두로 고정되어 없음을 고를 수 없음
   - 해설: 등록을 막았다면 사용자는 이 단계에서 거부됩니다
   - 예 → 3
   - 아니오 → [차단] 차단 — 디바이스 등록 정책이 없음
3. [처리] 등록 시 MFA 요구 평가
   - 주체: Entra ID
   - 위치: 디바이스 설정 토글 또는 CA 사용자 작업 "디바이스 등록 또는 조인"
   - 데이터: MFA 충족 여부 · 토글 기본 아니요 · CA 정책은 Conditional Access Administrator 이상이 만들고 권한 부여에 기본 제공 MFA 인증 강도를 사용
   - 해설: 등록 시점의 추가 인증 요구는 정책이 정합니다. CA 사용자 작업을 쓰면 디바이스 설정 토글을 아니요로 둡니다. 처음에는 보고서 전용으로 만들어 영향을 본 뒤 켭니다
4. [처리] 디바이스 개체 생성 — 등록(Workplace)
   - 주체: Entra ID
   - 위치: ID › 디바이스 › 모든 디바이스 (Join 유형 = Microsoft Entra registered)
   - 데이터: devices (trustType = Workplace) · 감사 로그 Device "Register device" · 등록 사용자 지정은 Device "Add registered owner to device" · "Add registered users to device"
   - 해설: 등록 기기는 조인이 아니므로 trustType이 Workplace로 나옵니다
5. [처리] 키 쌍 생성 — 브로커가 있을 때 PRT 가능
   - 주체: 디바이스
   - 위치: 기기의 보안 저장소 (TPM 또는 보안 하드웨어)
   - 데이터: 디바이스 키 · 전송 키 (iOS·Android·macOS·Linux는 Authenticator · 회사 포털 같은 브로커 필요 — iOS Authenticator, Android Authenticator · Link to Windows · 회사 포털, macOS·Linux Intune 회사 포털. macOS는 SSO 확장 프로필로 브로커를 활성화하려면 MDM 필요)
   - 해설: 브로커가 없으면 등록 PRT를 받을 수 없습니다
6. [처리] WAM 플러그인이 PRT 요청 — 등록 기기의 PRT 권한자
   - 주체: 디바이스
   - 위치: Windows WAM(Web Account Manager) Entra 플러그인
   - 데이터: 보조 계정 추가 시점에 PRT 발급
   - 해설: Windows에는 이 계정으로 로그온하지 않으므로 WAM이 PRT를 관리합니다
7. [처리] PRT 사용과 갱신 — 앱 토큰 요청마다 SSO
   - 주체: 앱
   - 위치: Windows WAM Entra 플러그인 (앱 토큰 요청 시)
   - 데이터: PRT 90일 유효 · 사용 중 지속 갱신 · 로그인 빈도 정책으로 재인증 강제 가능 · Android는 네이티브 앱 인증 중에만 PRT를 발급·갱신하고 브라우저 세션에서는 하지 않음 · 기기 등록 없이 얻은 PRT는 기기 상태·준수 기반 CA를 충족하지 못함
   - 해설: 등록 PRT가 있어야 기기 등록 정책을 만족하는 로그인으로 인정됩니다
8. [끝] 사용 안 함 또는 삭제 시 PRT·갱신 토큰 폐기
   - 주체: 관리자
   - 위치: ID › 디바이스 › 모든 디바이스 › {기기} › 사용 안 함 (Cloud Device Administrator · Intune Administrator) · 삭제는 Cloud Device Administrator · Intune Administrator · Windows 365 Administrator
   - 데이터: PRT · 기기의 갱신 토큰 폐기 · 감사 로그 Device · 사용 안 함이면 기기 기반 CA와 Windows Hello for Business 자격 증명도 쓸 수 없음 · 삭제는 BitLocker 키 같은 기기 세부 정보까지 지우고 복구 불가 (Intune 관리 기기는 먼저 초기화·사용 중지)
   - 해설: 분실이나 퇴사 시 기기를 끊으면 기기 기반 접근이 즉시 차단됩니다. 이미 로그인한 기기에서는 계속 로그인할 수 있지만 그 기기의 모든 토큰이 무효가 되어 리소스 SSO가 되지 않습니다
- 시나리오: 예 :: 등록이 허용돼 PRT 발급부터 폐기까지 진행
- 시나리오: 아니오 :: 등록이 허용되지 않아 개인 기기 추가 차단

> 교육 포인트: Join 유형(trustType)은 AzureAd = Entra join, ServerAd = 하이브리드 조인, Workplace = 등록입니다. 등록 기기에서만 PRT를 기기 정책 충족용으로 인정합니다.
>
> 주의: 서드파티 IdP를 페더레이션하는 경우 WS-Trust가 지원되지 않으면 조인 기기에서 PRT를 발급할 수 없습니다.
