## L2 · 사용자 · 그룹 — 동적 멤버십 · 그룹 기반 할당

- 설정(Control Plane): 사용자 · 그룹 개체 | 동적 멤버십 규칙(membershipRule) | 그룹에 라이선스 할당
- 강제(Enforcement): Entra 동적 그룹 처리 | 그룹 기반 라이선스 처리 (오류 기록 · 재처리)
- 증적(Evidence): 감사 로그 UserManagement · GroupManagement | GET /v1.0/groups · GET /v1.0/users/{id}?$select=licenseAssignmentStates
- 메뉴(Admin Center): ID > 사용자 · 그룹
- 라이선스(License): 동적 멤버십 그룹은 Entra ID P1 이상(멤버가 되는 고유 사용자마다) · 사용자·정적 그룹 관리는 Free [확인 필요: 고객 라이선스]

### L3 · 0 · 기능 상태 전이 — 수동 관리 → 동적 규칙·그룹 라이선스 → 속성 변경이 자동 반영

#### L4 · ⓪ 비활성 — 그룹과 라이선스를 사람이 직접 관리한다

1. [시작] 입사자 계정 생성 — 사용자 속성 입력
   - 주체: 관리자
   - 위치: ID › 사용자 › 모든 사용자 › 새 사용자 › 새 사용자 만들기 (Basics · Properties · Assignments 탭) — 최소 User Administrator 역할
   - 데이터: user (userPrincipalName · mailNickname · displayName · accountEnabled 기본 켜짐 · 비밀번호 자동 생성 기본) · department · usageLocation은 Properties 탭의 Settings에서 지정 · Assignments 탭에서 그룹·역할을 최대 20개, 관리 단위는 1개까지 함께 지정 가능
   - 해설: 새 사용자가 만들어지지만 그룹과 라이선스는 아직 비어 있습니다. 위치(usageLocation)가 비어 있으면 라이선스 할당 전에 지정해야 합니다
2. [처리] 그룹 멤버를 하나씩 수동 추가 — 입사·이동마다 반복
   - 주체: 관리자
   - 위치: ID › 그룹 › 모든 그룹 › {그룹} › 멤버 › 멤버 추가
   - 데이터: 정적 그룹(Assigned)의 members 목록 · 사용자 생성 화면의 Assignments 탭에서도 그룹에 함께 넣을 수 있음 · 보안 그룹과 Microsoft 365 그룹 모두 수동 멤버 관리 가능
   - 해설: 사람이 멤버를 직접 넣기 때문에 담당자의 기억에 의존합니다. 이동할 때 이전 그룹에서 빼는 일도 사람이 해야 합니다
3. [처리] 라이선스를 사용자별로 직접 할당 — 사용자마다 클릭
   - 주체: 관리자
   - 위치: Microsoft 365 관리 센터 › 사용자 › 활성 사용자 › 라이선스 및 앱 [확인 필요: 한글 메뉴명]
   - 데이터: user.assignedLicenses · licenseAssignmentStates (assignedByGroup = null) · 라이선스를 받으려면 사용자에게 usageLocation(위치)이 있어야 함
   - 해설: 직접 할당은 그룹과 연결되지 않아 이동·퇴사 시 따로 회수해야 합니다. 사용자를 삭제하면 그 사용자가 쓰던 라이선스는 다른 사용자가 쓸 수 있게 반환됩니다
4. [판단] 부서 이동·퇴사 후 멤버십을 바로 정리했는가?
   - 주체: 관리자
   - 위치: ID › 그룹 › {그룹} › 멤버 · Microsoft 365 관리 센터 › 활성 사용자
   - 데이터: 정적 그룹 멤버십 · 사용자 직접 라이선스. 그룹을 대상으로 한 조건부 액세스 정책 · 앱 할당 · 라이선스가 모두 멤버십을 따라가므로 정리가 늦어지면 함께 남습니다
   - 해설: 정리 시점이 늦으면 이전 부서의 앱과 정책 대상에 계속 남습니다
   - 예 → 5
   - 아니오 → [차단] 권한 잔존 — 이전 부서 앱·CA 대상에 계속 포함
5. [끝] 운영 부담이 사람에게 집중 — 누락이 상시 위험
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 감사 로그 (Audit logs) — 범주 GroupManagement · UserManagement
   - 데이터: 감사 로그 GroupManagement "Add member to group" (수동 행위자 기록만 남음) · 직접 라이선스 변경은 UserManagement "Change user license"
   - 해설: 기록은 남지만 규칙이 없어 누락과 지연을 자동으로 막지 못합니다
- 시나리오: 예 :: 바로 정리해도 운영 부담이 사람에게 집중
- 시나리오: 아니오 :: 멤버십 정리를 놓쳐 권한이 남는 경우

#### L4 · ① 구성 — 동적 규칙과 그룹 기반 라이선스를 만든다

1. [시작] 관리자가 Entra 관리 센터에 로그인 — 필요 역할 확인
   - 주체: 관리자
   - 위치: entra.microsoft.com (그룹 생성·동적 규칙은 Groups Administrator 이상, 라이선스 할당은 문서상 Groups Administrator · License Administrator · User Administrator 이상이며 Microsoft 365 관리 센터 절차는 License Administrator 이상으로 안내)
   - 데이터: roleAssignments. 동적 멤버십 그룹을 쓰려면 멤버가 되는 고유 사용자마다 Entra ID P1(또는 Intune for Education) 라이선스가 필요하며, 라이선스를 사용자에게 할당하지 않아도 총 보유 수량만 충족하면 됩니다. 디바이스 멤버에는 라이선스가 필요 없습니다
   - 해설: 그룹 규칙과 라이선스 할당은 필요한 역할이 서로 다릅니다
2. [처리] 규칙에 쓸 속성의 쓰기 권한 점검
   - 주체: 관리자
   - 위치: ID › 사용자 › {사용자} › 속성 · 온프레미스 AD 위임 권한 (동기화 속성)
   - 데이터: department · extensionAttribute1-15 등 규칙 후보 속성과 그 속성을 쓸 수 있는 주체. 온프레미스 AD에서 동기화된 일부 속성은 SELF 쓰기가 허용될 수 있음
   - 해설: 규칙 속성을 사용자가 직접 고칠 수 있으면 스스로 그룹에 들어갈 수 있습니다. 접근 통제나 조건부 액세스에 쓰는 그룹일수록 속성 쓰기 권한이 곧 보안 수준입니다. 역할 할당 가능 그룹은 동적 멤버십이 아니라 할당 멤버십만 써서 이 위험을 막습니다
3. [처리] 새 그룹 만들기 — 멤버십 유형 = 동적 사용자
   - 주체: 관리자
   - 위치: ID › 그룹 › 모든 그룹 › 새 그룹 (그룹 유형 · 이름 · 멤버십 유형 = 동적 사용자 또는 동적 디바이스)
   - 데이터: group.groupTypes = ["DynamicMembership"] · membershipRule · membershipRuleProcessingState = On (Graph POST /v1.0/groups 또는 New-MgGroup) · 보안 그룹은 사용자 또는 디바이스, Microsoft 365 그룹은 사용자만 · 테넌트당 동적 멤버십 그룹 최대 15,000개
   - 해설: 멤버를 손으로 넣지 않고 규칙으로 결정하는 그룹을 만듭니다. 에이전트 ID(서비스 주체)는 동적 그룹 멤버가 될 수 없고, 에이전트의 사용자 계정은 일반 사용자 규칙에 걸리므로 필요하면 규칙에서 따로 제외합니다
4. [처리] 동적 쿼리 추가 — 규칙 작성기로 식 작성
   - 주체: 관리자
   - 위치: 새 그룹 › 동적 쿼리 추가 › 규칙 작성기 (식 5개 초과·직속 보고자는 텍스트 상자)
   - 데이터: membershipRule 예) user.department -eq "Sales" (본문 최대 3,072자) · 속성 이름은 대소문자 구분 · 문자열·정규식 비교는 대소문자 구분 안 함 · null 비교는 -eq/-ne null만 사용
   - 해설: 속성 · 연산자 · 값 형태의 식으로 멤버 조건을 정의합니다. 규칙 작성기가 표현하지 못하는 규칙은 텍스트 상자에 직접 씁니다
5. [처리] 확장 특성 속성 가져오기 — 선택 사항
   - 주체: 관리자
   - 위치: 동적 쿼리 › 사용자 지정 확장 속성 가져오기 (Get custom extension properties) › 앱 ID 입력 › 속성 새로 고침 (Refresh properties) [확인 필요: 한글 메뉴명]
   - 데이터: 앱별 사용자 지정 확장 속성 (AD에서 동기화한 디렉터리 확장 포함) · extensionAttribute1~15는 ExtensionAttribute<X> 형식으로 바로 사용 · 다중 값 확장 속성은 규칙에서 지원되지 않음
   - 해설: AD에서 동기화한 확장 속성도 규칙 조건으로 쓸 수 있습니다
6. [처리] 저장 후 그룹 만들기 — 규칙 유효성 검사
   - 주체: 관리자
   - 위치: 동적 쿼리 › 저장 → 새 그룹 › 만들기
   - 데이터: group 생성 · membershipRuleProcessingState = On (잘못된 규칙은 포털이 사유를 표시) · Microsoft 365 그룹이면 새로 추가된 멤버에게 환영 메일이 가며 Exchange PowerShell(Set-UnifiedGroup)로 끌 수 있음
   - 해설: 규칙이 유효해야 저장되고 곧바로 첫 평가가 시작됩니다. 사용하지 않는 오래된 사용자·디바이스도 평가 대상이라 규칙 만들기 전에 정리하면 처리가 빨라집니다
7. [처리] 그룹에 라이선스 할당 — 제품과 서비스 플랜 선택
   - 주체: 관리자
   - 위치: Microsoft 365 관리 센터 › 청구 › 라이선스 › 라이선스 할당 › 그룹 검색 › 구독 선택 › 앱 및 서비스 켜기/끄기 [확인 필요: 한글 메뉴명]
   - 데이터: group.assignedLicenses (skuId · disabledPlans) — POST /v1.0/groups/{id}/assignLicense 또는 Set-MgGroupLicense · 대상 그룹은 보안 그룹·메일 사용 그룹·Microsoft 365 그룹 · 중첩 그룹은 미지원
   - 해설: 라이선스를 그룹에 걸면 멤버 모두에게 상속됩니다 (한 번에 최대 20개 그룹). 10만 명 같은 큰 그룹은 처리 성능에 영향을 줄 수 있습니다
8. [끝] 처리 상태 확인 — Update complete 대기
   - 주체: 관리자
   - 위치: ID › 그룹 › {그룹} › 개요 › 동적 규칙 처리 상태 · 마지막 멤버십 변경
   - 데이터: Evaluating → Processing → Update complete (오류 시 Processing error) · 마지막 멤버십 변경은 날짜·시각 / In Progress / Unknown (새 그룹일 수 있음)
   - 해설: 첫 평가가 끝나면 규칙에 맞는 사용자가 멤버로 채워집니다. 그룹 하나에서 오류가 나면 개요 상단에 경고가 뜨고, 조직 전체의 동적 그룹 업데이트가 24시간 넘게 처리되지 못하면 모든 그룹 화면 위에 경고가 뜹니다

#### L4 · ② 활성 — 속성 변경이 멤버십과 라이선스로 이어진다

1. [시작] 사용자 속성 변경 — 예: 부서 이동
   - 주체: 관리자
   - 위치: ID › 사용자 › {사용자} › 속성 · 또는 AD 변경이 동기화로 도착 (동기화 사용자의 이름·연락처·직무 정보는 AD에서만 수정 가능)
   - 데이터: user.department 변경. 클라우드 전용은 포털·PATCH /v1.0/users/{id}, 동기화 사용자는 다음 동기화 주기에 반영
   - 해설: HR이나 디렉터리에서 속성이 바뀌면 흐름이 시작됩니다
2. [처리] 디렉터리가 변경을 기록
   - 주체: Entra ID
   - 위치: 모니터링 및 상태 › 감사 로그 (Audit logs)
   - 데이터: 감사 로그 UserManagement "Update user"
   - 해설: 변경이 디렉터리에 저장되고 감사 로그에 남습니다
3. [처리] 테넌트의 모든 동적 그룹 규칙을 다시 평가
   - 주체: Entra ID
   - 위치: Entra 동적 그룹 처리 (서비스 내부)
   - 데이터: 전체 membershipRule 평가 — 사용자·디바이스 속성이 바뀔 때마다 조직의 모든 동적 그룹 규칙을 처리 · 비활성 사용자와 오래된 디바이스도 평가 대상이라 처리 시간을 늘릴 수 있음 · 테넌트당 최대 15,000개 동적 그룹
   - 해설: 속성이 바뀌면 이 사용자가 걸릴 만한 모든 동적 그룹을 다시 계산합니다. 반영 시간은 규칙 수와 복잡도에 따라 달라집니다 [확인 필요: 공식 지연 시간 수치 없음]
4. [판단] 사용자가 규칙을 만족하는가?
   - 주체: Entra ID
   - 위치: Entra 동적 그룹 처리 (서비스 내부)
   - 데이터: 규칙 표현식의 참/거짓 결과 · 그룹 처리 상태가 Processing error이면 평가가 끝나지 않아 이 판정이 멤버십에 반영되지 않음
   - 해설: 참이면 멤버, 거짓이면 비멤버가 됩니다
   - 예 → 5
   - 아니오 → 6
5. [처리] 멤버로 자동 추가 — 수동 추가·제거 불가
   - 주체: Entra ID
   - 위치: ID › 그룹 › {그룹} › 멤버 (동적 그룹은 멤버 추가·제거 메뉴로 직접 수정할 수 없음)
   - 데이터: 감사 로그 GroupManagement "Add member to group" · Microsoft 365 그룹이면 새 멤버에게 환영 메일
   - 해설: 규칙을 만족하면 사람이 손대지 않아도 멤버가 됩니다
   - 다음 → 7
6. [처리] 멤버에서 자동 제거 — 조건에서 벗어난 사용자
   - 주체: Entra ID
   - 위치: ID › 그룹 › {그룹} › 멤버
   - 데이터: 감사 로그 GroupManagement "Remove member from group"
   - 해설: 부서를 옮기면 이전 그룹에서 자동으로 빠집니다
7. [처리] 그룹에 걸린 라이선스를 다시 계산
   - 주체: Entra ID
   - 위치: Entra 그룹 기반 라이선스 처리 (서비스 내부)
   - 데이터: user.licenseAssignmentStates (assignedByGroup = 그룹 ID · state = Active) · 감사 로그 GroupManagement "Start applying group based license to users" · "Finish applying group based license to user" · "Trigger group license recalculation"
   - 해설: 추가된 사용자에게는 라이선스가 부여되고 제거된 사용자에게서는 회수됩니다. 다른 라이선스 그룹으로 옮길 때는 대상 그룹에 먼저 넣어 라이선스가 적용된 것을 확인한 뒤 원래 그룹에서 빼야 서비스 공백이 없습니다
8. [끝] 앱·조건부 액세스 대상이 함께 바뀜
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 감사 로그 · 보호 › 조건부 액세스 › 정책 (그룹 대상) · 엔터프라이즈 앱 › 사용자 및 그룹 (앱 할당)
   - 데이터: 그룹을 대상으로 한 CA 정책 · 앱 할당 · 감사 로그 UserManagement "Change user license"
   - 해설: 그룹에 걸린 모든 할당이 멤버십을 따라 함께 바뀝니다. 동적 그룹이 Processing error 상태이면 신규 멤버가 추가되지 않아 이 그룹으로 정책·앱을 지정한 사용자가 대상에서 빠질 수 있습니다
- 시나리오: 예 :: 규칙을 만족해 멤버로 추가되고 라이선스 재계산
- 시나리오: 아니오 :: 규칙을 만족하지 않아 멤버에서 제거되고 라이선스 재계산

### L3 · B · 동적 그룹 규칙 평가 — 규칙 작성 · 처리 상태 · 제한

#### L4 · 규칙 한 줄이 검증되고 처리 상태가 바뀐다

1. [시작] 규칙 본문 작성 — 속성 · 연산자 · 값
   - 주체: 관리자
   - 위치: ID › 그룹 › {그룹} › 동적 멤버십 규칙 (Dynamic membership rules) — 새 그룹에서는 동적 쿼리 추가
   - 데이터: user.department -eq "Sales" 형태의 식 (사용자 규칙과 디바이스 규칙은 한 규칙에 혼합 불가) · 본문 최대 3,072자 · 단일 식은 괄호 생략 가능 · 연산자는 -eq -ne -startsWith -notStartsWith -endsWith -notEndsWith -contains -notContains -match -notMatch -in -notIn · 여러 식은 -and -or -not으로 연결
   - 해설: 식은 속성 · 연산자 · 값의 순서를 지켜야 문법 오류가 없습니다. 우선순위는 비교 연산자 > -not > -and > -or이며 필요할 때만 괄호로 순서를 정합니다
2. [판단] 규칙 작성기로 표현할 수 있는가?
   - 주체: 관리자
   - 위치: 동적 멤버십 규칙 › 규칙 작성기(Rule builder) · 규칙 구문 텍스트 상자
   - 데이터: 규칙 작성기는 사용자 기반 동적 그룹 전용 · 식 최대 5개 · 모든 규칙을 표현하지는 못함. 텍스트 상자가 필요한 경우: 식 5개 초과 · 직속 보고자(Direct Reports) 규칙 · -contains / -notContains 연산자 · 연산자 우선순위 지정 · 복합 식 (예: user.proxyAddresses -any 식)
   - 해설: 작성기가 지원하지 않는 규칙은 텍스트 상자로 직접 씁니다. 텍스트 상자에서 만든 규칙을 작성기가 표시하지 못할 수 있으며, 작성기는 지원 문법·검증·처리 방식을 바꾸지 않습니다. 디바이스 기반 동적 그룹은 작성기를 쓸 수 없고 텍스트 상자만 가능합니다
   - 예 → 3
   - 아니오 → 4
3. [처리] 규칙 작성기로 식 구성
   - 주체: 관리자
   - 위치: 동적 쿼리 추가 › 규칙 작성기 › 식 추가
   - 데이터: 속성 · 연산자 · 값 목록에서 선택 · 식은 최대 5개
   - 해설: 목록에서 고르면 문법 실수를 줄일 수 있습니다. 문자열 값은 큰따옴표로 감싸야 하고 값 안에 큰따옴표가 있으면 백틱(`)으로 이스케이프합니다
   - 다음 → 5
4. [처리] 텍스트 상자로 복합 규칙 작성
   - 주체: 관리자
   - 위치: 동적 쿼리 › 규칙 구문 텍스트 상자
   - 데이터: 예) (user.proxyAddresses -any (_ -startsWith "contoso")) · -any / -all 은 다중 값 속성에서 한 개 이상 / 모두 일치를 뜻하고 _ 는 컬렉션의 각 항목 · 디바이스 규칙 예) device.deviceOSType -eq "Windows" · 한 규칙에 사용자와 디바이스를 함께 쓸 수 없고 디바이스 규칙은 디바이스 속성만 참조 가능 (디바이스 소유자의 사용자 속성으로 디바이스 그룹을 만들 수 없음)
   - 해설: 복합 조건과 디바이스 규칙은 직접 문법을 써야 합니다. 직속 보고자 규칙은 관리자의 직속 보고자만 지원하고 그 아래 보고자까지 포함하는 그룹은 만들 수 없습니다
5. [처리] 규칙 효율 점검 — 처리 시간 단축
   - 주체: 관리자
   - 위치: 동적 멤버십 규칙 편집 화면 (저장 전 규칙 구문 검토)
   - 데이터: -match · -contains 최소화, 전체 값을 알면 -eq, 앞·뒤만 알면 -startsWith · -endsWith 우선 · 같은 속성의 여러 값을 -or로 이으면 -in으로, 여러 부정 비교는 -notIn으로 묶음 · 중복 조건 제거 (예: user.city -eq "Lagos" -or user.city -startsWith "Lag" → -startsWith 하나)
   - 해설: 단순한 규칙이 테넌트 전체 동적 그룹 처리 시간을 줄입니다. 특히 -contains는 동적 그룹이 많은 테넌트에서 처리 시간을 늘립니다
6. [처리] 저장 시 유효성 검사
   - 주체: Entra ID
   - 위치: 동적 멤버십 규칙 › 저장 (잘못된 규칙은 포털이 사유를 표시)
   - 데이터: 처리 켜짐: 지원하지 않는 속성은 저장 거부 · 일시 중지: 저장 후 재개 시 Processing error · 속성 이름 대소문자와 null 비교(-eq/-ne null) 문법도 여기서 걸림
   - 해설: 처리가 일시 중지된 그룹은 잘못된 규칙도 저장되니 재개 후 상태를 봅니다
7. [판단] 처리 상태가 Update complete인가?
   - 주체: Entra ID
   - 위치: ID › 그룹 › {그룹} › 개요 › 동적 규칙 처리 상태
   - 데이터: Evaluating(변경 수신·평가 중) · Processing(업데이트 처리 중) · Update complete · Processing error(규칙 평가 오류) · Update paused(membershipRuleProcessingState = Paused) · Not started
   - 해설: 정상 완료면 멤버십이 최신이고 오류면 마지막 성공 결과가 유지됩니다. 오류 상태에서는 기존 멤버가 그대로 남고 새 멤버는 추가되지 않아 이 그룹을 정책·할당 대상으로 쓰면 빠지는 사용자가 생깁니다

   - 아니오 → [차단] 갱신 중단 — Processing error면 신규 멤버가 추가되지 않음
8. [끝] 필요 시 처리 일시 중지 — 마지막 멤버십 변경 시각 갱신
   - 주체: 관리자
   - 위치: ID › 그룹 › {그룹} › 개요 › 처리 일시 중지 (Groups Administrator 이상, 그룹 소유자만으로는 불가)
   - 데이터: membershipRuleProcessingState = Paused · 재개 후 마지막 멤버십 변경 갱신 (재개 직후에는 자리표시자 값이 보이다가 처리가 끝나면 갱신됨) · 포털 버튼이 생기기 전에는 이 속성(On / Paused)을 직접 수정했음
   - 해설: 규칙을 대량 수정할 때 처리를 멈췄다가 재개할 수 있습니다
- 시나리오: 예 ▸ 예 :: 작성기로 표현하고 갱신이 완료된 경우
- 시나리오: 예 ▸ 아니오 :: 작성기로 표현했으나 갱신이 중단됨
- 시나리오: 아니오 ▸ 예 :: 복합 규칙을 직접 쓰고 갱신 완료 후 일시 중지
- 시나리오: 아니오 ▸ 아니오 :: 복합 규칙을 직접 썼으나 갱신이 중단됨

> 교육 포인트: 속성 하나가 바뀌면 테넌트의 모든 동적 규칙이 평가됩니다. 규칙이 많고 복잡할수록 반영이 느려집니다.
>
> 주의: 규칙에 쓰는 속성을 일반 사용자가 직접 고칠 수 있으면(예: AD의 SELF 쓰기) 스스로 보안 그룹에 들어갈 수 있습니다. 역할 할당 가능 그룹은 동적 멤버십을 쓸 수 없습니다.

### L3 · C · 그룹 기반 라이선스 — 상속 · 오류 · 재처리

#### L4 · 그룹의 라이선스가 사용자에게 내려가고 오류가 남는다

1. [시작] 그룹에 제품 라이선스 할당

   - 위치: Microsoft 365 관리 센터 › 청구 › 라이선스 › 라이선스 할당 [확인 필요: 한글 메뉴명] — 최소 License Administrator

2. [처리] 처리 대상 사용자 확정 — 1단계 멤버만
   - 주체: Entra ID
   - 위치: Entra 그룹 기반 라이선스 처리 (서비스 내부)
   - 데이터: 그룹의 직접 멤버 (중첩 그룹은 미지원) · 대상 그룹 유형은 보안 그룹·메일 사용 그룹·Microsoft 365 그룹
   - 해설: 그룹 안의 그룹 멤버에게는 라이선스가 내려가지 않습니다. 10만 명 같은 큰 그룹은 라이선스·멤버십 변경 처리에 시간이 오래 걸릴 수 있습니다
3. [판단] 사용 위치가 허용되는 국가인가?
   - 주체: Entra ID
   - 위치: ID › 사용자 › {사용자} › 속성 › 사용 위치
   - 데이터: user.usageLocation (없으면 테넌트 위치 상속) · 해결: 위치 지정 · 지원하지 않는 위치의 사용자는 그룹에서 제거
   - 해설: 일부 서비스는 국가별로 제공되지 않아 위치가 막히면 부여가 실패합니다
   - 예 → 4
   - 아니오 → [차단] 오류 — ProhibitedInUsageLocationViolation
4. [판단] 남은 수량과 서비스 플랜 충돌이 없는가?
   - 주체: Entra ID
   - 위치: Microsoft 365 관리 센터 › 청구 › 라이선스 › {제품} › 오류 및 문제
   - 데이터: 구독 잔여 수량 · 직접 할당과 겹치는 서비스 플랜 (예: 직접 할당된 Office 365 E1에 그룹의 E3가 겹치면 Exchange Online Plan 1과 2가 충돌) · 선행 플랜 (예: Audio Conferencing은 Skype for Business에 의존, 애드온은 선행 플랜과 같은 그룹에 할당)
   - 해설: 수량 부족, 플랜 충돌, 선행 조건 누락이 대표적 실패 원인입니다. 충돌 플랜은 하나를 끄거나 중복된 직접 라이선스를 제거해 해결합니다
   - 예 → 5
   - 아니오 → [차단] 오류 — CountViolation · MutuallyExclusiveViolation · DependencyViolation
5. [처리] 사용자에게 상속 라이선스 부여
   - 주체: Entra ID
   - 위치: GET /v1.0/users/{id}?$select=licenseAssignmentStates
   - 데이터: licenseAssignmentStates[] (assignedByGroup = 그룹 ID · state = Active · skuId · disabledPlans · lastUpdatedDateTime) · state 값은 Active · ActiveWithError · Disabled · Error
   - 해설: 직접 할당은 assignedByGroup이 비어 있고 그룹 상속은 그룹 ID가 채워집니다
6. [처리] 멤버 변경에 따라 부여·회수
   - 주체: Entra ID
   - 위치: 모니터링 및 상태 › 감사 로그 — GroupManagement 범주
   - 데이터: 그룹 멤버 추가 → 부여 · 제거 → 회수 · 여러 그룹이 같은 라이선스를 동시에 부여하면 감사 로그에 LicenseAssignmentAttributeConcurrencyException이 보일 수 있으나 자동 재시도되어 조치가 필요 없음
   - 해설: 다른 라이선스 그룹으로 옮길 때는 대상 그룹에 먼저 추가한 뒤 새 라이선스가 적용된 것을 확인하고 원래 그룹에서 제거합니다. 원래 그룹에서 먼저 빼면 새 그룹 처리가 끝날 때까지 라이선스가 없어집니다
7. [처리] 오류 확인 — 오류 및 문제 탭
   - 주체: 관리자
   - 위치: Microsoft 365 관리 센터 › 청구 › 라이선스 › {제품} › 오류 및 문제 · ID 관리 센터 › 청구 › 라이선스 › 개요 [확인 필요: 한글 메뉴명]
   - 데이터: licenseAssignmentStates[].error · state = Error · ActiveWithError · 오류 값 CountViolation · MutuallyExclusiveViolation · DependencyViolation · ProhibitedInUsageLocationViolation · UniquenessViolation · Other · Entra 관리 센터에서는 오류 사용자가 있는 그룹을 열어 상단 알림을 눌러 영향받은 사용자를 확인
   - 해설: 그룹 라이선스 오류는 비동기로 기록되어 나중에 포털에 나타납니다. 오류 사용자·그룹 목록은 999명씩 페이지로 나뉘어 아래로 스크롤하면 다음 묶음이 로드됩니다
8. [끝] 원인 수정 후 재처리
   - 주체: 관리자
   - 위치: 오류 및 문제 › 그룹 또는 사용자 선택 › 재처리 (Reprocess) (한 번에 최대 20명)
   - 데이터: 중복 프록시 주소 · 수량 · 플랜 충돌 같은 원인 수정 후 다시 처리 · 라이선스가 걸린 그룹을 삭제하기 전에는 그룹의 라이선스를 모두 제거해야 하며, 직접 라이선스가 의존하는 플랜이 있으면 상속 라이선스가 직접 할당으로 전환될 수 있음
   - 해설: 원인을 고친 뒤 재처리해야 오류 상태가 풀립니다. 라이선스 변경이 mail·proxyAddresses 속성 재계산을 일으킬 수 있으므로 값의 원본을 함께 점검합니다
- 시나리오: 예 ▸ 예 :: 정상 상속 후 오류는 원인 수정해 재처리
- 시나리오: 예 ▸ 아니오 :: 수량·플랜 충돌로 라이선스 오류
- 시나리오: 아니오 :: 허용되지 않는 국가라 라이선스 오류

> 교육 포인트: 그룹 하나에 여러 제품을 걸면 한 제품의 실패가 같은 그룹의 다른 제품 부여에도 영향을 줄 수 있습니다.
>
> 주의: 그룹 기반 라이선스의 라이선스 요건은 고객 구독에서 확인합니다 [확인 필요: 라이선스 요건]. 대규모 그룹의 라이선스 변경은 처리에 시간이 걸릴 수 있습니다.
