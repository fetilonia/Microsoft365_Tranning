## L2 · 워크로드 ID — 서비스 주체 · 관리 ID · 앱 자격 증명

- 설정(Control Plane): 앱 등록 · 서비스 주체 · 소유자 | 관리 ID · 인증서 · 페더레이션 자격 증명
- 강제(Enforcement): Entra 토큰 발급 (client credentials) | 워크로드용 CA (Workload ID Premium)
- 증적(Evidence): 서비스 주체 · 관리 ID 로그인 로그 | 감사 로그 ApplicationManagement
- 메뉴(Admin Center): ID > 애플리케이션 > 앱 등록 · 엔터프라이즈 앱 · 워크로드 ID
- 라이선스(License): 서비스 주체 · 관리 ID 사용은 추가 비용 없음, 워크로드용 조건부 액세스는 Workload Identities Premium 필요 [확인 필요: 고객 라이선스]

### L3 · 0 · 기능 상태 전이 — 장기 비밀 키 방치 → 비밀 없는 자격 증명 → 워크로드 통제

#### L4 · ⓪ 비활성 — 장기 비밀 키와 소유자 불명 앱

1. [시작] 앱 · 스크립트가 Entra에 토큰을 요청
   - 주체: 앱
   - 위치: Entra 토큰 엔드포인트 (OAuth 2.0 client credentials, https://login.microsoftonline.com/{tenant}/oauth2/v2.0/token)
   - 데이터: client_id · 클라이언트 비밀 또는 인증서(client_assertion) · scope = 대상 리소스 앱 ID URI + /.default · grant_type = client_credentials
   - 해설: 사람이 아닌 워크로드가 자기 신원으로 토큰을 요청합니다. 사용자가 없으므로 위임 권한은 쓸 수 없고 관리자가 부여한 앱 권한(앱 역할)만 쓸 수 있습니다
2. [처리] 코드 · 설정 파일에 저장된 장기 비밀 키로 인증
   - 주체: 앱
   - 위치: 앱 등록 › 인증서 및 암호 › 클라이언트 암호 (Certificates & secrets › Client secrets)
   - 데이터: passwordCredentials (긴 만료 · 저장 위치 불명) · 포털에서 만드는 비밀은 수명이 최대 24개월이고 12개월 미만을 권장 · 비밀 값은 만든 직후 한 번만 표시됨
   - 해설: 비밀은 안전하게 보관하고 주기적으로 교체해야 하지만 방치되기 쉽습니다. 클라이언트 비밀은 인증서·페더레이션 자격 증명보다 약해 개발용으로만 쓰고 운영 환경에는 쓰지 않도록 권고합니다
3. [처리] Entra는 비밀 일치만 확인
   - 주체: Entra ID
   - 위치: Entra 토큰 서비스 (client credentials 검증)
   - 데이터: 워크로드는 MFA를 할 수 없고 위치 · 위험 조건 평가가 없음
   - 해설: 비밀만 알면 어디서든 토큰을 받을 수 있습니다. 워크로드 ID는 MFA를 못 하고 정식 수명 주기도 없어 사용자 계정보다 침해 위험이 큽니다
4. [처리] 앱 권한이 필요 이상으로 넓고 소유자가 없음
   - 주체: 관리자
   - 위치: 엔터프라이즈 앱 › {앱} › 권한 · 소유자
   - 데이터: appRoleAssignment (앱 권한) · owners 비어 있음 · 앱 전용 토큰은 roles 클레임이 없어도 발급될 수 있고, 리소스가 직접 권한을 확인하지 않으면 허용됨 (할당 필요를 켜면 이런 토큰을 막을 수 있음)
   - 해설: 정식 수명 주기가 없어 누가 만들었고 누가 책임지는지 알기 어렵습니다. 앱 권한은 사용자 컨텍스트 없이 조직 전체 데이터에 접근할 수 있어 최소 권한 점검이 필요합니다
5. [끝] 비밀 유출 시 누구든 앱 권한으로 접근 — 소유자 · 사용처 추적 어려움
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 로그인 로그 › 서비스 주체 로그인
   - 데이터: 서비스 주체 로그인 로그는 남지만 평가하는 정책이나 알림은 없음 · 같은 서비스 주체 · 상태 · IP · 리소스는 한 행으로 묶여 보임
   - 해설: 유출을 알아채기 어렵고 알아도 영향 범위를 가늠하기 어렵습니다. 로그 항목은 시스템이 생성하며 수정·삭제할 수 없습니다

#### L4 · ① 구성 — 관리 ID와 페더레이션으로 바꾸고 정책을 건다

1. [시작] 현재 앱 자격 증명을 점검
   - 주체: 관리자
   - 위치: ID › 애플리케이션 › 앱 등록 › {앱} › 인증서 및 암호 (Entra ID › App registrations › {app} › Certificates & secrets)
   - 데이터: passwordCredentials · keyCredentials · 만료일 · 소유자 · 인증서는 .cer · .pem · .crt 파일로 업로드
   - 해설: 어떤 앱이 장기 비밀을 쓰는지 먼저 목록으로 확인합니다. 만료 열(Expires)과 Entra 권장 사항의 만료 임박 자격 증명 알림으로 교체 대상을 찾습니다
2. [처리] 실행 환경별로 대체 방식을 정한다
   - 주체: 관리자
   - 위치: 설계 단계 (Azure 리소스 / 외부 CI·CD · Kubernetes)
   - 데이터: Azure에서 실행 → 관리 ID, Azure 밖 · 외부 IdP → 페더레이션 자격 증명 (GitHub Actions · Kubernetes · Google Cloud · AWS · SPIFFE/SPIRE · Azure Pipelines 서비스 연결 등 문서화된 시나리오)
   - 해설: 비밀 없이 신원을 증명하는 방식을 실행 위치에 맞춰 고릅니다. 둘 다 안 맞으면 클라이언트 비밀보다 인증서를 우선합니다
3. [처리] 사용자 할당 관리 ID 만들기
   - 주체: 관리자
   - 위치: Azure 포털 › 관리 ID › 만들기 (구독 · 리소스 그룹 필요) · CLI: az identity create
   - 데이터: 관리 ID 리소스 + 특수 서비스 주체 (Entra에 자동 생성) · 독립된 수명 주기(명시적으로 삭제해야 함) · 여러 Azure 리소스에 공유 가능
   - 해설: 여러 리소스가 함께 쓸 독립된 ID를 만듭니다. 리소스를 자주 재생성해도 권한을 유지해야 하거나 프로비저닝 흐름에서 사전 권한 부여가 필요할 때 적합합니다
4. [처리] 컴퓨트 리소스에 관리 ID 할당
   - 주체: 관리자
   - 위치: Azure 포털 › VM · App Service 등 › ID (Identity) · CLI: az vm identity assign --identities
   - 데이터: 리소스 ↔ 관리 ID 연결 (시스템 할당은 리소스 수명과 같이 생성 · 삭제, 리소스 하나에만 연결, 이름은 리소스 이름과 같고 배포 슬롯은 <앱>/slots/<슬롯>)
   - 해설: 리소스에서 도는 코드가 이 ID로 토큰을 받을 수 있게 됩니다. 단일 리소스에 묶인 워크로드는 시스템 할당, 여러 리소스가 공유하면 사용자 할당이 맞습니다
5. [처리] 대상 리소스에 최소 권한만 부여
   - 주체: 관리자
   - 위치: 대상 리소스(Key Vault · 스토리지 등) › 액세스 제어(IAM) › 역할 할당 추가
   - 데이터: Azure RBAC 역할 할당 (관리 ID의 서비스 주체 대상) · 관리 ID 서비스 주체는 권한은 부여할 수 있지만 직접 수정할 수 없고 앱 객체가 없음
   - 해설: 관리 ID를 만들어도 권한은 따로 부여해야 접근할 수 있습니다. 관리 ID는 추가 비용 없이 쓸 수 있습니다
6. [처리] 외부 워크로드용 페더레이션 자격 증명 추가
   - 주체: 관리자
   - 위치: ID › 애플리케이션 › 앱 등록 › {앱} › 인증서 및 암호 › 페더레이션 자격 증명 › 자격 증명 추가 · 사용자 할당 관리 ID에도 같은 방식으로 추가 가능
   - 데이터: issuer · subject · audiences(권장 api://AzureADTokenExchange, 값 1개) · name (3-120자, 영숫자 · 대시 · 밑줄, 생성 뒤 변경 불가) · 앱 또는 사용자 할당 관리 ID당 최대 20개 · issuer + subject 조합은 앱 안에서 고유 · 각 값 최대 600자
   - 해설: 외부 IdP(GitHub · Kubernetes 등)의 토큰을 신뢰하도록 연결합니다. 앱 소유자이거나 Application Administrator · Cloud Application Administrator · Global Administrator · Hybrid Identity Administrator 역할이 필요하고, 사용자가 앱을 등록할 수 없게 설정돼 있으면(Users can register applications = 아니요) 직접 만들 수 없습니다. RS256 서명 토큰을 발급하는 IdP만 지원됩니다
7. [처리] 기존 클라이언트 비밀 · 인증서 삭제
   - 주체: 관리자
   - 위치: 앱 등록 › {앱} › 인증서 및 암호 › 클라이언트 암호 › 삭제
   - 데이터: passwordCredentials 제거 · 만료 일정 해소 · 감사 로그 'Update application – Certificates and secrets management'
   - 해설: 새 방식이 동작함을 확인한 뒤 장기 비밀을 없앱니다. 삭제 전에 아직 비밀을 쓰는 사용처가 남아 있는지 서비스 주체 로그인 로그로 확인합니다
8. [처리] 앱 권한 최소화 · 소유자 지정
   - 주체: 관리자
   - 위치: 애플리케이션 › 엔터프라이즈 앱 › {앱} › 권한 · 소유자
   - 데이터: appRoleAssignment 정리 · owners · 감사 로그 'Add owner to service principal' · 서비스 주체 대상 액세스 검토는 Workload ID Premium 필요
   - 해설: 필요 없는 앱 권한을 지우고 책임자를 정해 수명 주기를 만듭니다. 서비스 주체에는 앱 인스턴스 속성 잠금(app instance property lock)으로 민감 속성 변경을 막는 방법도 있습니다
9. [처리] 워크로드용 조건부 액세스 정책 만들기 (선택)
   - 주체: 관리자
   - 위치: 보호 › 조건부 액세스 › 정책 › 새 정책 › 사용자 또는 워크로드 ID › 워크로드 ID (Entra ID › Conditional Access › Policies › New policy › Users or workload identities) · 필요 역할 Conditional Access Administrator 이상
   - 데이터: 대상 = 서비스 주체 선택 · 조건 = 위치 또는 서비스 주체 위험 · 권한 부여 = 차단만 가능 · 대상 리소스는 모든 리소스(토큰 요청 때만 평가) · Workload Identities Premium 필요
   - 해설: 허용된 IP 밖이나 위험한 서비스 주체의 토큰 요청을 막습니다. 위치 정책은 '모든 위치'를 포함하고 허용할 위치를 제외하며, 위험 정책에는 ID Protection의 서비스 주체 위험 판정이 쓰입니다
10. [끝] 보고서 전용으로 시작한 뒤 켠다
   - 주체: 관리자
   - 위치: 정책 상태 = 보고서 전용 → 켜기
   - 데이터: 로그인 로그 › 서비스 주체 로그인 › Report-only 탭 · Conditional Access Insights and Reporting 워크북(위치 기반 정책)
   - 해설: 영향을 확인한 뒤에 켜서 서비스 중단을 피합니다. 되돌리려면 정책을 삭제하거나 끕니다

#### L4 · ② 활성 — 토큰 요청이 자격 증명과 정책으로 판정된다

1. [시작] 워크로드가 토큰을 요청
   - 주체: 앱
   - 위치: 관리 ID(IMDS) 또는 login.microsoftonline.com/{tenant}/oauth2/v2.0/token
   - 데이터: client_id · scope(.default) · 자격 증명 (인증서 · 페더레이션 토큰 등)
   - 해설: 앱이 자기 신원으로 대상 리소스용 액세스 토큰을 요청합니다. 한 번에 한 리소스에 대한 scope만 요청할 수 있습니다
2. [처리] Entra가 자격 증명 종류를 확인
   - 주체: Entra ID
   - 위치: Entra 토큰 서비스
   - 데이터: 클라이언트 비밀 · 인증서 · 외부 토큰(client_assertion) · 관리 ID 토큰
   - 해설: 어떤 방식으로 신원을 증명하는지에 따라 검증 절차가 달라집니다. 인증서·외부 토큰은 client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer로 전달됩니다
3. [처리] 자격 증명을 검증
   - 주체: Entra ID
   - 위치: Entra 토큰 서비스 (앱의 자격 증명 · 페더레이션 자격 증명 대조)
   - 데이터: 인증서 서명 · 페더레이션 토큰의 issuer · subject · audience 일치 (대소문자 구분, 와일드카드 미지원, issuer 앞뒤 공백이 있으면 교환 차단)
   - 해설: 비밀 없이 신원을 확인하고 일치하지 않으면 교환이 실패합니다. 페더레이션 자격 증명을 만든 직후 몇 분 동안은 전파 지연으로 AADSTS70021(일치하는 페더레이션 ID 레코드 없음)이 날 수 있어 재시도 로직을 둡니다
4. [판단] 서비스 주체가 사용 가능한 상태인가?
   - 주체: Entra ID
   - 위치: 엔터프라이즈 앱 › {앱} › 속성 › 사용자 로그인 사용 (Enabled for users to sign-in?)
   - 데이터: servicePrincipal.accountEnabled · 앱 등록 비활성화(isDisabled) · Microsoft 차단(disabledByMicrosoftStatus)도 활성화 상태를 '비활성'으로 만듦
   - 해설: 서비스 주체가 비활성이면 토큰 발급이 거부됩니다. 로그인 사용 = 아니요이면 사용자뿐 아니라 앱 권한으로 접근하는 서비스 주체의 토큰도 발급되지 않습니다
   - 예 → 5
   - 아니오 → [차단] 차단 — 서비스 주체 사용 안 함
5. [판단] 워크로드용 조건부 액세스 조건을 충족하는가?
   - 주체: Entra ID
   - 위치: 보호 › 조건부 액세스 (워크로드 ID 정책 · 관리 ID는 대상 아님)
   - 데이터: 요청 IP 위치 · 서비스 주체 위험 수준
   - 해설: 정책이 있으면 위치·위험 조건을 평가해 허용 또는 차단합니다. 정책은 이 테넌트에 등록된 단일 테넌트 서비스 주체에만 적용되고 그룹으로 지정한 서비스 주체에는 적용되지 않습니다
   - 예 → 6
   - 아니오 → [차단] 차단 — 조건부 액세스 정책으로 접근 차단
6. [처리] 액세스 토큰 발급
   - 주체: Entra ID
   - 위치: Entra 토큰 서비스 → 워크로드
   - 데이터: 토큰 클레임 (aud · tid · appid · roles = 부여된 앱 권한)
   - 해설: 앱 권한은 roles 클레임으로 담겨 대상 리소스에 전달됩니다. 관리 ID 토큰은 IMDS가 응답으로 주며 응답에 expires_in(문서 예시 3599초) · expires_on이 포함되고 refresh_token은 쓰이지 않습니다
7. [처리] 대상 리소스가 토큰을 검증하고 권한을 확인
   - 주체: 리소스
   - 위치: 대상 리소스 (API · Key Vault · 스토리지 등)
   - 데이터: 서명 · aud · 만료 확인 → roles 또는 Azure RBAC 역할 할당 확인
   - 해설: 토큰만으로 끝나지 않고 리소스가 부여된 권한 범위를 다시 확인합니다. 리소스 API가 roles 클레임을 확인하지 않으면 권한 없는 앱 전용 토큰도 통과할 수 있습니다
8. [끝] 서비스 주체 로그인 로그에 기록
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 로그인 로그 › 서비스 주체 로그인 · 관리 ID 로그인
   - 데이터: ServicePrincipalSignInLogs · ManagedIdentitySignInLogs (Log Analytics)
   - 해설: 사람 로그인과 별도로 워크로드 로그인이 이 로그에 남습니다. 서비스 주체 로그인은 같은 서비스 주체 · 상태 · IP · 리소스일 때 한 행으로 묶이고, 관리 ID 로그인은 서비스 주체 로그와 별도의 관리 ID 로그에만 기록됩니다
- 시나리오: 예 ▸ 예 :: 사용 가능한 서비스 주체가 조건도 충족해 토큰 발급
- 시나리오: 예 ▸ 아니오 :: 서비스 주체는 정상이나 조건부 액세스 미충족으로 차단
- 시나리오: 아니오 :: 서비스 주체를 쓸 수 없는 상태라 차단

> 교육 포인트: 워크로드 ID는 앱 · 서비스 주체 · 관리 ID 세 가지입니다. 최선은 비밀을 아예 없애는 것(관리 ID 또는 페더레이션)이고, 비밀이 남는다면 위치·위험 정책으로 둘러쌉니다.
>
> 주의: 워크로드용 조건부 액세스는 조직 소유의 단일 테넌트 서비스 주체만 대상입니다. 관리 ID · 멀티테넌트 앱 · Microsoft/타사 SaaS 앱은 제외됩니다. 관리 ID는 정책 대신 액세스 검토로 점검합니다.

### L3 · A · 앱 등록 vs 서비스 주체 — 정의와 이 테넌트의 동작

#### L4 · 어디서 무엇을 바꾸고 어떤 객체에 권한이 붙는가

1. [시작] 개발자가 앱 등록을 만든다
   - 주체: 관리자
   - 위치: ID › 애플리케이션 › 앱 등록 › 새 등록 (Entra ID › App registrations › New registration)
   - 데이터: 애플리케이션 객체 (전역 정의) · Application (client) ID · Object ID · 단일 테넌트 / 멀티테넌트 선택 · 선택적 리디렉션 URI
   - 해설: 앱 등록은 앱이 토큰을 어떻게 받고 무엇에 접근할지 정의하는 전역 객체입니다. 앱은 앱 객체 하나만 가지며 객체는 앱을 등록한 홈 테넌트에 있습니다
2. [처리] 홈 테넌트에 서비스 주체가 생성된다
   - 주체: Entra ID
   - 위치: 애플리케이션 › 엔터프라이즈 앱 › 모든 애플리케이션
   - 데이터: servicePrincipal (이 테넌트의 앱 인스턴스) · 포털에서 등록하면 서비스 주체가 함께 생성되지만 Microsoft Graph API로 등록하면 서비스 주체 생성은 별도 단계 (PowerShell · CLI로도 직접 생성 가능)
   - 해설: 서비스 주체는 앱이 실제로 이 테넌트에서 할 수 있는 일을 정하는 지역 객체입니다. 서비스 주체 종류는 Application · Managed identity · Legacy 세 가지입니다
3. [처리] 식별자를 구분 — 앱 등록 Object ID ≠ 서비스 주체 Object ID
   - 주체: 관리자
   - 위치: 앱 등록 › 개요 (Object ID) / 엔터프라이즈 앱 › 개요 (Object ID)
   - 데이터: 조건부 액세스는 서비스 주체의 Object ID를 사용 (앱 등록의 Object ID는 사용 불가) · 두 객체가 공유하는 값은 Application (client) ID
   - 해설: 두 Object ID를 혼동하면 정책이 앱에 적용되지 않습니다. 정책 대상 앱은 엔터프라이즈 앱의 개요 탭에서 Object ID를 복사해 찾습니다
4. [처리] 다른 테넌트가 앱을 쓰면 그 테넌트에 서비스 주체가 생김
   - 주체: Entra ID
   - 위치: 사용하는 테넌트의 엔터프라이즈 앱
   - 데이터: 앱 객체는 하나, 서비스 주체는 사용하는 테넌트마다 하나 (앱 객체 : 서비스 주체 = 1 : 다)
   - 해설: 멀티테넌트 앱은 정의 하나를 템플릿 삼아 테넌트별 인스턴스가 만들어집니다. 그 테넌트의 사용자가 동의해 사용을 시작하는 시점에 만들어집니다
5. [처리] 자격 증명은 앱 객체에 둔다
   - 주체: 관리자
   - 위치: 앱 등록 › {앱} › 인증서 및 암호 (클라이언트 암호 · 인증서 · 페더레이션 자격 증명)
   - 데이터: passwordCredentials · keyCredentials · federatedIdentityCredentials · 감사 로그 'Update application – Certificates and secrets management'
   - 해설: 앱이 자기를 증명하는 수단은 정의 쪽에서 관리합니다
6. [처리] 권한 부여와 할당은 서비스 주체에서 한다
   - 주체: 관리자
   - 위치: 엔터프라이즈 앱 › {앱} › 권한 · 사용자 및 그룹
   - 데이터: appRoleAssignment (앱 권한) · oauth2PermissionGrant (위임 권한 동의) · 감사 로그 'Consent to application' · 'Add delegated permission grant'
   - 해설: "이 테넌트에서 무엇을 허용하는가"는 서비스 주체에 기록됩니다. 사용자·앱의 접근 정책과 권한은 서비스 주체가 정의합니다
7. [판단] 지금 바꾸려는 것이 정의인가, 이 테넌트의 동작인가?
   - 주체: 관리자
   - 위치: 앱 등록(정의) vs 엔터프라이즈 앱(이 테넌트 동작)
   - 데이터: 정의 = 자격 증명 · 리디렉션 URI · 필요한 API 권한 선언 / 동작 = 할당 · 동의 · 조건부 액세스 · 로그인 차단
   - 해설: 객체가 둘이라 같은 일도 고치는 곳이 다릅니다. 관리 ID의 서비스 주체는 앱 객체가 없어 엔터프라이즈 앱 쪽에서만 다루며 직접 수정할 수 없습니다
   - 정의 → 8
   - 테넌트 동작 → 9
8. [처리] 앱 등록에서 수정 — 앱 정의가 바뀐다
   - 주체: 관리자
   - 위치: ID › 애플리케이션 › 앱 등록 › {앱}
   - 데이터: application 객체 변경 → 감사 로그 ApplicationManagement ('Update application')
   - 해설: 앱 객체는 홈 테넌트에만 있으므로 멀티테넌트 앱의 정의도 그 홈 테넌트에서 바꿉니다. 정의를 바꾸면 그 앱의 모든 서비스 주체가 파생 속성을 이어받습니다
   - 다음 → 10
9. [처리] 엔터프라이즈 앱에서 수정 — 이 테넌트에만 영향
   - 주체: 관리자
   - 위치: 애플리케이션 › 엔터프라이즈 앱 › {앱} › 속성 (사용자 로그인 사용 = 아니요) 등
   - 데이터: servicePrincipal.accountEnabled = false → 이 테넌트에서 앱 로그인 차단 · 감사 로그 'Update service principal'
   - 해설: 다른 테넌트에는 영향 없이 이 테넌트의 앱 동작만 바꿉니다. 이 설정은 활성화 상태를 '비활성'으로 보이게 하지만 앱 등록이 비활성화된 것은 아닙니다
10. [끝] 변경이 감사 로그에 기록
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 감사 로그 (범주 ApplicationManagement)
   - 데이터: AuditLogs — 앱 · 서비스 주체 변경 · 수행자 · 활동 예: Add service principal · Add service principal credentials · Update application · Consent to application
   - 해설: 정의 변경과 동작 변경 모두 누가 했는지 남습니다
- 시나리오: 정의 :: 정의를 바꾸려는 경우 앱 등록에서 수정
- 시나리오: 테넌트 동작 :: 테넌트 동작을 바꾸려는 경우 엔터프라이즈 앱에서 수정

> 교육 포인트: 앱 등록 = 전역 정의(템플릿), 서비스 주체 = 테넌트별 인스턴스, 관리 ID = 자격 증명을 플랫폼이 관리하는 특수한 서비스 주체입니다.
>
> 주의: 조건부 액세스 정책 대상은 앱 등록이 아닌 서비스 주체(엔터프라이즈 앱)의 Object ID로 찾습니다.

>

### L3 · B · 관리 ID · 페더레이션 자격 증명 — 비밀 없는 토큰 발급

#### L4 · Azure 안에서는 IMDS, 밖에서는 외부 토큰 교환으로 토큰을 받는다

1. [시작] 워크로드가 Entra 보호 리소스를 호출해야 한다
   - 주체: 앱
   - 위치: 워크로드 실행 환경 (Azure VM · App Service · Kubernetes · CI/CD 등)
   - 데이터: 대상 리소스 (예: Key Vault · Graph · 스토리지)
   - 해설: 비밀 키를 저장하지 않고 토큰을 받는 두 경로를 비교합니다
2. [판단] 워크로드가 어디에서 실행되는가?
   - 주체: 앱
   - 위치: 설계 단계 (실행 위치 확인)
   - 데이터: Azure 컴퓨트 리소스 vs Azure 밖 · 외부 IdP를 쓰는 플랫폼
   - 해설: 실행 위치에 따라 관리 ID 또는 페더레이션이 맞는 경로입니다. Azure 안에서도 앱 등록 신원을 쓰는 워크로드는 사용자 할당 관리 ID를 앱의 페더레이션 자격 증명으로 신뢰하는 구성을 쓸 수 있습니다
   - Azure 리소스 → 3
   - Azure 밖 · 외부 IdP → 5
3. [처리] 코드가 로컬 IMDS 엔드포인트에 토큰 요청
   - 주체: 앱
   - 위치: GET http://169.254.169.254/metadata/identity/oauth2/token?resource=… (헤더 Metadata: True)
   - 데이터: resource · api-version(2018-02-01 이상) · client_id 또는 object_id 또는 msi_res_id (사용자 할당 ID가 여러 개일 때 지정) · 헤더 Metadata: true는 SSRF 완화용으로 소문자 true여야 함
   - 해설: 이 주소는 해당 VM 안에서만 접근되며 요청에 비밀이 필요 없습니다. 보안 경계는 ID를 쓰는 리소스이므로 그 VM에서 도는 모든 코드가 VM에 붙은 어떤 관리 ID의 토큰도 요청할 수 있습니다
4. [처리] IMDS가 관리 ID로 Entra에서 토큰을 받아 반환
   - 주체: Azure
   - 위치: Azure Instance Metadata Service → Entra 토큰 서비스
   - 데이터: 관리 ID 서비스 주체의 client ID · 인증서 (플랫폼이 보관 · 자동 갱신) · 응답 access_token · expires_in(문서 예시 3599초) · resource · token_type=Bearer
   - 해설: 인증서는 개발자가 볼 수 없고 플랫폼이 관리하므로 유출·만료 위험이 없습니다. 관리 ID 하위 시스템이 토큰을 캐시하지만 코드에서도 만료에 대비해 캐싱하고, 404 · 429 · 5xx 응답은 지수 백오프로 재시도합니다(4xx 요청 오류는 재시도하지 않음)
   - 다음 → 9
5. [처리] 외부 IdP가 워크로드에 토큰 발급
   - 주체: 외부
   - 위치: GitHub Actions · Kubernetes · 클라우드 IdP 등
   - 데이터: 외부 토큰 클레임 (iss · sub · aud)
   - 해설: 워크로드가 자기 플랫폼의 IdP에서 먼저 자기 토큰을 받습니다. 예를 들어 GitHub 워크플로의 subject는 repo:{조직}/{저장소}:ref:refs/heads/{브랜치} 형태이며 RS256 서명 토큰을 발급하는 IdP가 지원 대상입니다
6. [처리] 외부 토큰을 Entra에 보내 액세스 토큰 교환 요청
   - 주체: 앱
   - 위치: POST /oauth2/v2.0/token (client credentials · client_assertion = 외부 토큰)
   - 데이터: client_id (앱 또는 관리 ID) · client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer · scope(.default) · grant_type=client_credentials
   - 해설: 비밀 대신 외부 토큰을 자격 증명으로 내밉니다. 외부 토큰은 직접 만들지 않고 IdP가 준 JWT를 그대로 전달합니다
7. [판단] 페더레이션 자격 증명과 일치하는가? — issuer · subject · audience
   - 주체: Entra ID
   - 위치: 앱 등록 › {앱} › 인증서 및 암호 › 페더레이션 자격 증명
   - 데이터: 저장된 issuer · subject · audiences 와 외부 토큰의 iss · sub · aud (대소문자 구분 · 와일드카드 없음, 2024년부터 대소문자 구분 매칭으로 변경)
   - 해설: 한 글자만 달라도 교환이 거부되며 설정 시에는 오류가 나지 않습니다. 대소문자 차이나 issuer 앞뒤 공백도 불일치로 처리되므로 외부 플랫폼의 값을 그대로 복사합니다
   - 예 → 8
   - 아니오 → [차단] 교환 실패 — 외부 토큰 불일치
8. [처리] 외부 토큰 검증 후 액세스 토큰 발급 — OIDC issuer 키 사용
   - 주체: Entra ID
   - 위치: Entra 토큰 서비스 (외부 IdP의 OIDC 서명 키 검증)
   - 데이터: 외부 IdP의 OIDC 서명 키 검증 → Entra 액세스 토큰
   - 해설: 신뢰하는 IdP의 서명이 맞으면 일반 토큰과 같은 액세스 토큰을 줍니다. 자격 증명을 방금 만들었다면 리전 전파가 끝날 때까지 AADSTS70021이 날 수 있어 재시도가 필요합니다
9. [처리] 워크로드가 액세스 토큰으로 리소스 호출
   - 주체: 리소스
   - 위치: 대상 리소스 API (Authorization: Bearer 헤더)
   - 데이터: Authorization: ****** · Azure RBAC 역할 또는 앱 권한 확인
   - 해설: 리소스는 토큰을 검증한 뒤 부여된 역할 범위만 허용합니다
10. [끝] 서비스 주체 · 관리 ID 로그인 로그에 기록
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 로그인 로그 › 서비스 주체 로그인 · 관리 ID 로그인
   - 데이터: ServicePrincipalSignInLogs · ManagedIdentitySignInLogs
   - 해설: 어떤 ID가 언제 어떤 리소스 토큰을 받았는지 남습니다. 관리 ID의 생성·수정·삭제는 Azure 활동 로그에서, 앱 등록의 자격 증명 변경은 Entra 감사 로그에서 확인합니다
- 시나리오: Azure 리소스 :: Azure 리소스가 IMDS로 관리 ID 토큰 발급
- 시나리오: Azure 밖 · 외부 IdP ▸ 예 :: 외부 IdP 토큰이 일치해 액세스 토큰 발급
- 시나리오: Azure 밖 · 외부 IdP ▸ 아니오 :: 외부 토큰이 불일치해 교환 실패

> 교육 포인트: 두 방식 모두 "저장된 비밀이 없다"는 점이 핵심입니다. 관리 ID는 Azure가 자격 증명을 관리하고, 페더레이션은 외부 IdP 토큰을 신뢰 관계로 교환합니다.
>
> 주의: 페더레이션 자격 증명의 subject를 잘못 넣어도 생성은 성공하고 토큰 교환 때 조용히 실패합니다. 외부 플랫폼 설정값과 정확히 맞춰 확인합니다.
>
> 주의: Entra가 발급한 토큰은 페더레이션 교환에 쓸 수 없습니다. 앱이 사용자 할당 관리 ID를 신뢰하도록 구성하는 방법은 별도 시나리오로 문서화되어 있습니다.
>
> 주의: 같은 사용자 할당 관리 ID에 페더레이션 자격 증명을 동시에 여러 개 만들면 409 충돌이 나므로 자동화에서는 순차로 만듭니다. Malaysia South 리전의 사용자 할당 관리 ID에는 만들 수 없습니다.

### L3 · C · 워크로드용 조건부 액세스 — 서비스 주체에 위치 · 위험 정책

#### L4 · 정책 대상 지정부터 보고서 전용 · 적용 · 결과 확인까지

1. [시작] 보호할 서비스 주체를 선정
   - 주체: 관리자
   - 위치: 애플리케이션 › 엔터프라이즈 앱 › 개요 (Object ID 복사)
   - 데이터: 대상 = 조직 소유 단일 테넌트 서비스 주체 (관리 ID · 멀티테넌트 · SaaS 제외) · 앱 등록의 Object ID는 사용 불가
   - 해설: 정책이 닿는 범위를 먼저 확인해 놓치는 앱이 없게 합니다. 관리 ID는 정책 대신 액세스 검토로 점검합니다
2. [처리] 라이선스 확인 — Workload Identities Premium
   - 주체: 관리자
   - 위치: ID › 워크로드 ID (라이선스 상태) [확인 필요: 확인 메뉴 위치]
   - 데이터: 없으면 기존 정책은 동작하지만 만들거나 수정할 수 없음 · 서비스 주체 위험(ID Protection)과 서비스 주체 액세스 검토도 Premium 기능
   - 해설: 라이선스가 있어야 새 정책을 만들거나 바꿀 수 있습니다. 서비스 주체 만들기·수정, 관리 ID, 페더레이션, 로그인·감사 로그는 Premium 없이도 쓸 수 있습니다
3. [처리] 정책 대상으로 워크로드 ID 선택
   - 주체: 관리자
   - 위치: 보호 › 조건부 액세스 › 정책 › 새 정책 › 사용자 또는 워크로드 ID › 워크로드 ID › 서비스 주체 선택
   - 데이터: includeServicePrincipals (서비스 주체 개체 ID 또는 ServicePrincipalsInMyTenant) · 대상 리소스 = 모든 리소스
   - 해설: 서비스 주체는 그룹에 넣어도 정책이 적용되지 않으므로 직접 지정합니다. 정책은 서비스 주체가 토큰을 요청할 때만 평가됩니다
4. [처리] 조건 구성 — 위치 또는 서비스 주체 위험
   - 주체: 관리자
   - 위치: 정책 › 조건 › 위치 (포함 = 모든 위치, 제외 = 허용할 위치) / 서비스 주체 위험 (구성 = 예 → 위험 수준 선택)
   - 데이터: 명명된 위치 · ID Protection 서비스 주체 위험 수준 · Graph conditions.locations.excludeLocations (명명된 위치 ID 또는 AllTrusted)
   - 해설: 알려진 공용 IP 밖의 요청이나 위험 판정을 조건으로 삼습니다. 위치 정책과 위험 정책은 각각 따로 만듭니다
5. [처리] 권한 부여는 차단만 선택 가능
   - 주체: 관리자
   - 위치: 정책 › 권한 부여 › 액세스 차단
   - 데이터: grantControls.builtInControls = block
   - 해설: 워크로드는 MFA를 못 하므로 허용 조건이 아니라 차단 조건으로 씁니다. 지정한 허용 범위 밖에서 토큰 요청이 오면 차단됩니다
6. [처리] 보고서 전용으로 저장하고 영향 확인
   - 주체: 관리자
   - 위치: 정책 상태 = 보고서 전용 → 로그인 로그 › 서비스 주체 로그인 › Report-only 탭
   - 데이터: 로그인 로그의 보고서 전용 평가 결과 · Graph state = enabledForReportingButNotEnforced · 위치 기반 정책은 Conditional Access Insights and Reporting 워크북도 사용
   - 해설: 켜기 전에 어떤 서비스 주체가 막힐지 로그로 확인합니다
7. [처리] 정책 켜기
   - 주체: 관리자
   - 위치: 정책 상태 = 켜기
   - 데이터: policy.state = enabled
   - 해설: 영향이 없음을 확인하면 강제 적용으로 전환합니다. 되돌리려면 정책을 삭제하거나 끕니다
8. [판단] 이후 토큰 요청이 정책 조건을 통과하는가?
   - 주체: Entra ID
   - 위치: Entra 토큰 서비스 (정책 평가)
   - 데이터: 요청 IP 위치 · 서비스 주체 위험 수준
   - 해설: 서비스 주체가 토큰을 요청할 때만 정책이 평가됩니다
   - 예 → 9
   - 아니오 → [차단] 차단 — "Access has been blocked due to Conditional Access policies."
9. [끝] 결과를 로그인 로그의 조건부 액세스 탭에서 확인
   - 주체: 로그
   - 위치: 모니터링 및 상태 › 로그인 로그 › 서비스 주체 로그인 › 항목 › 조건부 액세스 탭 (Entra ID › Monitoring & health › Sign-in logs › Service principal sign-ins)
   - 데이터: 정책별 평가 결과 · 실패 이유 (차단 시 "Access has been blocked due to Conditional Access policies.")
   - 해설: 차단 사유와 적용된 정책을 로그 항목에서 바로 확인합니다
- 시나리오: 예 :: 조건을 통과해 로그인 로그에서 결과 확인
- 시나리오: 아니오 :: 정책 조건에 걸린 토큰 요청이라 차단

> 교육 포인트: 관리 ID는 이 정책의 대상이 아닙니다. 대신 액세스 검토로 점검합니다. 정책으로 막고 싶은 자격 증명(비밀 · 인증서)을 쓰는 서비스 주체가 대상입니다.
>
> 주의: 위치 기반 정책은 클라우드 NAT · 공용 IP가 바뀌는 환경에서 정상 워크로드를 막을 수 있으므로 보고서 전용으로 먼저 확인합니다.
